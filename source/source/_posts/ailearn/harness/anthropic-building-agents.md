**一句话结论：最成功的智能体实现，用的不是复杂框架或专门库，而是简单、可组合的模式。**

过去一年，Anthropic 与数十个团队合作，帮助他们在各行各业构建 LLM 智能体。这个规律反复出现。这篇文章分享我们从客户合作和自己构建智能体中学到的东西，给开发者提供构建高效智能体的实践建议。

<!-- more -->

## 什么是智能体？

"智能体"这个词有很多种定义。有人把它定义为完全自主的系统，能独立运行很长时间，使用各种工具完成复杂任务。也有人用这个词描述更规范的实现，遵循预定义的工作流。

在 Anthropic，我们把所有这些变体统称为**智能体系统**，但在架构上区分两种类型：

- **工作流（Workflows）**：LLM 和工具通过预定义的代码路径进行编排
- **智能体（Agents）**：LLM 动态地指导自己的流程和工具使用，自主控制如何完成任务

下面我们会详细探讨这两种类型。

## 什么时候用智能体，什么时候不用

构建 LLM 应用时，我们建议找到最简单的解决方案，只在必要时才增加复杂度。这可能意味着根本不需要构建智能体系统。

智能体系统通常用延迟和成本换取更好的任务性能，你需要考虑这个权衡是否值得：

- 当任务有明确定义时，**工作流**提供可预测性和一致性
- 当需要灵活性和模型驱动的决策时，**智能体**是更好的选择
- 对于很多应用，优化单次 LLM 调用（加上检索和上下文示例）通常就足够了

## 关于框架的使用

有很多框架可以让智能体系统更容易实现，包括：

- [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview)
- [Strands Agents SDK by AWS](https://strandsagents.com/latest/)
- [Rivet](https://rivet.ironcladapp.com/)，拖拽式 LLM 工作流构建器
- [Vellum](https://www.vellum.ai/)，另一个构建和测试复杂工作流的 GUI 工具

这些框架通过简化标准底层任务（调用 LLM、定义和解析工具、链接调用）让你快速上手。但它们往往会创建额外的抽象层，可能会遮蔽底层的提示词和响应，让调试变得更难。

**我们建议开发者从直接使用 LLM API 开始**：很多模式只需要几行代码就能实现。如果你确实使用框架，确保你理解底层代码。对底层机制的错误假设是客户常见的错误来源。

## 五种核心构建模式

### 基础构建块：增强型 LLM

智能体系统的基本构建块是一个增强了检索、工具和记忆能力的 LLM。当前的模型可以主动使用这些能力——生成自己的搜索查询、选择合适的工具、决定保留什么信息。

我们建议关注两个关键方面：针对你的具体用例定制这些能力，并确保它们为 LLM 提供简单、文档完善的接口。

### 模式一：提示词链（Prompt Chaining）

将任务分解为一系列步骤，每次 LLM 调用处理上一次的输出。可以在任何中间步骤添加程序化检查（"门控"），确保流程仍在正轨上。

**适用场景**：任务可以清晰地分解为固定子任务时。主要目标是用延迟换取更高的准确性，让每次 LLM 调用处理更简单的任务。

**典型例子**：
- 生成营销文案，然后翻译成另一种语言
- 写文档大纲，检查大纲是否满足某些标准，然后根据大纲写文档

### 模式二：路由（Routing）

对输入进行分类，并将其定向到专门的后续任务。这种工作流允许关注点分离，构建更专业的提示词。如果不用路由，针对某类输入的优化可能会损害其他输入的性能。

**适用场景**：复杂任务中有不同类别需要分别处理，且分类可以准确完成时。

**典型例子**：
- 将不同类型的客服查询（一般问题、退款请求、技术支持）定向到不同的下游流程
- 将简单/常见问题路由到更小、更经济的模型（如 Claude Haiku 4.5），将困难/罕见问题路由到更强大的模型（如 Claude Sonnet 4.5）

### 模式三：并行化（Parallelization）

LLM 同时处理任务的不同部分，输出以程序化方式聚合。有两种变体：

- **分段（Sectioning）**：将任务分解为独立的并行子任务
- **投票（Voting）**：多次运行同一任务以获得多样化输出

**适用场景**：子任务可以并行处理以提高速度，或者需要多个视角/尝试来获得更高置信度的结果时。对于有多个考量因素的复杂任务，LLM 通常在每个考量由单独的 LLM 调用处理时表现更好。

**典型例子**：
- **分段**：实现护栏，一个模型实例处理用户查询，另一个筛查不当内容；自动化评估，每次 LLM 调用评估模型性能的不同方面
- **投票**：代码漏洞审查，多个不同提示词分别审查并标记问题；内容审核，多个提示词评估不同方面

### 模式四：编排者-工作者（Orchestrator-Workers）

中央 LLM 动态地分解任务，委托给工作者 LLM，并综合它们的结果。

**适用场景**：复杂任务中无法预测所需的子任务时。与并行化的关键区别在于灵活性——子任务不是预先定义的，而是由编排者根据具体输入动态决定的。

**典型例子**：
- 每次需要对多个文件进行复杂更改的编码产品
- 需要从多个来源收集和分析信息的搜索任务

### 模式五：评估者-优化者（Evaluator-Optimizer）

一次 LLM 调用生成响应，另一次在循环中提供评估和反馈。

**适用场景**：有明确的评估标准，且迭代改进能提供可衡量价值时。两个好的适用信号：LLM 响应在人类表达反馈后可以明显改善；LLM 可以提供这样的反馈。这类似于人类作家在打磨文档时经历的迭代写作过程。

**典型例子**：
- 文学翻译：翻译 LLM 可能最初无法捕捉到细微差别，但评估 LLM 可以提供有用的批评
- 复杂搜索任务：需要多轮搜索和分析来收集全面信息，评估者决定是否需要进一步搜索

## 自主智能体

随着 LLM 在关键能力上的成熟——理解复杂输入、推理和规划、可靠地使用工具、从错误中恢复——智能体正在生产环境中涌现。

智能体从用户的命令或交互讨论开始工作。一旦任务明确，智能体独立规划和运行，可能会在需要更多信息或判断时返回给人类。在执行过程中，智能体在每一步从环境中获取"真实情况"（如工具调用结果或代码执行结果）来评估进度。

**何时使用智能体**：适用于开放式问题，难以或不可能预测所需步骤数量，且无法硬编码固定路径的情况。LLM 可能会运行很多轮，你必须对其决策有一定程度的信任。

智能体的自主性意味着更高的成本，以及错误复合的可能性。我们建议在沙盒环境中进行广泛测试，并配备适当的护栏。

**Anthropic 自己的实现案例**：
- 解决 [SWE-bench 任务](https://www.anthropic.com/research/swe-bench-sonnet)的编码智能体，根据任务描述对多个文件进行编辑
- ["computer use" 参考实现](https://github.com/anthropics/anthropic-quickstarts/tree/main/computer-use-demo)，Claude 使用计算机完成任务

## 组合和定制这些模式

这些构建块不是规定性的，而是开发者可以根据不同用例塑造和组合的常见模式。成功的关键，和任何 LLM 功能一样，是衡量性能并迭代实现。

**记住**：只有在能明显改善结果时，才应该增加复杂度。

## 三条核心原则

在实现智能体时，我们遵循三条核心原则：

1. **保持简单**：智能体设计要简洁
2. **优先透明**：明确展示智能体的规划步骤
3. **精心设计 ACI**：通过充分的工具文档和测试，精心设计智能体-计算机接口（Agent-Computer Interface）

框架可以帮助你快速上手，但在进入生产环境时，不要犹豫，减少抽象层，用基本组件构建。遵循这些原则，你可以创建不仅强大，而且可靠、可维护、受用户信任的智能体。

## 附录一：智能体的实际应用

我们与客户的合作揭示了两个特别有前景的 AI 智能体应用场景，展示了上述模式的实际价值。两者都说明了智能体在以下任务中最能发挥价值：需要对话和行动、有明确的成功标准、能形成反馈循环、并整合有意义的人工监督。

### A. 客户支持

客户支持将熟悉的聊天机器人界面与工具集成的增强能力结合起来。这是更开放式智能体的自然契合点，因为：

- 支持交互自然地遵循对话流程，同时需要访问外部信息和执行操作
- 可以集成工具来获取客户数据、订单历史和知识库文章
- 退款或更新工单等操作可以程序化处理
- 成功可以通过用户定义的解决方案清晰衡量

几家公司通过按成功解决方案收费的定价模式证明了这种方法的可行性，显示出对其智能体效果的信心。

### B. 编码智能体

软件开发领域展示了 LLM 功能的巨大潜力，能力从代码补全演进到自主解决问题。智能体特别有效，因为：

- 代码解决方案可以通过自动化测试验证
- 智能体可以使用测试结果作为反馈来迭代解决方案
- 问题空间定义明确且结构化
- 输出质量可以客观衡量

在我们自己的实现中，智能体现在可以仅根据 Pull Request 描述就解决 [SWE-bench Verified](https://www.anthropic.com/research/swe-bench-sonnet) 基准中的真实 GitHub 问题。

## 附录二：工具的提示词工程

无论你在构建哪种智能体系统，工具都可能是智能体的重要组成部分。工具定义和规范应该得到与整体提示词同等的提示词工程关注。

**选择工具格式的建议**：

- 给模型足够的 Token 在"写死"之前"思考"
- 保持格式接近模型在互联网文本中自然见到的内容
- 确保没有格式"开销"，比如必须精确计算数千行代码，或对代码进行字符串转义

**设计好的 ACI（智能体-计算机接口）的思路**：

- **站在模型的角度**：基于描述和参数，使用这个工具是否显而易见？如果你需要仔细思考，模型也可能需要。好的工具定义通常包括使用示例、边界情况、输入格式要求，以及与其他工具的清晰边界。
- **优化参数名称和描述**：把这想象成为团队中的初级开发者写一个很好的文档字符串。在使用许多相似工具时尤其重要。
- **测试模型如何使用你的工具**：在工作台中运行许多示例输入，看看模型犯了什么错误，然后迭代。
- **防错设计（Poka-yoke）**：改变参数，使其更难犯错。

在构建我们的 SWE-bench 智能体时，我们实际上花在优化工具上的时间比整体提示词更多。例如，我们发现模型在智能体移出根目录后使用相对文件路径的工具时会犯错。为了解决这个问题，我们将工具改为始终要求绝对文件路径——结果模型完美地使用了这个方法。
