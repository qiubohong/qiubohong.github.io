**一句话结论：把 GAN 的思路搬进 AI 工程——用一个专门的评估器来"对抗"生成器，能让 Claude 在前端设计和全栈开发上都突破单智能体的性能天花板。**

过去几个月，我一直在研究两个相互关联的问题：让 Claude 产出高质量的前端设计，以及让它在没有人工干预的情况下构建完整的应用程序。

这项工作起源于我们早期在[前端设计技能](https://github.com/anthropics/claude-code/blob/main/plugins/frontend-design/skills/frontend-design/SKILL.md)和[长时运行编程智能体 Harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) 上的努力——通过提示词工程和 Harness 设计，我们能够将 Claude 的性能大幅提升，但两者最终都遇到了瓶颈。

为了突破，我从**生成对抗网络（GAN）**中获得灵感，设计了一个包含**生成器**和**评估器**智能体的多智能体结构。

## 为什么朴素实现会失败

我们之前已经证明，Harness 设计对长时运行的智能体编码有实质性影响。在早期实验中，我们用初始化智能体分解产品规格为任务列表，用编码智能体逐个功能实现，并在会话间通过结构化交接传递上下文。更广泛的开发者社区也收敛到了类似的洞察，比如用钩子或脚本让智能体保持持续迭代循环的 ["Ralph Wiggum" 方法](https://ghuntley.com/ralph/)。

但一些问题依然存在。

### 问题一：上下文窗口焦虑

对于更复杂的任务，智能体随着时间推移仍然容易"跑偏"。我们观察到两种常见失败模式：

- 随着上下文窗口填满，模型在冗长任务上失去连贯性
- 某些模型会出现"上下文焦虑"——当它们认为接近上下文限制时，开始过早地收尾工作

**上下文重置**（完全清除上下文窗口，启动新的智能体，并通过结构化交接传递前一个智能体的状态）可以解决这两个问题。

这与**压缩（Compaction）**不同——压缩是对早期对话进行摘要，让同一个智能体在缩短的历史上继续工作。压缩保留了连续性，但不能给智能体一个干净的起点，上下文焦虑仍然可能存在。重置提供了干净的起点，代价是交接文件必须包含足够的状态让下一个智能体能顺利接手。

在我们早期的测试中，Claude Sonnet 4.5 的上下文焦虑严重到仅靠压缩无法支撑强大的长任务性能，因此上下文重置成为 Harness 设计的关键。这解决了核心问题，但给每次 Harness 运行增加了编排复杂度、Token 开销和延迟。

### 问题二：自我评估偏差

当被要求评估自己产出的工作时，智能体倾向于自信地称赞这些工作——即使对人类观察者来说，质量明显平庸。这个问题在主观任务（如设计）上尤为突出，因为没有等同于可验证软件测试的二元检查。

**解决方案**：将做工作的智能体与评判工作的智能体分离。单独调优一个持怀疑态度的评估器，比让生成器批评自己的工作要容易得多。一旦外部反馈存在，生成器就有了具体的迭代依据。

## 前端设计：让主观质量可量化

我从前端设计开始实验，因为自我评估问题在这里最为明显。没有任何干预的情况下，Claude 通常会倾向于安全、可预测的布局——技术上可用，但视觉上平淡无奇。

两个洞察塑造了我为前端设计构建的 Harness：

1. 虽然美学无法完全简化为分数，但可以用编码了设计原则和偏好的评分标准来改进。"这个设计漂亮吗？"很难一致地回答，但"这个设计是否遵循了我们的好设计原则？"给了 Claude 具体的评分依据。

2. 通过将前端生成与前端评分分离，可以创建一个驱动生成器向更强输出迈进的反馈循环。

### 四个评分标准

我写了四个评分标准，同时给生成器和评估器智能体：

| 标准 | 说明 |
|------|------|
| **设计质量** | 设计是否感觉是一个连贯的整体，而不是零件的集合？颜色、排版、布局、图像等是否共同创造了独特的氛围和身份？ |
| **原创性** | 是否有自定义决策的证据，还是模板布局、库默认值和 AI 生成的模式？人类设计师应该能识别出刻意的创意选择。未修改的库存组件——或 AI 生成的典型标志如白色卡片上的紫色渐变——在这里会失分。 |
| **工艺** | 技术执行：排版层次、间距一致性、色彩和谐、对比度比率。这是能力检查而非创意检查。大多数合理的实现默认就能做好；失败意味着基础功能损坏。 |
| **功能性** | 独立于美学的可用性。用户能否理解界面的功能，找到主要操作，完成任务？ |

我特别强调设计质量和原创性，因为 Claude 在工艺和功能性上默认就表现不错，但在设计和原创性上经常产出平淡的输出。标准明确惩罚高度通用的"AI 垃圾"模式，通过加权设计和原创性，推动模型进行更多美学冒险。

我用少样本示例和详细的分数分解来校准评估器，确保评估器的判断与我的偏好一致，并减少迭代间的分数漂移。

### 实验结果

每次运行 5 到 15 次迭代，每次迭代通常将生成器推向更有特色的方向。评估器在迭代中的评估有所改善，然后趋于平稳，仍有提升空间。

标准的措辞以我没有完全预料到的方式引导了生成器。加入"最好的设计是博物馆级别的"这样的短语，会将设计推向特定的视觉收敛，这表明与标准相关的提示词直接塑造了输出的特征。

**一个值得注意的例子**：我提示模型为一家荷兰艺术博物馆创建网站。到第九次迭代，它产出了一个干净的深色主题登陆页面。然后，在第十次循环，它完全推翻了方案，将网站重新想象为一种空间体验：用 CSS 透视渲染的 3D 房间，带有棋盘格地板，艺术品以自由形式挂在墙上，通过门廊式导航在画廊房间之间切换。这是我以前从未见过的单次生成的创意飞跃。

## 扩展到全栈编码

有了这些发现，我将这种 GAN 启发的模式应用到了全栈开发。生成器-评估器循环自然地映射到软件开发生命周期，代码审查和 QA 扮演着与设计评估器相同的结构角色。

### 三智能体架构

在我们早期的[长时运行 Harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) 中，我们用初始化智能体、一次一个功能的编码智能体和会话间的上下文重置解决了连贯的多会话编码问题。

对于这项工作，我在原有基础上构建了一个三智能体系统：

**规划者（Planner）**

接受简单的 1-4 句话提示，将其扩展为完整的产品规格。提示它对范围保持雄心勃勃，专注于产品上下文和高层技术设计，而不是详细的技术实现。

这种强调是因为：如果规划者试图预先指定细粒度的技术细节并出错，规格中的错误会级联到下游实现中。更聪明的做法是约束智能体要交付的成果，让它们在工作过程中自己找到路径。

**生成器（Generator）**

一次一个功能的方法对范围管理效果很好。生成器以冲刺（Sprint）方式工作，每次从规格中选取一个功能。每个冲刺用 React、Vite、FastAPI 和 SQLite 栈实现应用，生成器在每个冲刺结束时自我评估工作，然后交给 QA。它还有 git 用于版本控制。

**评估者（Evaluator）**

早期 Harness 的应用通常看起来令人印象深刻，但实际使用时仍然有真实的 Bug。为了捕捉这些问题，评估者使用 Playwright MCP 像用户一样点击运行中的应用，测试 UI 功能、API 端点和数据库状态。

然后根据发现的 Bug 和一组标准（涵盖产品深度、功能性、视觉设计和代码质量）对每个冲刺进行评分。每个标准都有一个硬性阈值，如果任何一个低于阈值，冲刺就失败，生成器会收到关于出了什么问题的详细反馈。

**冲刺合约（Sprint Contract）**

在每个冲刺之前，生成器和评估者协商一份冲刺合约：在写任何代码之前，就那块工作的"完成"是什么样子达成一致。这存在是因为产品规格是有意高层次的，我想要一个步骤来弥合用户故事和可测试实现之间的差距。

生成器提出它将构建什么以及如何验证成功，评估者审查该提案以确保生成器在构建正确的东西。两者迭代直到达成一致。通信通过文件处理：一个智能体写文件，另一个读取并响应。

### 第一版 Harness 运行结果

为了测试，我用以下提示生成了一个复古游戏制作器：

> "创建一个 2D 复古游戏制作器，包含关卡编辑器、精灵编辑器、实体行为和可玩的测试模式。"

| Harness 类型 | 运行时长 | 成本 |
|-------------|---------|------|
| 单智能体（Solo） | 20 分钟 | $9 |
| 完整 Harness | 6 小时 | $200 |

Harness 的成本超过 20 倍，但输出质量的差异立竿见影。

**单智能体的问题**：布局浪费空间，工作流程僵硬，最关键的是——游戏本身坏了。实体出现在屏幕上，但没有任何东西响应输入。深入代码发现实体定义和游戏运行时之间的连接断了，表面上没有任何迹象。

**完整 Harness 的结果**：应用立即显示出更多的精致感。画布使用了完整的视口，面板大小合理，界面有一致的视觉标识。最重要的是——我实际上能够移动实体并玩游戏。

评估者在整个过程中保持了实现与规格的一致性。每个冲刺，它都会遍历冲刺合约的测试标准，通过 Playwright 操作运行中的应用，对任何偏离预期行为的地方提交 Bug。合约非常细粒度——仅第 3 个冲刺就有 27 个涵盖关卡编辑器的标准。

**让评估者达到这个水平需要大量工作**。开箱即用，Claude 是一个糟糕的 QA 智能体。在早期运行中，我看到它识别出合理的问题，然后说服自己这些问题不是大问题，然后批准了工作。它也倾向于表面测试，而不是探测边界情况。调优循环是：读取评估者的日志，找到其判断与我不同的例子，更新 QA 的提示词来解决这些问题。经过几轮这样的开发循环，评估者的评分方式才达到我认为合理的水平。

## 迭代 Harness：移除冲刺结构

第一版 Harness 结果令人鼓舞，但也很笨重、缓慢且昂贵。

**一个重要原则**：Harness 中的每个组件都编码了一个关于模型自身无法做到什么的假设，这些假设值得压力测试——既因为它们可能是错误的，也因为随着模型改进，它们可能很快过时。

随着 Opus 4.6 的发布，我移除了冲刺构造，因为 4.6 的原生能力已经足够强大，不再需要这种分解。我保留了规划者和评估者，因为每个都继续增加明显的价值：

- 没有规划者，生成器会低估范围：给定原始提示，它会直接开始构建而不先规格化工作，最终创建比规划者更少功能的应用
- 没有评估者，生成器仍然容易遗漏细节或在没有监督的情况下存根功能

移除冲刺结构后，我将评估者移到了运行结束时的单次评估，而不是每个冲刺评分一次。

**实践含义**：评估者不是一个固定的是/否决定。当任务超出当前模型可靠独立完成的范围时，它才值得付出成本。

## 更新版 Harness 的运行结果

为了测试更新后的 Harness，我用以下提示生成了一个数字音频工作站（DAW）：

> "在浏览器中使用 Web Audio API 构建一个功能完整的 DAW。"

| 智能体 & 阶段 | 时长 | 成本 |
|--------------|------|------|
| 规划者 | 4.7 分钟 | $0.46 |
| 构建（第 1 轮） | 2 小时 7 分钟 | $71.08 |
| QA（第 1 轮） | 8.8 分钟 | $3.24 |
| 构建（第 2 轮） | 1 小时 2 分钟 | $36.89 |
| QA（第 2 轮） | 6.8 分钟 | $3.09 |
| 构建（第 3 轮） | 10.9 分钟 | $5.88 |
| QA（第 3 轮） | 9.6 分钟 | $4.06 |
| **总计** | **3 小时 50 分钟** | **$124.70** |

QA 智能体在第一轮反馈中指出：

> "这是一个强大的应用，设计保真度出色，AI 智能体良好，后端扎实。主要失败点是功能完整性——虽然应用看起来令人印象深刻，AI 集成运行良好，但几个核心 DAW 功能只是展示性的，没有交互深度：片段无法在时间线上拖动/移动，没有乐器 UI 面板（合成器旋钮、鼓垫），也没有可视化效果编辑器（EQ 曲线、压缩器仪表）。这些不是边缘情况——它们是使 DAW 可用的核心交互，规格明确要求了它们。"

最终应用有所有核心功能：在浏览器中运行的工作排列视图、混音器和传输控制。我能够完全通过提示组合一段短歌：智能体设置了节拍和调性，铺设了旋律，构建了鼓轨，调整了混音器电平，并添加了混响。

这款应用距离专业音乐制作程序还很远，智能体的歌曲创作技能显然还需要大量工作。此外，Claude 实际上听不到声音，这使得 QA 反馈循环在音乐品味方面效果较差。但核心原语已经存在，智能体可以自主驱动它们，使用工具从头到尾创建一个简单的制作。

## 未来展望

随着模型继续改进，我们可以大致预期它们能够工作更长时间，处理更复杂的任务。在某些情况下，这意味着围绕模型的脚手架随着时间推移变得不那么重要。另一方面，模型越好，就越有空间开发能够实现超出模型基线能力的复杂任务的 Harness。

从这项工作中，我的信念是：**随着模型改进，有趣的 Harness 组合空间不会缩小，而是会移动。** AI 工程师的有趣工作，就是不断找到下一个新颖的组合。

几条值得带走的经验：

1. **始终对你正在构建的模型进行实验**，阅读它在真实问题上的 Trace，并调优其性能以实现你期望的结果
2. **对于更复杂的任务**，有时可以通过分解任务并将专门的智能体应用于问题的每个方面来获得提升空间
3. **当新模型发布时**，重新审视 Harness 是好的实践——剥离不再对性能起关键作用的部分，并添加新部分以实现以前可能不可能的更大能力
