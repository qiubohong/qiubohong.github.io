**随着模型越来越强，Harness 还有存在的必要吗？**

这是一个很多人都在问的问题。答案比你想象的更有意思。

<!-- more -->

![未来展望 —— Harness 会消失吗？AI Agent 的持续性与准确性](/assets/img/ailearn/harness/06/main_title.png)

先说结论：**Harness 不会消失，但它会持续演变**。

---

## 模型变强了，Harness 会简化

这是真的。

Anthropic 的工程师在从 Claude Sonnet 4.5 升级到 Opus 4.6 时，发现了一件事：很多之前必须靠 Harness 来解决的问题，新模型自己就能处理了。

比如"上下文焦虑"——Sonnet 4.5 在上下文窗口快满时会草草收尾，所以需要上下文重置机制。但 Opus 4.6 基本上没有这个问题，上下文重置这个组件就可以移除了。

比如 Sprint 分解——Sonnet 4.5 需要把大任务拆成小 Sprint 才能保持连贯性。Opus 4.6 能自己维持长时间的连贯工作，Sprint 结构就变得不那么必要了。

Anthropic 的工程师总结了一个原则：

> "每个 Harness 组件都编码了一个关于模型不能自己做什么的假设，这些假设值得持续检验——因为它们可能是错的，而且随着模型改进，它们会很快过时。"

这意味着：**好的 Harness 工程师，不只是会加组件，还要知道什么时候该移除组件**。

---

## 但 Harness 的空间不会缩小，只会移动

这是更重要的一点。

模型变强，意味着它能处理更复杂的任务。这不是说 Harness 变得不重要，而是说**Harness 需要处理的问题变得更复杂了**。

Anthropic 的工程师说得很清楚：

> "随着模型继续改进，我们可以大致预期它们能够工作更长时间，处理更复杂的任务。在某些情况下，这意味着围绕模型的脚手架随着时间推移变得不那么重要。另一方面，模型越好，就越有空间开发能够实现超出模型基线能力的复杂任务的 Harness。"

换句话说：**Harness 的有趣组合空间不会随着模型改进而缩小，而是会移动**。

今天需要 Harness 来解决的问题（比如上下文焦虑），明天模型自己就能处理。但今天模型根本做不到的事情（比如跨越数周的持续性工作），明天有了更强的模型，就需要新的 Harness 来实现。

---

## AI Agent 需要解决的问题

### AI Agent 的持续性问题

这是 Harness Engineering 里最前沿、也最难解决的问题之一。

**持续性（Continuity）**是指：AI Agent 能否在多次会话、多天、甚至多周的时间跨度内，保持对任务的连贯理解和持续推进？

今天的 AI Agent 在这方面还很弱。每次会话结束，上下文就消失了。下次开始，AI 需要重新"上手"。对于需要长期推进的复杂任务，这是一个根本性的障碍。

OpenAI 的工程师在构建百万行代码项目时，用了一个方法：**把所有重要信息都存进代码仓库**。设计决策、架构选择、进行中的计划——全部以文档形式存进仓库。这样 AI 每次启动，都能通过读取仓库来"恢复记忆"。

但这个方法有局限：它依赖人类（或 AI）持续维护这些文档，而且文档的质量直接影响 AI 的"记忆"质量。

未来更理想的解决方案，可能是**专门的记忆系统**——AI Agent 能自动提取和存储关键信息，在需要时检索，实现真正的跨会话持续性。

---

### AI Agent 的准确性问题

准确性是另一个核心挑战。

今天的 AI Agent 在准确性上有一个根本性的问题：**它不知道自己不知道什么**。

当 AI 缺少某个关键信息时，它不会说"我不确定"，而是会基于已有信息做出推断，给出一个"看起来合理"的答案。这个答案可能是错的，但 AI 不知道。

Harness Engineering 目前的解决方案是：
- 通过 Build & Verify 模式，让 AI 用测试来验证自己的答案
- 通过独立评估者，用外部视角来检验 AI 的工作
- 通过 Trace 分析，找到 AI 的系统性错误并修复

但这些都是"事后补救"——在 AI 已经给出答案之后，再去验证。

更理想的解决方案，是让 AI 在生成答案的过程中就能感知自己的不确定性，并主动寻求更多信息或承认局限。这需要模型层面的改进，不只是 Harness 层面的设计。

## 未来的 Harness 会是什么样？

基于目前的趋势，我们可以做一些预测。**每个预测都附带了预期时间线和你可以提前做的准备**：

### 📅 四大趋势预测（含时间线）

![Harness 四大趋势预测——演变路线图 2025→2029](/assets/img/ailearn/harness/06/four_trends.png)

#### 预测一：Harness 会更加自适应
##### ⏰ 时间线：2026 H2 - 2027 H1（正在发生）

今天的 Harness 是静态的——你设计好了，它就按照设计运行。未来的 Harness 可能是动态的——它能根据任务的特点、模型的表现、实时的反馈，自动调整自己的配置。

比如，Harness 能自动检测 AI 是否出现了"死循环"，并动态调整中间件的干预策略。

| 时间节点 | 预期进展 | 你现在可以做什么 |
|----------|---------|----------------|
| **现在** | 手动配置 Harness | 学习本系列的六大组件设计方法 |
| **2026 Q3** | 基于规则的自适应（如：超时自动降低推理预算） | 在你的 Harness 中加入简单的条件逻辑 |
| **2026 Q4** | 基于 Trace 的自适应（如：自动识别失败模式并调整） | 搭建 Trace 收集系统（参考第05篇） |
| **2027+** | 完全自优化的 Harness（AI 自己调自己的参数） | 关注 AutoML + LLM 自优化方向的研究 |

#### 预测二：多模型协作会成为标配
##### ⏰ 时间线：2027 H1 - 2028 H1（早期阶段）

今天的 Harness 通常只用一个模型。未来可能会有更多多模型架构——用不同的模型处理不同类型的任务，发挥各自的优势。

LangChain 的工程师提到了这个方向：

> "在多模型 Harness 中，平衡推理预算可能会演变为：用大模型做规划，把实现交给小模型。"

**典型架构演进**：

![多模型协作典型架构演进——从单模型全包到专业分工生态](/assets/img/ailearn/harness/06/arch_evolution.png)

```
当前（2025-2026）:
  GPT/Claude → 全包（规划+实现+评估）

短期（2027）:
  大模型(规划) → 小模型(实现) → 大模型(评估)

中期（2028+）:
  规划专家模型 → 编码专用模型 → 测试专用模型 → 领域专家模型
       ↕ 动态调度引擎 ↕     （根据任务类型自动选择最优组合）
```

| 时间节点 | 预期进展 | 你现在可以做什么 |
|----------|---------|----------------|
| **现在** | 单模型为主 | 掌握第04篇的多智能体架构设计 |
| **2027 Q1** | "大规划+小实现"模式出现 | 尝试在不同步骤使用不同规格的API调用 |
| **2027 Q2-Q4** | 多模型编排框架成熟 | 学习模型路由和负载均衡技术 |
| **2028+** | 专业分工模型生态 | 关注垂直领域专用模型的发布 |

#### 预测三：记忆系统会成为核心组件
##### ⏰ 时间线：2027 H2 - 2029（中期愿景）

随着 AI Agent 承担越来越长期的任务，记忆系统会变得越来越重要。不只是"这次会话里发生了什么"，而是"过去几周、几个月里，这个项目发生了什么，做了哪些决策，为什么这样决策"。

**记忆系统的三代演进**：

| 代际 | 方案 | 能力 | 局限 |
|------|------|------|------|
| **第一代（现在）** | 文档即记忆（AGENTS.md + 交接文档） | 跨会话传递信息 | 依赖人工维护，容易过时 |
| **第二代（2027-2028）** | 结构化记忆数据库 | 自动提取/存储/检索关键信息 | 语义理解有限，检索精度不够 |
| **第三代（2029+）** | 神经记忆系统 | 类人记忆： episodic + semantic + procedural | 需要新的模型架构支持 |

##### 🗄️ 结构化记忆数据库：是什么？怎么用？

**结构化记忆数据库**是第二代记忆方案的核心，本质上是把 AI Agent 的"经历"以结构化的方式存入数据库，让 AI 在下次启动时能精准检索，而不是靠人工维护文档。

它解决的核心问题是：**文档记忆太粗糙，上下文窗口太短暂**。

**工作原理**：

```
会话结束时（自动触发）：
  AI 提取本次会话的关键事件
    ↓
  生成结构化记录（事件类型 + 内容 + 重要性评分 + 时间戳）
    ↓
  向量化（Embedding）后存入数据库

下次会话开始时：
  AI 根据当前任务生成查询向量
    ↓
  从数据库检索最相关的历史记忆（Top-K）
    ↓
  注入上下文，AI "想起"了相关经历
```

**三类核心记忆存储**：

| 记忆类型 | 存什么 | 检索方式 | 推荐工具 |
|---------|--------|---------|--------|
| **事件记忆** | "2025-04-10 修复了登录模块的 JWT 过期 Bug" | 时间范围 + 关键词 | PostgreSQL + pgvector |
| **决策记忆** | "选择 Redis 而非 Memcached，原因是需要持久化" | 语义相似度 | Pinecone / Weaviate |
| **错误记忆** | "调用 OpenAI API 时如果不设置 timeout，会卡死" | 错误类型匹配 | Chroma（本地轻量） |

**今天就能搭建的最简版本**：

```python
# 用 Chroma + OpenAI Embedding 搭建最简结构化记忆
import chromadb
from openai import OpenAI

client = OpenAI()
chroma = chromadb.PersistentClient(path="./agent_memory")
collection = chroma.get_or_create_collection("project_memory")

def store_memory(event_type: str, content: str, importance: int = 5):
    """存储一条记忆"""
    embedding = client.embeddings.create(
        input=content,
        model="text-embedding-3-small"
    ).data[0].embedding
    
    collection.add(
        documents=[content],
        embeddings=[embedding],
        metadatas=[{"type": event_type, "importance": importance}],
        ids=[f"{event_type}_{len(collection.get()['ids'])}"]
    )

def recall_memory(query: str, top_k: int = 5) -> list[str]:
    """检索相关记忆"""
    query_embedding = client.embeddings.create(
        input=query,
        model="text-embedding-3-small"
    ).data[0].embedding
    
    results = collection.query(
        query_embeddings=[query_embedding],
        n_results=top_k
    )
    return results["documents"][0]

# 使用示例
store_memory("bug_fix", "修复了用户登录时 JWT token 过期未刷新的问题", importance=8)
store_memory("decision", "选择 PostgreSQL 而非 MongoDB，因为数据关系复杂", importance=7)

# 下次会话时检索
memories = recall_memory("登录相关的历史问题")
print("\n".join(memories))  # AI 能"想起"之前的修复经历
```

**局限性**：结构化记忆数据库的瓶颈在于**语义理解的精度**。当你问"上次那个性能问题"，AI 可能检索到不相关的记忆。这需要更好的 Embedding 模型和检索策略（如混合检索：向量相似度 + 关键词匹配）来改善。

##### 🧠 神经记忆系统：终极愿景

**神经记忆系统**是第三代方案，目标是让 AI 拥有类似人类的多层次记忆结构。它不只是"存数据库"，而是在模型架构层面实现记忆的编码、巩固和提取。

人类记忆分为四种类型，神经记忆系统试图在 AI 中复现：

| 记忆类型 | 人类类比 | AI 实现目标 | 当前状态 |
|---------|---------|-----------|--------|
| **情景记忆 (Episodic)** | "上周三我修复了那个 Bug" | 记录具体的事件、时间、地点、结果 | 研究阶段，MemGPT 有初步尝试 |
| **语义记忆 (Semantic)** | "Python 的 GIL 是全局解释器锁" | 存储通用知识和概念，跨项目复用 | 部分可用（RAG + 知识库） |
| **程序性记忆 (Procedural)** | "骑自行车不需要想每一步" | 内化的技能和流程，自动执行不需要推理 | 尚无成熟方案 |
| **工作记忆 (Working)** | "我现在正在做 X" | 当前任务的即时上下文 | 已有（上下文窗口） |

**为什么程序性记忆最难实现？**

程序性记忆的本质是"肌肉记忆"——熟练到不需要思考。对 AI 来说，这意味着某些常用操作不需要每次都经过完整的推理链，而是直接"知道"怎么做。这需要模型在训练层面就把这些技能内化，而不是靠 Harness 在推理时注入。这是为什么神经记忆系统需要新的模型架构支持，而不只是工程层面的改进。

**现在能做的准备**：
- 学习 **MemGPT / Letta** 框架（最接近神经记忆系统的开源实现）
- 了解 **向量数据库**（Pinecone、Weaviate、Chroma）的使用
- 关注 **长上下文模型**（Gemini 1.5 Pro 的 100 万 Token 窗口是过渡方案）

#### 预测四：Harness 可观测性会智能化
##### ⏰ 时间线：2026 H2 - 2027 H2（快速发展中）

今天的 Trace 分析还相对原始——主要是人工分析日志。未来可能会有更智能的可观测性工具，能自动识别失败模式，自动生成改进建议，甚至自动测试改进效果。

**可观测性成熟度模型**：

![Harness 可观测性成熟度模型——从手动查日志到自愈式 Harness](/assets/img/ailearn/harness/06/observability_maturity.png)

```
Level 1: 手动查看日志 ← 现在很多团队在这里
Level 2: 结构化 Trace 记录 ← LangSmith/Langfuse 提供
Level 3: 自动失败模式识别 ← 本篇05篇的 Trace Analyzer Skill
Level 4: 自动生成改进建议 + A/B 测试 ← 2027年预期
Level 5: 自愈式 Harness（发现问题→自动修复→验证）← 2028+ 远景
```

## 工程师的角色会怎么变？

这是最后一个问题，也是最重要的问题。

OpenAI 的工程师给出了一个很好的答案：

> "工程师工作的重点转向了系统、架构和杠杆作用。"

不是写代码，而是**设计让 AI 能写好代码的环境**。

具体来说：
- **设计 Harness**：理解 AI 的能力边界，设计合适的脚手架
- **管理上下文**：把重要信息组织成 AI 能访问和理解的形式
- **建立反馈回路**：通过 Trace 分析持续改进
- **设定约束和标准**：用 Linter、测试、架构规范来保证 AI 输出的质量

这些工作，需要的不只是编程能力，还需要对 AI 行为的深刻理解，对系统设计的整体把握，以及对业务目标的清晰认知。

## 写在最后

这个系列写到这里，我想说一件事。

Harness Engineering 不是一个"高大上"的概念，它本质上是一个很朴素的工程思维：**AI 有能力，但能力需要被引导；AI 会犯错，但错误可以被系统性地减少**。

LangChain、OpenAI、Anthropic 这些大厂的实践告诉我们：
- 同样的模型，Harness 设计好了，效果可以提升 20% 以上
- 三个工程师，用好 Harness，可以快速做出上百万行代码的高质量产品
- 一个精心设计的评估者，可以让 AI 的输出质量大幅提升

这些不是遥不可及的事情，它们是可以学习、可以实践的工程方法。

AI 时代，会设计 Harness 的工程师，会比只会写代码的工程师更有价值。

希望这个系列对你有帮助。

## 📎 附录：持续性问题的过渡方案

既然完整的记忆系统还需要时间成熟，**今天我们能做什么来缓解持续性问题？** 以下是分阶段的过渡方案：

### 第一阶段：文档驱动（现在就能做）

这是 OpenAI 百万行代码项目使用的方法，也是成本最低的方案：

```
每次 Agent 会话结束时：
1. 自动生成交接文档（参考第03篇模板）
2. 写入项目 docs/ 目录
3. 下次启动时自动加载最近的交接文档
4. Agent 阅读后继续工作
```

**优点**：零成本，立即可用  
**缺点**：依赖文档维护质量，信息有损压缩

### 第二阶段：结构化记忆（2027年可用）

用数据库/向量数据库存储关键事件：

```python
# 概念设计（未来可用）
class ProjectMemory:
    def store(self, event_type, content, importance):
        """存储关键事件到结构化记忆"""
        pass
    
    def recall(self, query, time_range=None):
        """根据查询检索相关记忆"""
        pass
    
    def summarize(self, since=None):
        """生成时间范围内的记忆摘要"""
        pass
```

**工具准备**（现在就可以开始学习）：
- **向量数据库**：Pinecone / Weaviate / Chroma / pgvector
- **Embedding模型**：OpenAI text-embedding-3 / Cohere embed
- **RAG框架**：LlamaIndex / Haystack

### 第三阶段：神经记忆系统（2029+ 远景）

这是终极方案——AI 像人类一样拥有不同类型的记忆：

| 记忆类型 | 类比 | 功能 | 状态 |
|---------|------|------|------|
| **情景记忆 (Episodic)** | "上周三我修复了那个Bug" | 记录具体的事件和经历 | 研究阶段 |
| **语义记忆 (Semantic)** | "Python 的 GIL 是全局解释器锁" | 存储通用知识和概念 | 部分可用（RAG） |
| **程序性记忆 (Procedural)** | "骑自行车不需要想每一步" | 内化的技能和流程 | 尚无方案 |
| **工作记忆 (Working)** | "我现在正在做X" | 当前任务的即时上下文 | 已有（上下文窗口） |
