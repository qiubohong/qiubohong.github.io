> **📖 原文来源**：Do Tuan Anh，《The Jevons Paradox in AI Infrastructure: Efficiency, Rebound, and the Limits of Cost Reduction》（用户提供 PDF）
> **✍️ 原文作者**：Do Tuan Anh
> **📅 文档生成时间**：2026 年 6 月

模型价格一路下降，企业的 AI 账单却未必会跟着变小。这篇论文想说明的正是这件事：降下来的往往只是**一次调用的价格**；被释放出来的预算，会通过更多模型、更多功能、更多订阅和更多基础设施重新长出来。

## 1. 杰文斯悖论如何落到 AI 上

1865 年，经济学家 William Stanley Jevons 观察到：蒸汽机更省煤后，英国的煤炭消耗没有下降，反而增加了。原因不复杂——单次动力更便宜，蒸汽机便进入了更多行业，新增需求吃掉了效率带来的节省。

论文认为，AI 基础设施正在经历同样的反弹效应。

过去几年，量化、蒸馏、开源模型和 API 价格竞争，把训练与推理的单位成本压低了一个到两个数量级。文中举例：GPT-4 的输入价格从 2023 年 3 月每千 token 0.03 美元，降到 2024 年 7 月 GPT-4o-mini 的 0.00015 美元，16 个月内下降约 200 倍。

不过，企业并没有因此少用 AI。它们会解除限流、把 AI 接到更多工作流、部署更多专用模型，也让以前无法承担成本、隐私或延迟限制的团队开始使用 AI。

```text
单位成本下降
      ↓
可行场景变多，使用门槛变低
      ↓
部署量与调用量增长
      ↓
总算力与总支出不降反升
```

论文最重要的判断是：企业 AI 成本并没有简单消失，而是从人力费用转移、重组成新的技术支出。

## 2. 不能混为一谈的两种效率

作者把 AI 效率分成两条线：

- **训练效率**：训练出同等能力模型所需的计算量；
- **推理效率**：在线运行模型时，每次请求所需的计算和成本。

企业侧更直接感受到的是推理效率。量化让模型占用更少显存，小模型和开源模型降低了部署门槛，API 降价让后台处理、实时审核、环境式 AI 功能开始有经济性。

但是，前沿模型的训练算力仍在快速增长。论文引用已有研究指出，自 2015 年起，最大模型的训练算力约以每年 4 倍的速度增长，快于硬件和算法效率的改善。单次操作更省，不代表整体预算会收缩；部署规模常常增长得更快。

## 3. 四种常见的反弹路径

论文用四个案例把这件事讲得更具体。

### 3.1 量化：省下的显存会被新模型填满

从 FP32 转为 INT8，显存需求大约可降到四分之一。原来只能跑一个大模型的硬件，现在可以同时承载客服、文档处理、企业搜索、代码生成等多个专用模型。

结果不是 GPU 空出来，而是模型舰队变大；当已有容量再次触顶，企业又会采购更多硬件。

### 3.2 API 降价：被取消的限制会放大 Token 吞吐

当每百万 token 的成本从几十美元降到不到一美元，原本为了控成本而设置的调用上限、频率限制就容易被取消。后台文档处理、实时内容审核和常驻式辅助能力，都会从“太贵”变成“可以默认开启”。

### 3.3 开源模型：新增的是此前进不来的使用者

可以在单张消费级 GPU 上运行的开源模型，让有数据隐私、低延迟或预算约束的组织开始自行部署。医疗、金融和公共部门并不只是把原有云 API 换成自托管，它们会带来此前不存在的推理硬件需求。

### 3.4 编程助手：人力效率提高，会扩大软件产出

论文引用 GitHub Copilot 相关研究：使用者完成任务的速度可提高 55%。作者的推论是，团队通常不会因为更快就少做功能，而是会交付更多功能；每个新功能又需要后端服务、数据管道、存储、监控和持续运行的算力。

开发效率节省的是人力边际成本，不是线上基础设施成本。

## 4. 企业 AI 成本的三本账

论文认为，企业之所以容易误判 AI 成本，是因为相关开支被拆散在三种不同的会计与采购口径中。

| 类别 | 包含什么 | 主要随什么增长 | 常见账务归属 |
|---|---|---|---|
| A：算力基础设施 | GPU、云推理端点、向量库、Embedding 管道、监控、网络与存储 | 部署规模、模型数量 | IT 资本预算、云基础设施账单 |
| B：API Token 消费 | LLM、Embedding、多模态 API 与托管微调调用 | 查询量、上下文长度 | 工程或产品云预算、研发费用 |
| C：按席位 AI 订阅 | 编程助手、知识工作 Copilot、法律或合规等领域工具 | 员工规模、采用广度 | 软件许可、团队运营费用 |

这三类成本之间还会互相传导：

```text
B 变高：API 调用规模上来
      ↓
开始评估自托管
      ↓
A 增加：购置或租用基础设施

C 变高：更多员工用 AI 提升产出
      ↓
交付更多软件与功能
      ↓
A 增加：后端、数据与运行基础设施继续扩张
```

作者称它们的共同乘数是**组织内 AI 采用的广度**。AI 触及的员工、产品和工作流越多，A、B、C 往往是叠加增长，而不是彼此抵消。

---

## 5. 别只算“省了多少人力”

论文特别批评一种常见算法：拿被自动化的人工工时，减去某个 Copilot 或 API 的费用，就宣布 AI ROI 为正。

问题在于，这只计入了部分支出。真实总拥有成本还包括 GPU 或云资源、向量和监控系统、不断增长的 Token 消费，以及多个部门分别购买的按席位工具。短期看像是人力成本下降，中期却常以“意外的云账单”和“不断新增的软件订阅”出现。

文中举了两个按席位订阅的算例：1,000 人的工程组织若全面采用 GitHub Copilot Enterprise，按每用户每月 39 美元计算，年支出约为 46.8 万美元；5,000 人的知识工作组织若采用每用户每月 21 美元的 Microsoft 365 Copilot，年支出又约为 126 万美元。两项都还未计入基础设施与 API 成本。

这些例子说明，AI 预算应该按总拥有成本来衡量，而不能只看单项工具是否便宜。

## 6. 三层企业成本管理框架

论文没有反对效率优化。它反对的是只做效率优化、却不管理需求扩张。作者提出三层框架。

### 6.1 可见性：统一 AI FinOps

先把 A、B、C 三类开支汇总为一张账，至少持续追踪：各类别与总计支出、月度增长率，以及 AI 支出占云基础设施、软件许可和人力相关成本的比例。

如果没有统一视图，跨类别的增长往往要等到预算超支后才会被发现。

### 6.2 架构：分别压低每次操作成本

- **A 类**：按工作负载规格选择 GPU、推理批处理、容忍延迟的任务使用可中断实例、将批处理排到低峰、在质量允许时使用量化模型。
- **B 类**：缓存重复 Prompt 前缀、简单任务路由到小模型、控制上下文长度、缓存高频且结果稳定的查询。
- **C 类**：续费前审计席位活跃度、合并重叠工具、以企业规模统一谈判而不是让部门零散采购。

这些做法都值得做，但它们只控制单位成本，无法天然限制总调用量。

### 6.3 治理：管理会吃掉节省的需求

作者建议使用成本分摊、消费预算和总支出 ROI 三种机制：

- 将 A、B 类成本分摊给实际消耗的产品团队；
- 给产品或工作流设 Token 预算，并在 70% 和 90% 阈值告警；
- ROI 按 A+B+C 总支出计算，而不是只对比某一项被替代的人力成本。

说到底，架构优化解决的是“每次调用更便宜”，治理解决的是“调用规模要不要继续扩大”。两者缺一不可。

## 7. 论文自己承认的边界

这篇文章是基于行业汇总数据的定性分析，并不是用企业级一手数据做出的因果测量。作者明确承认：需求弹性可能在市场趋于饱和后下降；有些优化并不会带来同等比例的新增查询；A/B 替代和 C→A 传导的强度，尚缺少系统实证。

它还指出了一个尚未充分展开的方向：Agent 工作流。相较一次普通问答，多步推理、工具调用和迭代循环的 Agent 每项任务可能消耗 5 到 30 倍 Token。推理时扩展计算也会带来类似机制——单次回答质量提高，可能让模型进入更高频或更高风险的业务场景，即使 token 单价继续下跌，总推理成本仍会上升。

这部分是论文提出的未来研究方向，应视为待验证的判断，不是已被完整量化的结论。

---

## 8. 📝 小结

- AI 单位成本下降，不等于企业 AI 总支出会下降；需求与部署扩张可能吃掉全部节省。
- 量化、API 降价、开源模型与编程助手，都可能通过不同路径带来反弹效应。
- 企业 AI 成本至少应合并计算三类：基础设施（A）、API Token（B）和按席位订阅（C）。
- A、B、C 的关系更多是随 AI 采用扩张而共同增长，而不是简单替代。
- 有效管理需要三层同时推进：统一 FinOps 可见性、逐类架构优化、以及面向需求扩张的预算和治理。
- 文中的组织成本耦合与 Agent 消耗判断仍待更多一手数据和独立研究验证。
