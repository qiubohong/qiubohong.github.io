iajev 把 Jev 做成了一个可以直接上手的 Playground。它展示的不是聊天窗口，而是一张决策表：给出上下文、写下问题、列出候选答案，然后看模型如何分配概率。

<!-- more -->

---

## 1. 一个决策由什么组成

页面将一次调用拆成三项输入：

- **Context**：消息、任务说明或事实信息，最多 8,000 个字符；
- **Question**：希望程序解决的判断，例如“这个请求该交给哪个团队？”；
- **Choices**：2 到 8 个候选项。

以客服路由为例，候选项可以是 Billing、Technical、Sales 和 Fraud。Jev 返回的不是一段“我建议交给账单团队，因为……”，而是候选项间的概率比较和置信度。对程序来说，这个结果更接近一个带模糊边界的枚举值。

---

## 2. 可以直接尝试的任务

Playground 内置了几类准备好的工具，重点是让人看到“同一个决策接口”能落在什么地方：

| 工具 | 要回答的问题 |
|---|---|
| 客服路由 | 这个请求应由哪个团队处理？ |
| 文本分类 | 这是缺陷反馈、功能请求、表扬还是问题？ |
| 意图识别 | 用户想购买、求助、取消还是了解更多？ |
| 工具选择 | Agent 下一步应调用搜索、计算器、代码还是数据库？ |
| 线索评估 | 这条销售线索的购买可能性如何？ |
| 评论分类 | 评价的情绪是正面、中性、负面还是混合？ |

每个范例都允许改写上下文。页面特别强调“before / after”对比：同一个问题，替换一个字段，例如套餐、国家或预算后，观察概率如何移动。这个动作很适合在自动化前检查决策边界是否符合直觉。

---

## 3. 使用流程

页面给出的流程很简单：描述情况、定义决策、读取信号。真正有用的部分在第三步——不要只看胜出的选项，也要看它和其他选项之间的差距。

```text
上下文：用户上月被重复扣费，退款尚未到账
问题：哪个团队应该处理？
候选项：Billing / Technical / Sales / Fraud
结果：选择 + 各候选项概率 + 置信度
```

如果 Billing 的概率遥遥领先，应用可以直接转单；如果 Billing 与 Fraud 接近，就可以追加信息、交给 LLM 复核或人工介入。这个例子说明，概率不是展示用的装饰，而是控制流的一部分。

---

## 4. API 形态

iajev 提供 REST API。请求中包含 `state` 和 `decision` 两个对象：前者放业务上下文，后者声明决策类型、问题和候选项。响应返回选择、概率和置信度，代码再决定是否执行。

页面也提醒，免费预览有额度限制；要保留决策历史或使用 API，需要登录。实际集成时还应使用幂等键，并将模型决策连同输入版本、阈值和最终结果一起记录，才能在出问题时回看系统为何走到了某条路径。

---

## 5. 📝 小结

- iajev 把 Jev 的决策接口可视化为“上下文 + 问题 + 候选项”。
- 它覆盖客服路由、文本分类、意图识别、工具选择、销售线索和评论分类等任务。
- 重点不只是模型选了什么，更是比较概率和置信度，决定自动执行还是升级处理。
- API 的输出适合进入应用控制流，但生产系统仍应保留阈值、幂等和审计记录。
