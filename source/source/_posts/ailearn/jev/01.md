> **📖 系列难度说明**：本篇为**入门导读**。没有写过 Agent 也能读；已经在做 LLM 应用的读者，可以重点看决策层、概率校准和边界部分。
> **🎁 核心收获**：读完你会知道 Jev 解决的到底是什么问题、它与 LLM/规则/人工分别如何分工，以及后续该从哪一篇开始读。

一个 Agent 收到用户请求后，先让 LLM 判断要不要搜资料；搜完后，再让 LLM 判断该调用哪个工具；工具报错了，又让 LLM 判断重试、换路还是停下。

这些判断通常不需要一段漂亮解释。程序真正想要的，只是：`search`、`retry`、`stop`，或者“转人工”。

如果软件需要的是决策，为什么还要先让模型生成一段文字？

Jev 想解决的，就是这层问题：不负责写内容，而是在有限的动作空间里，给软件一个带概率的结构化判断。

## Jev 是什么：先别把它和杰文斯悖论混在一起

这里先把一个容易绕进去的名字说清楚。

本系列谈的 **Jev**，是 TypeSafe AI 推出的决策模型，官方称它为 **System One Model**。它的工作方式不是聊天，而是接收上下文和预先定义好的问题，返回软件可直接使用的选择、分数或真伪判断，并附上概率与置信度。

```text
用户消息、任务状态、工具结果
              ↓
             Jev
              ↓
选择 / 分数 / 真伪 + 概率
              ↓
          软件控制流
```

比如客服系统看到“上个月重复扣费，退款一直没到账”，真正需要的可能不是一段安抚用户的话，而是：该交给账单组、技术组、销售组还是风控组。写回复的工作可以交给 LLM；把工单送到哪里，则是一个受限的决策问题。

还有一个很像的词：**Jevons Paradox（杰文斯悖论）**。它来自经济学，讲的是“单位成本下降，使用规模反而可能上升”。TypeSafe 用 Jev 这个名字，也确实借用了这层含义。不过，模型本身和经济学概念不是一回事。后面讲到成本、Agent 调用量和基础设施时，我们会再回到这个话题。

> 💡 **来源**：[TypeSafe 发布文章](https://typesafe.ai/blog/introducing-system-one-models-and-jev) — Jev 被定义为面向软件的类型化概率决策模型；[IEEE Micro 对杰文斯悖论的讨论](https://ieeexplore.ieee.org/abstract/document/10989062) — 解释效率提升为何不必然降低总资源需求。

## 从“生成字符串”到“做类型化决策”

大语言模型最擅长的事情，是根据上下文继续生成 token。你问它“下一步该怎么办”，它可以给出很聪明的回答，也可以按 JSON 格式输出。可程序接到之后，仍然要面对几个问题：字符串能不能解析？字段是否合法？模型是不是凭空写了一个不存在的工具名？这次的“我很确定”到底能不能信？

Jev 的思路是把问题倒过来：先由程序声明允许的结果，再让模型在这个范围里判断。

```text
传统 LLM
上下文 → 生成文字 / JSON → 解析与校验 → 执行

Jev
上下文 + 候选决策 → 选择与概率 → 执行
```

看起来只是少了几步，工程含义却不一样。前者的重点是“模型说了什么”；后者的重点是“程序允许模型做哪些选择”。

| 你要解决的问题                       | 更自然的方式        |
| ------------------------------------ | ------------------- |
| 写邮件、总结文档、解释原因、生成代码 | LLM 生成文本        |
| 客服该路由到哪里                     | 决策模型或分类器    |
| Agent 下一步选哪个工具               | 决策模型或规则      |
| 某项政策是否满足                     | 决策模型 + 业务校验 |
| 金额、权限、硬性合规条件             | 普通代码和明确规则  |

这不是“Jev 比 LLM 强”或“LLM 已经过时”。它更像一次职责拆分：LLM 负责开放式理解、推理和表达；决策模型负责把受限判断交给程序。规则足够清楚时，甚至不该调用 AI，直接写代码就行。

对于刚入门的读者，先记住一句话就够了：**Jev 不是更小的 ChatGPT，而是试图成为软件里的智能分支。**

## Jev 在 Agent 和工作流里应该放在哪

一个能做事的 Agent，通常不只有一个模型。它需要理解目标、规划步骤、调用工具、读取结果、判断是否继续，还要在风险高时停下来。

把这些都压到同一个 LLM 上，当然可以跑起来。但很多步骤其实是“是不是”“选哪一个”“要不要再试一次”。它们频率高、结果受限，而且往往不值得等待一整段自然语言生成。

Jev 比较适合嵌在这些路口：

```mermaid
graph TD
    A[用户任务] --> B[LLM：理解、规划、生成]
    B --> C{Jev：下一步怎么走？}
    C -->|调用工具| D[Search / DB / Code / MCP]
    C -->|需要复核| E[LLM 或人工]
    C -->|停止| F[返回结果]
    D --> G{Jev：继续、重试还是升级？}
    G --> B
    G --> E
    G --> F
    style C fill:#1a2332,stroke:#58a6ff,color:#c9d1d9
    style G fill:#1a2332,stroke:#58a6ff,color:#c9d1d9
    style F fill:#0d4a2a,stroke:#3fb950,color:#c9d1d9
```

落到实际系统里，常见位置有这些：

- 用户意图识别和工单路由；
- 选择搜索、数据库、代码执行等工具；
- 判断工作流该继续、重试、暂停还是结束；
- 对 LLM 结果打分，决定是否需要复核；
- 根据风险和不确定性决定自动执行还是人工升级。

你可以把它想成一个带模糊判断能力的 `if`。普通 `if` 要求条件写得极其明确；Jev 处理的是“文本里看起来像重复扣费”“这次工具失败是否值得重试”这类难以完全穷举、但候选动作有限的问题。

> 💡 **来源**：[Vercel 对 Jev 的介绍](https://vercel.com/blog/ai-gateway-jev-model-launch) — 列举了工具选择、重试/停止、风险评分、输出验证等软件内决策场景；[iajev Playground](https://iajev.com/) — 展示工单路由、意图识别、工具选择等可交互示例。

## 概率不是装饰：它决定系统怎样对待不确定性

假设模型只返回一句“交给账单组”。程序其实还缺一个关键信息：它到底有多大把握？

Jev 的产品主张之一，就是每个判断都有概率或置信度。这样，软件不必把模型输出当作绝对命令，而是可以把不确定性写进控制流。

```python
if confidence >= 0.90:
    route_to_billing()
elif confidence >= 0.70:
    request_more_context()
else:
    escalate_to_human()
```

这个模式对新手很好理解：把“AI 猜一下”改成“AI 给建议，程序按把握大小处理”。对做过生产系统的人，重点会更进一步：阈值不能凭感觉拍；不同错误的代价不同；每次升级、重试和人工审核都要被记录，之后才能回看策略是否真的有用。

更深一层是 **概率校准（calibration）**。模型说 90% 的时候，在足够多的同类样本里，正确率是否真的接近 90%？只有接近，0.9 这个阈值才有工程意义。一个准确率很高、但总在错的时候自信满满的模型，反而可能比普通分类器更危险。

TypeSafe 将其训练目标称为 RLCD（Reinforcement Learning for Calibrated Decisions）。这是厂商对产品方向的描述；校准究竟做到什么程度，仍需在具体业务数据和独立评测里验证。

## 先把边界画清：类型安全不等于决策正确

Jev 的宣传中有“不能幻觉”之类的说法。更准确的翻译是：如果调用前已经限定 Schema、候选项和输出类型，它不会突然给你一个候选集合外的工具名，也不会把枚举字段写成不合法的格式。

这个保证很实用，但范围很窄。

```text
候选项：账单组 / 技术组 / 销售组 / 风控组

类型安全保证：结果一定在这四项之内
不保证：模型一定选对其中那一项
```

所以生产系统仍要保留业务规则、状态校验、权限边界、回滚机制和人工兜底。尤其涉及资金、账号权限、安全处置、医疗或法律判断时，模型只能参与建议或分流，不能悄悄变成最后的责任主体。

性能数字也一样要带着前提读。TypeSafe 在自家工作流评测中报告过大幅速度和成本优势，但这些结论来自特定任务、特定接口包装和厂商评测设置。真正要问的是：在**你的**候选动作、你的数据分布、你的延迟要求和你的失败成本下，它是否比规则、传统分类器、JSON Mode 或一次普通 LLM 调用更合适。

这也是本系列的基调：不把 Jev 当成万能答案，而是把它作为一个值得严肃测试的新组件。

> 💡 **来源**：[Learn Jev 对概念与主张的拆解](https://learnjev.com/concepts) — 区分类型约束、实测结果与尚未公开的实现细节；[RL Research 的独立分析](https://www.rlresearch.ai/blog/is-jev-an-llm/) — 提醒类型安全和置信度都不能替代任务完成率与真实结果验证。

## 先跑一次官方 Jev：从 Playground 到第一条 API

别急着把 Jev 接进 Agent。先做一个很小的实验：用一段真实但不敏感的文本，问一个候选项有限的问题，看看概率分布是不是符合直觉。

官方给出的路径很短：

1. 打开 [TypeSafe Playground](https://console.typesafe.ai/playground) 并登录；
2. 粘贴一段 `state`，例如一条客服消息；
3. 添加一个 `Choice`、`Score` 或 `Noul` 问题；
4. 改动一项关键事实，再比较候选概率是否按预期变化；
5. 确认问题和候选项设计合理后，再到 [Console 的 API Keys 页面](https://console.typesafe.ai/keys) 创建密钥。

第一步用 Playground 很重要。它能暴露大多数接口设计问题：候选项是否重叠、有没有“无法判断”的出口、用户消息中增加一条证据后概率是否发生合理变化。等到代码已经接入生产才发现这些问题，代价会高得多。

拿到密钥后，不要把它写进源码。macOS/Linux 可以先放进当前 Shell：

```bash
export TYPESAFE_API_KEY="你的 API Key"
```

然后用官方 `POST /v1/systemone` 接口跑通一个最小请求：

```bash
curl -X POST https://api.typesafe.ai/v1/systemone \
  -H "Authorization: Bearer $TYPESAFE_API_KEY" \
  -H "Content-Type: application/json" \
  -d @- <<'EOF'
{
  "state": "我的订阅上个月被扣了两次钱，退款还没有到账。",
  "model": "jev-latest",
  "questions": {
    "department": {
      "type": "choice",
      "instructions": "这个请求应该由哪个团队处理？",
      "criteria": {
        "billing": "付款、订阅、发票或退款问题",
        "technical": "缺陷、故障或集成问题",
        "sales": "价格、合同或购买咨询",
        "human_review": "信息不足、风险较高或无法可靠归类"
      }
    },
    "urgent": {
      "type": "noul",
      "instructions": "这条消息是否表达了紧迫的时间要求？"
    }
  }
}
EOF
```

响应里最值得看的不是只有 `choice`。还要看每个候选项的 `probabilities`、`confidence`，以及 `usage`。如果 `billing` 与 `human_review` 接近，就别急着写自动路由；先检查状态里是否缺少订单或退款记录。

Python 项目可以安装官方 SDK：

```bash
pip install typesafe-sdk
```

```python
from typesafe_sdk import Choice, Noul, TypeSafeClient

client = TypeSafeClient()  # 从 TYPESAFE_API_KEY 读取密钥

response = client.system_one(
    state="我的订阅上个月被扣了两次钱，退款还没有到账。",
    questions={
        "department": Choice(
            instructions="这个请求应该由哪个团队处理？",
            criteria={
                "billing": "付款、订阅、发票或退款问题",
                "technical": "缺陷、故障或集成问题",
                "sales": "价格、合同或购买咨询",
                "human_review": "信息不足或需要人工判断",
            },
        ),
        "urgent": Noul(
            instructions="这条消息是否表达了紧迫的时间要求？",
        ),
    },
)

print(response.answers["department"].choice)
print(response.answers["department"].probabilities)
```

这段代码只是“把决策跑起来”，还不是自动化。要进入真实工作流，下一步仍然要补齐上一节说过的权限校验、阈值策略、幂等、日志和最终结果验证。

> 💡 **来源**：[TypeSafe 官方 Quick Start](https://docs.typesafe.ai/introduction/quickstart) — 官方文档说明了 Playground、Console API Key、`/v1/systemone`、Python SDK 与 `jev-latest` 的最小调用方式。

## 不想把决策送上云：三种核心开源替代方案

官方 Jev 适合想快速验证产品想法、希望少维护模型服务的团队。但如果数据不能离开本机、需要离线运行、想研究训练配方，或者只是想先在自己的电脑上跑通决策模型，开源方案已经足够丰富。

先给一个不带滤镜的对比：开源不是“免费获得同一个 Jev”。它换来的是权重、服务和训练的控制权，也把硬件、模型升级、校准与评测的责任交回给你。

| 方案 | 更适合谁 | 核心特点 | 先注意什么 |
|---|---|---|---|
| [Laya](https://github.com/NandhaKishorM/laya) | 想要轻量、本地、多语言决策 | 322M/421M 非自回归模型，支持 Choice / Score / Noul | 基础 checkpoint 存在过度自信和原语弱项，阈值须自测 |
| [Bespoke Nimble](https://github.com/bespokelabsai/nimble) | 想研究公开数据、配方与 9B 本地模型 | Qwen3.5-9B LoRA、训练与评测材料公开 | 9B 未量化权重约需 18GB，当前模型与评测覆盖仍有限 |
| [Kev](https://github.com/jaredpalmer/kev) | 想低成本本地部署且尽量复用 TypeSafe 接口 | 0.8B / 4B / 9B，多平台运行，System One API 兼容 | 仍需以自己的业务数据验证模型版本与校准 |

### Laya：轻量、多语言，适合先在本机验证思路

Laya 是 Convai Innovations 发布的开源非自回归 System 1 决策引擎，Apache-2.0 许可。它提供英文、100+ 语言的多语言 checkpoint，以及面向 typed decisions 的专用 checkpoint；模型规模在 322M 到 421M 之间。

最小安装和调用可以从下面开始：

```bash
python3 -m venv .venv
.venv/bin/python -m pip install laya
```

```python
from laya import Router

router = Router()
result = router.predict(
    {"body": "I was billed twice. Please refund the duplicate."},
    {
        "refund_requested": {
            "type": "noul",
            "instructions": "Does the user explicitly request a refund?",
        }
    },
)
print(result)
```

如果你用的是 Apple Silicon Mac，可以试试社区维护的 [laya-mlx](https://github.com/mizorewww/laya-mlx)。它以 MLX 为运行时，首个 checkpoint 下载后可离线推理：

```bash
pip install laya-mlx
```

```python
import laya_mlx as laya

agent = laya.load("aac6fef/laya-mlx")
print(agent.predict(
    "I was billed twice. Please refund the duplicate.",
    {
        "department": {
            "type": "choice",
            "instructions": "Who should handle this?",
            "criteria": ["billing", "technical", "sales"],
        }
    },
))
```

`laya-mlx` 的 M3 Max 基准中，短问题可以做到个位数到十几毫秒级，但这不是“你的 Mac 一定比云端 Jev 快 20 倍”的证明。输入长度、问题数、机器型号、模型加载状态、网络和批量方式都会改变结果。更重要的是，Laya 官方 README 明确提示：基础模型的置信度可能过度自信，`Score` 与 `Noul` 也有已知弱点；将概率接进自动化前，必须用自己的留出集重新校准。

### Bespoke Nimble：想看训练配方和数据构造，可以从它开始

Bespoke Labs 的 Nimble 更像一个“开放的 Jev 研究包”：公开模型、数据、LoRA 训练方法、推理与评测代码。它以 Qwen3.5-9B 为底座，在候选答案 token 上做 LoRA 微调，并以对比式数据构造训练模型关注真正改变结论的事实。

仓库已经给出本地运行步骤，但别低估资源要求：未量化的 9B 权重约占 18GB，合并 LoRA 时还需要额外内存和磁盘；Apple Silicon 本地运行需要 MLX 环境，Linux 则需要支持 BF16 的 NVIDIA GPU。

它适合两类工作：一是你想理解“为什么一个决策模型不是普通 Prompt 分类”；二是你已经有几百条高质量标注样本，准备做领域微调。Nimble 自己也写得很诚实：训练集规模有限，标签主要由合成流程生成，324 条留出集的对齐结果不能替代你自己的业务评测。仓库近期为特定版本加入温度校准后，也特别提醒：候选答案排序不变，但概率和依赖阈值的策略可能变化，需要重测。

### Kev：最适合做 API 替换实验的本地路线

Kev 的优势是直接对齐 TypeSafe System One API。它提供 0.8B、4B、9B 三个 Qwen3.5 底座版本，仓库建议从 4B 开始；4B 和 9B 可以放进 32GB 内存的 Mac，Apple Silicon 会走 MLX 后端。

最小服务启动方式如下：

```bash
git clone https://github.com/jaredpalmer/kev.git
cd kev
uv sync --extra serve
uv run --extra serve python -m kev.serve --run jaredpalmer/kev-4b --port 8009
```

启动后，原本使用 TypeSafe SDK 的代码只要把服务地址改到本机，就能复用相近的调用形状：

```python
from typesafe_sdk import Choice, TypeSafeClient

client = TypeSafeClient(
    api_key="local",
    base_url="http://127.0.0.1:8009",
    model="kev-latest",
)

response = client.system_one(
    state="I was charged twice. Please fix this ASAP.",
    questions={
        "billing": Choice(
            instructions="Which team should handle this?",
            criteria={"billing": None, "technical": None, "human_review": None},
        )
    },
)
print(response.answers["billing"].choice)
```

这是做“同一 Harness 下云端 Jev 与本地模型对比”的好起点。Kev 也把局限写在 README 中：不同尺寸、不同数据来源和不同版本的准确率/校准会变化；它公开的对比不等于你的业务表现。把 `base_url` 换掉之前，先按第 05 篇的方法跑相同样本、相同候选项、相同成功标准的对照。

## 不只是模型：值得跟踪的 Jev 应用生态

决策模型真正有意思的地方，是它开始被嵌进原本嫌 LLM 太慢、太自由的系统里。

- [**jev-ultrafast**](https://github.com/browser-use/jev-ultrafast)：Browser Use 的开源浏览器 Agent。它将页面转成带编号的 DOM 元素表，让 Jev 在允许的操作和目标中选择；只有 `TYPE_TEXT` 这类真正需要生成文字的动作才交给小型 LLM。它展示了“生成和决策分层”在浏览器自动化里的具体形态。项目 README 也写明，它目前仍是 MVP，页面验证、复杂控件和跨页面能力都有边界，不能把单个演示速度当作通用可靠性结论。
- **Jev Search**：Search1API 的产品化示例，用决策层理解自然语言中的意图、时间和来源限制，再调度搜索能力。它更适合当作“先解析约束，再执行检索”的设计参考，而非替代所有搜索排序算法。
- **pg-jev / duckdb-jev**：社区尝试把自然语言条件变成数据库行的概率筛选、分类或排序。这个方向很有想象力，但越接近数据访问和业务规则，越要把权限过滤、SQL 安全和最终条件校验放在模型之外。

这些项目有一个共同结构：先由程序构造受限动作空间或候选集合，再让决策模型选下一步，最后由确定性执行器和结果校验收尾。它也正是本系列一直强调的分工。

## 📝 小结

- Jev 是面向软件内受限决策的模型：输入上下文和候选结果，输出选择、分数或真伪判断，并给出概率。
- 它不替代 LLM；更合适的分工是 LLM 负责理解和生成，Jev 负责路由、分支、评分与升级判断，硬规则继续由代码承担。
- 概率的价值在于让系统按不确定性分层处理，但置信度只有经过业务数据校准后才值得信任。
- 类型安全保证输出形态受约束，不保证决策本身正确；高风险动作仍需要验证与人工兜底。
- 这个系列会从决策接口一路讲到 Agent 集成、评测、成本和治理，重点始终是：它在你的系统里是否真的划算、可靠且可控。
