> **案例验证**：全文以"用户登录失败锁定功能"为实战案例，演示 `Spec-Kit + 评审驱动开发 `的完整流程。

## 引言：流程有了，质量呢？

你有没有过这样的经历——需求明明写清楚了，AI 也照着生成了代码，跑起来一看，缺了边界处理，漏了异常场景，最后还得自己擦屁股？

这事儿我遇到不止一次。GitHub 的 spec-kit 确实给出了清晰的 AI 驱动工作流：`/speckit.specify` → `/speckit.plan` → `/speckit.tasks` → `/speckit.implement`，一步一步把想法变成代码。流程看着很美，但问题是——流程本身不等于质量。每一步都可能藏着坑：需求没想清楚、技术方案有硬伤、任务拆漏了关键场景……

所以我琢磨出一个办法：在 spec-kit 的每个环节里，加一道**魔鬼式评审**。不是走形式的"review 一下"，而是 AI 主动提问、给出建议选项、按建议修复，反复循环直到没有问题。

这篇文章就拿"用户登录失败锁定"这个功能当靶子，把六步流程走一遍，每一步都给出可以直接复制的提示词。你照着来，至少能少踩一半的坑。

## 整体流程一览

![SDD评审驱动开发流程](/assets/img/ailearn/ai-learn15-1.png)

| 步骤                | 命令/操作            | 评审重点                          | 重复机制                               |
| ------------------- | -------------------- | --------------------------------- | -------------------------------------- |
| 1. 创建规范         | `/speckit.specify`   | 需求完整吗？有没有歧义？          | AI 提问 → 给出建议 → 修复 → 直到无问题 |
| 2. 澄清需求（可选） | 评审 + 现有代码      | 有没有已实现的部分？会不会冲突？  | 同上                                   |
| 3. 制定技术方案     | `/speckit.plan`      | 符合 spec 吗？跟业界做法一致吗？  | 同上                                   |
| 4. 拆解任务清单     | `/speckit.tasks`     | 满足 spec/plan 吗？TDD 用例够吗？ | 同上                                   |
| 5. 执行实施         | `/speckit.implement` | 遇到疑问必须停，遵循 TDD          | 代码生成后自动 review                  |
| 6. 代码审查         | code-review 子 Agent | 坏味道识别，重构建议              | 修复后重新审查                         |

## 准备工作：设置全局评审规则

先别急着开干。在 CodeBuddy 里把下面这段加为**全局规则**，后面每一步都会自动遵循：

```
如果你针对要执行的任务（如：修改代码，文件等操作）存在疑问，请先提出来和我讨论，先不要去执行代码。

在每一步骤中，遵循 SDD 评审驱动流程：
1. AI 针对当前步骤输出提出问题
2. 用户要求 AI 给出最佳建议原因和其他选项
3. AI 根据最佳建议进行修复
4. 回到步骤1，直到 AI 针对当前步骤没有问题
```

说白了，就是不让 AI "闷头干活"。有疑问先说，有问题先问，别等生成完了才发现方向错了。

![SDD评审循环机制](/assets/img/ailearn/ai-learn15-2.png)

## 第一步：创建规范（/speckit.specify）—— 只说"做什么"和"为什么"

### 命令执行

```
/speckit.specify 我们需要为 Web 应用增加一个安全功能：当用户连续登录失败达到 5 次后，账户将被临时锁定 15 分钟。锁定期间，即使密码正确也不允许登录。解锁后失败次数清零。管理员可以手动解锁账户。
```

AI 会生成一份初始的 `spec.md`。别急着往下走，这时候该评审上场了。

### 评审提示词

```
基于你生成的 spec.md，结合原始的需求内容，是否包含了全部内容？请检查并提问。
```

### AI 输出问题（第一轮）

AI 通常会揪出一些你没想到的点，比如：

1. "连续失败"的定义是什么？成功登录后要不要重置计数？
2. 用户名不存在和密码错误，都算失败吗？
3. 解锁后清零——是自动解锁清零，还是手动解锁也清零？
4. 管理员手动解锁需要权限控制吗？操作要不要留日志？

你看，这些细节原始需求里都没提，但 AI 帮你问出来了。这就是评审的价值。

### 采纳最佳建议

输入这个通用提示词：

```
请针对上述问题，给出你的推荐建议和其他参考选项，以及为什么推荐该选项。
```

AI 会逐一回复，比如：

- 问题 1：推荐"成功登录后立即重置计数"。另一个选项是"超时自动重置"，但从安全实践看，即时重置更常见也更合理。
- 问题 2：推荐"两者都计入"，防止攻击者通过尝试用户名来探测账户是否存在。
- 问题 3：推荐"两种解锁方式都清零"，在 spec 里写明。
- 问题 4：推荐"需要管理员角色权限 + 操作日志"。

### 要求修复

```
请按照最佳建议修复，重新输出完整内容。
```

AI 更新 `spec.md`，补上了权限、日志、清零逻辑这些。然后 AI 会再检查一轮——还有问题吗？没有就过，有就继续修。

## 第二步：澄清需求（/speckit.clarify）—— 别跟已有代码打架

如果你的项目不是从零开始，这步很重要。新需求跟已有功能撞车，是出 bug 的高发区。

### 评审提示词

```
评审 spec.md 需求，需要先阅读当前项目已实现功能点，然后评估需求是否已经有实现的部分，如果有实现是否存在冲突应该如何解决。
```

AI 扫一遍项目代码，可能告诉你：

- 已经有个基于 IP 的失败计数中间件了，不过粒度是 IP 不是用户——要不要复用还是另起一套？
- 管理员日志模块已经存在，可以直接对接。

这些信息直接影响技术方案。早发现早处理，比后面返工强多了。

### 用通用提示词调整方案

```
请针对上述问题，给出你的推荐建议和其他参考选项，以及为什么推荐该选项。
```

AI 可能建议：复用 Redis 客户端但逻辑独立，避免耦合；日志模块直接用现有的。你再输入"请按照最佳建议修复，重新输出完整内容"，AI 更新 spec.md 或记录决策。

重复这个流程，直到 AI 没有新问题。

---

## 第三步：制定技术方案（/speckit.plan）—— 对齐 spec，对标业界

### 命令执行

```
/plan 在生成 plan 计划之前，请先阅读 spec.md 文件，必须要求生成 plan 符合 spec.md 的要求，必须参考业界主流方案。
```

AI 生成 `plan.md`，里面会有技术栈选型、模块划分、降级策略等内容。

### 评审提示词

```
请检查一下生成的内容，是否与 spec.md 文件描述符合，功能是否可以完整实现，同时符合业界主流方案。
```

AI 可能会提出这些问题：

1. Redis 高可用考虑了吗？挂了之后降级方案够不够？
2. 登录接口加了 Redis 操作，响应时间会受影响吗？
3. 管理员解锁接口需要单独的权限中间件吗？

说实话，这些问题你不评审的话，大概率会被跳过。等上线了才暴露，代价就大了。

### 用通用提示词闭环

```
请针对上述问题，给出你的推荐建议和其他参考选项，以及为什么推荐该选项。
```

AI 给建议（比如：加降级开关 + 告警；Redis 用 pipeline 减少往返；复用现有的 adminAuth 中间件）。

```
请按照最佳建议修复，重新输出完整内容。
```

AI 更新 `plan.md`。有新问题继续，没有就往下走。

---

## 第四步：拆解任务清单（/speckit.tasks）—— spec/plan 要落地，TDD 不能少

### 命令执行

```
/task 在生成任务前，请先阅读 spec.md 和 plan.md 文件的要求，结合现有项目代码，必须生成符合要求且能实现完整功能的任务内容。可以减少后续评审迭代次数。
```

AI 生成 `tasks.md`。

### 评审提示词

```
请检查一下生成的 tasks.md，是否满足 spec.md 和 plan.md 文件的实现要求，结合现有项目代码，能否按照该任务描述完整实现功能。
- 验证功能完整性
- 验证代码可行性
- 是否符合测试驱动开发规范
```

AI 可能指出：

- 任务 1 漏了"锁定期间尝试登录"的处理逻辑。
- 单元测试缺了 Redis 异常降级这个场景。
- 管理员解锁没写权限测试用例。

这些遗漏在实际开发中很常见。评审环节把它们提前暴露出来，后面写代码就顺畅多了。

### 闭环修复

输入通用提示词，AI 给出补充建议。要求修复后，AI 更新 `tasks.md`。反复直到 AI 确认所有要求都满足了。

最终拿到的 `tasks.md`，每个任务都带着详细的测试用例列表——这才算可以动手写代码了。

---

## 第五步：执行实施（/speckit.implement）—— TDD 走起，有疑问就停

### 命令执行

```
/speckit.implement 必须严格按照宪章和 tasks.md、spec.md、plan.md 中的描述来，如果在生成的代码遇到任何疑问都需要停留下来。必须遵循以下步骤：
1. 测试驱动开发规范
2. 生成后的代码必须符合当前 lint 规则
```

AI 开始一个任务一个任务地实现。关键是：**遇到拿不准的地方，AI 必须停下来问你**，不能自己猜着写。

举个例子：

> "在实现登录接口时，关于 Redis 降级策略：如果 Redis 查询锁定状态超时，按照 plan.md 应该允许继续登录。我准备用 try-catch 包裹，捕获异常后记录日志并假设未锁定。这个实现是否正确？还是有其他推荐？"

这种时候，你可以直接回答，也可以用通用提示词让 AI 自己给建议。确认之后 AI 再继续。

每个函数写完，AI 会自动补上对应的单元测试（TDD 红绿循环），跑一遍测试，挂了就修，过了再往下走。

## 第六步：代码审查（code-review 子 Agent）—— 专抓坏味道

代码写完不算完。让 code-review 子 Agent 过一遍，往往能发现一些"写的时候觉得没问题，回头看一身冷汗"的地方。

### 提示词

```
使用 code-review 子 Agent，请根据你刚刚生成代码进行 code review。
```

### code-review 子 Agent 的角色设定

这里我参考了 Martin Fowler 在《重构：改善既有代码的设计（第 2 版）》中的思路——先识别"代码坏味道"，再对症下药。

![代码坏味道诊断流程](/assets/img/ailearn/ai-learn15-3.png)

**审查目标：**

- 可读性、可维护性、扩展性，哪个拖后腿了？
- 重复代码、过长函数、过大的类，有没有？
- 面向对象设计原则（单一职责、开放封闭等），遵守了吗？
- 重构手法要具体，不能只说"建议优化"。

**审查流程：**

1. 先理解代码上下文。
2. 对照坏味道清单逐项排查。
3. 分析问题根源。
4. 给出重构建议（手法 + 示例代码）。
5. 按优先级排序。

**附录：常用代码坏味道（基于《重构》第 2 版）**

- 神秘命名、重复代码、过长函数、过长参数列表、全局数据、可变数据、发散式变化、霰弹式修改、依恋情结、数据泥团、基本类型偏执、重复的 switch、循环语句、冗赘的元素、夸夸其谈通用性、临时字段、过长的消息链、中间人、内幕交易、过大的类、异曲同工的类、纯数据类、被拒绝的遗赠、注释。

Martin Fowler 说过："代码有很多种坏味道，重复是最坏的一种。"他把坏味道比作病症——知道了症状，才能对症下药。这套清单就是你的诊断手册。

### 示例输出

> 整体来看，登录函数实现了需求，但有几个地方可以改：
>
> **1. 过长函数**（`login` 函数，约 60 行）：锁定检查、密码验证、失败计数、成功清理全挤在一个函数里，读起来费劲，测试也麻烦。
>
> - **建议**：用"提取函数"手法，把锁定检查拆成 `isUserLocked(username)`，失败计数拆成 `recordFailedAttempt(username)`，成功清理拆成 `clearFailedAttempts(username)`。每个函数只干一件事，单独测试和复用都方便。
>
> **2. 重复代码**（多处 try-catch Redis 操作）：每个 Redis 操作都写了一遍错误日志 + 降级逻辑，看得出是复制粘贴的。
>
> - **建议**：用"提炼函数"手法，抽一个 `withRedisFallback(operation, fallbackValue)` 包装函数，把重复消灭掉。
>
> **3. 基本类型偏执**：Redis key 的模板字符串散落在代码各处，改一个要搜半天。
>
> - **建议**：用"引入常量"手法，定义 `REDIS_KEYS` 对象集中管理，改起来只动一处。

根据建议让 AI 修复，重构完跑一遍测试——功能不变、测试通过，才算过关。不满意就再来一轮 code-review。

## 写在最后：质量左移，少返工

说到底，魔鬼评审模式做了一件事：**把发现问题的时机往前挪**。

- 需求阶段——多轮提问把歧义逼出来，spec 写到位了。
- 方案阶段——对标业界做法，降级和性能提前考虑，plan 站得住。
- 任务阶段——测试用例写细了，TDD 能落地，功能不漏项。
- 实施阶段——遇疑即停，TDD 红绿循环，代码和测试同步推进。
- 审查阶段——基于《重构》抓坏味道，可维护性持续改善。

整个过程就是"提问 → 建议 → 修复 → 再提问"的循环，简单粗暴但管用。你会发现，真正花在"改 bug"上的时间少了很多，因为大部分问题在写代码之前就被拦住了。

每个步骤的提示词都给你准备好了，复制就能用。"用户登录失败锁定"只是个例子，换成任何需求，流程一样走。

现在就打开你的 CodeBuddy，设好全局规则，试一次评审驱动开发吧。
