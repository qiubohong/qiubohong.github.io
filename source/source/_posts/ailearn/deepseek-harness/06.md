你让 Agent 帮你做一个完整的代码审查——检查风格、找安全漏洞、评估性能，最后出一份综合报告。

单个 Agent 能做，但做得不够好。它的注意力会分散，风格审查做到一半开始想安全问题，安全问题没查完又跳去看性能。最后给你一份什么都提了、什么都没说透的报告。

这种场景，就是多 Agent 的用武之地。

## dsh 的多 Agent 和"自己搭"有什么不一样

上一篇讲架构时提到，dsh 原生支持子代理、工作流和 Teams。这不是说你可以自己写代码实现多 Agent——而是说 dsh 框架本身就内置了这套机制。

区别在哪？

自己搭多 Agent，你要处理：Agent 间的消息传递、上下文隔离、错误传播、调用深度控制……每一个都是坑。

用 dsh 的原生机制，这些问题框架帮你处理了。你只需要关心"这个任务该交给哪个 Agent"，不需要关心"怎么把消息传过去"。

具体来说，dsh 提供了三种多 Agent 模式：

**子代理（Sub-agent）**：当前 Agent 把一个子任务委托给另一个 Agent，等结果回来再继续。最简单的多 Agent 形式。

**工作流（Workflow）**：预定义的 Agent 执行序列，支持串行和并行。适合流程固定的场景。

**Teams**：多个 Agent 组成一个团队，共享目标，协同完成任务。适合需要持续协作的复杂场景。

## 子代理：最简单的多 Agent 形式

子代理是 dsh 里最直接的多 Agent 机制。当前 Agent 在执行过程中，可以把一个子任务"委托"给另一个 Agent。

从用户视角看，这是透明的——你只是发了一条指令，但背后可能有多个 Agent 在协作。

从开发者视角看，子代理的关键是**作用域隔离**。

### `agent.ctx`：每个 Agent 有自己的上下文

这是 dsh 子代理机制里最重要的设计。

每个 Agent 有自己的 `agent.ctx`——一个从父 `ctx` 派生出来的子上下文。在 `agent.ctx` 上注册的工具、提示词、事件监听，只对这个 Agent 有效，不会影响其他 Agent。

```typescript
import type { Context } from '@deepseek-ai/cordis'

export const name = 'sub-agent-demo'
export const inject = ['agents', 'tools']

export function apply(ctx: Context) {
  // 监听 Agent 创建事件
  ctx.on('agent/create', (event) => {
    const agent = event.agent

    // 在这个 Agent 的专属上下文里注册工具
    // 这个工具只有这个 Agent 能用，不会污染全局工具列表
    agent.ctx.tools.register({
      name: 'specialized_search',
      description: '这个工具只对当前 Agent 可见',
      parameters: { type: 'object', properties: {} },
      async execute() {
        return { result: '专属搜索结果' }
      }
    })
  })
}
```

为什么要作用域隔离？

想象一下：你有一个"安全审查 Agent"和一个"代码生成 Agent"。安全审查 Agent 需要一个"扫描漏洞"工具，但这个工具不应该出现在代码生成 Agent 的工具列表里——不然代码生成 Agent 可能会莫名其妙地调用它。

`agent.ctx` 解决的就是这个问题。每个 Agent 只能看到自己上下文里注册的工具，不会被其他 Agent 的工具干扰。

### 子代理的调度：`ctx.agents`

子代理的调度通过 `ctx.agents` 服务完成。你可以在工具里调用 `ctx.agents.run()` 来启动一个子代理：

```typescript
import type { Context } from '@deepseek-ai/cordis'

export const name = 'orchestrator-tools'
export const inject = ['tools', 'agents']

export function apply(ctx: Context) {
  // 注册一个"调用子代理"的工具
  ctx.tools.register({
    name: 'delegate_to_security_agent',
    description: '将代码安全审查任务委托给专门的安全审查 Agent。' +
      '当需要深入分析代码安全漏洞时使用。',
    parameters: {
      type: 'object',
      properties: {
        code: {
          type: 'string',
          description: '需要审查的代码内容'
        },
        focus: {
          type: 'string',
          description: '重点关注的安全问题类型',
          enum: ['injection', 'auth', 'crypto', 'all']
        }
      },
      required: ['code']
    },
    async execute({ code, focus = 'all' }) {
      // 启动安全审查子代理
      const result = await ctx.agents.run({
        preset: 'security-reviewer',  // 使用预定义的 Agent preset
        task: `请对以下代码进行安全审查，重点关注：${focus}\n\n${code}`,
      })

      return {
        success: true,
        securityReport: result.output,
        agentId: result.agentId
      }
    }
  })
}
```

这里有个关键概念——**Agent preset**。

## Agent Preset：给 Agent 定制"人设"

Preset 是 dsh 里预定义的 Agent 配置，包括系统提示词、工具集、运行模式等。你可以把它理解成 Agent 的"职位描述"。

不同的 preset 对应不同的专业角色：

```yaml
# cordis.yml 里定义 preset
- insert:
  - id: security-reviewer-preset
    name: '@deepseek-ai/dsh-preset'
    config:
      presetId: security-reviewer
      systemPrompt: |
        你是一个专业的代码安全审查专家。
        你的职责：深入分析代码中的安全漏洞，包括 SQL 注入、XSS、CSRF、权限绕过等。
        你不关心：代码风格、性能优化、业务逻辑。
        输出格式：按风险等级（高/中/低）列出安全问题，每条附上具体位置和修复建议。
      tools:
        - search_cve_database  # 只给这个 Agent 安全相关的工具
        - check_dependency_vulnerabilities
```

Preset 的好处是可复用——同一个 preset 可以被多个地方调用，不需要每次都重新定义 Agent 的行为。

对于架构师来说，preset 还有一个更深的意义：它是 dsh 里实现"最小权限原则"的机制。每个 preset 只配置它需要的工具，不会给 Agent 多余的能力。

## 工作流：当任务有固定流程时

子代理是"动态的"——当前 Agent 自己决定什么时候调用子代理、调用哪个。

工作流是"静态的"——你提前定义好执行顺序，框架按顺序跑。

dsh 的工作流支持串行和并行两种模式。

### 串行工作流

适合有依赖关系的任务——A 完成后才能开始 B。

```typescript
// 串行工作流：代码审查流程
// 分析 → 安全审查 → 性能审查 → 生成报告
const workflow = [
  {
    agentId: 'code-analyzer',
    task: (input) => `分析以下代码的结构和依赖：\n${input.code}`,
    outputKey: 'analysis'
  },
  {
    agentId: 'security-reviewer',
    // 依赖上一步的输出
    task: (input) => `基于以下分析结果，进行安全审查：\n${input.analysis}`,
    outputKey: 'securityReport'
  },
  {
    agentId: 'performance-reviewer',
    task: (input) => `基于以下分析结果，进行性能审查：\n${input.analysis}`,
    outputKey: 'performanceReport'
  },
  {
    agentId: 'report-generator',
    // 汇总前面所有步骤的输出
    task: (input) => `生成综合审查报告：\n安全：${input.securityReport}\n性能：${input.performanceReport}`,
    outputKey: 'finalReport'
  }
]
```

### 并行工作流

适合没有依赖关系的任务——A 和 B 可以同时跑。

```typescript
// 并行工作流：安全审查和性能审查可以同时进行
const parallelWorkflow = {
  // 第一阶段：串行（必须先分析）
  sequential: [
    { agentId: 'code-analyzer', task: '分析代码结构', outputKey: 'analysis' }
  ],
  // 第二阶段：并行（安全和性能审查互不依赖）
  parallel: [
    { agentId: 'security-reviewer', task: (ctx) => `安全审查：${ctx.analysis}`, outputKey: 'security' },
    { agentId: 'performance-reviewer', task: (ctx) => `性能审查：${ctx.analysis}`, outputKey: 'performance' }
  ],
  // 第三阶段：串行（汇总报告需要等前两步完成）
  sequential2: [
    { agentId: 'report-generator', task: (ctx) => `生成报告：${ctx.security} + ${ctx.performance}`, outputKey: 'report' }
  ]
}
```

并行工作流的时间收益很明显——安全审查和性能审查同时跑，总时间是两者中较长的那个，而不是两者之和。

## `ctx.goals`：让 Agent 记住它在做什么

多 Agent 协作里有一个容易被忽视的问题：**Agent 在执行子任务时，可能忘了整体目标是什么**。

比如你让 Orchestrator 完成"重构整个认证模块"，它把子任务分给了开发者 Agent。开发者 Agent 在改代码时，可能会因为某个细节问题陷进去，忘了整体目标是"重构认证模块"，而不是"把这个函数改得完美"。

dsh 的 `ctx.goals` 服务解决这个问题。

```typescript
import type { Context } from '@deepseek-ai/cordis'

export const name = 'goal-manager'
export const inject = ['agents']

export function apply(ctx: Context) {
  ctx.on('agent/create', (event) => {
    const agent = event.agent

    // 给 Agent 设置目标
    // 目标会在每次步骤开始时注入到上下文，提醒 Agent 它在做什么
    ctx.goals.set(agent, {
      primary: '重构认证模块，提高代码可维护性',
      constraints: [
        '不要改变现有 API 接口',
        '保持向后兼容',
        '每个函数不超过 50 行'
      ],
      successCriteria: '所有测试通过，代码覆盖率不低于 80%'
    })
  })
}
```

`ctx.goals` 的工作原理是：目标信息会在每次 `agent/pre-step` 时自动注入到模型的上下文里。这样 Agent 在每一步都能"看到"自己的目标，不容易跑偏。

对于普通用户来说，这意味着 Agent 更专注、更少跑偏。对于开发者来说，这是一个可以精确控制 Agent 行为边界的机制。

## Teams：持续协作的多 Agent 模式

子代理和工作流都是"一次性"的——完成任务就结束了。

Teams 是不同的——多个 Agent 组成一个持续运行的团队，共享目标，可以互相通信，协同完成长期任务。

Teams 适合的场景：

- 长期项目维护（不是一次性任务，而是持续的工作）
- 需要多个专家持续协作（比如一个 Agent 负责监控、一个负责修复、一个负责报告）
- 任务之间有复杂的依赖和反馈关系

来看一个 Teams 的配置示例——一个代码质量监控团队：

```yaml
# cordis.yml：配置一个代码质量监控 Team
- insert:
  - id: code-quality-team
    name: '@deepseek-ai/dsh-teams'
    config:
      teamId: code-quality
      members:
        - agentId: monitor-agent
          role: monitor
          description: '持续监控代码变更，发现质量问题'
          triggers:
            - event: 'file/changed'
              filter: '*.ts'

        - agentId: reviewer-agent
          role: reviewer
          description: '对监控 Agent 发现的问题进行深入审查'
          triggers:
            - event: 'team/message'
              from: 'monitor-agent'

        - agentId: reporter-agent
          role: reporter
          description: '汇总审查结果，生成质量报告'
          schedule: 'daily'  # 每天定时生成报告
```

Teams 里的 Agent 可以通过 `team/message` 事件互相通信：

```typescript
// monitor-agent 发现问题后通知 reviewer-agent
ctx.on('file/changed', async (event) => {
  const issues = await analyzeFile(event.path)

  if (issues.length > 0) {
    // 发消息给团队里的其他 Agent
    await ctx.teams.send({
      to: 'reviewer-agent',
      message: {
        type: 'review-request',
        file: event.path,
        issues: issues
      }
    })
  }
})
```

## 一个完整的实战：代码审查 Team

把上面这些概念串起来，看一个完整的例子。

场景：给一个 TypeScript 项目搭一个自动化代码审查系统。每次有代码提交，自动触发三个专家 Agent 并行审查，最后汇总报告。

**项目结构：**

```
code-review-team/
├── src/
│   ├── agents/
│   │   ├── style-reviewer.ts    # 风格审查 Agent
│   │   ├── security-reviewer.ts # 安全审查 Agent
│   │   ├── perf-reviewer.ts     # 性能审查 Agent
│   │   └── report-generator.ts  # 报告生成 Agent
│   └── orchestrator.ts          # 编排插件
└── cordis.yml
```

**编排插件：**

```typescript
// src/orchestrator.ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'code-review-orchestrator'
export const inject = ['tools', 'agents']

export function apply(ctx: Context) {
  ctx.tools.register({
    name: 'run_code_review',
    description: '对指定文件或代码片段运行完整的代码审查，包括风格、安全和性能三个维度。',
    parameters: {
      type: 'object',
      properties: {
        filePath: {
          type: 'string',
          description: '要审查的文件路径'
        },
        reviewType: {
          type: 'string',
          enum: ['full', 'security-only', 'style-only', 'performance-only'],
          description: '审查类型，full 表示全面审查',
          default: 'full'
        }
      },
      required: ['filePath']
    },
    async execute({ filePath, reviewType = 'full' }) {
      // 读取文件内容
      const { readFileSync } = await import('fs')
      let code: string
      try {
        code = readFileSync(filePath, 'utf-8')
      } catch {
        return { success: false, error: `文件不存在：${filePath}` }
      }

      ctx.logger.info('[orchestrator] 开始审查：%s（类型：%s）', filePath, reviewType)

      // 根据审查类型决定启动哪些子代理
      const reviewTasks: Promise<any>[] = []

      if (reviewType === 'full' || reviewType === 'style-only') {
        reviewTasks.push(
          ctx.agents.run({
            preset: 'style-reviewer',
            task: `审查以下代码的风格规范：\n\`\`\`typescript\n${code}\n\`\`\``,
          }).then(r => ({ type: 'style', report: r.output }))
        )
      }

      if (reviewType === 'full' || reviewType === 'security-only') {
        reviewTasks.push(
          ctx.agents.run({
            preset: 'security-reviewer',
            task: `审查以下代码的安全漏洞：\n\`\`\`typescript\n${code}\n\`\`\``,
          }).then(r => ({ type: 'security', report: r.output }))
        )
      }

      if (reviewType === 'full' || reviewType === 'performance-only') {
        reviewTasks.push(
          ctx.agents.run({
            preset: 'performance-reviewer',
            task: `审查以下代码的性能问题：\n\`\`\`typescript\n${code}\n\`\`\``,
          }).then(r => ({ type: 'performance', report: r.output }))
        )
      }

      // 并行等待所有子代理完成
      const results = await Promise.all(reviewTasks)

      // 汇总报告
      const summary = results.map(r =>
        `【${r.type === 'style' ? '风格' : r.type === 'security' ? '安全' : '性能'}审查】\n${r.report}`
      ).join('\n\n---\n\n')

      ctx.logger.info('[orchestrator] 审查完成：%s', filePath)

      return {
        success: true,
        filePath,
        reviewType,
        summary,
        details: results
      }
    }
  })
}
```

**各专家 Agent 的 preset 配置：**

```yaml
# cordis.yml
- insert:
  - id: orchestrator
    name: './src/orchestrator.ts'

  - id: style-reviewer-preset
    name: '@deepseek-ai/dsh-preset'
    config:
      presetId: style-reviewer
      systemPrompt: |
        你是代码风格审查专家。只关注：命名规范、代码格式、注释质量、函数长度。
        不关注：安全问题、性能问题、业务逻辑。
        输出：列出具体问题，每条附行号和改进建议。

  - id: security-reviewer-preset
    name: '@deepseek-ai/dsh-preset'
    config:
      presetId: security-reviewer
      systemPrompt: |
        你是代码安全审查专家。只关注：SQL注入、XSS、CSRF、权限控制、敏感信息泄露。
        不关注：代码风格、性能问题。
        输出：按风险等级（高/中/低）列出安全问题，附修复建议。

  - id: performance-reviewer-preset
    name: '@deepseek-ai/dsh-preset'
    config:
      presetId: performance-reviewer
      systemPrompt: |
        你是性能优化专家。只关注：不必要的循环、重复查询、内存泄漏、算法复杂度。
        不关注：代码风格、安全问题。
        输出：列出性能问题，附预估影响和优化方案。
```

启动后，你可以这样使用：

```
帮我审查 src/auth/login.ts 这个文件
```

Agent 会自动调用 `run_code_review` 工具，并行启动三个专家子代理，等全部完成后汇总报告给你。

## 多 Agent 的几个实用原则

用了一段时间多 Agent 之后，总结了几个实际有用的原则：

**专注比全能更重要**。每个 Agent 的 system prompt 要写清楚"我不关注什么"，不只是"我关注什么"。一个专注安全的 Agent，如果它的 prompt 里没有明确说"不关注性能"，它可能会忍不住顺手提几个性能建议，结果报告变得杂乱。

**上下文传递要完整**。Orchestrator 把任务分给子代理时，必须把相关上下文一起传过去。"帮我审查这段代码"和"帮我审查这段代码（这是一个 Node.js 后端服务，使用 Express 框架，需要符合 OWASP Top 10 安全标准）"，子代理给出的结果会差很多。

**并行不是万能的**。有依赖关系的任务不能并行——安全审查依赖代码分析的结果，就必须串行。强行并行会导致子代理拿到不完整的上下文，结果质量下降。

**控制调用深度**。子代理可以再调子代理，但不要超过 3 层。层级越深，调试越难，信息传递的损耗也越大。

## 📝 小结

- dsh 原生支持三种多 Agent 模式：子代理（动态委托）、工作流（预定义序列）、Teams（持续协作）
- `agent.ctx` 是作用域隔离的关键——每个 Agent 有自己的上下文，工具和提示词不会互相污染
- Agent preset 是预定义的 Agent 配置，实现"最小权限原则"，每个 Agent 只有它需要的工具
- 工作流支持串行和并行：有依赖关系用串行，无依赖关系用并行，时间收益明显
- `ctx.goals` 让 Agent 在每一步都能"看到"整体目标，减少跑偏
- Teams 适合长期协作场景，Agent 之间通过 `team/message` 事件通信
- 实用原则：专注比全能重要、上下文传递要完整、控制调用深度不超过 3 层
