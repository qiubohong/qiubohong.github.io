> **📖 篇章难度**：📗 **进阶**。这一篇开始进入推理模型的参数世界，重点不再是“会不会生成”，而是“愿意花多少算力去想”。
> **🎯 核心收获**：推理模型和非推理模型的本质差异 + 四家主流平台推理参数对比 + 一套更实用的选型与控费思路

**为什么有些问题，用普通模型一下就答了，但一换到推理模型，参数逻辑像突然变了一套？**

因为它确实变了。

<!-- more -->

前面三篇，我们讲的核心还是传统 LLM API 的世界：采样参数、平台差异、不同任务下怎么调 `temperature`、`top_p`、`top_k`。这些东西当然还重要，但到了推理模型这里，重点已经悄悄换了。

你会发现，很多熟悉的参数不是被锁死，就是干脆失效。取而代之的，是另一类更像“资源调度器”的参数：

- 模型愿意想多深？
- 推理过程要不要展示出来？
- 一次回答最多能花多少 token？
- 这些“思考 token”到底怎么算钱？

这也是很多人第一次用 `o1`、DeepSeek-R1、Kimi thinking 模型时最别扭的地方：

**你不再是在调一句话怎么说，而是在调模型要不要先认真想。**

这一篇就把这件事讲清楚。

---

## 先把核心区别说透：推理模型和非推理模型，调的不是同一层

如果你前面已经熟悉了普通模型，那这里最容易犯的错，就是还想用老经验去理解推理模型。

但两者其实不在同一个工作层。

普通模型，比如 `GPT-4o`、`Claude Sonnet`、`DeepSeek-V3`，大多数时候更像“直接作答型”模型。你给它 prompt，它就往下生成，采样参数主要作用在**最终输出**上。

推理模型不一样。它们在把答案给你之前，往往会先经历一个内部推理阶段。这个阶段可能包含：

- 多步拆解
- 自我验证
- 不同路径比较
- 中间结论回溯

最后，模型再把这些内部过程压缩成你看到的最终答案。

所以差别不只是“它更聪明一点”，而是：

**普通模型主要在调输出风格，推理模型主要在调思考强度。**

| 维度               | 非推理模型            | 推理模型                                   |
| ------------------ | --------------------- | ------------------------------------------ |
| **生成模式**       | 单阶段，直接输出      | 两阶段：推理 → 输出                        |
| **用户可见内容**   | 基本就是最终回答      | 可隐藏推理，也可展示思考过程               |
| **参数主要作用点** | 最终输出 token        | 推理阶段 + 输出阶段                        |
| **成本构成**       | 输入 + 输出 token     | 输入 + 推理 token + 输出 token             |
| **典型模型**       | GPT-4o、Claude Sonnet | OpenAI o1、DeepSeek-R1、Kimi k2.5-thinking |

你只要接受这个前提，后面很多参数为什么长那样，就顺了。

---

## 推理模型多出来的，其实是三类参数

不同平台叫法不一样，但拆开看，基本都绕不开这三件事：

| 类别               | 典型参数                                               | 它真正控制的是什么                     |
| ------------------ | ------------------------------------------------------ | -------------------------------------- |
| **推理强度控制**   | `reasoning_effort`、`thinking`                         | 模型愿意花多少计算资源去想             |
| **推理过程可见性** | `reasoning_content`、`thinking` 返回字段               | 你能不能看到它在想什么                 |
| **token 预算控制** | `max_completion_tokens`、`budget_tokens`、`max_tokens` | 这次回答最多允许消耗多少思考和输出额度 |

所以这类参数的重点，已经不只是“答得活不活”，而是：

- **正确率能不能上去**
- **延迟会不会明显变长**
- **成本会不会突然飙起来**

这也是为什么推理模型更像工程问题，而不是单纯的生成问题。

## OpenAI o1：最典型，也最容易让人误会的一个参数是 `reasoning_effort`

OpenAI 的 `o1` 系列是很多人接触推理模型的第一站。它最核心的控制项，就是 `reasoning_effort`。

### `reasoning_effort` 到底在调什么？

这个参数的含义其实很直白：

**模型在回答之前，愿意花多少“脑力”先想一轮。**

可选值一般是：`low`、`medium`、`high`。

| 取值     | 推理深度 | 适用场景                 | 延迟 | 推理 token 消耗 |
| -------- | -------- | ------------------------ | ---- | --------------- |
| `low`    | 浅层推理 | 简单问题、快速响应场景   | 低   | 较少            |
| `medium` | 中等推理 | 大多数需要思考的问题     | 中   | 中等            |
| `high`   | 深度推理 | 复杂数学、规划、科学分析 | 高   | 较多            |

如果你把它理解成“让模型多想一会儿”，基本就不会偏。

### 为什么 `o1` 让很多老参数突然没意义了？

因为 `o1` 的设计思路本来就不是“靠采样来找答案”，而是“靠推理来找答案”。

所以它会把一批你熟悉的旋钮直接锁掉：

- `temperature=1.0`，不能改
- `top_p=1.0`，不能改
- `presence_penalty` 和 `frequency_penalty` 不可用
- 不支持 `logprobs`

这背后的意思很明确：

**OpenAI 不希望你用表面的随机性去干预推理结果，而是希望你用推理强度来换正确率。**

所以用 `o1` 时，别再纠结“要不要把温度调低一点更稳”。这条路在这里走不通。

### 一个够用的使用方式

```python
from openai import OpenAI

client = OpenAI()

response = client.chat.completions.create(
    model="o1-2024-12-17",
    messages=[
        {"role": "user", "content": "一个池塘里的荷花每天增长一倍，30天长满整个池塘。问第几天长满一半？"}
    ],
    reasoning_effort="high",
    max_completion_tokens=5000
)

print(response.choices[0].message.content)
```

```javascript
import { generateText } from "ai";
import { openai } from "@ai-sdk/openai";

const { text, reasoning } = await generateText({
  model: openai("o1"),
  prompt: "一个池塘里的荷花每天增长一倍，30天长满整个池塘。问第几天长满一半？",
  reasoningEffort: "high",
  maxTokens: 5000,
});
```

### 真正实用的选值建议

| 场景                         | 推荐 `reasoning_effort` | 说明                 |
| ---------------------------- | ----------------------- | -------------------- |
| 常识问答、简单分类           | `low`                   | 更快，成本更低       |
| 代码审查、业务逻辑分析       | `medium`                | 准确率和延迟比较平衡 |
| 数学证明、复杂规划、科学研究 | `high`                  | 更适合换正确率       |

我自己的建议是：**默认先从 `medium` 起步。**

因为很多问题其实并不需要一路开到 `high`。如果你一上来就给最高推理强度，最先涨上去的通常不是质量，而是账单和等待时间。

## Claude 的 `thinking` 更像“开不开深度思考”，而不是轻量调节

Anthropic 这边的思路和 OpenAI 有点像，但表达方式更直接：它给了你一个 `thinking` 开关和配套预算。

### `thinking` 怎么配？

Claude 的 `thinking` 不是写在 `messages` 里面，而是一个顶层请求参数，通常长这样：

```json
{
  "thinking": {
    "type": "enabled",
    "budget_tokens": 2048
  }
}
```

这里最重要的两个字段是：

| 字段            | 说明                                        |
| --------------- | ------------------------------------------- |
| `type`          | `enabled` 或 `disabled`                     |
| `budget_tokens` | 分配给思考过程的 token 上限，通常要求 ≥1024 |

你可以把它理解成：

- `enabled`：这题允许你认真想
- `budget_tokens`：但最多只能想这么多

### 为什么 Claude 也会限制 `temperature`？

因为这套逻辑本来就在强调“用思考替代采样”。

当 `thinking` 启用时，Claude 往往要求 `temperature=1.0`。这个限制背后的意思和 `o1` 很像：

**深度推理这件事，平台希望模型自己控制，而不是让你再从外部加一层随机性。**

如果你还拿普通聊天模型那套“温度越低越稳”的习惯过来，就会觉得这个限制很奇怪；但放到推理模型语境里，它其实很统一。

### Claude 的一个优势：思考过程可以看

启用 `thinking` 后，响应里通常会带回思考内容。这个能力很实用，尤其在两类场景下：

- **调试阶段**：你想知道模型为什么会跑偏
- **高透明业务场景**：你希望用户知道这不是拍脑袋回答

示例：

```python
import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-sonnet-4-20250514",
    max_tokens=4096,
    thinking={
        "type": "enabled",
        "budget_tokens": 2048
    },
    messages=[
        {"role": "user", "content": "解决这个逻辑谜题：有5个人站成一排，每个人戴着一顶黑色或白色的帽子..."}
    ]
)

print("思考过程:", response.thinking)
print("最终回答:", response.content[0].text)
```

如果你做的是面向内部分析、专业问答、教育辅导这类产品，Claude 这种“可看见的思考过程”会很有吸引力。

## DeepSeek-R1：最值得注意的，不只是 `thinking`，还有 `reasoning_content`

DeepSeek 的推理模型思路相对更“工程化”一点：你能比较明确地控制是否启用推理，也能比较方便地拿到思考过程。

### 参数并不复杂，但有个坑特别容易踩

常见参数大概是这样：

| 参数         | 类型      | 说明                                            |
| ------------ | --------- | ----------------------------------------------- |
| `thinking`   | `boolean` | 是否启用推理模式                                |
| `max_tokens` | `integer` | 输出总额度，通常包含推理 token + 最终输出 token |

这里最关键的一点是：

> **DeepSeek-R1 的 `max_tokens` 往往限制的是推理和输出的总和。**

这意味着，如果你把预算设得太小，模型可能不是“答得简洁”，而是“想了一半就被截断”。结果就是：思考过程耗光额度，最终答案反而不完整。

这和普通模型里“max_tokens 不够就少说两句”不太一样。推理模型里，它可能直接影响答案是否成立。

### `reasoning_content` 很适合做可视化展示

DeepSeek 的一个优点，是它在流式和非流式场景里都比较方便拿到 `reasoning_content`。

非流式：

```python
response = client.chat.completions.create(
    model="deepseek-reasoner",
    messages=[{"role": "user", "content": "一个复杂的数学问题..."}],
    thinking=True,
    max_tokens=8192
)

reasoning = response.choices[0].message.reasoning_content
answer = response.choices[0].message.content
```

流式：

```python
for chunk in client.chat.completions.create(
    model="deepseek-reasoner",
    messages=[{"role": "user", "content": "..."}],
    thinking=True,
    stream=True
):
    delta = chunk.choices[0].delta
    if hasattr(delta, 'reasoning_content') and delta.reasoning_content:
        print(f"[思考] {delta.reasoning_content}", end="")
    elif delta.content:
        print(delta.content, end="")
```

如果你做前端产品，我会很建议把这部分做成一个**默认折叠的“思考过程”区域**。原因很简单：

- 想看的人可以看
- 不想看的人不被打扰
- 对用户信任感通常有帮助

### 一个更实用的建议

- 复杂推理任务，`max_tokens` 尽量从 `4096` 起步
- 如果答案经常“像没说完”，先别怀疑模型，先看是不是预算太小
- UI 里把 `reasoning_content` 和最终答案分开展示，阅读体验会好很多

另外，DeepSeek 这类模型在成本上通常更有性价比，这也是它在很多实际业务里很受欢迎的原因。

## Kimi k2.5-thinking：参数更少，但不代表更简单

Kimi 的 thinking 模型给人的第一感觉往往是：参数没那么多，好像更省心。

某种程度上确实如此，因为很多采样参数都被平台锁住了。你能调的东西没有那么花哨，核心更接近一个问题：

**这次任务，你到底愿意给它多少输出和思考空间？**

### 它的特点很明确

- `temperature`、`top_p` 等采样参数通常不可调
- 主要通过 `max_completion_tokens` 控制总长度
- 支持在流式场景里拿到 `reasoning_content`

示例：

```python
response = client.chat.completions.create(
    model="kimi-k2.5-thinking",
    messages=[{"role": "user", "content": "详细分析一下..."}],
    max_completion_tokens=8192,
    stream=True
)
```

### 实际上该怎么配？

| 场景       | 推荐 `max_completion_tokens` | 说明                   |
| ---------- | ---------------------------- | ---------------------- |
| 简单问题   | 2048                         | 足够完成快速推理       |
| 中等复杂度 | 4096 ~ 8192                  | 适合展开思维链         |
| 深度分析   | 16384+                       | 更适合长文档、多步推理 |

Kimi 这类模型的经验反而更简单：**别老想着调风格，先把空间给够。**

如果空间不够，再强的推理模型也会被迫草草收尾。

## 一张表看懂四家主流推理模型差在哪

如果你不想一段段看，下面这张表可以直接拿来做第一轮选型。

| 平台 / 模型                     | 推理控制参数                          | 采样参数是否可调                               | 推理过程可见性                    | 推理 token 计费             |
| ------------------------------- | ------------------------------------- | ---------------------------------------------- | --------------------------------- | --------------------------- |
| **OpenAI o1**                   | `reasoning_effort`                    | ❌ `temperature` / `top_p` 锁定                | ❌ 通常不可见                     | ✅ 计入费用                 |
| **Anthropic Claude**            | `thinking` + `budget_tokens`          | ⚠️ 启用 `thinking` 时 `temperature` 常需为 1.0 | ✅ 可返回 `thinking`              | ✅ `budget_tokens` 计入计费 |
| **DeepSeek-R1**                 | `thinking`                            | ✅ 部分可调                                    | ✅ `reasoning_content` 字段       | ✅ 推理 token 计费          |
| **Kimi k2.5-thinking**          | 主要通过 `max_completion_tokens` 控制 | ❌ 大多锁定                                    | ✅ 可流式返回 `reasoning_content` | ✅ 计入输出相关费用         |
| **Google Gemini Thinking 系列** | 通常通过模型能力或模式启用            | ⚠️ 部分锁定                                    | ✅ 可返回思考字段                 | ✅ 计入输出相关费用         |

你会发现，它们虽然名字不同，但本质上都在回答同样的问题：

- 要不要多想？
- 想多久？
- 想的过程能不能给你看？
- 这笔“思考费”你愿不愿意出？

## 什么时候该用推理模型，什么时候其实没必要？

很多团队真正浪费钱的地方，不是不会用推理模型，而是**什么都想上推理模型**。

但说白了，不是所有任务都值得先想一大轮。

### 一个简单的判断方法

```text
开始
├── 任务是否需要多步推理？
│   ├── 是
│   │   ├── 是否需要展示思考过程？
│   │   │   ├── 需要 → DeepSeek-R1 / Kimi / Gemini Thinking
│   │   │   └── 不需要 → OpenAI o1
│   │   └── 是否特别在意成本？
│   │       ├── 是 → 优先看 DeepSeek-R1
│   │       └── 否 → 可选 o1 / Claude Thinking
│   └── 否
│       └── 优先用普通模型（GPT-4o / Claude Sonnet / DeepSeek-V3）
```

### 哪些场景值得上推理模型？

- 数学题、逻辑题、复杂规划
- 长链路代码审查
- 多条件业务判断
- 需要中间推导过程的专业问答
- 长文档分析和证据归纳

### 哪些场景别急着上？

- 普通闲聊
- 常规客服问答
- 简单翻译
- 轻量摘要
- 格式化改写

这些任务上推理模型，不一定更好，但大概率更慢、更贵。

## 真正该管理的，是推理 token 成本

推理模型最容易被忽略的一点，是它的“思考过程”并不是免费的。

而且很多时候，贵的不是最后那几句答案，而是前面那一大段内部推理。

### 1. 不要所有请求都走推理模型

最常见也最有效的做法，就是加一个简单的路由层：

```text
用户请求 → 路由判断
├── 简单问题 → 普通模型
└── 复杂问题 → 推理模型
```

这件事看起来很朴素，但能直接把很多不必要的成本砍掉。

### 2. 尽量缓存高价值推理结果

如果你的业务里会反复遇到同类复杂问题，比如：

- 相似法规问答
- 相似财务分析
- 固定模板的报告判断
- 重复出现的复杂支持问题

那就别每次都让模型从头再想一遍。推理结果能缓存的，尽量缓存。

### 3. 给预算设硬上限

`max_completion_tokens`、`budget_tokens`、`max_tokens` 这些参数，说到底不是装饰品，而是**防超支阀门**。

比如：

```python
response = client.chat.completions.create(
    model="o1",
    messages=[...],
    reasoning_effort="medium",
    max_completion_tokens=3000
)
```

这类限制不能保证模型一定答得最好，但至少能保证它不会在你没注意的时候无限扩张成本。

## 小结

到了推理模型这里，参数思路确实换了一套。

前几篇里我们更多是在调“怎么说”；这一篇开始，重点变成了“要不要先认真想，以及愿意为这次思考付出多少代价”。

如果把整篇内容压缩成几个最关键的判断，大概就是：

- **普通模型主要调输出风格，推理模型主要调思考强度**
- **很多传统采样参数在推理模型里会被锁定，这不是限制，而是设计思路变了**
- **`reasoning_effort`、`thinking`、`max_tokens` 这类参数，本质上都在管正确率、延迟和成本之间的平衡**
- **推理过程可见性不仅影响调试，也影响产品透明度**
- **不是所有任务都值得上推理模型，路由和控费比盲目追强模型更重要**

下一篇，我们从“模型自己想”切到“模型自己调用工具”：`tools`、`tool_choice`、`parallel_tool_calls` 这些参数，才是 Agent 场景里真正开始变复杂的地方。
