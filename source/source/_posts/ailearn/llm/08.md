> **📖 篇章难度**：📘 **总结篇**。这一篇不再讨论单个参数怎么调，而是开始处理多模型系统真正会失控的地方：接入、路由、成本、权限和稳定性。
> **🎯 核心收获**：什么时候该上 LLM 网关 + 主流方案怎么选 + LiteLLM 落地骨架 + 路由、预算、审计与高可用设计的关键判断

**前面七篇，我们一直在研究“怎么把一次调用做好”；到了这一篇，问题变成了：当调用越来越多、模型越来越杂时，怎么把整个系统管住。**

一开始，很多团队都会直接在业务代码里接模型。OpenAI 一套 SDK，Anthropic 一套 SDK，DeepSeek 再来一套。项目小的时候，这么做没什么问题，甚至是最快的办法。

<!-- more -->

可一旦模型开始混用，问题很快就冒出来了。

一个接口切换模型要改代码；一个供应商波动，服务就跟着抖；成本涨了，不知道是谁在烧；密钥散在各个服务里，轮换一次像拆炸弹；想做统一限流、预算、审计，发现根本没有抓手。

这时候你会意识到，真正麻烦的不是“模型变多了”，而是：

**你还在用单模型时代的接法，硬扛多模型时代的复杂度。**

所以这一篇，我们聊的不是某个具体 SDK 的用法，而是更上面这一层：为什么很多团队最后都会引入一层 LLM 网关，网关到底解决什么，不解决什么，什么时候值得上，以及该怎么选、怎么落地。

---

## 为什么模型一多，直连模式很快就不够用了？

直连模式最开始看起来很干脆：应用直接调用模型提供商，少一层抽象，也少一点维护成本。

```text
应用 A ──→ OpenAI SDK
应用 B ──→ Anthropic SDK
应用 C ──→ DeepSeek SDK
```

如果你只是做一个单体 Demo，这种方式完全合理。

问题在于，业务不会永远停在 Demo 阶段。等到你开始同时接多个模型，或者多个团队共同开发，直连模式的隐性成本会迅速超过它的简单性。

最常见的几个痛点，其实都很现实：

| 问题             | 真正麻烦的地方                                           |
| ---------------- | -------------------------------------------------------- |
| **接口碎片化**   | 每家平台格式、参数、SDK 习惯不同，迁移一次要改一片代码   |
| **成本不可见**   | 各平台各算各的，月底只看到总账，看不到是谁、在哪、为什么 |
| **容灾能力太弱** | 主模型一旦波动，应用往往只能报错，切备用模型全靠手工补救 |
| **密钥分散**     | 原始 API Key 散落在多个服务里，轮换、回收、审计都很痛苦  |
| **流量管不住**   | 很难按用户、团队、接口做统一限流和权限隔离               |
| **可观测性缺口** | 没有统一入口，日志、延迟、失败率和成本很难放到一张图里看 |

这些问题单个看都不一定致命，但一旦叠起来，系统会进入一种很熟悉的状态：

**能用，但不好管；能跑，但不敢放大。**

---

## LLM 网关真正解决的，不只是“统一接口”

很多人第一次接触网关，会把它理解成一个“把多个模型包装成同一种 API 的适配层”。这当然没错，但还不够。

更准确地说，网关的价值在于：**把原本散落在各个业务服务里的模型接入复杂度，集中到一个可以统一治理的位置。**

引入网关后，整体形态通常会变成这样：

```text
应用 A ─┐
应用 B ─┼──→ LLM 网关 ──→ OpenAI
应用 C ─┘      │        └─→ Anthropic
               └─→ DeepSeek
                    └─→ 其他模型
```

这多出来的一层，带来的不只是接口统一，还包括下面这些能力：

| 能力         | 价值                                                   |
| ------------ | ------------------------------------------------------ |
| **统一接口** | 业务代码面向统一入口，切模型时不用到处改 SDK           |
| **智能路由** | 可以按成本、延迟、任务类型、可用性选择模型             |
| **故障转移** | 主模型失败时自动切换备用模型，提高整体可用性           |
| **成本治理** | 统一统计 token 消耗、预算、配额和告警                  |
| **安全收口** | 原始 API Key 不再分散暴露，改用虚拟密钥和权限策略      |
| **统一观测** | 请求、响应、时延、错误率、花费可以放在同一条链路里分析 |

不过也要说清楚：

**网关不是万能解法。**

它能帮你把多模型系统“管起来”，但不会自动帮你解决所有提示词问题、业务编排问题、评测问题，更不会替你做产品决策。它解决的是“治理层”的问题，不是“应用层”的全部问题。

---

## 什么时候该上网关，什么时候其实还不用急？

不是所有项目一开始都需要 LLM 网关。

如果你现在符合下面这种状态：

- 只有一个模型提供商
- 只有一个或两个简单服务调用模型
- 成本规模还很小
- 没有明显的权限、审计、配额管理需求

那直接接 SDK 往往是更划算的方案。因为这个阶段，**少一层就少一层复杂度**。

但如果你已经碰到以下任意两三件事，网关通常就不是“以后再说”的问题了：

- 模型开始混用，或者准备做主备切换
- 多个业务线共用模型能力
- 想按用户、团队、项目看成本
- 需要统一限流、配额、预算
- 需要把原始密钥收口管理
- 想做统一日志、追踪和审计
- 想把“切模型”从改代码变成改配置

可以把判断标准说得更直接一点：

**当模型接入开始成为平台问题，而不再只是某个业务服务自己的实现细节时，就该考虑网关了。**

## 先别急着选工具，先分清你需要的是哪一类网关

现在市面上的方案不少，看起来都能“统一接模型”。但如果不先看自己的场景，很容易选成一个功能很多、却不适合自己团队的东西。

下面这几类方案，适合的人其实不一样。

| 方案                  | 类型         | 核心特点                                                        | 更适合谁                                         |
| --------------------- | ------------ | --------------------------------------------------------------- | ------------------------------------------------ |
| **LiteLLM Proxy**     | 开源网关     | 支持 100+ 模型，兼容 OpenAI SDK，带虚拟密钥、预算管理、负载均衡 | 需要统一多模型访问、偏工程化、自建能力较强的团队 |
| **One API / New API** | 开源网关     | 对国产模型支持好，界面友好，支持渠道管理和多账号分发            | 主要使用国内模型、希望有现成管理界面的团队       |
| **OpenRouter**        | 托管网关     | 无需自建，统一接入大量模型，试验成本低                          | 个人开发者、小团队、快速验证阶段                 |
| **LangChain**         | 框架抽象层   | 提供统一模型接口，但本质更像应用内抽象层                        | 已经深度使用 LangChain，希望在应用层保持统一接口 |
| **Portkey Gateway**   | 企业级网关   | 护栏、工作流、观测和企业能力更完整                              | 对合规、安全和治理要求更高的企业场景             |
| **Kong AI Gateway**   | API 网关扩展 | 能融入已有 Kong 体系                                            | 本身已经有成熟 API 网关基础设施的企业            |

### LiteLLM：最像“工程团队会自己搭起来”的方案

LiteLLM Proxy 的优点很明确：OpenAI 兼容性强、模型覆盖广、工程能力比较全，而且不会把你绑死在某种特定工作流里。

它特别适合这样一类团队：

- 已经习惯 OpenAI 风格接口
- 想尽快把多模型统一起来
- 需要预算、虚拟密钥、路由、fallback 和监控能力
- 愿意自己部署、自己维护

### One API / New API：更适合国产模型主场

如果你的主要供应商在国内，或者你非常看重渠道管理、多账号分发、图形化后台，那么 One API / New API 往往更顺手。

它们的优势不是“抽象更漂亮”，而是**对本地实际使用场景更接地气**。

### OpenRouter：适合试模型，不一定适合承载全部治理职责

OpenRouter 很适合快速试验。尤其在你还没决定最终模型组合时，它能明显降低接入门槛。

但如果你后面要做更细粒度的预算治理、企业级审计、复杂权限隔离，通常还是会走向自建或更强的企业方案。

### LangChain：更像应用内适配层，不是完整治理入口

LangChain 的统一模型接口很好用：

```python
from langchain.chat_models import init_chat_model

model = init_chat_model("openai:gpt-4o", temperature=0.7)
model = init_chat_model("anthropic:claude-sonnet-4", temperature=0.7)
model = init_chat_model("deepseek:deepseek-chat", temperature=0.7)
```

但它更适合解决“应用代码里怎么优雅切模型”的问题，而不是“整个组织怎么统一管模型接入、权限、预算和审计”的问题。

所以如果你要的是平台层治理，只靠 LangChain 通常不够。

---

## 如果你准备自建，一般会从 LiteLLM 这一类方案开始

原因很简单：它足够轻，功能又够用，很多团队不需要一上来就上重型平台。

### 一个最小可用的部署骨架

下面这份 `docker-compose.yml` 就已经能搭出一个可用的 LiteLLM 网关雏形：

```yaml
version: "3.8"

services:
  litellm:
    image: ghcr.io/berriai/litellm:main-latest
    ports:
      - "4000:4000"
    volumes:
      - ./litellm_config.yaml:/app/config.yaml
    environment:
      - DATABASE_URL=postgresql://user:pass@postgres:5432/litellm
      - LITELLM_MASTER_KEY=sk-your-master-key-change-this
    depends_on:
      - postgres

  postgres:
    image: postgres:15
    environment:
      - POSTGRES_DB=litellm
      - POSTGRES_USER=user
      - POSTGRES_PASSWORD=pass
    volumes:
      - postgres_data:/var/lib/postgresql/data

volumes:
  postgres_data:
```

这个阶段最重要的不是“一口气把所有能力配全”，而是先把三件事跑通：

- 至少接两到三个不同来源的模型
- 能从统一入口发请求
- 能看到基本的路由、权限和花费数据

### 配置文件里，真正关键的是路由和 fallback

```yaml
model_list:
  - model_name: gpt-4o
    litellm_params:
      model: openai/gpt-4o
      api_key: ${OPENAI_API_KEY}
      rpm: 500
      tpm: 100000

  - model_name: claude-sonnet-4
    litellm_params:
      model: anthropic/claude-sonnet-4-20250514
      api_key: ${ANTHROPIC_API_KEY}
      rpm: 100

  - model_name: deepseek-chat
    litellm_params:
      model: deepseek/deepseek-chat
      api_key: ${DEEPSEEK_API_KEY}

  - model_name: cheap-model
    litellm_params:
      model: openai/gpt-4o-mini
      api_key: ${OPENAI_API_KEY}

  - model_name: fallback-model
    litellm_params:
      model: deepseek/deepseek-chat
      api_key: ${DEEPSEEK_API_KEY}

router_settings:
  routing_strategy: "usage-based"
  enable_loadbalancing: true
  num_retries: 3
  timeout: 30
  fallbacks: [{ "gpt-4o": ["fallback-model"] }]

general_settings:
  master_key: ${LITELLM_MASTER_KEY}
  database_url: ${DATABASE_URL}
  store_model_in_db: true
```

这份配置里，真正值得你花时间想清楚的，其实不是字段写法，而是下面这些问题：

- 哪些模型是主力模型，哪些只是 fallback
- 路由优先级是按成本、延迟还是业务等级决定
- 重试几次才合理，避免把供应商波动放大成全链路阻塞
- 哪些模型允许普通应用访问，哪些只开放给关键链路

启动和验证也很直接：

```bash
docker-compose up -d
curl http://localhost:4000/health

curl http://localhost:4000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer sk-your-master-key-change-this" \
  -d '{
    "model": "gpt-4o",
    "messages": [{"role": "user", "content": "Hello, gateway!"}]
  }'
```

## 真的开始用起来后，你会发现“虚拟密钥”比“统一接口”还重要

统一入口能帮你把接入抽象掉，但真正让治理落地的，通常是虚拟密钥、配额和权限模型。

因为业务系统最好不要直接拿供应商原始 Key 去跑。那样做的后果很明显：权限过粗、泄露风险高、成本归属不清、轮换痛苦。

更稳的做法，是让业务方只拿网关发出来的虚拟密钥。

```bash
curl http://localhost:4000/key/generate \
  -H "Authorization: Bearer sk-your-master-key-change-this" \
  -H "Content-Type: application/json" \
  -d '{
    "models": ["gpt-4o", "deepseek-chat"],
    "max_budget": 50.0,
    "budget_duration": "1mo",
    "rpm_limit": 100,
    "tpm_limit": 10000,
    "metadata": {"user": "alice@company.com", "team": "marketing"}
  }'
```

这样做的好处很直接：

- 哪个应用能访问哪些模型，一眼清楚
- 哪个用户、哪个团队花了多少钱，可以直接归因
- 超预算、超频率时，可以在网关层直接拦住
- 原始供应商密钥不用到处发

很多团队是到了成本开始上涨、或者权限开始混乱时，才意识到这一层的重要性。其实越早收口，后面越省事。

---

## 路由不是“会切模型”这么简单，它本质上是在做业务取舍

这是很多网关文章最容易写得太轻的一点。

大家都爱说“智能路由”，但真正落地时，你会发现路由不是一个技术噱头，而是一套非常现实的业务策略：

- 你到底是优先省钱，还是优先稳定
- 高价值请求要不要强制走更强模型
- 简单任务要不要下沉到便宜模型
- 供应商波动时，是等恢复，还是立刻切备用

### 成本优先路由

如果你的任务大量是总结、分类、翻译这类轻任务，成本优先就很合理：

```yaml
model_list:
  - model_name: smart-router
    litellm_params:
      model: openai/gpt-4o-mini
      api_key: ${OPENAI_API_KEY}
  - model_name: smart-router
    litellm_params:
      model: deepseek/deepseek-chat
      api_key: ${DEEPSEEK_API_KEY}
  - model_name: smart-router
    litellm_params:
      model: openai/gpt-4o
      api_key: ${OPENAI_API_KEY}

router_settings:
  routing_strategy: "usage-based"
  enable_loadbalancing: false
```

### 延迟优先路由

如果你的产品是实时对话、客服、辅助写作这类前台场景，延迟优先通常更重要：

```yaml
router_settings:
  routing_strategy: "latency-based"
  ttl: 60
```

### 自定义路由，才是很多业务最终会走到的状态

通用策略能解决 60% 到 70% 的问题，真正和业务贴合的，往往还是自定义规则。

```python
import litellm
from litellm.integrations.custom_logger import CustomLogger

class CustomRouter(CustomLogger):
    async def async_pre_call_hook(self, user_api_key_dict, cache, data, call_type):
        user_query = data.get("messages", [])[-1].get("content", "")

        if "紧急" in user_query:
            data["model"] = "gpt-4o"
        elif "总结" in user_query or "翻译" in user_query:
            data["model"] = "deepseek-chat"
        else:
            data["model"] = "claude-sonnet-4"

        return data

litellm.callbacks = [CustomRouter()]
```

这段代码背后真正表达的是一个原则：

**路由决策应该尽量贴近业务价值，而不是只贴近模型参数。**

## 成本追踪不是财务动作，而是架构动作

很多团队到月账单出来才开始紧张，但那时往往已经晚了。

因为 LLM 成本一旦缺乏实时可见性，就很容易出现几种情况：

- 某个实验接口被意外打爆
- 某个团队默认全走最贵模型
- fallback 频繁触发，成本 silently 上升
- 一段时间后已经没人说得清钱花在哪

如果你用 LiteLLM，一些基础能力可以直接配起来。

```yaml
model_list:
  - model_name: gpt-4o
    litellm_params:
      model: openai/gpt-4o
      api_key: ${OPENAI_API_KEY}
      input_cost_per_token: 0.000005
      output_cost_per_token: 0.000015
```

然后通过接口或后台看花费：

```bash
curl http://localhost:4000/spend/keys?api_key=sk-xxx \
  -H "Authorization: Bearer sk-your-master-key"
```

预算告警也建议尽早加上：

```yaml
general_settings:
  alerting: ["slack"]
  alerting_threshold: 0.8
  webhook_url: "https://hooks.slack.com/services/..."
```

这类配置看起来像“运营功能”，其实本质上是在给系统建立反馈回路。没有反馈回路，路由和模型选择就只能靠感觉调。

---

## 如果没有统一追踪，网关最后也可能只是“多了一层转发”

网关值不值钱，不在于它能不能把请求转发出去，而在于它有没有把这层转发变成可观测、可分析、可优化的治理入口。

所以很多团队搭好网关后，下一步就该接追踪系统。

```yaml
general_settings:
  success_callback: ["langfuse"]
  failure_callback: ["langfuse"]

litellm_settings:
  langfuse_public_key: ${LANGFUSE_PUBLIC_KEY}
  langfuse_secret_key: ${LANGFUSE_SECRET_KEY}
  langfuse_host: "https://cloud.langfuse.com"
```

接入后，你至少应该能回答这些问题：

- 最近失败最多的是哪个模型、哪个接口、哪个租户
- 延迟抖动是供应商问题，还是你自己的网关层问题
- 哪些请求老是在 fallback
- 某类任务是不是用错了模型，导致成本偏高

这才是“网关作为平台层”的真正价值。否则它只是把原本分散的复杂度，换了个地方继续黑盒运行。

---

## 真到生产环境，网关架构一般都不会只有一台

单机网关当然可以作为起点，但如果你真的把它当成统一入口，迟早会走向多实例和共享状态。

一个常见的形态大概是这样：

```text
                      ┌─────────────────────────────┐
                      │      Load Balancer (Nginx)  │
                      └─────────────┬───────────────┘
                                    │
          ┌─────────────────────────┼─────────────────────────┐
          │                         │                         │
          ▼                         ▼                         ▼
┌─────────────────┐       ┌─────────────────┐       ┌─────────────────┐
```

- **多实例**：避免网关本身成为单点
- **共享数据库**：统一保存配置、预算、租户、审计等状态
- **Redis / 缓存层**：承接限流状态、热点配置、延迟数据等高频读写
- **外层负载均衡**：把网关当成正式服务来管理，而不是脚本工具

很多人会把注意力都放在“接了多少模型”，其实生产环境里更容易出问题的，反而是这层自身的可用性和状态一致性。

## 安全这件事，网关帮你收口，但前提是你真的把口收住了

很多文章讲安全最佳实践，会列一串原则。真正有用的，其实就几条。

### 第一，尽量别把供应商原始 Key 暴露给业务侧

网关的一个核心价值，就是把原始 Key 收口。否则你虽然搭了网关，业务服务却还在直连供应商，那治理能力基本等于没落地。

### 第二，权限要按最小单位分出去

| 实践             | 说明                                                 |
| ---------------- | ---------------------------------------------------- |
| **使用虚拟密钥** | 不直接暴露提供商原始 Key，而是发带权限边界的虚拟密钥 |
| **定期轮换**     | 在网关层轮换原始密钥，业务侧尽量无感                 |
| **最小权限**     | 每个虚拟密钥只开放必要模型和额度                     |
| **来源限制**     | 有条件的话加 IP 白名单或调用来源约束                 |

### 第三，审计别只停留在“记日志”

```yaml
general_settings:
  store_model_in_db: true
  disable_spend_logs: false
```

日志记录不是为了堆表，而是为了后面真的能追：谁调了、调了什么模型、花了多少、什么时候异常。

### 第四，内容安全要放在真正能拦住请求的地方

```python
class ContentSafetyHook(CustomLogger):
    async def async_pre_call_hook(self, user_api_key_dict, cache, data, call_type):
        messages = data.get("messages", [])
        if contains_sensitive_content(messages):
            raise Exception("内容违反安全策略")
        return data
```

如果你的场景对内容合规要求高，前置检查最好放在网关入口，而不是寄希望于每个下游应用各自实现一套。

## 一个更实用的选型矩阵

到了真正决策时，很多团队最需要的不是“方案大全”，而是一句更直接的话：我这种情况到底先上哪个。

| 场景                         | 更推荐的方案          | 判断依据                                     |
| ---------------------------- | --------------------- | -------------------------------------------- |
| **个人项目 / 快速试验**      | OpenRouter            | 上手最快，不用自建，适合先把模型试起来       |
| **创业团队，多模型混用**     | LiteLLM Proxy         | 轻量、自建成本可控，和 OpenAI 风格生态兼容好 |
| **国内团队，国产模型为主**   | One API / New API     | 国产模型适配和管理界面通常更顺手             |
| **企业生产环境，高可用要求** | LiteLLM Proxy 集群    | 更适合做多实例、容灾、预算和统一治理         |
| **已有 Kong 网关体系**       | Kong AI Gateway 插件  | 接入现有 API 管理体系，组织成本更低          |
| **深度使用 LangChain**       | LangChain + LangServe | 应用层抽象顺滑，但别把它当完整平台治理替代   |
| **需要更强护栏与企业能力**   | Portkey Gateway       | 合规、工作流、治理能力更完整                 |

一句话概括就是：

- **先试模型**，优先托管方案
- **开始治理**，优先自建网关
- **已有基础设施**，优先贴着组织现状选

## 如果你要从零开始搭，顺序最好别反

很多团队一上来就急着接十几个模型、配几十条路由。最后不是没有搭起来，而是搭出来的东西没人敢碰。

更稳的顺序通常是：

1. **先确认需求边界**：到底是要统一接入，还是要做平台治理
2. **先选一个主方案**：不要并行评估太多套，先把最可能的那套跑通
3. **先接少量关键模型**：通常 2 到 3 个就够，别一开始贪多
4. **先打通虚拟密钥和预算**：这比把所有高级路由都配好更重要
5. **先接监控和追踪**：没有观测，后面调优都会变成盲调
6. **再做 fallback 和路由细化**：等你有真实流量数据后再调，会靠谱很多
7. **最后再考虑集群化**：确定它真成了核心入口，再做高可用放大

这个顺序看起来保守，但实际更省事。因为网关一旦承担关键流量，后续每一次改动都会影响多个业务方。前期克制一点，后期会轻松很多。

## 小结：收官时，真正要记住的不是某个工具，而是这一层的职责

这一篇是整个系列的最后一篇，所以比起再记几个工具名字，我更希望你真正带走的是对“网关层职责”的理解。

当我们从单次调用走到多模型系统，复杂度已经不再只来自 prompt、参数或模型本身，而是来自这些更平台化的问题：

- 接多个模型时，怎么避免业务代码被 SDK 绑死
- 供应商波动时，怎么让系统还有回旋空间
- 成本怎么归因、限制、预警
- 密钥、权限、审计怎么统一收口
- 调用链怎么观测，出了问题怎么查
- 网关自己怎么做成一个能承载正式流量的服务

如果把这篇压缩成几个关键判断，大概就是：

- **LLM 网关的本质不是转发，而是治理**
- **不是所有项目都需要网关，但一旦进入多模型、多团队、多预算场景，网关往往会变成刚需**
- **选型时先看组织现状，再看功能清单，别反过来**
- **LiteLLM 更像通用工程方案，One API 更贴近国产模型管理场景，OpenRouter 更适合快速试验**
- **真正让网关产生价值的，是虚拟密钥、路由、预算、审计和可观测性，而不是“统一接口”这四个字本身**
- **如果没有权限和成本治理，网关只是把复杂度搬了个地方**
- **如果没有高可用和共享状态设计，网关自己会变成新的单点**
