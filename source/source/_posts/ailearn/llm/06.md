> **🎯 核心收获**：多模态输入的主流格式差异 + 文生图参数取舍 + `response_format` 与 `json_schema` 的边界 + 生产环境中的降级策略

**很多人以为，多模态就是“给模型塞一张图”，结构化输出就是“让它吐 JSON”。**

话不能算错，但真要上线，这两个能力远没有看上去那么省心。

<!-- more -->

同样是图片输入，有的平台吃 URL，有的平台只认 base64；同样是 JSON 输出，有的平台只是“尽量像 JSON”，有的平台才能真正按 Schema 卡死。

而且，一旦进到发票识别、表单抽取、图像理解、自动生成素材这些业务里，你会很快发现，问题根本不在“API 有没有这个字段”，而在：

**这个字段能不能稳定地支撑真实场景。**

所以这一篇，我们不只是讲参数怎么填，而是把三件事讲清楚：

- 模型如何接收和理解非文本输入
- 模型如何生成图片类结果
- 模型如何输出系统真正能消费的结构化数据

如果上一篇 Function Calling 解决的是“模型能不能动手”，那这一篇解决的就是：

**模型看到的是什么，产出的又能不能直接接进系统。**

---

## 为什么多模态和结构化输出，会一起成为产品分水岭？

因为这两者，分别打通了输入端和输出端。

没有多模态，模型看到的世界仍然很窄。用户上传一张发票、一张截图、一页设计稿、一段音频，你还得先自己做一轮预处理，模型只接最后那段文本。

没有结构化输出，模型哪怕理解对了，结果也很难直接落进程序。它可能解释得头头是道，但你的后端只想要一段合法 JSON，最好字段齐全、类型稳定、没有多余内容。

所以这两个能力组合起来，才真的像一条完整链路：

- **多模态**：让模型更接近真实输入
- **结构化输出**：让模型结果更接近真实系统接口

这也是为什么很多团队做着做着会发现，决定系统可用性的，已经不只是模型本身有多聪明，而是 **输入格式和输出约束有没有设计好**。

---

## 这一篇真正要关心的，是三类能力

如果把原理抽干净，这一篇其实就三块：

| 能力方向       | 它解决的问题                         | 典型场景                          |
| -------------- | ------------------------------------ | --------------------------------- |
| **多模态输入** | 模型能不能理解图像、音频、视频等输入 | OCR、截图分析、票据识别、视觉问答 |
| **文生图**     | 模型能不能产出图像类结果             | 封面图、营销图、概念草图、海报    |
| **结构化输出** | 模型输出能不能被程序稳定消费         | 数据抽取、表单填充、事件解析      |

这三类能力看起来分散，但在工程里往往是一起出现的。

举个很典型的场景：用户上传一张发票图片，系统要识别字段，最后输出成标准 JSON 写入数据库。这里面至少就同时用到了：

- 图片输入
- 多模态理解
- 严格结构化输出

所以别把它们拆成三门互不相干的知识点。更好的理解方式是：**这是一条从输入到消费的链路。**

---

## 多模态输入，不是“把文件传进去”这么简单

多模态这件事，最容易踩坑的地方在于：

**不同平台看起来都支持图片，真正接入时格式却差很多。**

有的平台接受 URL，有的平台必须是 base64；有的平台支持视频上传，有的平台只支持图像；有的平台同样一张图，还会因为分辨率策略不同导致 token 成本完全不一样。

所以你真正需要先搞明白的不是“它支不支持”，而是：

- 传什么介质：URL 还是 base64
- 放在哪个字段里
- 是否支持多个媒体混传
- 是否存在尺寸、体积、分辨率限制

### OpenAI：最容易上手，但 `detail` 会直接影响成本

OpenAI 的 GPT-4o、GPT-4o-mini 对图像输入支持比较成熟，常见格式如下：

```json
{
  "model": "gpt-4o",
  "messages": [
    {
      "role": "user",
      "content": [
        { "type": "text", "text": "这张图片里有什么？" },
        {
          "type": "image_url",
          "image_url": {
            "url": "https://example.com/image.jpg",
            "detail": "auto"
          }
        }
      ]
    }
  ]
}
```

这里最值得注意的是 `image_url.detail`：

| 参数     | 取值                        | 说明                                                                    |
| -------- | --------------------------- | ----------------------------------------------------------------------- |
| `url`    | 字符串                      | HTTP/HTTPS URL，或 `data:image/jpeg;base64,{base64}` 形式的本地编码内容 |
| `detail` | `"auto"`、`"low"`、`"high"` | 控制图像理解分辨率；更高细节通常意味着更高 token 成本                   |

一个很实用的经验是：

- **OCR、细节判断、表格识别**：优先考虑 `high`
- **粗粒度内容理解**：`low` 或 `auto` 往往就够

因为很多业务里，图像理解效果不稳，不一定是模型不行，而是你把该高精度处理的图片按低精度送进去了。

### OpenAI 的 Python 示例

```python
import base64
from openai import OpenAI

client = OpenAI()

response = client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {
            "role": "user",
            "content": [
                {"type": "text", "text": "描述这张图片"},
                {"type": "image_url", "image_url": {"url": "https://example.com/cat.jpg"}}
            ]
        }
    ]
)


def encode_image(image_path):
    with open(image_path, "rb") as f:
        return base64.b64encode(f.read()).decode("utf-8")

base64_image = encode_image("local_cat.jpg")
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {
            "role": "user",
            "content": [
                {"type": "text", "text": "这是什么动物？"},
                {"type": "image_url", "image_url": {"url": f"data:image/jpeg;base64,{base64_image}"}}
            ]
        }
    ]
)
```

### Claude：能看图，但接法比 OpenAI 更“硬”

Claude 3 系列和 Sonnet 4 也支持图像输入，不过它不走 OpenAI 那套 `image_url` 格式，而是要求你显式传图片块。

```json
{
  "model": "claude-sonnet-4-20250514",
  "messages": [
    {
      "role": "user",
      "content": [
        { "type": "text", "text": "描述这张图片" },
        {
          "type": "image",
          "source": {
            "type": "base64",
            "media_type": "image/jpeg",
            "data": "{base64_string}"
          }
        }
      ]
    }
  ]
}
```

Claude 这里有几个边界一定要记住：

- **不支持直接传图像 URL**
- **必须显式给 `media_type`**
- **单张图片大小有限制**

它支持的媒体类型包括：`image/jpeg`、`image/png`、`image/gif`、`image/webp`。

所以如果你做的是面向公网图片的轻量分析，OpenAI 风格通常更省事；但如果你的图片来自本地上传、内部系统或文件流，Claude 的 base64 路径也不难接，只是前处理要更明确一点。

### Gemini：多模态更全，但接入方式和其他家不太一样

Gemini 的优势，是它对图像、视频、音频支持更完整。尤其视频和文件上传这块，原生路径更自然一些。

```python
import google.generativeai as genai

model = genai.GenerativeModel("gemini-2.0-flash-exp")
response = model.generate_content(
    ["描述这张图片", genai.upload_file("cat.jpg")]
)

response = model.generate_content(
    [
        "描述这张图片",
        {"mime_type": "image/jpeg", "data": base64_bytes}
    ]
)
```

Gemini 最大的特点不是“也能看图”，而是它在多媒体输入这件事上更像一个原生文件系统入口，而不是单纯的图片字段扩展。

所以如果你的场景里不只是图片，还要处理视频、音频或者多文件组合输入，Gemini 会更值得认真看一眼。

### Kimi：如果你已经走 OpenAI 风格，迁移成本会低很多

Kimi k2.5 的图像输入格式基本兼容 OpenAI：

```python
from openai import OpenAI

client = OpenAI(
    api_key="your-kimi-key",
    base_url="https://api.moonshot.cn/v1"
)

response = client.chat.completions.create(
    model="kimi-k2.5",
    messages=[
        {
            "role": "user",
            "content": [
                {"type": "text", "text": "这张图片里有什么文字？"},
                {"type": "image_url", "image_url": {"url": "https://example.com/document.jpg"}}
            ]
        }
    ]
)
```

这类平台的最大好处，不是能力一定更强，而是**迁移成本低**。如果你原来已经按 OpenAI 风格封装过请求层，适配起来会轻松不少。

### 多模态输入平台速览

| 平台                 | 支持类型               | URL 支持       | base64 支持 | 特殊说明                              |
| -------------------- | ---------------------- | -------------- | ----------- | ------------------------------------- |
| **OpenAI**           | 图像                   | ✅             | ✅          | `detail` 控制分辨率，细节越高成本越高 |
| **Anthropic Claude** | 图像                   | ❌             | ✅          | 必须 base64，接入前处理更明确         |
| **Google Gemini**    | 图像、视频、音频       | ✅（需先上传） | ✅          | 文件能力更强，多媒体支持更完整        |
| **Kimi**             | 图像                   | ✅             | ✅          | 兼容 OpenAI 风格，迁移成本较低        |
| **DeepSeek**         | 不支持（纯文本）       | —              | —           | 当前重点仍在文本推理                  |
| **MiniMax**          | 图像、视频（部分模型） | ✅             | ✅          | 能力随模型而异，接入前要看具体版本    |

## 文生图参数真正影响的，不只是“画得好不好”

文生图常常被当成一个独立能力来讲，但真正进项目之后，你更关心的往往是三件事：

- 图的尺寸对不对
- 成本能不能接受
- 返回结果适不适合后续流程

如果是做海报、封面、配图，你可能更关心风格和画质；如果是给工作流里某个后续环节供图，你更关心输出格式和稳定性。

### DALL·E 3：参数不多，但每个都很实用

OpenAI 的图像生成通常通过 Images API 调用：

| 参数              | 类型    | 说明                                          |
| ----------------- | ------- | --------------------------------------------- |
| `model`           | string  | `dall-e-3` 或 `dall-e-2`                      |
| `prompt`          | string  | 图像描述，`dall-e-3` 支持更长提示词           |
| `n`               | integer | 生成张数；`dall-e-3` 基本上按单张生成思路来用 |
| `size`            | string  | 如 `1024x1024`、`1792x1024`、`1024x1792`      |
| `quality`         | string  | `standard` 或 `hd`                            |
| `style`           | string  | `vivid` 或 `natural`                          |
| `response_format` | string  | `url` 或 `b64_json`                           |

一个很实用的判断方式是：

- **营销图、封面图、展示图**：可以优先考虑 `quality="hd"`
- **内部流程图、测试图、低成本批量试错**：`standard` 就够
- **强调戏剧感、视觉冲击**：`style="vivid"`
- **更接近真实、自然风格**：`style="natural"`

### DALL·E Python 示例

```python
from openai import OpenAI

client = OpenAI()

response = client.images.generate(
    model="dall-e-3",
    prompt="一只穿着宇航服的柴犬在月球上漫步，背景是地球，数字艺术风格",
    size="1792x1024",
    quality="hd",
    style="vivid",
    n=1
)

image_url = response.data[0].url
print(image_url)
```

### Gemini 的图像生成，更像“多模态生成”的一部分

Gemini 可以在 `generate_content` 中同时产出文本和图片：

```python
import google.generativeai as genai

model = genai.GenerativeModel("gemini-2.0-flash-exp")
response = model.generate_content(
    "生成一张图片：未来城市天际线，赛博朋克风格，霓虹灯闪烁",
    generation_config=genai.types.GenerationConfig(
        response_modalities=["Text", "Image"]
    )
)

for part in response.candidates[0].content.parts:
    if part.text:
        print(part.text)
    elif part.inline_data:
        with open("output.png", "wb") as f:
            f.write(part.inline_data.data)
```

这种模式的好处，是图像生成和文字解释可以在同一轮里一起出来。对于需要“生成图片 + 给说明”的工作流，会更顺手。

### 文生图平台对比

| 平台              | 模型          | 最大尺寸   | 批量生成     | 特色功能                 |
| ----------------- | ------------- | ---------- | ------------ | ------------------------ |
| **OpenAI**        | DALL·E 3      | 1792x1024  | ❌（偏单张） | 画质成熟，风格参数清晰   |
| **OpenAI**        | DALL·E 2      | 1024x1024  | ✅           | 成本更低，适合批量试错   |
| **Google Gemini** | 2.0 Flash Exp | 可变       | ⚠️ 实验性    | 文本与图像生成一体化     |
| **Stability AI**  | SDXL 等       | 1024x1024+ | ✅           | 第三方生态丰富，可控性高 |

## 结构化输出，难点从来不是 JSON，而是“稳定”

很多团队第一次做结构化输出时，都会先从 `json_object` 开始。这个起点没问题，但很快就会发现一个现实：

**“像 JSON” 和 “可稳定接入系统” 之间，差得非常远。**

模型可能少字段、乱加字段、把数字写成字符串，甚至在 JSON 前后多补一句解释。对人来说这不算大事，对程序来说就是直接报错。

所以结构化输出要分层看：

- **第一层**：尽量返回合法 JSON
- **第二层**：字段结构尽量稳定
- **第三层**：严格满足 Schema，不能多也不能少

### `response_format={"type": "json_object"}`：够用，但别过度乐观

OpenAI 风格接口里最常见的，是这类写法：

| 取值                        | 说明                       |
| --------------------------- | -------------------------- |
| `{ "type": "text" }`        | 默认，自由文本             |
| `{ "type": "json_object" }` | 要求模型输出合法 JSON 对象 |

一个基础示例：

```python
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {"role": "system", "content": "你是一个助手，请始终以 JSON 格式输出。"},
        {"role": "user", "content": "列出三种水果及其颜色"}
    ],
    response_format={"type": "json_object"}
)

print(response.choices[0].message.content)
```

这里有个很容易漏掉的细节：**提示词里最好明确出现“JSON”字样。**

但更重要的是，你要知道 `json_object` 能解决什么，不能解决什么：

- 它更像是在说“请你认真输出 JSON”
- 它**不等于**“字段一定完全符合我的结构要求”

所以如果你的下游系统对字段完整性、类型准确性要求不高，`json_object` 很方便；但如果你要直接入库、触发自动化流程、驱动严肃业务，就别太依赖它的“自觉”。

### 真正严肃的结构化输出，要看 `json_schema`

OpenAI 的 Structured Outputs 把这件事往前推进了一步：直接让你声明 Schema，并要求模型严格按这个结构输出。

```python
from openai import OpenAI

client = OpenAI()

response = client.chat.completions.create(
    model="gpt-4o-2024-08-06",
    messages=[
        {"role": "system", "content": "从用户输入中提取事件信息。"},
        {"role": "user", "content": "下周三下午3点在会议室A开会讨论Q2预算"}
    ],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "calendar_event",
            "strict": True,
            "schema": {
                "type": "object",
                "properties": {
                    "title": {"type": "string"},
                    "date": {"type": "string", "format": "date"},
                    "time": {"type": "string"},
                    "location": {"type": "string"},
                    "attendees": {"type": "array", "items": {"type": "string"}}
                },
                "required": ["title", "date", "time"],
                "additionalProperties": False
            }
        }
    }
)
```

这里真正重要的不是语法，而是三个控制点：

| 字段                          | 作用                                         |
| ----------------------------- | -------------------------------------------- |
| `name`                        | 给这份 Schema 一个可识别名字，便于日志和调试 |
| `strict`                      | 开启严格模式，尽量避免“差不多对”的输出       |
| `additionalProperties: false` | 告诉模型：未定义字段别乱加                   |

这套能力最适合的场景，不是“顺手让它输出 JSON”，而是：

- 抽取结构化业务字段
- 输出要直接被后端消费
- 字段多、层级复杂、不能容忍幻觉字段

> ⚠️ 这类严格模式通常对模型版本有要求，接入前一定要确认目标模型是否支持。

### 其他平台的结构化输出，大多仍然要留后手

| 平台                 | 结构化输出支持情况                                                          |
| -------------------- | --------------------------------------------------------------------------- |
| **DeepSeek**         | 支持 `response_format={"type": "json_object"}`，但不走严格 JSON Schema 路线 |
| **Kimi**             | 支持 `response_format={"type": "json_object"}`                              |
| **Anthropic Claude** | 不提供完全同款原生 `response_format`，很多时候要靠提示词或工具调用降级实现  |
| **Google Gemini**    | 支持 `response_schema`，可用于结构化约束                                    |
| **MiniMax**          | 支持 `json_object` 风格输出                                                 |
| **零一万物（Yi）**   | 支持 `json_object` 风格输出                                                 |

Gemini 的结构化输出示例如下：

```python
import google.generativeai as genai

model = genai.GenerativeModel("gemini-1.5-pro")
response = model.generate_content(
    "列出3种水果及其颜色",
    generation_config=genai.types.GenerationConfig(
        response_mime_type="application/json",
        response_schema={
            "type": "object",
            "properties": {
                "fruits": {
                    "type": "array",
                    "items": {
                        "type": "object",
                        "properties": {
                            "name": {"type": "string"},
                            "color": {"type": "string"}
                        }
                    }
                }
            }
        }
    )
)
```

这类能力很有价值，但真正上线时还是建议你保留校验和降级逻辑。别把“接口承诺”直接当成“系统永远不会出错”。

## 真正进项目以后，最好把结构化输出分成三层防线

很多时候，稳定性不是靠某一个参数解决的，而是靠多层兜底。

### 第一层：提示词里明确约束输出格式

哪怕你已经用了 `json_object`，也最好在系统提示或用户提示里明确写：**请输出 JSON，不要附加解释文本。**

### 第二层：程序侧始终做解析保护

这个环节别省。只要结果要进程序，就应该包解析异常。

```python
import json

try:
    data = json.loads(response.choices[0].message.content)
except json.JSONDecodeError:
    # 降级处理：修复、重试、或回退到人工检查
    pass
```

### 第三层：在不支持严格 Schema 的平台上，用工具调用兜底

如果某个平台没有原生严格结构化输出，一个常见降级方案是：

**把目标结构定义成一个函数参数，让模型通过工具调用来“吐参数”。**

```python
tools = [{
    "type": "function",
    "function": {
        "name": "format_output",
        "description": "格式化输出为指定结构",
        "parameters": {
            "type": "object",
            "properties": {
                "title": {"type": "string"},
                "items": {"type": "array", "items": {"type": "string"}}
            },
            "required": ["title", "items"]
        }
    }
}]

response = client.chat.completions.create(
    model="claude-sonnet-4",
    messages=[...],
    tools=tools,
    tool_choice={"type": "function", "function": {"name": "format_output"}}
)
```

这不是最优雅的方案，但在很多兼容性一般的平台上，很实用。

## 两个最典型的落地场景

### 场景一：发票识别，本质上是“多模态输入 + 严格结构化输出”

这是最典型的生产场景之一。

用户上传的是图片，模型要先看懂内容；业务系统要的不是解释，而是发票号码、日期、金额、销售方这些字段。

```python
import base64
import json
from openai import OpenAI

client = OpenAI()


def extract_invoice(image_path):
    with open(image_path, "rb") as f:
        image_b64 = base64.b64encode(f.read()).decode("utf-8")

    response = client.chat.completions.create(
        model="gpt-4o-2024-08-06",
        messages=[
            {
                "role": "user",
                "content": [
                    {"type": "text", "text": "从这张发票图片中提取以下字段：发票号码、日期、总金额、销售方名称。"},
                    {"type": "image_url", "image_url": {"url": f"data:image/jpeg;base64,{image_b64}"}}
                ]
            }
        ],
        response_format={
            "type": "json_schema",
            "json_schema": {
                "name": "invoice",
                "strict": True,
                "schema": {
                    "type": "object",
                    "properties": {
                        "invoice_number": {"type": "string"},
                        "date": {"type": "string"},
                        "total_amount": {"type": "number"},
                        "seller_name": {"type": "string"}
                    },
                    "required": ["invoice_number", "date", "total_amount", "seller_name"],
                    "additionalProperties": False
                }
            }
        }
    )

    return json.loads(response.choices[0].message.content)
```

这个场景能不能稳定跑起来，关键其实不在“能看图”，而在**最后输出能不能被系统稳定消费**。

### 场景二：文生图 + 对话解释，适合内容生产工作流

比如用户输入一句需求，你不仅要给出图，还要顺手补一句设计说明。这个时候，图像生成和文本生成最好别分成两个完全孤立的系统。

```python
def generate_image_with_explanation(prompt):
    image_response = client.images.generate(
        model="dall-e-3",
        prompt=prompt,
        size="1024x1024",
        quality="standard",
        n=1
    )
    image_url = image_response.data[0].url

    explanation = client.chat.completions.create(
        model="gpt-4o",
        messages=[
            {"role": "user", "content": f"请简要解释你为以下描述生成的图像设计思路：{prompt}"}
        ]
    )

    return {
        "image_url": image_url,
        "explanation": explanation.choices[0].message.content
    }
```

这类场景的重点，不只是“把图画出来”，而是让生成结果更容易进入编辑、审核、发布这些后续流程。

## 小结

多模态和结构化输出真正改变的，不只是 API 的字段数量，而是模型和业务系统之间的接口方式。

有了多模态，模型开始能接收更接近真实世界的输入；有了结构化输出，模型的结果才更像一个稳定的系统组件，而不是只能靠人眼去读的自然语言回答。

如果把这篇文章压缩成几个最关键的判断，大概就是：

- **多模态接入先别急着看“支不支持”，先看传输格式、体积限制和成本模型**
- **图像理解效果不稳，很多时候不是模型笨，而是分辨率策略没配对**
- **文生图参数不多，但 `size`、`quality`、`style` 会直接决定成本和可用性**
- **`json_object` 适合轻量结构化，`json_schema` 才更适合严肃业务输出**
- **别把结构化输出当成单点能力，程序侧校验、异常处理和降级策略必须一起上**
- **最有价值的落地场景，往往是把多模态输入和结构化输出串成一条完整工作流**
