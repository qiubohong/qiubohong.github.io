**为什么很多人明明都走“OpenAI 兼容接口”，一迁移平台还是到处踩坑？**

问题往往不在 SDK，而在参数。

<!-- more -->

在第一篇里，我们已经把 `temperature`、`top_p`、`top_k`、`max_tokens` 这些核心参数拆开讲清楚了。但真到项目里，理解参数本身还不够。你迟早会碰到这些问题：

- 同样写 `temperature=1.0`，为什么不同平台出来的风格不一样？
- 为什么有的平台支持 `top_k`，有的平台压根没有？
- 为什么有的平台嘴上说兼容 OpenAI，结果你一上 `penalty`、`seed` 或 `response_format`，马上就开始出岔子？
- 为什么同一个适配层接多个模型时，参数看起来统一了，行为却没统一？

说到底，**“兼容 OpenAI”通常只意味着接口长得像，不代表语义完全一样。**

这一篇就做一件事：把主流平台在 API 参数层面的差异摊开讲清楚。你可以把它当成一张“迁移地图”——以后要做多平台接入、统一网关、模型切换，先来对照这篇，能少踩很多坑。

> 本文以 OpenAI API 为“基准坐标系”，其他平台围绕它来对比。

## 先看结论：真正会让你踩坑的，主要是这五类差异

如果你现在没时间看完整篇，先记住下面这几点：

1. **同名参数，取值范围不一定一样**。最典型的就是 `temperature`，有的平台是 `0 ~ 2`，有的平台是 `0 ~ 1`。
2. **有些参数不是每家都有**。最明显的是 `top_k`、`presence_penalty`、`frequency_penalty`、`seed`、`logprobs`。
3. **有些参数虽然有，但不一定能改**。比如 Kimi 某些模型会直接锁定 `temperature`、`top_p`。
4. **有些平台限制参数组合**。Claude 新版本里，`temperature` 和 `top_p` 不能随便一起传。
5. **“兼容 OpenAI”更多是协议兼容，不是行为兼容**。这句话真的很重要。

你如果只把平台切换理解成“换个 `base_url`”，后面基本一定会补交学费。

## 真正会让你翻车的，不是表格本身，而是下面这些差异

### 1. `temperature` 的范围差异，比你想的更要命

`temperature` 看起来只是个常规参数，但它是最容易在跨平台迁移时造成“同配置不同结果”的一个。

- **OpenAI、DeepSeek、MiniMax、零一万物**：通常是 `0 ~ 2`
- **Kimi**：`0 ~ 1`，而且不同模型默认值还不一样
- **Anthropic Claude**：`0 ~ 1`

这意味着什么？

很简单：**在 Claude 和 Kimi 上，`temperature=1.0` 已经是上限；但在 OpenAI 或 DeepSeek 上，`temperature=1.0` 更像中间值。**

如果你把一套在 OpenAI 上调好的采样配置原样搬到 Claude，上来就可能觉得“怎么风格变了”“怎么更飘了”“怎么没预期稳定”。很多时候不是模型本身坏了，而是你把区间理解错了。

还有一类更隐蔽的坑：Kimi 的不同模型系列默认值并不统一，`k2.5` 甚至会把部分参数直接锁死。你代码里写得再漂亮，平台不让改，就是不让改。

**工程上的建议很直接：不要把 `temperature` 当成绝对值来理解，要把它当成“平台内相对位置”。**

### 2. `top_k` 是差异最大的采样参数之一

如果你前一篇已经习惯了 `temperature + top_p + top_k` 这套组合，那迁移到 OpenAI 时大概率会先愣一下：

**OpenAI 不支持 `top_k`。**

而 Claude、Gemini，以及这篇列出的国内主流平台，基本都支持。

这会直接影响你对“候选池”控制的细腻程度。对代码生成、低随机性任务来说，`top_k` 往往很有用，因为它能给候选 token 设一个更明确的数量上限。

没有 `top_k` 时，你只能更多依赖 `temperature` 和 `top_p` 去逼近目标效果。能不能做到？能，但调法会变。

所以如果你的系统高度依赖 `top_k`，那 OpenAI 至少在“采样控制粒度”这件事上，不是最灵活的那个。

### 3. `penalty` 参数不是家家都有

`presence_penalty` 和 `frequency_penalty` 这两个参数，在做长文生成、创意写作、去重复控制时其实挺有用。

但问题是：

- **OpenAI、DeepSeek、Kimi、MiniMax、零一万物**：都支持
- **Claude、Gemini**：不支持这两个字段

也就是说，如果你的应用很依赖“控制重复程度”和“鼓励新话题”这类能力，那么 OpenAI 系、国产平台会给你更细的旋钮；Claude 和 Gemini 则更像是让你换一种思路，用别的采样参数或提示策略去间接实现。

零一万物这边还有一个比较特别的点：它多给了一个 **`repetition_penalty`**。这个字段不是简单等同于 `presence_penalty` 或 `frequency_penalty`，它更像是在采样前直接对 logits 做缩放。

如果你在做长文、对话生成或内容去重，这个参数会很有价值。

### 4. `max_tokens` 这事，名字比你想得更麻烦

很多人会觉得，长度控制没什么好讲的，不就是 `max_tokens` 吗？

真做兼容层时你就知道，这事一点也不简单。

- **OpenAI**：现在更推荐 `max_completion_tokens`
- **DeepSeek、Kimi**：两个字段都支持，但 Kimi 已经把 `max_tokens` 标成“已弃用”
- **MiniMax、零一万物**：更偏向继续使用 `max_tokens`

所以如果你要做统一调用层，一个很常见、也很务实的做法是：**两个参数一起传，内部再按平台做兼容**。

```python
params = {
    "max_tokens": 1024,
    "max_completion_tokens": 1024
}
```

这不优雅，但很实用。工程里很多事就是这样，先把坑填平，比追求形式统一更重要。

## 各平台最值得你记住的一件事

如果你不想背完整张大表，可以只记每个平台最鲜明的那个特征。

### DeepSeek：最像 OpenAI，也最适合拿来做低成本替代或调试

| 独特参数/能力               | 说明                                                                                 |
| --------------------------- | ------------------------------------------------------------------------------------ |
| **thinking**                | 推理模型专用，控制是否返回推理过程                                                   |
| **reasoning_content**       | 响应中返回模型的思考链内容                                                           |
| **logprobs + top_logprobs** | 支持返回每个 token 的对数概率，`top_logprobs` 可指定返回概率最高的 token 数量（≤20） |

DeepSeek 的优势很明确：**接口和参数体系整体最贴近 OpenAI，兼容成本低，同时保留了不错的可调空间。**

如果你的目标是“尽量少改代码、尽量快完成替换”，DeepSeek 往往是一个很自然的备选项。

### Kimi：兼容 OpenAI 没问题，但模型级参数锁定必须注意

| 独特参数/能力      | 说明                                                                                      |
| ------------------ | ----------------------------------------------------------------------------------------- |
| **模型级参数锁定** | kimi-k2.5 模型的 `temperature`、`top_p` 等参数被平台锁定，不可修改                        |
| **多模态输入**     | kimi-k2.5 支持图像等多模态理解                                                            |
| **长思考模式**     | 支持流式输出思考过程（`reasoning_content`），建议 `temperature=0.8` 和 `max_tokens>=4096` |

Kimi 的坑不在“能不能接”，而在“你以为自己在调，实际上有些模型根本不让你调”。

这一点特别容易在统一 SDK 或通用参数面板里出问题：前端明明给了参数输入框，后端也把参数传出去了，结果模型端直接忽略。

### MiniMax：能力扩展多，适合想把平台能力吃得更深的场景

| 独特参数/能力          | 说明                                                   |
| ---------------------- | ------------------------------------------------------ |
| **ChatCompletion Pro** | 提供增强版接口，支持 Function Call、网络检索和群聊模式 |
| **reasoning_content**  | 返回模型的推理过程内容                                 |
| **logprobs**           | 支持返回 token 对数概率                                |

MiniMax 给人的感觉不是“最标准”，而是“扩展能力比较多”。如果你不只是想发起一次简单补全，而是准备往检索、工具调用、复杂会话场景走，它会有额外吸引力。

### 零一万物（Yi）：重复控制能力很有辨识度

| 独特参数/能力          | 说明                                                                  |
| ---------------------- | --------------------------------------------------------------------- |
| **repetition_penalty** | 直接对 logits 缩放以抑制重复内容，是与其他 penalty 参数互补的独特能力 |
| **接入方式**           | 通过阿里云 DashScope 接入，使用 DashScope SDK                         |
| **Yi-Large-RAG**       | 支持实时联网搜索能力                                                  |

如果你的业务对“重复内容”特别敏感，比如长文生成、内容改写、多轮对话，Yi 的 `repetition_penalty` 会是一个值得认真看的点。

### OpenAI：标准参考系，功能全，但 `top_k` 缺席

| 独特参数/能力                    | 说明                                                 |
| -------------------------------- | ---------------------------------------------------- |
| **reasoning_effort**             | o1 系列模型专用，控制推理强度（low / medium / high） |
| **seed**                         | 设置随机种子，实现输出可复现                         |
| **logprobs + top_logprobs**      | 支持返回 token 级对数概率                            |
| **response_format（JSON 强制）** | `{"type": "json_object"}` 强制模型输出合法 JSON      |

OpenAI 依然是最常被当作“标准坐标系”的平台，但别把它想成“什么都有”。至少在 `top_k` 这件事上，它就是没有。

### Anthropic Claude：强在长上下文和整体体验，但参数哲学不太一样

| 独特参数/能力      | 说明                                                                        |
| ------------------ | --------------------------------------------------------------------------- |
| **强制二选一限制** | `temperature` 和 `top_p` 不能同时指定（Sonnet 4.5 和 Haiku 4.5 及更高版本） |
| **system 参数**    | 作为顶层参数而非 `messages` 中的 `system` 角色                              |
| **thinking**       | 推理模型专用，控制是否输出思考过程                                          |
| **stop_sequences** | 功能等同于 OpenAI 的 `stop` 参数                                            |

Claude 最典型的不是“参数少”，而是**参数哲学不同**。它不鼓励你把采样参数全部拧一遍，而是更强调有节制地调整。

如果你是从 OpenAI 迁过去，最先要适应的就是这一点。

### Gemini：参数体系差异最大，但多模态和安全配置很完整

| 独特参数/能力    | 说明                                               |
| ---------------- | -------------------------------------------------- |
| **候选响应数量** | 支持 `candidate_count` 返回多个响应候选            |
| **安全设置**     | 提供 `safety_settings` 控制内容过滤等级            |
| **top_k**        | 默认值为 40，与很多平台默认值不同                  |
| **原生多模态**   | 支持图像、视频、音频等多模态输入，参数体系更加丰富 |

Gemini 的特点很清楚：**它不是 OpenAI 那套 API 思维的平移版本。**

如果你的系统重心在原生多模态、安全管控或 Google 生态，Gemini 值得考虑；但如果你最在意的是迁移成本，那它通常不是最轻松的选择。

## OpenAI 兼容性怎么理解？

“兼容 OpenAI”这句话，工程里最好把它拆成三层来理解：

1. **协议兼容**：路径、字段名、请求格式长得像
2. **参数兼容**：字段存在，调用不会报错
3. **行为兼容**：相同参数在不同平台上，表现尽量一致

现实里，大多数平台能做到前两层，但第三层基本做不到完全一致。

下面这张表，可以帮助你更现实地判断兼容性：

| 平台                 | 兼容性等级     | 说明                                                                  |
| -------------------- | -------------- | --------------------------------------------------------------------- |
| **DeepSeek**         | ★★★★★ 高度兼容 | 参数命名、取值范围、默认值均与 OpenAI 高度一致，可直接使用 OpenAI SDK |
| **Kimi**             | ★★★★☆ 基本兼容 | 兼容 OpenAI SDK，但 `temperature` 范围不同（0~1）且 k2.5 参数被锁定   |
| **MiniMax**          | ★★★☆☆ 部分兼容 | 接口路径不同（`/v1/text/chatcompletion_v2`），但参数体系整体相似      |
| **零一万物**         | ★★★★☆ 基本兼容 | 通过 DashScope 接入，参数体系兼容 OpenAI 标准                         |
| **Anthropic Claude** | ★★☆☆☆ 接口不同 | 使用独立的 Messages API，参数体系和取值范围差异较大                   |
| **Google Gemini**    | ★★☆☆☆ 接口不同 | 使用独立的 API 体系，参数命名和结构差异显著                           |

如果你问我一句最实在的话：

**DeepSeek 是最像 OpenAI 的替代项；Claude 和 Gemini 则更适合当“独立平台”来适配，而不是当成 OpenAI 的皮肤。**

## 如果你现在就要选型，我会怎么选

下面这个矩阵，保留了原始信息，但我更建议你把它当成“场景优先”而不是“平台排行榜”。

| 应用场景                                     | 首选平台                    | 理由                                                                 |
| -------------------------------------------- | --------------------------- | -------------------------------------------------------------------- |
| **需要确定性输出（代码 / 数学 / 事实问答）** | DeepSeek / OpenAI           | 参数控制清晰，`penalty` 与 `logprobs` 能力较完整，调试手感更好       |
| **创意写作 / 头脑风暴**                      | Claude / Kimi               | Claude 采样控制细腻，Kimi 的长思考模式更适合深度创作                 |
| **构建复杂 AI Agent**                        | Kimi / DeepSeek             | 工具调用能力成熟，参数控制灵活；DeepSeek 还支持 `logprobs` 便于调试  |
| **长文档处理（200K+ 上下文）**               | MiniMax / Claude            | MiniMax 上下文窗口大，Claude 长上下文整体表现稳定                    |
| **多模态应用**                               | Kimi / Gemini               | Kimi k2.5 和 Gemini 原生支持多模态输入                               |
| **追求性价比**                               | DeepSeek / 零一万物         | 成本表现更有竞争力，同时参数覆盖比较全面                             |
| **需要返回概率信息（`logprobs`）**           | DeepSeek / OpenAI / MiniMax | 这三家在 token 级概率信息上更有优势                                  |
| **需要抑制重复内容**                         | 零一万物 / DeepSeek         | Yi 有 `repetition_penalty`，DeepSeek 的 `frequency_penalty` 也很好用 |

### 一个更直白的选型流程

如果你不想反复查表，可以直接按这个流程走：

```text
1. 先确定硬需求
   ├── 要多模态？→ Kimi k2.5 / Gemini
   ├── 要超长上下文？→ MiniMax / Claude
   ├── 要 token 概率信息？→ DeepSeek / OpenAI / MiniMax
   └── 要低成本？→ DeepSeek / 零一万物

2. 再看参数需求
   ├── 需要 top_k → 避开 OpenAI
   ├── 需要 presence_penalty / frequency_penalty → 避开 Claude、Gemini
   ├── 需要 temperature + top_p 同时细调 → 避开 Claude 新版本限制
   └── 需要可复现输出 seed → 优先 OpenAI / Gemini

3. 最后看迁移成本
   ├── 希望尽量少改代码 → DeepSeek / Kimi / 零一万物
   └── 接受独立适配 → Claude / Gemini
```

## 别直接裸接：一旦多平台并存，最好加一层适配层

到这里你会发现一个现实问题：

**参数差异不是靠记忆解决的，而是靠抽象层解决的。**

如果你只接一家模型，直接调用当然没问题。但一旦要做：

- 模型切换
- A/B 测试
- 多供应商容灾
- 成本路由
- 国内外平台混接
- 团队里不同语言共享同一套能力

那你迟早会想要一层统一适配层。

社区里这类方案通常叫 **AI Gateway**、**LLM Gateway** 或 **统一模型适配层**。它们的价值很直接：

- **统一接口**：尽量用一套调用方式抹平平台差异
- **降低耦合**：不必每个平台维护一套独立调用代码
- **增强治理**：支持路由、限流、故障转移、预算追踪、密钥管理等能力

说白了，**它们不是让差异消失，而是把差异收敛到一层里。**

### Python 生态

Python 还是 LLM 开发最热闹的地方，选择最多。

| **LLM Gateway**       | 开源统一 API 网关   | -            | 完全开源，兼容 OpenAI 风格，支持多语言集成              | 强调自托管和数据可控       |

**LiteLLM Proxy 快速部署**：

```yaml
services:
  litellm:
    image: ghcr.io/berriai/litellm:main-latest
    ports:
      - "4000:4000"
    environment:
```

部署后，任何语言的应用只要把 endpoint 改成 `http://localhost:4000`，就能用统一的 OpenAI 风格接口调用已经配置好的模型。

### 如果只给一句框架建议

- **只是想统一调用多模型**：优先看 `LiteLLM`
- **还想顺手搭 Agent / RAG / 工作流**：优先看 `LangChain`
- **前端体验优先**：优先看 `Vercel AI SDK`
- **多语言团队想集中治理**：优先看 `LiteLLM Proxy` 或 `OpenRouter`
- **偏国产模型和 API 分发**：优先看 `One API / New API`

## 写在最后

这一篇最重要的结论，其实不是“哪家平台最好”，而是另一件更基础的事：

**参数兼容，不等于结果兼容。**

你在多平台之间迁移时，真正要对齐的是三层东西：

- 字段能不能传
- 参数能不能改
- 相同参数在不同平台上，行为是不是接近

从这个角度看，几家平台的特点可以压缩成下面几句：

- **DeepSeek**：最像 OpenAI，迁移成本低
- **Kimi**：兼容层友好，但模型级锁参要格外留意
- **MiniMax**：扩展能力丰富，适合更复杂的产品场景
- **Yi**：重复控制能力有特色
- **Claude**：长上下文和整体体验强，但参数规则和 OpenAI 不是一回事
- **Gemini**：多模态和安全配置完整，但参数体系最不像 OpenAI
- **OpenAI**：仍然是很多适配层的基准，但别默认它“什么都有”

如果你的系统后面准备接两家以上模型，我真心建议尽早把统一参数层和适配层抽出来。越往后拖，越容易在各个平台的兼容细节里积累技术债。

下一篇，我们就回到更具体的调参问题：同样是 `temperature`、`top_p`、`top_k` 这几个参数，**不同任务到底该怎么搭配，才能既稳又不死板？**
