> **🎯 核心收获**：四大采样参数的组合逻辑 + 四类典型场景推荐配置 + 一套能直接落地的调参顺序

**为什么同一个模型，有的人一出手就稳，有的人怎么调都觉得别扭？**

很多时候，差的不是模型，而是采样参数没配对。

<!-- more -->

前两篇里，我们已经把参数是什么、不同平台有什么差异，基本交代清楚了。到了这一篇，重点就不是“认识参数”，而是另一件更实际的事：

**面对一个具体任务，你到底该怎么配？**

这一步其实比想象中难。因为 `temperature`、`top_p`、`top_k`、`min_p` 看起来都在控制“随机性”，但它们管的不是一回事。你要是把这几个旋钮一起乱拧，最后的结果通常不是“更灵活”，而是“更不可控”。

所以这一篇，我不打算继续按教科书方式一个个解释参数，而是直接从实战角度出发，回答三个最常见的问题：

- 哪个参数应该先调？
- 什么场景该收紧，什么场景该放开？
- 为什么同样一组数值，换个任务就不好用了？

如果你经常做代码生成、知识问答、客服对话、创意写作，这一篇基本就是一张够你反复查的“调参地图”。

## 先说结论：采样参数不是越多越好，关键是别同时乱动

如果只能先记一句话，我会建议你记这个：

> **先用 `temperature` 定基调，再用 `top_p` 或 `top_k` 管范围，最后才考虑 `min_p` 这种细调项。**

很多人刚开始调参时，喜欢一口气把 `temperature`、`top_p`、`top_k` 全改掉，想着这样更容易“调到最佳状态”。但实际情况通常相反——你一旦同时改太多参数，最后根本分不清到底是谁在起作用。

所以真正好用的调参方法，反而有点“笨”：

1. **先判断任务要稳还是要活**
2. **先把 `temperature` 调到顺眼**
3. **再决定要不要收缩候选池**
4. **最后再处理重复、噪声或边缘 token**

这套顺序不炫技，但特别实用。尤其在生产环境里，稳定比“玄学手感”重要得多。

## 调参前，先建立五个不会出错的原则

### 1. 一次只动一个旋钮

这是最重要的一条。

`temperature` 和 `top_p` 都会影响输出风格，很多平台和官方文档也都反复强调：**最好一次只重点调整一个主采样参数。** Claude 甚至在部分版本里直接限制 `temperature` 和 `top_p` 不能一起自由乱配。

原因很简单：它们影响的是同一件大事——模型到底要多保守、还是多敢“放开”。如果你同时动两个，最后效果变了，你很难知道到底是谁造成的。

所以我的建议是：

- **先调 `temperature`**，找整体风格
- **再看要不要加 `top_p` 或 `top_k`**，控制候选范围
- **最后再动 `min_p` 或 penalty**，做局部修边

这比一开始就追求“最优组合”靠谱得多。

### 2. `temperature` 定基调，`top_p` / `top_k` 管范围

这句话你会在很多资料里看到，但真正理解了，调参会轻松很多。

- `temperature` 决定的是：**模型敢不敢跳出最高概率答案**
- `top_k` 决定的是：**最多从前 K 个候选里选**
- `top_p` 决定的是：**只从累计概率达到 p 的那一小撮 token 里选**

所以它们的分工其实很清楚：

- 想让整体风格更稳、更敢、更发散，先看 `temperature`
- 想把候选池卡得更窄、更可控，去看 `top_k` 或 `top_p`

如果你把这几者都理解成“随机性参数”，那就容易越调越乱；但如果你把它们理解成“一个管胆子，一个管候选范围”，事情就清楚多了。

### 3. 低 `temperature` 也不等于绝对确定

很多人会把 `temperature=0` 理解成“模型每次都一定输出一样的结果”。严格说，不一定。

原因在于，真实运行时还会受到推理实现、硬件环境、并发、随机种子等因素影响。所以 `temperature=0` 更接近“尽量确定”，不是“数学意义上的绝对一致”。

如果你的业务真的特别在意复现性，比如自动评测、固定模板生成、实验对比，除了把 `temperature` 压低，还要留意：

- 平台是否支持 `seed`
- 模型版本是否固定
- 运行环境是否尽量一致

所以别把低温度神化。它能提高稳定性，但不包办一切。

### 4. 从任务出发，不要迷信某个“万能数值”

网上很容易看到类似“最佳 temperature 是 0.7”这种说法。问题是，**0.7 到底对什么任务最佳？**

这才是关键。

一个更实用的起点是先问自己：

- 我需要的是**准确率**，还是**多样性**？
- 我更怕它答错，还是更怕它答得太死板？
- 我希望它“像工程师”，还是“像写作者”？

从这个角度看，任务和参数的关系大概是这样的：

| 任务类型                                 | `temperature` 起点 | 候选池策略                          |
| ---------------------------------------- | ------------------ | ----------------------------------- |
| **需要精确答案（代码 / 数学 / 事实）**   | 0.0 ~ 0.3          | 窄候选池（低 `top_p` 或小 `top_k`） |
| **需要平衡（对话 / 翻译 / 摘要）**       | 0.5 ~ 0.8          | 中等候选池                          |
| **需要创造性（写作 / 头脑风暴 / 诗歌）** | 0.8 ~ 1.2          | 宽候选池（高 `top_p` 或大 `top_k`） |

参数从来不是孤立的，它背后对应的是任务目标。

### 5. 用实验代替“我感觉这个值不错”

说实话，调参特别容易让人产生错觉。

你跑了一次，觉得 `temperature=0.9` 挺好；再跑一次，又觉得 `0.6` 更顺；第三次换了个 prompt，结论又反过来了。这种事情太常见了。

所以要想真正调出能用的配置，最好还是做最基础的实验：

- 固定同一个 prompt
- 只改一个参数
- 每组跑 5~10 次
- 观察稳定性、错误率、表达风格、重复度

这套方法不高级，但能把“直觉”变成“有依据的判断”。

## 真正最先该调的，是 `temperature`

在实际工作里，`temperature` 通常是最先碰的参数，因为它最直接决定输出气质。

### `temperature` 到底在做什么？

从数学上说，它是在 softmax 之前对 logits 做缩放：

`probs = softmax(logits / temperature)`

你不一定需要死记公式，但最好理解它的方向：

| `temperature` 取值 | 概率分布变化                      | 实际效果                         |
| ------------------ | --------------------------------- | -------------------------------- |
| `T < 1`（如 0.3）  | 分布更陡，高概率 token 优势更明显 | 输出更稳、更聚焦，但可能有点死板 |
| `T = 1`            | 保持原始分布                      | 更接近模型原本的默认风格         |
| `T > 1`（如 1.2）  | 分布更平，更多 token 有机会入选   | 输出更活、更散，但更容易跑偏     |

简单说：

- **低温度**像是“别乱想，按最靠谱的来”
- **高温度**像是“你可以多试几个方向”

### 一个更实用的分段理解

我更建议你把 `temperature` 粗分成三个工作区间，而不是盯着某个绝对值：

- **0.0 ~ 0.3：低温区**
  - 适合代码生成、数学推理、事实问答
  - 目标是少出错，少跑偏
- **0.4 ~ 0.8：生产区**
  - 适合对话、翻译、摘要
  - 目标是稳里带一点自然变化
- **0.9 ~ 1.5：高温区**
  - 适合创意写作、头脑风暴、诗歌
  - 目标是放开一点，换取新鲜感和多样性

很多场景其实不用一步到位。完全可以从中间值起步，然后逐步偏向更稳或更活。

### 调 `temperature` 的一个笨办法，但很好用

固定其他参数不动，比如先让 `top_p=1`，然后：

- 从 `0.2` 开始试
- 每次增加 `0.1` 或 `0.2`
- 观察它什么时候开始“太僵”，什么时候开始“太飘”

你真正要找的，不是一个理论最优值，而是**任务可接受区间**。

因为在真实项目里，参数要为业务服务，不是为了在纸面上好看。

## `top_k` 和 `top_p`，一个更像硬限制，一个更像软限制

很多人最容易混淆的就是这两个。

### 先把区别讲明白

| 维度               | `top_k`                              | `top_p`                                      |
| ------------------ | ------------------------------------ | -------------------------------------------- |
| **候选池确定方式** | 固定数量：只看概率最高的 K 个 token  | 动态阈值：取累计概率达到 p 的最小 token 集合 |
| **适用场景**       | 需要短名单、强约束的任务，如代码补全 | 更自然、更自适应的任务，如对话、写作         |
| **对上下文敏感度** | 低：无论模型多自信，候选池大小都固定 | 高：模型自信时候选池更小，不自信时候选池更大 |
| **典型取值**       | 10 ~ 50                              | 0.85 ~ 0.95                                  |

一句话概括：

- `top_k` 是**硬上限**
- `top_p` 是**软阈值**

### 什么场景更适合 `top_k`？

`top_k` 最大的好处，是它的控制感比较强。

如果你知道这个任务不该太发散，甚至希望模型尽量只在一小撮高概率候选里选，那 `top_k` 很合适。尤其是下面几种情况：

- **代码补全**：避免模型突然冒出奇怪符号或罕见结构
- **数学推理**：希望每一步都尽量沿着最稳的路径走
- **分类任务**：候选本来就不多，硬限制反而更直接

推荐起点：

- 代码生成：`K=10~20`
- 数学推理：`K=10~30`
- 分类任务：`K=5~20`

### 什么场景更适合 `top_p`？

`top_p` 的好处在于它更“聪明”一点。

模型很自信时，候选池会自动变小；模型没那么自信时，候选池会适度放宽。这个特性决定了它在自然语言任务里通常更顺手。

更常见的适用场景是：

- **日常对话**：既自然，又不会太飘
- **创意写作**：保留变化，但别彻底失控
- **翻译**：允许措辞灵活，但不离题

推荐起点：

- 日常对话：`0.85 ~ 0.95`
- 创意写作：`0.9 ~ 0.95`
- 翻译：`0.8 ~ 0.9`

如果你只想选一个更通用、更容易上手的候选池参数，通常还是 `top_p` 更友好。

---

## `min_p`：不是主角，但在一些场景里很值钱

### `min_p` 是干什么的？

`min_p` 代表一个 token 被保留下来的**最低相对概率门槛**。

比如你设 `min_p=0.05`，而当前概率最高的 token 是 `0.9`，那低于 `0.9 × 0.05 = 0.045` 的 token，都会被过滤掉。

它不像 `top_k` 那样固定砍到前 K 个，也不像 `top_p` 那样按累计概率截断。它更像是在说：

**那些明显离谱、明显太弱的候选，就别进来了。**

### 它真正有价值的地方在哪里？

`min_p` 最有意思的点，是它能在不明显损伤整体灵活性的情况下，过滤掉一批很差的 token。

所以它特别适合这种需求：

- 不想把候选池收得太死
- 但又想顺手滤掉一些明显不合理的噪声
- 希望输出更干净一点，但不想把创造性一起掐掉

我会把它理解成一个“噪声门”。不是主旋钮，但在一些边缘场景里很好用。

### 一个够用的使用建议

| 场景               | `min_p` 推荐值 | 说明                             |
| ------------------ | -------------- | -------------------------------- |
| **日常使用**       | 0.01 ~ 0.05    | 轻微过滤，移除明显不合理的 token |
| **代码生成**       | 0.01 ~ 0.03    | 值要低，主要过滤乱码或离谱候选   |
| **创意写作**       | 0.0            | 建议关闭，保留更多自由度         |
| **高质量稳定输出** | 0.05 ~ 0.1     | 过滤更积极，但也更容易收得过紧   |

如果你刚开始调参，其实完全可以先不碰 `min_p`。等你发现“整体差不多对了，但还想再干净一点”，再来用它。

## 四类最常见场景，到底该怎么配？

这一部分我尽量不说空话，直接给能落地的思路。

### 1. 代码生成：宁可保守一点，也别胡发挥

代码任务最怕的不是“平淡”，而是“自信地写错”。

所以这里的核心思路是：**低温度 + 窄候选池 + 尽量少发散。**

- **`temperature`**：0.0 ~ 0.3
- **`top_p`**：0.1 ~ 0.5，或者 **`top_k`**：10 ~ 30
- **`min_p`**：0.01 ~ 0.03
- **`frequency_penalty`**：0.0 ~ 0.1
- **`presence_penalty`**：0.0

如果你只想要一个起步配置，我会推荐：

- `temperature=0.2`
- `top_p=0.3`

这组值通常已经足够让模型在写函数、补代码、改 bug 时更稳一些。

**Python 示例**：

```python
code_params = {
    "model": "gpt-4o",
    "messages": [{"role": "user", "content": "Write a Python function to quicksort a list"}],
    "temperature": 0.2,
    "top_p": 0.3,
    "frequency_penalty": 0.0
}
```

**JavaScript 示例**：

```javascript
const { text } = await generateText({
  model: openai("gpt-4o"),
  prompt: "Write a Python function to quicksort a list",
  temperature: 0.2,
  topP: 0.3,
  frequencyPenalty: 0.0,
});
```

### 2. 知识问答 / 事实查询：稳是第一位，但别答得像机器公告

知识问答和代码生成有点像，都强调准确性；但它又没必要像代码那样“死控”。

你希望模型：

- 事实别乱
- 结构清楚
- 语言别太僵

所以这里会比代码任务稍微放松一点：

- **`temperature`**：0.0 ~ 0.4
- **`top_p`**：0.5 ~ 0.8
- **`min_p`**：0.01 ~ 0.05
- **`frequency_penalty`**：0.0
- **`presence_penalty`**：0.0

一个比较常见且稳妥的起点是：

- `temperature=0.2`
- `top_p=0.7`

这通常能在“别瞎编”和“别太僵硬”之间取得一个不错的平衡。

### 3. 日常对话 / 客服系统：别太木，也别太飘

对话类任务的难点在于，它既要自然，又要可控。

太低温时，回答会有一种机械重复感；太高温时，又容易开始兜圈子、跑题、废话变多。所以这类任务最适合放在“生产区”：

- **`temperature`**：0.5 ~ 0.8
- **`top_p`**：0.85 ~ 0.95
- **`min_p`**：0.01 ~ 0.05
- **`frequency_penalty`**：0.0 ~ 0.3
- **`presence_penalty`**：0.0 ~ 0.3

如果是客服、助手、问答机器人这类场景，我通常会建议从下面这个区间开始试：

- `temperature=0.6 ~ 0.7`
- `top_p=0.9`
- `frequency_penalty=0.1`

这组配置的好处是：说话不会太死，重复也能稍微压一点。

### 4. 创意写作 / 头脑风暴：可以放开，但别完全撒手

创意类任务最容易被误解。很多人会觉得：“既然要创意，那就把参数拉满。”

问题是，参数拉满不等于更有创意，很多时候只是更散、更飘、更不成型。

所以这里真正要做的是：**给模型足够的空间，但别完全失控。**

- **`temperature`**：0.8 ~ 1.2
- **`top_p`**：0.9 ~ 0.95
- **`min_p`**：0.0（关闭）
- **`frequency_penalty`**：0.3 ~ 0.7
- **`presence_penalty`**：0.5 ~ 1.0

创意写作里，我更建议先用：

- `temperature=0.9`
- `top_p=0.95`

先看它有没有足够的新鲜感，再决定要不要继续往上推。

如果一开始就冲到 `temperature=1.5`，很容易直接把可用性一起冲没了。

## 跨平台调参时，要多看一眼这些差异

前一篇我们已经讲过平台差异，这里只保留和调参最相关的部分。

| 平台                       | 关键注意事项                                                                                         |
| -------------------------- | ---------------------------------------------------------------------------------------------------- |
| **OpenAI**                 | 不支持 `top_k`；`temperature` 范围 0~2；`frequency_penalty` 和 `presence_penalty` 能力完整           |
| **Anthropic Claude**       | `temperature` 范围 0~1，默认 1.0；**部分版本强制 `temperature` 和 `top_p` 二选一**；支持 `top_k`     |
| **DeepSeek**               | 支持 `top_k`；`temperature` 范围 0~2，默认 1.0；penalty 参数齐全                                     |
| **Google Gemini**          | `temperature` 范围 0~2，默认约 0.7；不支持 `frequency_penalty` / `presence_penalty`；`top_k` 默认 40 |
| **Kimi**                   | `temperature` 范围 0~1，k2.5 模型部分参数被锁定；需使用 `max_completion_tokens`                      |
| **Llama 系列（本地部署）** | 常见推荐是 `temperature=0.6`、`top_p=0.95`、`min_p=0.01`；重复惩罚建议谨慎使用                       |

所以你在跨平台迁移时，最容易踩的坑有两个：

- **把别家的默认值当成自己的默认值**
- **把支持的字段，当成支持相同语义的字段**

同样一个 `temperature=1.0`，换个平台，味道可能完全不一样。

## 如果你现在就要开始调，我建议按这个顺序来

说到底，调参最怕的不是不会调，而是上来没顺序。

下面这套流程，我觉得是最容易落地的：

```text
1. 先判断任务属于哪一类
   ├── 准确性优先 → 从低 temperature 开始
   ├── 平衡型任务 → 从中温区开始
   └── 创造性优先 → 从高温区开始

2. 固定主采样策略
   ├── 先只调 temperature
   ├── 观察输出是否过稳或过飘
   └── 找到可接受区间

3. 再处理候选池
   ├── 想更稳、更短名单 → 加 top_k
   ├── 想更自然、更自适应 → 加 top_p
   └── 一次只重点调一个

4. 最后处理边缘问题
   ├── 噪声太多 → 试 min_p
   ├── 重复太多 → 试 frequency_penalty
   └── 话题老转不开 → 试 presence_penalty

5. 用固定 prompt 重复测试
   ├── 看稳定性
   ├── 看错误率
   └── 看风格是否符合业务要求
```

你会发现，这套方法并不复杂。它只是把原本容易凭感觉乱试的事情，变成了一套有顺序的检查流程。

## 写在最后

采样参数这件事，最容易让人误入两个极端。

一种极端是：把它神秘化，觉得这里面全是玄学；另一种极端是：把它机械化，觉得只要背几个数字就够了。

其实都不对。

更接近事实的说法是：

**它既不是玄学，也不是死表，而是一套围绕任务目标做取舍的工程手段。**

这一篇如果只留下三个重点，我希望是这三个：

- **先调 `temperature`，别一上来全动**
- **`top_p` 和 `top_k` 都在管候选池，但风格完全不同**
- **参数没有万能值，只有“对当前任务更合适的区间”**

你只要把这三个点抓牢，后面大多数调参工作，其实都能慢慢走顺。
