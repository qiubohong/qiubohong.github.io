**很多人第一次接 Function Calling，都会有个错觉：这不就是让模型吐一段 JSON 吗？**

表面上看，确实像。

<!-- more -->

但真正上手以后你很快就会发现，事情没那么简单。

模型会不会选对工具、会不会补全正确参数、什么时候该并行、什么时候必须串行、出错后怎么收口、怎么避免无限循环——这些都不是“多加一个字段”就能解决的。

所以到了这一篇，我们讨论的重点已经不只是 API 怎么调，而是另一件更接近工程现实的问题：

**怎么把一个“会说话的模型”，变成一个“能调用外部能力把任务往前推进”的系统。**

Function Calling 正是这条分界线。

---

## 为什么说 Function Calling 是 Agent 的分水岭？

没有工具调用的模型，本质上还是停留在“根据上下文生成文本”。

它可以解释天气是什么，甚至能写一段查询天气接口的示例代码，但它并不能真的帮你查今天北京的天气，更不能顺手把结果同步到你的系统里。

Function Calling 的价值就在这里：

**模型不再只负责“说”，而是开始负责“发起动作”。**

当然，真正执行动作的还是你的应用层。模型做的事，是用结构化的方式告诉你：

- 应该调用哪个工具
- 这个工具该带什么参数
- 是否还需要继续调用下一个工具

如果把这个链路跑通，模型的能力边界会突然往外扩一大圈。

| 能力             | 典型场景                           |
| ---------------- | ---------------------------------- |
| **实时数据获取** | 查询天气、股价、新闻、日志         |
| **数据库操作**   | 查订单、读用户资料、写业务记录     |
| **外部动作执行** | 发邮件、创建工单、触发流程         |
| **复杂计算**     | 调计算器、代码执行器、规则引擎     |
| **知识增强**     | 触发检索、RAG 查询、内部知识库访问 |

所以很多 Agent 产品真正的起点，不是“模型更强了”，而是 **工具链终于接上了**。

---

## 真正常用的，其实就三个参数：`tools`、`tool_choice`、`parallel_tool_calls`

Function Calling 相关参数看起来不少，但大多数场景里，真正决定行为的还是这三个：

| 参数                  | 类型                 | 它真正控制的是什么                 |
| --------------------- | -------------------- | ---------------------------------- |
| `tools`               | `array`              | 模型“能用哪些外部能力”             |
| `tool_choice`         | `string` 或 `object` | 模型“这次到底要不要用工具、用哪个” |
| `parallel_tool_calls` | `boolean`            | 多个工具“能不能一轮一起调”         |

别看只有三个，背后对应的是三层控制权：

- **能力边界**：你给了哪些工具
- **行为约束**：你允许模型怎么选
- **执行策略**：你允许它一次调几个

这也是为什么 Function Calling 不是“给模型开权限”这么简单。你其实是在设计一套受控执行接口。

---

## `tools` 不是参数列表，它其实是给模型看的“工具说明书”

很多人第一次定义 `tools`，只关注格式对不对。但实际效果往往取决于另一件事：

**你写给模型看的描述，是否足够清楚。**

一个标准的 `tools` 定义通常长这样：

```json
{
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "get_weather",
        "description": "获取指定城市的实时天气信息",
        "parameters": {
          "type": "object",
          "properties": {
            "city": {
              "type": "string",
              "description": "城市名称，如：北京、上海"
            },
            "unit": {
              "type": "string",
              "enum": ["celsius", "fahrenheit"],
              "description": "温度单位"
            }
          },
          "required": ["city"]
        }
      }
    }
  ]
}
```

这里最关键的不是语法，而是三个字段的质量：

### 1. `name` 要让人一眼知道它干什么

尽量用动词加对象的形式，比如 `get_weather`、`create_order`、`search_knowledge_base`。别起那种太泛的名字，比如 `weather`、`data_tool`、`query`。

名字越糊，模型越容易误判。

### 2. `description` 决定模型何时调用它

这部分很容易被低估。模型不是读你后端代码，它只能靠描述来判断这个工具是不是合适。

所以一个好的描述，不只是“它是什么”，还要告诉模型“什么时候该用它”。

### 3. `parameters` 不是越少越好，而是越清楚越好

很多工具调用出错，不是模型笨，而是 schema 太松。字段类型、枚举值、默认值、必填项、字段说明，这些越明确，模型越不容易乱猜。

说白了，`tools` 不是给程序员看的接口文档，而是给模型看的操作手册。

---

## `tool_choice` 决定的是自主权，不只是开关

如果说 `tools` 决定模型“有什么可用”，那 `tool_choice` 决定的就是：

**这次你打算给它多大自由。**

常见取值如下：

| 取值                                                | 含义                         | 适用场景             |
| --------------------------------------------------- | ---------------------------- | -------------------- |
| `"auto"`                                            | 让模型自己判断要不要调用工具 | 大多数通用场景       |
| `"none"`                                            | 禁止工具调用，强制纯文本回答 | 不希望触发外部动作时 |
| `"required"`                                        | 强制模型必须先调用一个工具   | 固定工作流入口       |
| `{"type": "function", "function": {"name": "xxx"}}` | 强制调用指定工具             | 多步流程中的确定环节 |

举个例子，强制模型调用天气工具：

```python
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "我想知道北京天气"}],
    tools=tools,
    tool_choice={"type": "function", "function": {"name": "get_weather"}}
)
```

这里有个很实用的经验：

- **开放式助手**，默认用 `auto`
- **流程型任务**，很多时候该用 `required`
- **高风险动作**，宁可先 `none`，再显式放开

因为你给模型的自由越大，系统体验可能越自然；但同时，可控性也会下降。

这不是哪个更高级的问题，而是哪种更适合你当前这条链路。

---

## `parallel_tool_calls` 决定的是效率，但不是所有场景都该开满

这个参数最容易被理解成“开了就更快”，但真正需要问的问题是：

**这些工具之间到底有没有依赖关系？**

如果没有依赖，并行当然好；如果有依赖，并行反而会把流程搞乱。

当 `parallel_tool_calls=true` 时，模型可能一轮里返回多个工具请求，比如：

```json
{
  "tool_calls": [
    {
      "function": { "name": "get_weather", "arguments": "{\"city\":\"北京\"}" }
    },
    {
      "function": { "name": "get_weather", "arguments": "{\"city\":\"上海\"}" }
    },
    {
      "function": { "name": "get_news", "arguments": "{\"topic\":\"科技\"}" }
    }
  ]
}
```

这类场景下，并行能明显减少来回轮次。

但如果任务是“先查最近订单，再根据订单号查物流”，那就不适合一股脑并行。因为第二步的参数压根来自第一步结果。

所以这个参数真正控制的不是“快不快”，而是：

**你允许模型把任务拆成并发执行，还是要求它按链路一步一步走。**

---

## 一次完整的 Function Calling，到底发生了什么？

如果把整个过程抽干净，它其实就四步：

```text
步骤 1：带着 tools 发请求
    ↓
步骤 2：模型返回 tool_calls
    ↓
步骤 3：应用层执行工具，并把结果回传
    ↓
步骤 4：模型结合工具结果生成最终回答
```

看起来不复杂，但真正关键的是：**模型不会替你执行工具**。它只会提出一个结构化调用请求。真正执行的是你的程序。

这也是很多初学者最容易误会的地方。

### 一个最小可运行的 Python 流程

```python
import json
import openai

client = openai.OpenAI()

tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "获取指定城市的实时天气",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名称"}
                },
                "required": ["city"]
            }
        }
    }
]

messages = [{"role": "user", "content": "北京今天天气怎么样？"}]

response = client.chat.completions.create(
    model="gpt-4o",
    messages=messages,
    tools=tools,
    tool_choice="auto"
)

assistant_message = response.choices[0].message

if assistant_message.tool_calls:
    messages.append(assistant_message)

    for tool_call in assistant_message.tool_calls:
        function_name = tool_call.function.name
        arguments = json.loads(tool_call.function.arguments)

        if function_name == "get_weather":
            city = arguments["city"]
            weather_result = f"{city}今天晴天，25°C"

            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,
                "content": weather_result
            })

    final_response = client.chat.completions.create(
        model="gpt-4o",
        messages=messages,
        tools=tools
    )

    print(final_response.choices[0].message.content)
else:
    print(assistant_message.content)
```

这个例子里真正重要的，不是天气查询本身，而是你能看清整个交互闭环：

- 模型先提请求
- 你的代码执行工具
- 执行结果再回到模型
- 模型最后把工具输出组织成自然语言

这条闭环跑通了，后面接数据库、搜索、工作流、企业系统，其实都是一个模式。

### JavaScript / Vercel AI SDK 的写法会更顺手一点

```typescript
import { generateText, tool } from "ai";
import { openai } from "@ai-sdk/openai";
import { z } from "zod";

const { text, toolCalls } = await generateText({
  model: openai("gpt-4o"),
  messages: [{ role: "user", content: "北京今天天气怎么样？" }],
  tools: {
    get_weather: tool({
      description: "获取指定城市的实时天气",
      parameters: z.object({
        city: z.string().describe("城市名称"),
      }),
      execute: async ({ city }) => {
        return `${city}今天晴天，25°C`;
      },
    }),
  },
  toolChoice: "auto",
  maxSteps: 5,
});

console.log(text);
```

这类 SDK 的好处，是把“定义工具 + 执行工具 + 多轮回填”封得更自然，写业务时负担会轻很多。

## 多工具协作，不外乎三种模式：并行、顺序、链式

文章写到这里，真正该关注的已经不是“单个工具怎么调”，而是：

**多个工具一起工作时，系统应该按什么节奏运行。**

### 并行调用：适合互不依赖的任务

典型场景就是“比较北京、上海、广州的天气”。这三次查询彼此没依赖关系，最合适的做法就是一轮把三个请求都发出去。

```python
tool_calls = [
    {"function": {"name": "get_weather", "arguments": '{"city": "北京"}'}},
    {"function": {"name": "get_weather", "arguments": '{"city": "上海"}'}},
    {"function": {"name": "get_weather", "arguments": '{"city": "广州"}'}}
]
```

这种场景下，`parallel_tool_calls=true` 几乎就是默认解。

### 顺序调用：后一步依赖前一步结果

比如“帮我查最近一个订单的物流状态”。这件事至少要分两步：

```text
用户 → 模型：调用 get_recent_order(user_id)
      ↓ 返回 order_id="12345"
模型 → 调用 get_logistics(order_id="12345")
      ↓ 返回物流信息
模型 → 生成最终回答
```

这时候如果你还想着并行，就会发现第二个工具根本拿不到参数。

### 链式调用：适合复杂任务分多轮推进

有些任务不是两步三步就结束，而是要一边拿结果，一边再判断下一步做什么。

这种情况通常就会写成循环：

```python
max_iterations = 5
for _ in range(max_iterations):
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=messages,
        tools=tools,
        tool_choice="auto"
    )

    message = response.choices[0].message
    messages.append(message)

    if not message.tool_calls:
        break

    for tool_call in message.tool_calls:
        result = execute_tool(tool_call)
        messages.append({
            "role": "tool",
            "tool_call_id": tool_call.id,
            "content": result
        })
```

链式调用的关键不在“能不能循环”，而在**你必须给它设上限**。不然模型很可能在边界不清的时候一直调下去。

## 不同平台都支持工具调用，但实现细节差别不小

如果你只用单一平台，这部分感受还不明显；但一旦做多平台适配，很快就会发现“都支持 Function Calling”和“用起来一样”完全是两回事。

| 平台                 | `tools` 支持 | `tool_choice`                       | `parallel_tool_calls` | 备注                                         |
| -------------------- | ------------ | ----------------------------------- | --------------------- | -------------------------------------------- |
| **OpenAI**           | ✅ 完整      | `auto` / `none` / `required` / 指定 | ✅ 支持               | 支持 `strict`，Schema 约束更强               |
| **DeepSeek**         | ✅ 较高兼容  | ✅ 常见模式兼容                     | ✅ 支持               | 迁移 OpenAI 风格代码相对顺手                 |
| **Anthropic Claude** | ✅ 支持      | `auto` / `any` / 指定               | ❌ 需结合自身流程处理 | 响应是 `tool_use` 内容块，和 OpenAI 风格不同 |
| **Google Gemini**    | ✅ 支持      | `AUTO` / `NONE` / 指定              | ⚠️ 视接口而定         | 通常通过 `function_declarations` 定义        |
| **Kimi**             | ✅ 较高兼容  | ✅ 常见模式兼容                     | ✅ 支持               | OpenAI 风格迁移成本较低                      |
| **MiniMax**          | ✅ 支持      | `auto` / `none` / `required`        | ✅ 支持               | 不同接口形态下能力略有差异                   |
| **零一万物（Yi）**   | ✅ 较高兼容  | ✅ 常见模式兼容                     | ✅ 支持               | 常见接入方式也偏 OpenAI 风格                 |

### Claude 是最容易踩格式差异的一个

Claude 的工具调用不是 `tool_calls` 那一套，而是独立的 `tool_use` 内容块：

```python
import anthropic

response = client.messages.create(
    model="claude-sonnet-4-20250514",
    max_tokens=1024,
    tools=[
        {
            "name": "get_weather",
            "description": "获取天气",
            "input_schema": {
                "type": "object",
                "properties": {"city": {"type": "string"}},
                "required": ["city"]
            }
        }
    ],
    messages=[{"role": "user", "content": "北京天气？"}]
)

for block in response.content:
    if block.type == "tool_use":
        tool_name = block.name
        tool_input = block.input
        # 执行工具，然后把结果作为 tool_result 传回
```

所以如果你在做统一适配层，别只看参数名。**消息结构本身**往往才是最麻烦的部分。

## 真正难的不是“能调起来”，而是别把系统做成一个不稳定的黑箱

这部分其实比参数本身更重要。因为真正进项目之后，问题往往不出在“不会定义 `tools`”，而出在系统行为开始不稳定。

### 坑 1：工具定义太宽，模型开始乱选

这类问题特别常见。两个工具职责边界模糊、命名相近、描述又很泛，模型自然会犹豫，甚至选错。

一个典型对比：

```json
// ❌ 差的定义
{
  "name": "weather",
  "description": "查询天气",
  "parameters": {"city": "string"}
}

// ✅ 好的定义
{
  "name": "get_current_weather",
  "description": "获取指定城市的实时天气信息，包括温度、湿度、天气状况。用于回答用户关于当前天气的询问。",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {
        "type": "string",
        "description": "城市名称，支持中文（如'北京'）或英文（如'Beijing'）"
      },
      "include_humidity": {
        "type": "boolean",
        "description": "是否返回湿度信息，默认 false",
        "default": false
      }
    },
    "required": ["city"]
  }
}
```

### 坑 2：异常处理没接住，模型收到的是半残状态

工具调用失败这件事本身不可怕。可怕的是系统失败了，却没有把失败信息明确回传给模型。

```python
try:
    result = execute_tool(tool_call)
    content = str(result)
except Exception as e:
    content = f"工具调用失败：{str(e)}"

messages.append({
    "role": "tool",
    "tool_call_id": tool_call.id,
    "content": content
})
```

你至少要让模型知道：

- 调用了哪个工具
- 为什么失败
- 现在是该重试、降级，还是直接告诉用户做不到

### 坑 3：无限循环调用工具

这类问题一旦出现在生产环境里，代价通常不只是多花几分钱，而是整条链路失控。

常见原因有两个：

- 工具返回太模糊，模型判断不了任务是否完成
- 没有设置最大轮数或停止条件

所以无论是 `maxSteps` 还是你自己的循环次数上限，最好都明确写死。

### 坑 4：什么问题都想靠工具解决

这也是很典型的“能力扩展上瘾”。

其实不是所有请求都需要调工具。一个简单问答、轻量解释、格式化改写，如果还非要查外部接口，系统只会更慢、更贵，而且更容易出错。

---

## 什么时候该用 Function Calling，什么时候别滥用？

你可以把这个问题理解成一句很朴素的话：

**用户要的是答案，还是动作？**

如果只是答案，很多时候普通生成就够了。

如果用户真正想要的是下面这些：

- 去查一个实时数据
- 去执行一个外部动作
- 去访问企业系统里的真实记录
- 去串多个系统把任务推进下去

那 Function Calling 就很适合。

反过来，如果请求本质上只是：

- 解释一个概念
- 总结一段文本
- 翻译一句话
- 改写一封邮件

那就别急着接工具。

这不是技术能力问题，而是系统设计里的一个基本判断：**能不调用，就别乱调用。**

---

## 小结

Function Calling 真正改变的，不只是 API 形态，而是模型在系统里的角色。

没有它，模型更多还是一个回答机器；有了它，模型才开始具备“请求外部能力、推动任务继续往前走”的可能性。

如果把这篇文章压缩成几个最重要的判断，大概就是：

- **`tools` 决定能力边界，定义质量会直接影响调用准确率**
- **`tool_choice` 决定自主权大小，本质上是在平衡灵活性和可控性**
- **`parallel_tool_calls` 决定执行节奏，适不适合并行要看依赖关系，不是越开越好**
- **完整的工具调用是一个闭环：模型提请求、应用执行、结果回传、模型再组织输出**
- **真正上线时最容易出问题的，是 schema 过松、异常没处理、停止条件不明确**
- **不是所有任务都需要接工具，能少一层外部调用，就少一层复杂度**

下一篇我们继续往下走：当模型开始同时接触图片、结构化输出和格式约束时，`response_format`、`json_schema`、多模态输入这些参数，才会真正开始影响产品体验。
