## 第一篇：LLM API 核心参数深度解析

很多人第一次接 LLM API，会以为这件事很简单：选个模型，塞一段 Prompt，等它吐结果。

真开始做项目之后你很快就会发现，事情没那么轻松。同样一个问题，为什么有时回答又稳又准，有时却开始发散；为什么有时明明提示词没变，输出风格却忽上忽下；为什么代码生成看起来像对的，一跑就出问题？

答案往往不只在 Prompt，也在参数。

`temperature` 决定它是保守一点还是放飞一点，`top_p` 和 `top_k` 决定它到底从多大的候选范围里挑词，`max_tokens` 直接影响输出长度和成本，`penalty` 则决定它会不会车轱辘话来回说。你把这些参数调对了，模型才像一个可控的工程组件；调不对，它就很容易变成“偶尔很聪明，偶尔很离谱”的黑盒。

这一组文章会把 LLM API 里最常见、也最容易踩坑的参数体系梳理清楚：从核心参数、平台差异，到调优实践、推理控制、工具调用、多模态和网关架构，尽量把这件事讲透。

这一篇先打基础。我们先不聊太花的能力，先把最常用、最影响结果的那几个参数弄明白。

### 1. 先有个全局印象：参数到底分哪几类？

如果你把一次 LLM API 调用拆开看，常见参数大致可以分成下面几组：

| 类别             | 典型参数                                                      | 作用                                     |
| ---------------- | ------------------------------------------------------------- | ---------------------------------------- |
| **基础参数**     | `model`, `messages`, `stream`                                 | 指定模型、传入对话、控制响应方式         |
| **采样控制参数** | `temperature`, `top_p`, `top_k`, `min_p`                      | 控制生成内容的随机性和多样性             |
| **输出长度参数** | `max_tokens`, `max_completion_tokens`                         | 限制生成内容的最大 token 数              |
| **重复惩罚参数** | `presence_penalty`, `frequency_penalty`, `repetition_penalty` | 减少重复内容，鼓励新话题                 |
| **停止条件参数** | `stop`, `stop_sequences`                                      | 指定停止生成的标志词                     |
| **高级控制参数** | `logit_bias`, `seed`, `user`                                  | token 级偏置、确定性控制、用户标识       |
| **工具调用参数** | `tools`, `tool_choice`, `parallel_tool_calls`                 | 启用 Function Calling 能力（详见第五篇） |
| **思维链参数**   | `thinking`, `reasoning_effort`                                | 控制推理模型的思考过程（详见第四篇）     |

这一篇先抓最核心的几组：**采样控制、输出长度、重复控制，以及基础响应行为**。

你不用一开始把所有参数都背下来。真正有用的方式是先理解一件事：**有些参数决定“说什么”，有些参数决定“说多少”，还有些参数决定“怎么停下来”**。带着这个视角往下看，会顺很多。

### 2. Temperature：它决定回答是“稳一点”还是“放一点”

如果只能选一个最常被提到的参数，那基本就是 `temperature`。

它控制的是模型输出概率分布的“平滑度”。说白一点，**温度越低，模型越倾向选高概率答案；温度越高，模型越愿意去尝试那些没那么稳、但可能更有变化的表达**。

它背后的数学形式一般写成：`probs = softmax(logits / temperature)`。

你不用死记这个公式，只要记住它的含义：**你其实是在重新塑形模型的选择偏好**。

| temperature 取值  | 概率分布变化                    | 实际效果                         |
| ----------------- | ------------------------------- | -------------------------------- |
| `T < 1`（如 0.3） | 分布变陡，高概率 token 优势放大 | 输出更确定、聚焦，但可能单调     |
| `T = 1`           | 原始分布，不做缩放              | 保持模型原本的自然概率分布       |
| `T > 1`（如 1.5） | 分布变平，各 token 概率趋于均匀 | 输出更随机、多样，但可能偏离逻辑 |

常见取值范围一般是 `[0.0, 2.0]`，默认值通常是 `1.0`。不过要注意，不同平台并不完全一样，比如 Anthropic Claude 和 Kimi 常见范围是 `0 ~ 1`。

### 什么时候该把 Temperature 调低？

当你要的是**稳定、可复现、少出幺蛾子**的结果时，就该把它调低。

| 场景                | 推荐 Temperature | 说明                                 |
| ------------------- | ---------------- | ------------------------------------ |
| 代码生成            | 0.0 ~ 0.2        | 需要确定性和准确性，避免随机引入 bug |
| 数学计算 / 逻辑推理 | 0.0 ~ 0.3        | 追求精确结果，降低随机干扰           |
| 知识问答 / 事实查询 | 0.2 ~ 0.5        | 在准确性和灵活性之间平衡             |
| 翻译                | 0.3 ~ 0.6        | 需要忠实于原文，但允许适度变体       |
| 日常对话            | 0.5 ~ 0.8        | 保持自然流畅，有适度的变化           |
| 创意写作 / 头脑风暴 | 0.8 ~ 1.2        | 需要多样性和新颖性                   |
| 诗歌 / 艺术创作     | 1.0 ~ 1.5        | 追求独特和意外的表达                 |

一个很常见的误区是：**把 temperature 调高，误以为模型会“更聪明”**。其实不是。它通常只会让输出更发散、更敢猜。

所以如果你在做代码、规则提取、分类、事实问答这类任务，第一反应通常不是把它调高，而是先往低了试。

> ⚠️ **额外提醒**：有些推理模型会固定 `temperature=1.0`、`top_p=1.0`，根本不让你自己调。像 OpenAI 某些推理模型就是这样。这不是你不会配，而是模型机制就这么定的。相关内容会在第四篇《思维链与推理控制参数详解》里展开。

### 3. Top-P：不是“选最可能的几个”，而是“选累计概率够高的一批”

`top_p` 又叫 nucleus sampling，中文常翻成“核采样”。

它和 `temperature` 很像，都是在控制随机性，但两者的切法不一样。

- `temperature` 调的是整体概率分布的形状
- `top_p` 控的是**候选集合的边界**

具体来说，模型不会在所有 token 里选，而是只保留“累计概率刚好达到阈值 `p` 的那一小撮 token”，后面那些低概率尾部候选直接丢掉。

这意味着：**`top_p` 不是固定选多少个，而是按概率质量动态截断**。

### 常见取值怎么理解？

- 取值范围通常是 `(0.0, 1.0]`
- `p=0.1`：只看最头部的一小批高概率 token
- `p=0.5`：只保留累计概率达到 50% 的候选
- `p=0.9`：常用值，给模型留一定发挥空间，同时把噪声挡在外面
- `p=1.0`：不过滤，等于全放开

| 场景       | 推荐 Top-P | 说明                                                |
| ---------- | ---------- | --------------------------------------------------- |
| 代码补全   | 0.1 ~ 0.5  | 低 Top-P 使生成内容更严谨一致，适合需要高精度的场景 |
| 知识问答   | 0.5 ~ 0.8  | 在准确性和完整性间取得平衡                          |
| 创意写作   | 0.9 ~ 0.95 | 允许更多样的 token 选择，增加创造性                 |
| 开放域对话 | 0.9 ~ 1.0  | 最大化语言的自然多样性                              |

### Temperature 和 Top-P 要不要一起调？

能一起用，但一般不建议一上来就两边同时乱拧。

经验上更稳的做法是：**先固定一个，再调另一个**。因为这两个参数都在影响采样行为，一起动的时候，很容易把问题越调越糊。

有的平台甚至直接不给你这个自由。Anthropic 在 Sonnet 4.5 及以上版本里，就要求 `temperature` 和 `top_p` 不能同时指定。

常见组合可以这样理解：

- **高确定性场景**：低 `temperature`（0.2）+ 低 `top_p`（0.5）→ 基本往最稳的结果收敛
- **平衡场景**：中等 `temperature`（0.7）+ 高 `top_p`（0.9）→ 既不死板，也不容易跑偏
- **高创造性场景**：高 `temperature`（1.2）+ 高 `top_p`（0.95）→ 留出更多变化空间

如果你刚开始调参，我更建议你记住一句话：**先把 `temperature` 当成主旋钮，再把 `top_p` 当成微调旋钮**。

### 4. Top-K：给候选池设个“人数上限”

`top_k` 的思路就更直接了：**每一步生成时，只允许模型从概率最高的 K 个 token 里选**。

它和 `top_p` 的区别在于：

- `top_p` 是按累计概率截断
- `top_k` 是按候选数量截断

所以 `top_k` 更像一句硬规则：不管后面的 token 概率有多接近，反正只留前 K 个。

### 这个参数通常怎么用？

- 取值范围：大于等于 1 的整数
- `K=1`：基本就是贪婪解码，每一步都选最可能的那个，结果最稳定，但也最死板
- `K=10~50`：比较常见，能过滤很多低概率噪声，又不会太僵
- `K` 越大：候选越多，输出越活

在很多实现里，`top_k` 会先把候选池裁一遍，然后再交给 `top_p` 和 `temperature` 去进一步处理。你可以把三者理解成三道闸：

1. `top_k` 先限人数
2. `top_p` 再限概率范围
3. `temperature` 最后决定怎么挑

### 有个现实问题：不是所有平台都支持 Top-K

这点挺重要，因为很多教程写参数时默认你都能调，实际不是。

OpenAI 的 API **不支持** `top_k`；Anthropic Claude、Google Gemini、DeepSeek 等平台则支持。也就是说，如果你在做多平台适配，`top_k` 很可能不是一个可以放心写死在统一参数层里的字段。

这一点，我们下一篇对比平台差异时会详细展开。

### 5. Max Tokens：这不是“小参数”，它直接关系到长度和成本

很多人前面几类参数研究半天，结果真正上线时最先出问题的，反而是 `max_tokens`。

因为这个参数很现实：**它直接控制模型最多能生成多少 token**。一旦达到上限，模型就停。哪怕它的话还没说完，也会硬停。

所以你会看到两类典型问题：

- 设太小：回答经常被截断，JSON 输出不完整，代码没写完
- 设太大：成本上去，响应时间变长，而且模型更容易啰嗦

### 这个参数该怎么配？

- 取值范围：大于等于 1 的整数
- 不同模型上限不同，比如 GPT-4o 可以到 16384，Claude Sonnet 4 可到 8192
- 费用通常跟输入 token 和输出 token 总量相关，所以它和成本是直接挂钩的

OpenAI 现在更推荐你用 `max_completion_tokens`，而不是旧的 `max_tokens`。不过现实里很多平台还在同时支持这两种写法。为了兼容性，工程上经常会同时做适配。

| 场景                    | 推荐 Max Tokens | 说明                                                                  |
| ----------------------- | --------------- | --------------------------------------------------------------------- |
| 短问答 / 分类任务       | 50 ~ 200        | 答案简洁明确                                                          |
| 摘要生成                | 200 ~ 500       | 保留核心信息                                                          |
| 代码生成                | 500 ~ 2000      | 更适合函数级或片段级代码                                              |
| 文章写作                | 1000 ~ 4000     | 适合完整文章或长段落内容                                              |
| 长篇创作 / 推理模型思考 | 4000+           | 需要长上下文模型，并为推理预留足够 token（如 DeepSeek-R1 建议 ≥4096） |

我的经验是，**先按任务类型估一个“够用但不过量”的范围，再看真实输出长度做微调**。不要一上来为了保险直接拉满，那往往不是最省事的办法。

### 6. Presence Penalty 和 Frequency Penalty：都在防重复，但不是一回事

这两个参数名字很像，第一次看确实容易混。

它们都在处理“重复”问题，但出手方式不同：

- `presence_penalty`：只要某个 token 出现过，就会对它施加惩罚，更倾向把话题往新方向带
- `frequency_penalty`：某个 token 出现得越多，惩罚越重，重点在压制反复重复同样的词句

### Presence Penalty

- 取值范围：`[-2.0, 2.0]`
- 默认值：通常为 `0.0`
- 正值：鼓励新话题、新表达
- 负值：反而会鼓励重复出现过的 token

### Frequency Penalty

- 取值范围：`[-2.0, 2.0]`
- 默认值：通常为 `0.0`
- 正值：降低逐字、逐句反复出现的概率
- 它是按“出现次数”来罚，不是按“是否出现过”来罚

| 场景       | Presence Penalty | Frequency Penalty | 说明                         |
| ---------- | ---------------- | ----------------- | ---------------------------- |
| 事实问答   | 0.0              | 0.0               | 不应惩罚重复关键信息         |
| 创意写作   | 0.5 ~ 1.0        | 0.3 ~ 0.7         | 鼓励新颖表达，减少重复       |
| 长文档生成 | 0.3 ~ 0.8        | 0.5 ~ 1.0         | 避免内容同质化               |
| 代码生成   | 0.0              | 0.0 ~ 0.2         | 代码里的重复很多时候是必要的 |

这里有个很实用的判断标准：**如果你想让模型“别老围着一个点打转”，优先看 `presence_penalty`；如果你想让它“别把同一句话换皮说三遍”，优先看 `frequency_penalty`。**

### 平台支持也不统一

这两个参数不是所有平台都有。

OpenAI、DeepSeek、Kimi、MiniMax 一般支持；Anthropic Claude 和 Google Gemini **不支持**这两个字段。零一万物还提供了 `repetition_penalty`，做法又不太一样，是在采样前直接对 logits 做缩放。

这也是为什么做统一 SDK 或网关时，参数适配层非常重要——你不能假设所有平台语义都一模一样。

### 7. Stop：告诉模型“说到这里就可以了”

`stop` 是个很容易被低估的参数。

很多人遇到输出超长、结构跑偏、模型开始“替用户发言”时，第一反应是去改 Prompt。其实不少时候，一个 `stop` 就够了。

它的作用很简单：**当模型生成到某个字符串时，立刻停下**。

示例：

```json
{
  "stop": ["\n", "。", "Human:", "END"]
}
```

典型用法有这几类：

- 单行回答：用 `["\n"]`，让模型输出一行就停
- 结构化输出：把某个分隔符当成结束标记
- 对话系统：用 `["Human:", "User:"]`，避免模型顺手把下一轮用户台词也补出来

如果你的输出边界总是控制不好，真的可以先试试 `stop`，往往比你继续堆 Prompt 更直接。

### 8. Stream：决定用户是“等整段”，还是“边生成边看到”

`stream` 是个布尔值，默认通常是 `false`。

这个参数不改变答案内容本身，但会明显改变用户体验。

- **非流式（false）**：等模型整段生成完，一次性返回
- **流式（true）**：按 token 或 chunk 持续返回，用户能立刻看到内容往外冒

如果你在做聊天产品、Copilot、问答助手，流式输出几乎是体验标配。因为哪怕总耗时没变，用户也会觉得“它在工作”。

但如果你在做批处理、后台摘要、离线任务，非流式反而更省心，处理逻辑也简单。

> 流式响应里还有很多工程细节，比如 chunk 拼接、断流恢复、前端渲染节奏、首 token 延迟等。这个话题我会放到第七篇《流式响应与性能优化》里单独展开。

### 9. 还有几个参数，最好也先混个脸熟

不是每个参数都值得在第一天深挖，但下面这些字段，你至少应该知道它们是干嘛的：

| 参数              | 作用                             | 典型取值                                 |
| ----------------- | -------------------------------- | ---------------------------------------- |
| `n`               | 返回多少个不同的响应候选         | 1（默认），最高可达 5+                   |
| `logit_bias`      | 对特定 token 的 logit 添加偏置   | `{"2435": -100}`，表示强力禁止某个 token |
| `seed`            | 设置随机种子，实现可复现输出     | 任意整数                                 |
| `user`            | 用户标识，用于 OpenAI 的滥用监控 | 用户 ID                                  |
| `response_format` | 强制输出为 JSON 格式             | `{"type": "json_object"}`（详见第六篇）  |

尤其是 `response_format`，如果你在做结构化抽取、工具调用、Agent 输出解析，这个参数非常关键。后面第六篇会详细讲。

### 10. 一个更实用的决策框架：先看任务，再看参数

参数很多，但真实工作里你不会一上来逐个抠定义。更实用的方式，是从任务目标反推。

可以先用下面这个简单框架定位：

```
开始
├── 任务更偏哪类？
│   ├── 精确型（代码 / 数学 / 事实问答）
│   │   ├── temperature: 0.0~0.3
│   │   ├── top_p: 0.5~0.8
│   │   ├── top_k: 10~30
│   │   └── penalty: 0.0
│   ├── 平衡型（日常对话 / 翻译 / 摘要）
│   │   ├── temperature: 0.5~0.8
│   │   ├── top_p: 0.8~0.95
│   │   ├── top_k: 30~50
│   │   └── penalty: 0.0~0.3
│   └── 创造型（创意写作 / 头脑风暴 / 诗歌）
│       ├── temperature: 0.8~1.5
│       ├── top_p: 0.9~1.0
│       ├── top_k: 50+
│       └── penalty: 0.3~1.0
├── 输出要多长？
│   ├── 短答案 → max_tokens: 50~200
│   ├── 中等长度 → max_tokens: 200~1000
│   └── 长文本 → max_tokens: 1000+
├── 用户是否需要即时反馈？
│   ├── 需要 → stream: true
│   └── 不需要 → stream: false
└── 是否要求结构化输出？
    ├── 是 → response_format: {"type": "json_object"}
    └── 否 → 默认 text
```

如果你想把它进一步压缩成一句经验，那就是：

- **想要稳**：降 `temperature`，必要时收紧 `top_p`
- **想要活**：升 `temperature`，适当放开采样范围
- **想防截断**：调大 `max_tokens`
- **想防啰嗦和重复**：看 `penalty`
- **想控制结束位置**：用 `stop`
- **想提升交互体感**：开 `stream`

### 11. 写在最后

如果你读到这里，应该已经能建立一个比较清晰的感觉：LLM API 的参数并不是一堆散乱开关，它们其实在共同回答几个很具体的问题：

- 模型该保守一点，还是大胆一点？
- 候选范围该收紧，还是放开？
- 输出该多长？
- 重复该不该压？
- 到哪里停？
- 用户是等完整结果，还是实时看生成过程？

说到底，**调参数不是玄学，而是在给模型设工作边界**。

真正做项目时，你不一定需要把每个参数都用上，但一定要知道：当输出质量不稳定、长度失控、内容重复、风格乱跳时，问题可能根本不在 Prompt，而在参数。

这一篇先把地基打好。下一篇，我们会把视角切到平台层面：**同样叫 `temperature`、`max_tokens`、`penalty`，不同平台到底支持到什么程度，语义又有哪些差别？** 这件事如果不搞清楚，后面做多平台适配会很容易踩坑。
