**很多人做 LLM 应用，最先盯的是回答质量；真到上线，最先挨打的往往却是等待时间。**

模型答得再好，如果用户要盯着转圈 12 秒，体验一样会崩。

<!-- more -->

而且问题通常不止一个。

请求慢、偶发超时、峰值限流、重复请求太多、token 成本飙高、前端迟迟没有首屏反馈——这些事，单独看都不算致命，一旦叠在一起，就会把一个“看起来能用”的 Demo 拖回原型阶段。

所以这一篇，我们不把重点放在“参数表背诵”上，而是把流式响应和性能优化当成一条完整链路来看：

- 用户什么时候能看到第一段内容
- 服务端怎么稳住长请求
- 大量任务进来时怎么提高吞吐
- 成本和延迟怎么一起压
- 出问题时怎么知道问题出在哪

如果前几篇解决的是“模型怎么更会做事”，这一篇解决的就是：

**模型开始真正接近生产环境时，你该怎么把体验、稳定性和成本一起管起来。**

---

## 为什么流式响应和性能优化，会成为上线后的第一道坎？

因为用户对“质量差一点”的容忍度，通常比对“等太久”的容忍度更高。

尤其在聊天、客服、问答、写作助手这类场景里，用户其实不是非要在 8 秒后一次性拿到一段完美答案。更多时候，他只想先确认一件事：**系统活着，而且正在工作。**

这也是流式响应真正的价值。

它不一定让总耗时大幅下降，但它能明显改善“体感延迟”。用户不用等到模型把整段话都想完，半秒到一秒内就能看到第一批内容开始出来。

而性能优化解决的，则是另一个更现实的问题：

**如果请求越来越多，系统还能不能保持这种体验。**

所以别把这篇理解成“开一个 `stream=true` 的技巧合集”。更准确地说，它讲的是：

- **前台**：怎么让用户尽快看到反馈
- **后台**：怎么让系统在高延迟、高波动、高成本条件下稳定运行

---

## 先分清一件事：流式响应优化的是“感知速度”，不是“真实算力”

这是很多人一开始容易混淆的地方。

流式响应不会让模型突然算得更快。模型该花 8 秒生成，可能还是 8 秒。它做的事情是，把原本 8 秒后一次性交付的结果，拆成若干 chunk 逐步吐出来，让用户在前面几百毫秒就先看到内容。

可以把它理解成两种完全不同的交付方式：

```text
非流式：请求 → [模型生成全文] → 一次性返回
流式：  请求 → [生成一点就返回一点] → 用户边看边等后续内容
```

这意味着一件非常重要的事：

- **如果你的目标是改善交互体验**，流式几乎是必选项
- **如果你的目标是提高后端吞吐**，光开流还远远不够

吞吐、并发、限流、缓存、批处理、模型选择，这些还是得另外做。

所以对流式响应最准确的预期应该是：

**它优先解决“用户感觉慢”的问题，而不是直接解决“系统真的慢”的问题。**

---

## 什么场景应该开流，什么场景反而不该开？

并不是所有请求都值得流式返回。

很多团队一看到 `stream` 好用，就想全量开启。结果很快发现，事情没有这么简单：有些任务天然适合边生成边展示，有些任务则更适合等结果完整后一次性交付。

### 适合开流的场景

这类场景通常满足一个特点：**用户会盯着界面等结果。**

比如：

- 对话助手
- 写作生成
- 客服机器人
- 代码解释
- 报告草稿生成

这些任务里，用户并不需要“最后那一刻的完整正确性”才开始读。他完全可以边看前面的内容，边等后面的补全。

### 不一定适合开流的场景

如果结果要先经过校验、合并、解析、结构化处理，再交给系统消费，那就未必值得流式输出。

比如：

- 严格 JSON / Schema 输出
- 工具调用后还要二次执行
- 批量离线任务
- 审批流、数据入库流

这类任务的重点不是“先吐一点给用户看”，而是“最后的结果必须完整、稳定、可消费”。

所以更实用的判断标准是：

| 场景类型             | 是否建议开流  | 原因                                 |
| -------------------- | ------------- | ------------------------------------ |
| **聊天/问答/写作**   | ✅ 建议       | 用户在前台等待，首字节体验最重要     |
| **代码生成/解释**    | ✅ 建议       | 长文本输出明显，逐步展示价值很高     |
| **结构化 JSON 输出** | ⚠️ 视情况而定 | 中途内容对前端价值有限，完整性更关键 |
| **工具调用链**       | ⚠️ 视情况而定 | 可能要先拼参数、执行业务动作         |
| **批量离线任务**     | ❌ 通常没必要 | 用户不在前台等待，更关心成本和吞吐   |

很多时候，**流不流不是模型能力问题，而是产品交互问题。**

## `stream` 参数本身不复杂，复杂的是你怎么接住它

主流平台基本都支持通过布尔参数控制流式响应：

| 平台                 | 参数           | 默认值  | 流式响应格式          |
| -------------------- | -------------- | ------- | --------------------- |
| **OpenAI**           | `stream: true` | `false` | SSE（`data: [JSON]`） |
| **DeepSeek**         | `stream: true` | `false` | 兼容 OpenAI SSE 格式  |
| **Kimi**             | `stream: true` | `false` | 兼容 OpenAI SSE 格式  |
| **Anthropic Claude** | `stream: true` | `false` | SSE，事件类型更丰富   |
| **Google Gemini**    | `stream: true` | `false` | SSE 或 gRPC 流        |
| **MiniMax**          | `stream: true` | `false` | 兼容 OpenAI SSE 格式  |
| **零一万物（Yi）**   | `stream: true` | `false` | 兼容 OpenAI SSE 格式  |

最基础的 Python 写法其实很直白：

```python
from openai import OpenAI

client = OpenAI()

response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "讲个故事"}],
    stream=False
)
print(response.choices[0].message.content)

stream = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "讲个故事"}],
    stream=True
)

for chunk in stream:
    if chunk.choices[0].delta.content:
        print(chunk.choices[0].delta.content, end="")
```

真正麻烦的地方不是把 `stream=True` 打开，而是后面这些问题：

- chunk 是不是可能为空
- 工具调用参数是不是分块返回
- 多平台事件格式是不是一致
- 前端怎么一边读流一边安全更新 UI
- 流中断后要不要重连

换句话说，**难点在消费端，不在参数本身。**

---

## 你真正要理解的，不是“流”，而是 chunk

流式响应到了客户端，看到的其实不是一整段自然语言，而是一串接一串的增量片段。

以 OpenAI 风格为例，每个 chunk 大致长这样：

```json
{
  "id": "chatcmpl-xxx",
  "object": "chat.completion.chunk",
  "created": 1713456789,
  "model": "gpt-4o",
  "choices": [
    {
      "index": 0,
      "delta": {
        "content": "从前",
        "role": "assistant"
      },
      "finish_reason": null
    }
  ]
}
```

这里真正有用的是两个字段：

- `delta.content`：这次新吐出来的文本
- `finish_reason`：什么时候可以判定流结束

所以处理流式输出时，一个常见误区是把每个 chunk 当成完整响应去解析。其实不是。你要做的是**累积增量**，而不是每次都重建一份完整对象。

### 工具调用时，情况还会更麻烦一点

当模型在流中触发 Function Calling，工具参数通常不是一口气返回，而是分块拼出来的。

```python
for chunk in stream:
    delta = chunk.choices[0].delta
    if delta.tool_calls:
        for tc in delta.tool_calls:
            if tc.function.arguments:
                tool_call_args[tc.index] += tc.function.arguments
```

这类场景里，最常见的问题不是“模型没返回”，而是你**太早解析了一个还没拼完的参数字符串**。

---

## 多平台都叫流式响应，但解析方式并不完全一样

这件事很容易被“兼容 OpenAI”几个字掩盖掉。

很多平台在简单文本输出上看起来都差不多，但一旦碰到推理内容、工具调用、富事件流，差异马上就会出来。

| 平台              | 特殊 chunk 字段                                                      | 说明                             |
| ----------------- | -------------------------------------------------------------------- | -------------------------------- |
| **OpenAI**        | `delta.tool_calls`                                                   | 工具调用参数分块                 |
| **DeepSeek**      | `delta.reasoning_content`                                            | 推理内容会单独分块               |
| **Kimi**          | `delta.reasoning_content`                                            | 长思考模式下会有额外推理片段     |
| **Anthropic**     | `message_start`、`content_block_start`、`content_block_delta` 等事件 | 事件粒度更细，建议按事件类型解析 |
| **Google Gemini** | `candidates[0].content.parts`                                        | 文本与内联数据可能混在 parts 中  |

Anthropic 的一个典型写法如下：

```python
import anthropic

client = anthropic.Anthropic()

with client.messages.stream(
    model="claude-sonnet-4-20250514",
    max_tokens=1024,
    messages=[{"role": "user", "content": "Hello"}]
) as stream:
    for text in stream.text_stream:
        print(text, end="")
```

Claude 的 SDK 帮你封装掉了一部分复杂性，所以表面上会轻松不少。但如果你自己做统一网关或者多模型抽象层，最好别偷懒地假设“所有流都长一样”。

## 前端集成时，最重要的不是“能显示”，而是“别抖、别乱、别卡”

很多 Demo 里，前端接流式输出几行代码就搞定了。但真到产品里，你要面对的是：

- 文本不断变化，UI 会不会疯狂重渲染
- chunk 边界不稳定，拆行会不会出错
- 中途网络抖一下，界面会不会直接卡死
- 用户切换页面后，流要不要中断

如果你用的是现成的 UI 层，比如 Vercel AI SDK，会轻松很多：

```tsx
import { useChat } from "ai/react";

function Chat() {
  const { messages, input, handleInputChange, handleSubmit } = useChat({
    api: "/api/chat",
  });

  return (
    <div>
      {messages.map((m) => (
        <div key={m.id}>
          {m.role}: {m.content}
        </div>
      ))}
      <form onSubmit={handleSubmit}>
        <input value={input} onChange={handleInputChange} />
      </form>
    </div>
  );
}
```

如果你自己用原生 `fetch` 去接 SSE，至少要确保解析逻辑足够稳：

```javascript
const response = await fetch("/api/chat", {
  method: "POST",
  body: JSON.stringify({ messages }),
  headers: { "Content-Type": "application/json" },
});

const reader = response.body.getReader();
const decoder = new TextDecoder();

while (true) {
  const { done, value } = await reader.read();
  if (done) break;

  const chunk = decoder.decode(value);
  const lines = chunk.split("\n");
  for (const line of lines) {
    if (line.startsWith("data: ")) {
      const data = JSON.parse(line.slice(6));
      if (data.choices[0].delta.content) {
        // 更新 UI
      }
    }
  }
}
```

工程里更稳的做法，一般还会补上：

- 节流更新，避免每个 token 都触发一次 React 渲染
- 中途取消能力，比如 `AbortController`
- 流结束、报错、重试三种状态的明确区分

## 只会开流还不够，超时和重试才是线上稳定性的底盘

流式输出把响应拆长了，超时问题反而更需要认真处理。

因为请求一旦持续几十秒，链路上的任何一点抖动都会暴露出来：网络闪断、平台临时抖动、模型处理时间过长、代理层回源不稳……这些都可能让流在中途断掉。

### 超时不要只设一个值

更实用的做法，是把超时拆成至少两个维度：

| 超时类型     | 说明                         | 推荐值（非流式） | 推荐值（流式）                                        |
| ------------ | ---------------------------- | ---------------- | ----------------------------------------------------- |
| **连接超时** | 建立 TCP 连接的最大等待时间  | 5 ~ 10 秒        | 5 ~ 10 秒                                             |
| **读取超时** | 等待服务器响应数据的最大间隔 | 60 ~ 120 秒      | 10 ~ 30 秒（首个 chunk），之后每个 chunk 间隔 5~10 秒 |

`httpx` 的配置示例如下：

```python
import openai
import httpx

client = openai.OpenAI(
    http_client=httpx.Client(
        timeout=httpx.Timeout(
            connect=10.0,
            read=90.0,
            write=10.0,
            pool=10.0
        )
    )
)
```

这里有个很关键的工程判断：

**流式请求的读取超时，不该按“整段回复总时长”来设，而该按“首个 chunk 多久没来、后续 chunk 多久没动静”来设。**

### 流式超时，更像是“长时间无增量”

```python
import time

last_chunk_time = time.time()
chunk_timeout = 15

for chunk in stream:
    last_chunk_time = time.time()
    # 处理 chunk
    if time.time() - last_chunk_time > chunk_timeout:
        raise TimeoutError("流式响应超时")
```

真实项目里，这段逻辑通常还会放在更外层的读取循环或监控逻辑里，不会像示例这样简化。但它表达的核心意思是对的：

**流式超时关注的是“有没有持续产出”，不是“整段回复花了多久”。**

## 重试不是万能药，先分清哪些错误值得重试

很多系统把所有异常都一把抓，然后统一重试三次。这个做法表面上很稳，实际上经常把简单问题放大成雪崩。

因为有些错误重试根本没意义。

| 错误类型                                  | 是否可重试 | 重试策略                         |
| ----------------------------------------- | ---------- | -------------------------------- |
| **429 Rate Limit**                        | ✅ 是      | 指数退避，优先参考 `Retry-After` |
| **5xx 服务器错误**                        | ✅ 是      | 指数退避，最多 3 次              |
| **连接超时 / 网络错误**                   | ✅ 是      | 指数退避，最多 3 次              |
| **401 认证错误**                          | ❌ 否      | 直接失败，检查 API Key           |
| **400 请求参数错误**                      | ❌ 否      | 直接失败，修正参数               |
| **上下文超长（context_length_exceeded）** | ❌ 否      | 截断输入或切换长上下文模型       |

所以重试策略的第一原则其实不是“怎么重试”，而是：

**别重试那些一看就不会自己变好的错误。**

指数退避的基础实现如下：

```python
import time
import random
from openai import OpenAI, RateLimitError, APIConnectionError, APIError


def call_with_retry(messages, max_retries=3):
    client = OpenAI()
    retries = 0

    while retries <= max_retries:
        try:
            return client.chat.completions.create(
                model="gpt-4o",
                messages=messages
            )
        except RateLimitError:
            retries += 1
            if retries > max_retries:
                raise
            wait_time = (2 ** retries) + random.uniform(0, 1)
            time.sleep(wait_time)
        except (APIConnectionError, APIError):
            retries += 1
            if retries > max_retries:
                raise
            wait_time = (2 ** retries) + random.uniform(0, 1)
            time.sleep(wait_time)
        except Exception:
            raise
```

如果你不想自己维护这些细节，用 `tenacity` 会省事很多：

```python
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type
from openai import RateLimitError, APIConnectionError, APIError

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=30),
    retry=retry_if_exception_type((RateLimitError, APIConnectionError, APIError))
)
def call_llm(messages):
    return client.chat.completions.create(model="gpt-4o", messages=messages)
```

不过也别把重试当银弹。真正要上线的系统，最好还能区分：

- 是否幂等
- 是否允许用户感知到重复执行
- 工具调用失败后能否安全重放

## 真正拉开吞吐差距的，往往不是流式，而是并发和批处理

如果你在做的是大量独立任务，比如批量分类、批量摘要、批量生成标题，光让它流出来其实没什么意义。此时更重要的是：**同一段时间内能处理多少个请求。**

### 互不依赖的任务，优先考虑异步并发

```python
import asyncio
from openai import AsyncOpenAI

client = AsyncOpenAI()

async def process_one(prompt):
    response = await client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": prompt}]
    )
    return response.choices[0].message.content

async def process_batch(prompts):
    tasks = [process_one(p) for p in prompts]
    results = await asyncio.gather(*tasks, return_exceptions=True)
    return results
```

这类方案的收益很直接，但一定要记得控并发，不然很快就会被限流反噬。

```python
semaphore = asyncio.Semaphore(10)

async def process_with_limit(prompt):
    async with semaphore:
        return await process_one(prompt)
```

### 非实时任务，Batch API 往往更划算

如果任务不要求秒回，而是允许几小时内完成，那很多平台的 Batch API 会是更好的选择。

| 平台              | 批量 API        | 成本折扣    | 说明                        |
| ----------------- | --------------- | ----------- | --------------------------- |
| **OpenAI**        | Batch API       | **50% off** | 上传 JSONL 文件，24h 内完成 |
| **Anthropic**     | Message Batches | **50% off** | 类似 OpenAI，上传 JSONL     |
| **DeepSeek**      | 暂不支持        | —           | 可通过并发实现              |
| **Google Gemini** | Batch API       | **50% off** | 支持批量预测                |

OpenAI 的基本流程如下：

```python
from openai import OpenAI
import time

client = OpenAI()

batch_input_file = client.files.create(
    file=open("batch_input.jsonl", "rb"),
    purpose="batch"
)

batch = client.batches.create(
    input_file_id=batch_input_file.id,
    endpoint="/v1/chat/completions",
    completion_window="24h"
)

while batch.status not in ["completed", "failed", "cancelled"]:
    batch = client.batches.retrieve(batch.id)
    time.sleep(60)

if batch.status == "completed":
    result = client.files.content(batch.output_file_id)
    for line in result.text.splitlines():
        print(line)
```

配套的 JSONL 结构一般是这样：

```jsonl
{"custom_id": "req-1", "method": "POST", "url": "/v1/chat/completions", "body": {"model": "gpt-4o-mini", "messages": [{"role": "user", "content": "Hello"}]}}
{"custom_id": "req-2", "method": "POST", "url": "/v1/chat/completions", "body": {"model": "gpt-4o-mini", "messages": [{"role": "user", "content": "World"}]}}
```

### 小任务很多时，还可以考虑请求合并

如果每个请求都很短、很轻，而且上下文彼此独立，有时候把多个任务塞到同一个 prompt 里，会比逐条调用更省。

```python
prompt = """
分析以下句子的情感（积极/消极/中性），以 JSON 数组格式返回：
1. 今天天气真好！
2. 我丢了钱包，太倒霉了。
3. 这本书一般般。

返回格式：[{"id": 1, "sentiment": "积极"}, ...]
"""

response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": prompt}],
    response_format={"type": "json_object"}
)
```

不过请求合并不是越多越好。合并过头了，单次失败的损失也会放大，而且输出更容易串格式。这个边界要靠你的业务特性来拿捏。

## 降成本最稳的办法，很多时候不是“更会省”，而是“别浪费 token”

性能和成本，在 LLM 里往往是一对连体问题。token 越多，通常意味着更高的延迟和更高的花费。

所以优化 token，不只是财务问题，也是体验问题。

### 先砍输入 token

| 策略            | 说明                             | 示例                                        |
| --------------- | -------------------------------- | ------------------------------------------- |
| **精简 Prompt** | 去掉冗余描述，使用更直接的指令   | “总结：” 而不是“请你帮我总结一下下面的内容” |
| **截断上下文**  | 只保留真正还会影响当前回答的历史 | 例如只保留最近 5 轮对话                     |
| **摘要压缩**    | 把长历史先压缩成摘要再带入       | 让小模型先做一轮总结                        |
| **RAG 优化**    | 只喂最相关的片段                 | 检索 + 重排序后只取 top 3 或 top 5          |

### 再控制输出 token

| 策略                | 参数                    | 说明                     |
| ------------------- | ----------------------- | ------------------------ |
| **设置 token 上限** | `max_completion_tokens` | 根据任务目标设置合理上限 |
| **使用停止词**      | `stop`                  | 到关键标记就停止         |
| **让回答更短**      | Prompt 工程             | 明确要求一句话、三点内等 |

### 模型别一把梭到最贵的

| 任务类型                 | 推荐模型                     | 相对成本（与 GPT-4o 比） |
| ------------------------ | ---------------------------- | ------------------------ |
| **复杂推理、代码生成**   | GPT-4o / Claude Sonnet 4     | 1x                       |
| **简单问答、分类、摘要** | GPT-4o-mini / DeepSeek-V3    | 0.05x ~ 0.1x             |
| **批量任务**             | GPT-4o-mini Batch / DeepSeek | 0.02x ~ 0.05x            |
| **边缘推理、本地部署**   | Llama 3 / Qwen 2.5           | 硬件成本                 |

很多团队前期最容易做错的一件事，就是把所有请求都交给最强模型处理。短期看是省开发时间，长期看往往是最贵、最慢，也最不稳的方案。

## 缓存不是锦上添花，很多时候是最划算的性能优化

如果你的产品里存在重复问题、重复前缀、重复上下文，那缓存往往比你继续压榨模型参数更有效。

### 精确缓存和语义缓存，解决的是两类不同问题

最简单的是精确匹配缓存：相同请求直接命中。

```python
import hashlib
from redis import Redis

redis_client = Redis()


def get_cache_key(messages, model):
    content = "".join([m["content"] for m in messages])
    key = hashlib.md5(f"{model}:{content}".encode()).hexdigest()
    return key


def cached_completion(messages, model):
    key = get_cache_key(messages, model)
    cached = redis_client.get(key)
    if cached:
        return cached.decode()

    response = client.chat.completions.create(model=model, messages=messages)
    result = response.choices[0].message.content
    redis_client.setex(key, 3600, result)
    return result
```

再往前一步，就是语义缓存：问题不完全一样，但足够相似，也可以直接复用旧答案。

这类方案对 FAQ、内部知识助手、固定业务问答特别有用。不过阈值别设太松，否则省下的 token 可能最后会变成错答成本。

### 平台原生 Prompt Caching，也值得认真看

| 平台                 | 支持情况           | 说明                                     |
| -------------------- | ------------------ | ---------------------------------------- |
| **Anthropic Claude** | ✅ Prompt Caching  | 长上下文前缀可缓存，读取成本显著更低     |
| **Google Gemini**    | ✅ Context Caching | 支持显式创建缓存资源                     |
| **OpenAI**           | ⚠️ 自动缓存        | 相同 prompt 在短时间重复调用可能获得折扣 |
| **DeepSeek**         | ✅ 服务端缓存      | 相同输入存在缓存收益，延迟可能下降       |

Anthropic 的示例如下：

```python
response = client.messages.create(
    model="claude-sonnet-4-20250514",
    messages=[...],
    system=[{
        "type": "text",
        "text": "你是一个...",
        "cache_control": {"type": "ephemeral"}
    }]
)
```

如果你的系统提示很长、上下文前缀相对稳定，这类原生缓存的收益会非常可观。

## 真正上线后，最怕的不是慢，而是你根本不知道它为什么慢

很多系统上线初期，看起来只是“偶尔卡一下”。可一旦你没有监控，很快就会进入一种特别难受的状态：

- 用户说慢，你不知道慢在首字节还是慢在整段生成
- 成本涨了，你不知道是哪个用户、哪个模型、哪个接口在烧钱
- 429 多了，你不知道是并发高了还是重试把自己打爆了
- 缓存命中低，你也不知道是策略问题还是数据分布问题

所以可观测性不是最后再补的东西，而是和流式、重试、缓存一起设计的。

### 生产环境至少要盯这些指标

| 指标           | 工具/统计方式      | 说明                                |
| -------------- | ------------------ | ----------------------------------- |
| **请求延迟**   | P50、P95、P99      | 同时看首个 chunk 延迟和完整响应延迟 |
| **Token 消耗** | 按请求/用户/天统计 | 用于成本控制和异常检测              |
| **错误率**     | 4xx、5xx 占比      | 判断服务健康度                      |
| **限流命中率** | 429 错误频率       | 判断并发策略是否过猛                |
| **缓存命中率** | 命中比例           | 判断缓存是否真正带来收益            |

常见工具也很明确：

- **LangSmith** / **LangFuse**：适合做 LLM 调用链追踪
- **LiteLLM Proxy**：适合统一接入层和指标导出
- **OpenTelemetry**：适合纳入现有监控体系

真正有用的不是“接了一个监控平台”，而是你有没有把指标定义清楚，能不能把问题定位到：模型、网络、缓存、并发还是前端渲染这一层。

## 一个更实用的性能优化决策树

很多时候，性能优化不是逐项堆技巧，而是先判断你面对的到底是哪类问题。

```text
开始
├── 用户是否在前台等待结果？
│   ├── 是 → 优先考虑 stream: true
│   └── 否 → 可先不流式，重点看吞吐和成本
├── 任务是否要求实时完成？
│   ├── 是 → 同步/异步并发处理
│   └── 否 → 优先考虑 Batch API
├── 请求是否大量重复？
│   ├── 是 → 做精确缓存或语义缓存
│   └── 否 → 继续看 token 和模型选择
├── 请求是否彼此独立？
│   ├── 是 → 并发执行，注意限流控制
│   └── 否 → 保持串行或拆阶段处理
└── 成本是否敏感？
    ├── 高 → 小模型 + 批处理 + 缓存优先
    └── 低 → 在关键链路上优先保证效果
```

它不是唯一正确答案，但至少比“哪里慢就哪里拍脑袋优化”可靠得多。

## 小结

流式响应和性能优化，真正改变的不是某一个参数值，而是你怎么看待 LLM 系统这条调用链。

在 Demo 阶段，我们很容易只盯着“模型回答得好不好”；一旦走到生产环境，问题马上会变成：

- 用户能不能尽快看到反馈
- 长请求能不能稳定跑完
- 高峰期会不会被限流打穿
- 大批量任务怎么做才划算
- token 和成本有没有被无意义地浪费
- 出问题时能不能快速定位

如果把这篇压缩成几个最重要的判断，大概就是：

- **流式响应优先优化的是体感速度，不是模型真实算力**
- **是否开启 `stream`，取决于产品交互，而不只是接口能力**
- **流式处理的核心不是开关本身，而是 chunk 的消费、拼接和异常收尾**
- **真正决定系统吞吐的，往往是并发控制、批处理和缓存，而不是单纯流式输出**
- **超时与重试必须按错误类型分层处理，不能无脑重放**
- **token 优化本质上同时在省成本和省延迟**
- **没有可观测性，所有性能优化最后都会变成猜**
