## 先说一个让人清醒的事实

Anthropic 工程团队在文章开头说了这么一句话：

> 没有评估的团队会陷入被动循环——修复一个失败，又制造另一个，无法区分真正的回归与噪声。

这句话我反复读了好几遍。

"被动循环"——这四个字太准了。

你改了个提示词，不知道好没好。你换了个模型，不知道进没进步。用户说"感觉变差了"，你手动测了几个 case，看起来没问题，上线，用户还是说差。

这个循环，做过 Agent 的人都经历过。

Anthropic 给出的数据更直接：**有评测的团队能在几天内完成模型升级，没有评测的团队需要几周。**

不是几小时的差距，是几天 vs 几周。

---

## 评测到底是什么

在讲怎么做之前，先把概念理清楚。

Anthropic 给了一套术语定义，我觉得比很多教材都清晰：

**任务（Task）**：一个测试单元，有明确的输入和成功标准。

**试验（Trial）**：对同一个任务的一次运行。注意，同一个任务要跑多次，因为 LLM 的输出不是确定的。

**评分器（Grader）**：判断这次试验成不成功的逻辑。一个任务可以有多个评分器。

**记录（Transcript）**：一次试验的完整日志——输出、工具调用、推理过程、中间结果，全在里面。

**评估套件（Evaluation Suite）**：一组任务的集合，用来衡量某个特定能力。

这几个概念搞清楚，后面的内容就好理解多了。

## 评分器：最核心的设计决策

评测里最难的不是"跑什么"，是"怎么判断对不对"。

Anthropic 把评分器分成三类，每类有自己的适用场景。

### 第一类：代码评分器

最简单，也最可靠。

字符串匹配、测试通过率、静态分析、工具调用验证……这些都是代码评分器。

好处是快、准、便宜，结果完全可复现。坏处是太死板——Agent 给了一个正确但格式不同的答案，代码评分器可能判它失败。

什么时候用？**能用代码判断的，优先用代码。**

编码 Agent 最典型——代码能不能跑、测试能不能过，这就是最好的评分器，不需要 LLM 来判断。

### 第二类：模型评分器（LLM-as-Judge）

当代码判断不了的时候，用 LLM 来打分。

比如"这个回答的语气合不合适"、"解释够不够清晰"、"有没有产生幻觉"——这些主观判断，只能靠 LLM。

Anthropic 用的方式包括：基于评分标准打分、自然语言断言、成对比较（A 和 B 哪个更好）。

好处是灵活，能处理开放式任务。坏处是贵，而且结果不是 100% 确定的，需要和人工评分做校准。

有一个细节很重要：**模型评分器要用比被评测 Agent 更强的模型来打分。** 用 GPT-3.5 评 GPT-4 的输出，结果不可信。

### 第三类：人工评分器

最贵，最慢，但是黄金标准。

领域专家审查、众包判断、A/B 测试……这些都是人工评分器。

实际用途主要有两个：一是处理代码和模型都搞不定的高难度判断；二是用来校准模型评分器——先让人工打一批分，再看模型评分器和人工的一致性有多高。

### 三类怎么组合？

Anthropic 的建议很实在：

**能用代码的，用代码。必须用 LLM 的，用 LLM。需要黄金标准的，用人工。**

实际项目里，一个任务往往同时用多个评分器。比如评测一个客服 Agent：

- 工单有没有关闭 → 代码评分器（状态检查）
- 有没有验证用户身份 → 代码评分器（工具调用验证）
- 语气有没有表达同理心 → 模型评分器（LLM 打分）
- 解决方案有没有说清楚 → 模型评分器（自然语言断言）

四个评分器，两种类型，覆盖不同维度。

## 非确定性：Agent 评测最头疼的问题

普通代码测试，同一个输入永远给同一个输出。

Agent 不一样。同一个任务跑两次，可能一次成功一次失败。这不是 bug，是 LLM 的本质特性。

那怎么办？

Anthropic 提出了两个指标，我觉得是这篇文章里最有价值的内容之一。

### pass@k：至少成功一次

`pass@k` 的意思是：跑 k 次，至少有一次成功的概率。

k 越大，pass@k 越高。跑 10 次，总有几次能成功。

什么时候用这个指标？**适合"一次成功就够"的工具型场景。**

比如你做了一个代码生成工具，用户可以反复点"重新生成"直到满意。这种场景下，pass@10 = 80% 就够用了，不需要每次都成功。

### pass^k：每次都要成功

`pass^k` 的意思是：跑 k 次，每次都成功的概率。

k 越大，pass^k 越低。要求越严，通过率越低。

什么时候用这个指标？**适合需要稳定性的面向用户场景。**

比如你做了一个自动处理工单的 Agent，每次来一个工单都要正确处理，不能靠运气。这种场景下，pass^1 = 95% 才算合格。

### 实际怎么用？

两个指标都要看，但侧重不同。

开发阶段，先看 pass@k——能不能做到？

上线前，再看 pass^k——稳不稳定？

如果 pass@5 很高但 pass^1 很低，说明 Agent 有能力但不稳定，需要优化一致性。

## 能力评估 vs 回归评估

这是 Anthropic 提到的另一个重要区分，很多团队没意识到这两件事是不同的。

**能力评估**：问的是"Agent 能做什么？"

这类评估应该有一定的失败率。如果 100% 通过，说明题目太简单了，没有区分度。Anthropic 的建议是从低通过率开始，专门针对 Agent 做不好的任务。

**回归评估**：问的是"Agent 还能做它以前能做的事吗？"

这类评估应该接近 100% 通过。一旦有任务失败，就是回归，需要立刻排查。

两类评估要分开维护，不能混在一起。

混在一起会发生什么？你改了个功能，能力评估通过率从 60% 升到 70%，但回归评估里有 3 个任务失败了——如果不分开看，你可能以为整体变好了，其实是引入了回归。

## 不同类型 Agent 的评测重点

Anthropic 按 Agent 类型给了具体建议，我觉得很有参考价值。

**编码 Agent**

最好评，因为软件本身就容易测试。

核心评分器：代码能不能跑、测试能不能过、静态分析有没有报错。

额外要追踪的：跑了几轮、调了几次工具、花了多少 token——这些效率指标决定了 Agent 能不能用在生产。

**对话 Agent**（客服、销售、辅导）

比编码 Agent 复杂，因为成功是多维度的。

工单关闭了吗（状态检查）？10 轮内解决了吗（记录约束）？语气合适吗（LLM 评分）？

这三个维度缺一不可。只看工单有没有关闭，忽略了用户体验；只看语气，忽略了实际效果。

**研究 Agent**

最难评，因为"研究质量"本身就是主观的。

Anthropic 的建议是结合多种评分器：基础性检查（关键事实有没有）、覆盖率检查（重要来源有没有引用）、来源质量检查（引用的是不是可信来源）。

而且要注意：研究 Agent 的参考内容会随时间变化，基准事实可能过期，评测套件需要定期更新。

**计算机使用 Agent**

最特殊，因为它直接操作界面——截图、点击、键盘输入。

评测必须在真实或沙箱环境里跑，不能 mock。而且要检查的是最终状态，不是中间步骤——文件有没有保存、表单有没有提交、操作有没有生效。

## 从零搭评测套件：8 步路线图

这是 Anthropic 文章里最实用的部分，我直接整理成可操作的步骤。

**第 0 步：现在就开始，别等**

不需要 100 个任务才能开始。20-50 个从真实失败里提取的任务，就是一个好的起点。

**第 1 步：从手动测试里挖任务**

你每次发布前手动验证的那些行为，就是最好的评测任务来源。把它们写下来，变成自动化任务。

**第 2 步：写清楚任务和参考答案**

好任务的标准：两个领域专家能独立得出相同的通过/失败判断。

每个任务都要有参考答案——一个已知能通过所有评分器的有效输出。

**第 3 步：正反两面都要测**

只测"应该成功的情况"是不够的。还要测"不应该发生的情况"——比如 Agent 不应该泄露用户数据、不应该在没有授权的情况下执行删除操作。

单方面的评估会产生单方面的优化。

**第 4 步：环境隔离**

每次试验都要从干净的环境开始。

残留文件、缓存数据、上次运行留下的状态——这些都会导致测试结果不稳定，让你以为是 Agent 的问题，其实是环境的问题。

**第 5 步：评分器设计要深思熟虑**

优先用代码评分器，必要时用 LLM 评分器，谨慎用人工评分器。

对有多个组件的复杂任务，建立部分分数机制——不是非黑即白，而是"完成了 70%"也是有意义的信息。

**第 6 步：读记录，读记录，读记录**

这一步很多人跳过，但 Anthropic 特别强调。

不读记录，你不知道评分器是否在正确工作。失败应该看起来是"公平的"——Agent 确实犯了错，而不是评分器误判了。

**第 7 步：监控评估饱和度**

当通过率接近 100%，这个评估套件就只能追踪回归，不能提供改进信号了。

这时候需要开发更难的任务，让评估套件继续有区分度。

**第 8 步：把评测套件当产品维护**

评测套件不是一次性的，是需要持续维护的活性产物。

需要明确所有权——谁负责更新任务、谁负责审查新的失败、谁负责决定什么时候需要新的评估维度。

## 评测不是万能的

说了这么多评测的好处，最后说一个容易被忽视的事：**自动化评测只是理解 Agent 性能的一种方式，不是全部。**

Anthropic 列了一张对比表，我觉得很有价值：

自动化评测的优势是快、可复现、不影响用户，可以在每次提交时跑。但它有一个致命弱点——如果评测任务不匹配真实使用模式，你会产生虚假的信心。

生产监控能发现合成评测遗漏的真实问题，但它是被动的，问题到达用户才知道。

A/B 测试能衡量实际用户结果，但慢，而且只能测已经部署的变更。

用户反馈能发现意想不到的问题，但稀疏，而且偏向严重问题。

这几种方式要组合用，就像安全工程里的瑞士奶酪模型——每一层都有漏洞，但叠在一起就能挡住大多数问题。

## 一个可以马上用的 YAML 评测配置

Anthropic 文章里给了一个编码 Agent 的评测配置示例，我觉得可以直接拿来参考：

```yaml
task:
  id: "fix-auth-bypass"
  desc: "修复当密码字段为空时的认证绕过漏洞"
  graders:
    # 代码评分器：测试必须通过
    - type: deterministic_tests
      required: [test_empty_pw_rejected.py, test_null_pw_rejected.py]
    # 模型评分器：代码质量
    - type: llm_rubric
      rubric: prompts/code_quality.md
    # 代码评分器：静态分析
    - type: static_analysis
      commands: [ruff, mypy, bandit]
    # 代码评分器：状态检查
    - type: state_check
      expect:
        security_logs: {event_type: "auth_blocked"}
    # 代码评分器：工具调用验证
    - type: tool_calls
      required:
        - {tool: read_file, params: {path: "src/auth/*"}}
        - {tool: edit_file}
        - {tool: run_tests}
  # 效率指标追踪
  tracked_metrics:
    - type: transcript
      metrics: [n_turns, n_toolcalls, n_total_tokens]
    - type: latency
      metrics: [time_to_first_token, output_tokens_per_sec]
```

注意这个配置里有 5 个评分器，覆盖了功能正确性、代码质量、安全性、状态验证、工具调用五个维度。

这才是生产级评测的样子——不是一个 assert，是一套体系。

## 📝 小结

Anthropic 的评测方法论，核心就几条：

**评分器三选一**：能用代码的用代码，必须主观判断的用 LLM，需要黄金标准的用人工。

**非确定性两个指标**：pass@k 看能力上限，pass^k 看稳定性下限。

**能力评估和回归评估分开**：前者允许失败，后者要求接近 100%。

**8 步路线图**：现在就开始，从手动测试挖任务，正反都测，环境隔离，读记录，监控饱和度，当产品维护。

**评测不是万能的**：和生产监控、A/B 测试、用户反馈组合用，才是完整的质量保障体系。

## 🔮 下一篇预告

Anthropic 的方法论解决了"怎么评"的问题。

但还有一个问题没解决：**评估标准从哪来？**

你做的是一个全新的 Agent，没有历史数据，没有参考答案，不知道"好"的标准是什么——这时候怎么办？

微软研究院给了一个很有意思的答案：让 AI 来定标准。
