> **📖 系列难度说明**：本篇为**数据工程篇**，适合已经跑通基础评测、想扩大测试覆盖面的开发者。
> **🎁 核心收获**：读完本篇你会掌握三种构建评测数据集的方法，以及为什么"忠实度"是 Agent 评测里最容易被忽视、也最容易出问题的指标。

上一篇结尾留了一个问题：

**测试用例从哪来？**

手写 20 个测试用例，能覆盖的场景太有限了。真实用户的输入千变万化，你不可能提前想到所有情况。

更麻烦的是，Agent 最容易出问题的地方，往往不是你能预想到的那些"正常场景"，而是边缘情况——工具返回空结果、用户问了一个模糊的问题、多轮对话中途改变了需求。

这篇讲三种构建评测数据集的方法，以及一个我觉得被严重低估的指标。

## 先说一个真实案例

AWS 的工程师在评测一个旅行规划 Agent 时，发现了一个奇怪的现象。

这个 Agent 的"响应质量"得分是 83.9%——回答清晰、可操作，用户看起来很满意。

但当他们深挖追踪数据之后，发现了一个严重问题：**忠实度只有 32.3%。**

什么意思？Agent 在工具返回空结果的时候，会自己"编"数据——汇率、温度、景点详情，全是捏造的。

用户看到的是一个流畅、自信的回答。实际上里面有大量幻觉。

这个问题用"输出质量"指标完全看不出来。只有追踪到工具调用层面，才能发现 Agent 在空结果上产生了幻觉。

这个案例说明了两件事：

**测试用例要覆盖边缘情况**（工具返回空结果就是一个典型的边缘情况）。

**指标要选对**（光看输出质量不够，还要看忠实度）。

## 三种构建数据集的方法

### 方法一：从生产日志里挖

这是最直接、也最有价值的方法。

真实用户的输入，比你手写的测试用例真实得多。生产日志里藏着你想不到的边缘情况、奇怪的问法、以及 Agent 真实失败的场景。

**怎么挖？**

如果你用了 DeepEval 的追踪功能，生产环境的每次调用都会被记录下来。你可以直接从这些追踪里筛选出有价值的用例：

```python
from deepeval.tracing import observe, update_current_trace
from deepeval.dataset import EvaluationDataset, Golden

# 生产环境：每次调用都被追踪
@observe()
def my_agent(user_input: str) -> str:
    result = run_agent_logic(user_input)
    update_current_trace(
        input=user_input,
        output=result,
        # 关联到 Confident AI 上的数据集，自动收集
        metric_collection="生产环境追踪"
    )
    return result
```

配置好之后，你可以在 Confident AI 平台上按条件筛选追踪记录：

- 筛选出**低分用例**（评测分数低于阈值的）
- 筛选出**工具调用失败的用例**
- 筛选出**用户反馈差的用例**（如果你有用户反馈数据）

把这些用例导出来，加上人工标注的 `expected_output`，就是一批高质量的测试用例。

**为什么这批用例特别有价值？**

因为它们是 Agent 真实失败过的场景。用这些用例做回归测试，能确保你修复了一个 bug 之后，同类问题不会再出现。

### 方法二：用 DeepEval 合成数据

生产日志的问题是：刚上线的 Agent 没有历史数据，而且有些边缘情况在生产环境里出现频率很低，等你收集到足够的样本，可能已经出了很多问题。

DeepEval 提供了合成数据生成功能，可以从你的文档或知识库里自动生成测试用例。

```python
from deepeval.synthesizer import Synthesizer
from deepeval.dataset import EvaluationDataset

# 从文档生成测试用例
synthesizer = Synthesizer()

# 方式一：从文本列表生成
dataset = synthesizer.generate_goldens_from_docs(
    document_paths=["./docs/product_manual.pdf", "./docs/faq.md"],
    include_expected_output=True,  # 同时生成参考答案
    max_goldens_per_document=20,   # 每个文档生成 20 个用例
)

# 方式二：从上下文列表生成
dataset = synthesizer.generate_goldens_from_contexts(
    contexts=[
        ["退款政策：30天内可全额退款，超过30天不予退款。"],
        ["配送时间：普通快递3-5天，加急快递1-2天。"],
    ],
    include_expected_output=True,
)

# 保存数据集
dataset.push(alias="客服 Agent 测试集 v1")
```

合成数据的优势是**可以定向生成边缘情况**。

比如你知道 Agent 在处理"退款超期"这类边界情况时容易出问题，可以专门生成这类用例：

```python
# 生成针对特定场景的测试用例
dataset = synthesizer.generate_goldens_from_contexts(
    contexts=[
        ["退款政策：30天内可全额退款。"],
    ],
    # 指定生成的问题类型
    evolutions={
        "边界情况": 0.4,   # 40% 生成边界情况（如"第31天能退吗"）
        "对抗性问题": 0.3,  # 30% 生成对抗性问题（如"你们的退款政策是骗人的"）
        "模糊问题": 0.3,    # 30% 生成模糊问题（如"我想退"）
    },
    max_goldens_per_context=10,
)
```

### 方法三：用 Agent-EvalKit 自动生成

AWS 的 Agent-EvalKit 走了另一条路：**让 AI 读你的代码，然后自动生成测试用例。**

这个思路很有意思。它不是从文档生成，而是直接分析 Agent 的源代码——工具定义、调用逻辑、错误处理——然后针对代码里的每个分支生成对应的测试用例。

```bash
# 安装
uv tool install evalkit --from git+https://github.com/awslabs/Agent-EvalKit.git

# 初始化评估项目
evalkit init my-agent-evaluation
cd my-agent-evaluation

# 把你的 Agent 代码复制进来
cp -r /path/to/your/agent .

# 启动 AI 助手（Claude Code）
claude
```

然后用自然语言告诉它你想评测什么：

```bash
# 快速模式：一键跑完所有阶段
/evalkit.quick 评估 ./travel_agent 的响应质量、工具参数准确性和忠实度

# 或者分阶段精细控制
/evalkit.plan 评估 ./travel_agent 的忠实度，重点关注工具返回空结果的情况
/evalkit.data   # 生成测试用例
/evalkit.trace  # 添加 OpenTelemetry 追踪
/evalkit.run_agent  # 运行 Agent
/evalkit.eval   # 计算指标
/evalkit.report # 生成报告
```

Agent-EvalKit 生成的测试用例有个特点：**它会针对代码里的错误处理路径专门生成用例。**

比如你的 Agent 代码里有这样一段：

```python
def get_exchange_rate(from_currency, to_currency):
    result = call_exchange_api(from_currency, to_currency)
    if not result:
        # 这里没有处理空结果，直接返回 None
        return None
```

Agent-EvalKit 会识别出这个潜在问题，生成一个"汇率 API 返回空结果"的测试用例，专门测试 Agent 在这种情况下会不会产生幻觉。

这正是 AWS 工程师发现旅行 Agent 忠实度只有 32.3% 的方式。

## 忠实度：最容易被忽视的指标

说到这里，不得不重点讲一下忠实度（Faithfulness）这个指标。

**忠实度衡量的是：Agent 的回答是否基于工具实际返回的数据。**

听起来很基础，但这个指标在实际项目里被忽视的程度，超出你的想象。

大多数团队评测 Agent 的时候，只看两件事：回答质量（好不好）和工具调用（对不对）。忠实度很少被单独评测。

结果就是：Agent 的回答看起来很好，工具也调对了，但回答里的数据和工具返回的数据对不上——Agent 在"编"。

用 DeepEval 评测忠实度很简单：

```python
from deepeval.test_case import LLMTestCase
from deepeval.metrics import FaithfulnessMetric
from deepeval import evaluate

# 关键：retrieval_context 是工具实际返回的数据
test_case = LLMTestCase(
    input="东京到上海的机票大概多少钱？",
    actual_output="东京到上海的经济舱机票大约在 ¥2,800 到 ¥4,500 之间，具体价格取决于出发日期和航空公司。",
    # 这是工具实际返回的数据
    retrieval_context=[
        "查询结果：东京（NRT）→ 上海（PVG），2026-08-15，经济舱，最低价 ¥3,200（国航），最高价 ¥4,100（全日空）。"
    ]
)

metric = FaithfulnessMetric(threshold=0.7)
evaluate(test_cases=[test_case], metrics=[metric])
```

`FaithfulnessMetric` 会检查 `actual_output` 里的每一个声明，看它是否能从 `retrieval_context` 里找到依据。

上面这个例子，Agent 说"¥2,800 到 ¥4,500"，但工具返回的是"¥3,200 到 ¥4,100"——下限偏低了，忠实度会扣分。

## 一个完整的数据集构建流程

把三种方法结合起来，是这样的：

```
阶段一：冷启动（没有生产数据）
  ↓
  用 Agent-EvalKit 分析代码，自动生成 50-100 个测试用例
  + 用 DeepEval Synthesizer 从文档生成 50 个用例
  ↓
  人工审核，筛选出有价值的用例，标注 expected_output
  ↓
  得到初始数据集（约 80-120 个用例）

阶段二：上线后持续扩充
  ↓
  生产环境追踪，自动收集每次调用
  ↓
  每周从低分用例、失败用例里筛选 10-20 个
  ↓
  加入数据集，更新版本
  ↓
  数据集持续增长，覆盖面越来越广
```

代码层面，用 DeepEval 管理数据集版本：

```python
from deepeval.dataset import EvaluationDataset, Golden

# 加载已有数据集
dataset = EvaluationDataset()
dataset.pull(alias="客服 Agent 测试集 v1")

# 添加新用例
new_goldens = [
    Golden(
        input="我的订单已经超过30天了，还能退款吗？",
        expected_output="非常抱歉，根据我们的退款政策，超过30天的订单无法申请退款。如有特殊情况，您可以联系客服说明情况。"
    ),
    Golden(
        input="退款",  # 模糊输入
        expected_output="您好，请问您需要申请退款吗？能告诉我您的订单号吗？"
    ),
]
dataset.add_goldens(new_goldens)

# 推送新版本
dataset.push(alias="客服 Agent 测试集 v2")
```

## 数据集质量比数量更重要

有一个误区要说清楚：**数据集不是越大越好。**

100 个精心设计的测试用例，比 1000 个随机生成的用例有价值得多。

判断一个测试用例是否有价值，看三点：

**覆盖了真实的失败场景吗？** 如果这个用例 Agent 从来不会失败，它的价值就很低。

**有明确的 expected_output 吗？** 没有参考答案的用例，评测的时候只能用 LLM 来判断，可信度会下降。

**边缘情况覆盖了吗？** 正常场景 Agent 一般都能处理，真正考验 Agent 的是边缘情况——空结果、模糊输入、多步骤任务中途失败。

所以我的建议是：**数据集里至少 30% 是边缘情况和失败场景。**

---

## 一个容易踩的坑

用合成数据的时候，有一个坑很多人踩过。

合成数据生成的 `expected_output` 是 LLM 生成的，不是人工标注的。

这意味着：如果你的 Agent 和生成 `expected_output` 的 LLM 用的是同一个模型，评测结果会虚高——因为两者的"思维方式"是一样的，Agent 的输出和参考答案会高度相似，但这不代表 Agent 真的做对了。

解决方法：**合成数据生成后，必须人工审核 expected_output。**

不需要全部审核，抽查 20-30% 就够了。重点看那些边缘情况和对抗性问题的参考答案是否合理。

---

## 📝 小结

三种构建评测数据集的方法：

**生产日志挖掘**：最真实，覆盖 Agent 真实失败的场景。适合上线后持续扩充数据集。

**DeepEval 合成数据**：从文档生成，可以定向生成边缘情况。适合冷启动阶段。

**Agent-EvalKit 自动生成**：分析代码逻辑，针对错误处理路径生成用例。适合发现代码层面的潜在问题。

三种方法结合用效果最好：Agent-EvalKit + Synthesizer 解决冷启动，生产日志持续扩充。

别忘了忠实度（Faithfulness）这个指标——Agent 回答质量高不代表没有幻觉，只有追踪到工具调用层面，才能发现 Agent 有没有在"编"数据。

数据集质量比数量重要，至少 30% 是边缘情况，合成数据的 expected_output 要人工抽查。
