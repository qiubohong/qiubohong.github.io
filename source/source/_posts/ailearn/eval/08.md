> **📖 系列难度说明**：本篇为**进阶挑战篇**，适合正在构建或评测多 Agent 系统的开发者。
> **🎁 核心收获**：读完本篇你会理解多 Agent 评测的核心难题是什么，微软 AgentEval 怎么用 AI 来评测 AI，以及怎么在实际项目里落地多 Agent 评测。

七篇讲下来，单个 Agent 的评测体系算是搭完了。

但现实是，越来越多的系统不是一个 Agent 在跑，而是一群 Agent 在协作。

一个 Agent 负责搜索，一个负责分析，一个负责生成报告，还有一个负责审核。

这时候评测就变了。

## 多 Agent 系统的评测难在哪

单个 Agent 出了问题，你能查日志找原因：工具调用错了，还是生成出了幻觉，还是上下文理解偏了。

多个 Agent 协作出了问题，你不知道该怪谁。

这就是多 Agent 评测最核心的挑战：**失败归因（Failure Attribution）**。

举个具体的例子。

你有一个内容生产系统，三个 Agent 串联工作：

```
ResearchAgent（搜索资料）
    ↓
WritingAgent（撰写内容）
    ↓
ReviewAgent（审核质量）
```

最终输出的内容质量很差。

是 ResearchAgent 搜到的资料不准确？

还是 WritingAgent 没有正确理解资料？

还是 ReviewAgent 审核标准太宽松，放过了低质量内容？

三个 Agent，三种可能。如果你只看最终输出，根本无法判断。

---

## 为什么单 Agent 的评测方法不够用

前几篇讲的评测方法，核心假设是：**有一个明确的输入，有一个明确的输出，评测这个输入-输出对。**

多 Agent 系统打破了这个假设。

**中间状态太多。** 每个 Agent 都有自己的输入和输出，这些中间状态都可能影响最终结果。

**依赖关系复杂。** Agent A 的输出是 Agent B 的输入。A 出了问题，B 的评测结果也会受影响。你不知道 B 的低分是 B 自己的问题，还是 A 传过来的问题。

**没有标准答案。** 单个 Agent 的评测，你可以设定 expected_output。多 Agent 系统的中间状态，很难预先定义"正确的中间结果应该是什么"。

**评测成本爆炸。** 三个 Agent 的系统，如果每个 Agent 都要单独评测，评测成本是单 Agent 的三倍以上（还要加上系统级评测）。

---

## 微软的思路：用 AI 来评测 AI

面对这个问题，微软研究院提出了一个有意思的思路：**既然 Agent 很难评测，那就用 Agent 来评测 Agent。**

这就是 **AgentEval** 框架的核心想法。

不是人工设计评测标准，而是让 AI 自动生成评测标准。不是人工打分，而是让 AI 来打分。

听起来有点绕，但逻辑是通的：

- 人工设计评测标准，需要领域专家，成本高，而且很难覆盖所有场景
- 让 AI 根据任务描述自动生成标准，可以快速适应新任务，不需要领域专家

微软在两个数据集上验证了这个思路：
- **数学问题求解**（MATH 数据集，12,500 道高中竞赛题）
- **ALFWorld 家务任务**（模拟家庭环境中的多轮交互）

结果是：AgentEval 生成的评测标准，能够区分不同解决方案的性能，而且和人工评测的结论高度一致。

## AgentEval 的三个智能体

AgentEval 框架由三个智能体组成，分工明确。

### CriticAgent：定标准

CriticAgent 的工作是：给它一个任务描述，以及几个成功/失败的例子，它会自动生成一套评测标准。

比如评测一个数学辅导 Agent，CriticAgent 可能会生成这样的标准：

| 标准 | 接受值 |
|------|--------|
| 准确性 | 正确、轻微错误、重大错误、不正确 |
| 简洁性 | 非常简洁、简洁、有些冗长、冗长 |
| 清晰度 | 非常清晰、清晰、有些不清晰、不清晰 |
| 完整性 | 完整、部分完整、不完整 |

这些标准不是人工预设的，是 CriticAgent 根据任务特点自动推导出来的。

用代码实现：

```python
import autogen
from autogen.agentchat.contrib.agent_eval.task import Task
from autogen.agentchat.contrib.agent_eval.agent_eval import generate_criteria

config_list = autogen.config_list_from_json("OAI_CONFIG_LIST")

# 定义任务
task = Task(**{
    "name": "内容质量评测",
    "description": "给定一篇 AI 生成的文章，系统需要评估其质量",
    "successful_response": """
    # 量子计算入门

    量子计算利用量子力学原理，通过量子比特（qubit）进行计算。
    与经典比特只能是 0 或 1 不同，量子比特可以同时处于 0 和 1 的叠加态。
    这使得量子计算机在处理特定问题时，速度远超经典计算机。

    主要应用场景：密码学、药物研发、优化问题。
    """,
    "failed_response": """
    量子计算是一种计算方式。它很厉害，可以做很多事情。
    量子比特和普通比特不一样。量子计算机很快。
    """,
})

# 让 CriticAgent 自动生成评测标准
criteria = generate_criteria(
    task=task,
    llm_config={"config_list": config_list}
)

print(criteria)
```

输出的标准大概长这样：

```json

    {

        "description": "内容中的技术信息是否准确，有无明显错误",

    },
    {
        "name": "深度",

        "accepted_values": ["深入", "适中", "浅显", "过于简单"]
    },
    {
        "name": "可读性",
        "description": "内容是否易于理解，结构是否清晰",
        "accepted_values": ["非常易读", "易读", "有些难懂", "难以理解"]
    }
]
```

### QuantifierAgent：打分数

有了标准，QuantifierAgent 负责对每个测试用例打分。

```python
from autogen.agentchat.contrib.agent_eval.agent_eval import quantify_criteria

# 要评测的内容
test_case = """
量子计算是利用量子力学现象（如叠加和纠缠）来处理信息的计算方式。
量子比特（qubit）是量子计算的基本单位，与经典比特不同，它可以同时表示 0 和 1。
这种特性使量子计算机在解决某些特定问题时，如大数分解和数据库搜索，
比经典计算机快得多。目前，量子计算主要应用于密码学、材料科学和优化问题。
"""

# 打分
result = quantify_criteria(
    llm_config={"config_list": config_list},
    criteria=criteria,
    task=task,
    test_case=test_case,
    ground_truth="量子计算的准确技术描述"
)

print(result)
# 输出：
# {
#   "actual_success": true,
#   "estimated_performance": {
#       "准确性": "高度准确",
#       "深度": "适中",
#       "可读性": "非常易读"
#   }
# }
```

### VerifierAgent：验质量

VerifierAgent 是整个框架里最有意思的部分。

它的工作是验证 CriticAgent 生成的标准是否靠谱。

怎么验证？两个方法：

**稳定性测试**：对同一个测试用例跑多次，看 QuantifierAgent 的打分是否一致。如果同一个内容，今天打"高度准确"，明天打"有些错误"，说明这个标准不稳定，需要重新生成。

**对抗性测试**：故意引入一个明显低质量的内容（比如把正确答案改错），看 QuantifierAgent 能不能识别出来。如果识别不出来，说明这个标准的判别力不够。

```python
# VerifierAgent 的对抗性测试
adversarial_case = """
量子计算使用量子比特，量子比特可以是 0 或 1（和经典比特一样）。
量子计算机比普通计算机快，因为它们使用了更好的芯片。
量子计算主要用于游戏和社交媒体。
"""
# 这个内容有明显错误：量子比特的描述错了，应用场景也错了

adversarial_result = quantify_criteria(
    llm_config={"config_list": config_list},
    criteria=criteria,
    task=task,
    test_case=adversarial_case,
    ground_truth="量子计算的准确技术描述"
)

# 如果 VerifierAgent 发现 QuantifierAgent 给这个明显错误的内容打了高分
# 就会触发标准重新生成
```

## 多 Agent 系统的评测策略

理解了 AgentEval 的思路，回到最开始的问题：多 Agent 系统怎么评测？

有三种策略，各有适用场景。

### 策略一：端到端评测 + 失败归因

最简单的方案：先做端到端评测，发现问题后再做失败归因。

```python
from deepeval import evaluate
from deepeval.test_case import LLMTestCase, ToolCall
from deepeval.metrics import AgentGoalCompletionMetric, FaithfulnessMetric

# 第一步：端到端评测
def test_multi_agent_system_e2e():
    # 运行整个多 Agent 系统
    result = run_content_pipeline(
        topic="量子计算入门",
        target_audience="技术爱好者"
    )

    test_case = LLMTestCase(
        input="写一篇关于量子计算的入门文章",
        actual_output=result["final_content"],
        tools_called=result["all_tools_called"],  # 所有 Agent 的工具调用
    )

    metric = AgentGoalCompletionMetric(threshold=0.7)
    results = evaluate(test_cases=[test_case], metrics=[metric])

    # 如果端到端评测不通过，进入失败归因
    if results.metrics_data["AgentGoalCompletionMetric"].avg_score < 0.7:
        diagnose_failure(result)

def diagnose_failure(pipeline_result: dict):
    """失败归因：逐个检查每个 Agent 的输出"""

    # 检查 ResearchAgent 的输出
    research_quality = evaluate_research_output(
        query=pipeline_result["research_query"],
        research_result=pipeline_result["research_output"]
    )

    # 检查 WritingAgent 的输出
    writing_quality = evaluate_writing_output(
        research_input=pipeline_result["research_output"],
        writing_result=pipeline_result["writing_output"]
    )

    # 检查 ReviewAgent 的输出
    review_quality = evaluate_review_output(
        content_input=pipeline_result["writing_output"],
        review_result=pipeline_result["review_output"]
    )

    print(f"ResearchAgent 质量：{research_quality:.2%}")
    print(f"WritingAgent 质量：{writing_quality:.2%}")
    print(f"ReviewAgent 质量：{review_quality:.2%}")

    # 找出最低分的 Agent，优先修复
    scores = {
        "ResearchAgent": research_quality,
        "WritingAgent": writing_quality,
        "ReviewAgent": review_quality,
    }
    worst_agent = min(scores, key=scores.get)
    print(f"\n优先修复：{worst_agent}（得分 {scores[worst_agent]:.2%}）")
```

### 策略二：分层评测

对每个 Agent 单独建立评测，然后组合成系统级评测。

```python
import pytest
from deepeval import assert_test
from deepeval.test_case import LLMTestCase
from deepeval.metrics import FaithfulnessMetric, GEval, SingleTurnParams

# 第一层：ResearchAgent 评测
class TestResearchAgent:
    def test_search_relevance(self):
        """搜索结果是否和查询相关"""
        result = research_agent.search("量子计算应用场景")

        test_case = LLMTestCase(
            input="量子计算应用场景",
            actual_output=result,
        )

        relevance_metric = GEval(
            name="搜索相关性",
            criteria="搜索结果是否与查询词高度相关，是否覆盖了主要应用场景",
            evaluation_params=[SingleTurnParams.INPUT, SingleTurnParams.ACTUAL_OUTPUT],
            threshold=0.8
        )

        assert_test(test_case, [relevance_metric])

    def test_search_accuracy(self):
        """搜索结果是否准确，有无明显错误"""
        result = research_agent.search("量子比特的基本原理")

        test_case = LLMTestCase(
            input="量子比特的基本原理",
            actual_output=result,
            retrieval_context=["量子比特可以同时处于0和1的叠加态"]  # 参考答案
        )

        faithfulness_metric = FaithfulnessMetric(threshold=0.8)
        assert_test(test_case, [faithfulness_metric])


# 第二层：WritingAgent 评测
class TestWritingAgent:
    def test_content_quality(self):
        """生成内容是否准确使用了研究资料"""
        research_data = [
            "量子比特可以同时处于0和1的叠加态",
            "量子纠缠允许量子比特之间的即时关联",
            "量子计算在密码学领域有重要应用"
        ]
        content = writing_agent.write(
            topic="量子计算入门",
            research_data=research_data
        )

        test_case = LLMTestCase(
            input="量子计算入门",
            actual_output=content,
            retrieval_context=research_data
        )

        faithfulness_metric = FaithfulnessMetric(threshold=0.8)
        assert_test(test_case, [faithfulness_metric])


# 第三层：系统级评测
class TestContentPipeline:
    def test_end_to_end_quality(self):
        """整个流水线的最终输出质量"""
        final_content = run_content_pipeline(
            topic="量子计算入门",
            target_audience="技术爱好者"
        )

        test_case = LLMTestCase(
            input="写一篇面向技术爱好者的量子计算入门文章",
            actual_output=final_content["content"],
        )

        quality_metric = GEval(
            name="内容综合质量",
            criteria="文章是否准确、深入、易读，是否适合技术爱好者阅读",
            evaluation_params=[SingleTurnParams.INPUT, SingleTurnParams.ACTUAL_OUTPUT],
            threshold=0.75
        )

        assert_test(test_case, [quality_metric])
```

### 策略三：用生成式智能体模拟用户评测

这是最接近真实用户体验的评测方式。

思路来自 arXiv 的一篇论文：用生成式智能体模拟不同类型的用户，让这些"虚拟用户"来评测 Agent 的输出。

```python
from deepeval.test_case import LLMTestCase, SingleTurnParams
from deepeval.metrics import GEval

# 模拟不同类型的用户
USER_PERSONAS = [
    {
        "name": "技术小白",
        "description": "对量子计算完全不了解，希望看完能有基本概念",
        "criteria": "文章是否用通俗易懂的语言解释了量子计算的基本概念，没有过多专业术语"
    },
    {
        "name": "技术爱好者",
        "description": "有一定编程基础，想了解量子计算的技术细节",
        "criteria": "文章是否提供了足够的技术深度，包括量子比特、叠加态、纠缠等核心概念的准确解释"
    },
    {
        "name": "业务决策者",
        "description": "关注量子计算的商业应用和投资价值",
        "criteria": "文章是否清晰说明了量子计算的实际应用场景和商业价值"
    }
]

def evaluate_with_personas(content: str, topic: str) -> dict:
    """用不同用户画像评测内容质量"""

    results = {}

    for persona in USER_PERSONAS:
        test_case = LLMTestCase(
            input=f"作为{persona['name']}，我想了解{topic}",
            actual_output=content,
        )

        metric = GEval(
            name=f"{persona['name']}满意度",
            criteria=persona["criteria"],
            evaluation_params=[SingleTurnParams.INPUT, SingleTurnParams.ACTUAL_OUTPUT],
            threshold=0.7
        )

        metric.measure(test_case)
        results[persona["name"]] = {
            "score": metric.score,
            "reason": metric.reason
        }

    return results

# 使用
content = run_content_pipeline("量子计算入门")["content"]
persona_results = evaluate_with_personas(content, "量子计算")

for persona, result in persona_results.items():
    print(f"{persona}：{result['score']:.2%}")
    print(f"  原因：{result['reason']}\n")
```

## 一个真实的踩坑经历

用 AI 评测 AI，有一个坑很多人会踩：**评判模型和被评测模型用同一个，结果会偏高。**

微软在 AgentEval 的实验里发现了这个问题。

用 GPT-4 评测 GPT-4 生成的内容，分数普遍偏高。因为同一个模型对自己的输出风格更"熟悉"，更容易给高分。

解决方法有两个：

**换一个不同系列的模型来评判。** 比如被评测的 Agent 用 GPT-4，评判模型用 Claude。两个不同公司的模型，风格差异大，评判结果更客观。

**加入人工校准。** 定期抽取一批样本，让人工打分，和 AI 评判的分数对比。如果两者差距超过 15%，说明评判模型需要重新校准。

```python
# 使用不同系列的模型作为评判
from deepeval.metrics import GEval

# 被评测的 Agent 用 GPT-4o
# 评判模型用 Claude
metric = GEval(
    name="内容质量",
    criteria="内容是否准确、深入、易读",
    evaluation_params=[SingleTurnParams.INPUT, SingleTurnParams.ACTUAL_OUTPUT],
    threshold=0.7,
    model="claude-opus-4-5"  # 用不同系列的模型评判
)
```

## 多 Agent 评测的成本问题

多 Agent 系统的评测成本，比单 Agent 高得多。

三个 Agent 的系统，如果每个 Agent 都要单独评测，加上系统级评测，一次完整评测可能要调用 LLM 10 次以上。

几个控制成本的思路：

**分层触发。** 平时只跑系统级评测（成本低）。系统级评测不通过时，才触发分层评测（成本高）。

**缓存评判结果。** 如果同一个 Agent 的输出没有变化，不需要重新评判。把评判结果缓存起来，只对变化的部分重新评测。

**关键路径优先。** 不是所有 Agent 都同等重要。找出对最终结果影响最大的 Agent，优先评测这些关键节点。

```python
# 分层触发的评测策略
def run_smart_evaluation(pipeline_result: dict) -> dict:
    """智能评测：先跑系统级，不通过再分层"""

    # 第一层：系统级评测（便宜）
    system_score = evaluate_system_level(pipeline_result)

    if system_score >= 0.75:
        # 系统级通过，不需要分层评测
        return {"system_score": system_score, "status": "passed"}

    # 第二层：分层评测（贵，但只在系统级不通过时才跑）
    agent_scores = {}
    for agent_name, agent_output in pipeline_result["agent_outputs"].items():
        agent_scores[agent_name] = evaluate_agent_level(
            agent_name=agent_name,
            agent_output=agent_output
        )

    # 找出最差的 Agent
    worst_agent = min(agent_scores, key=agent_scores.get)

    return {
        "system_score": system_score,
        "agent_scores": agent_scores,
        "worst_agent": worst_agent,
        "status": "failed",
        "action": f"优先修复 {worst_agent}"
    }
```

## 目前行业的现状

说实话，多 Agent 系统的评测，目前整个行业都还在摸索。

没有一套被广泛认可的标准方法。

微软的 AgentEval 是目前最系统的学术方案，但它主要解决的是"评测标准怎么生成"的问题，对于"失败归因"这个核心难题，还没有完美的答案。

DeepEval 提供了工具层面的支持（`@observe` 装饰器、Span 级别的评测），但怎么用这些工具设计多 Agent 评测方案，还需要开发者自己摸索。

AWS Agent-EvalKit 的 OTel 追踪方案，在追踪层面做得很好，但评测指标的设计还比较基础。

目前比较务实的做法是：

**先把单 Agent 评测做扎实。** 每个 Agent 都有自己的评测，有明确的质量基线。

**系统级评测作为集成测试。** 把整个多 Agent 系统当成一个黑盒，评测最终输出质量。

**失败时手动归因。** 当系统级评测不通过时，手动检查每个 Agent 的中间输出，找出问题所在。

这不是最优雅的方案，但是目前最可落地的方案。

---

## 📝 小结

多 Agent 系统的评测，核心难题是失败归因。

微软 AgentEval 的思路是用 AI 来评测 AI——CriticAgent 自动生成评测标准，QuantifierAgent 打分，VerifierAgent 验证标准质量。这个思路解决了"评测标准怎么来"的问题，但失败归因还需要配合分层评测来做。

实际落地的时候，三个策略可以组合使用：

- **端到端评测 + 失败归因**：先看整体，出问题再深挖
- **分层评测**：每个 Agent 单独建立评测，组合成系统级评测
- **生成式智能体模拟用户**：用不同用户画像来评测，更接近真实体验

还有一个坑要注意：用同一个模型评测自己的输出，分数会偏高。评判模型最好和被评测模型用不同系列。
