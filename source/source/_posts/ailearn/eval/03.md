> **📖 系列难度说明**：本篇为**框架拆解篇**，适合想深入理解 Agent 评测方法论的开发者。
> **🎁 核心收获**：读完本篇你会理解 AgentEval 三智能体架构的设计逻辑，以及如何用代码跑通标准生成和量化打分两个核心流程。

上一篇讲 Anthropic 的评测方法论，有读者问了一个很好的问题：

**评估标准从哪来？**

Anthropic 的方案是人工设计评分器——代码评分器、LLM 评分器、人工评分器，三类组合用。但这有个前提：你得知道要评什么。

如果你做的是一个全新场景的 Agent，没有历史数据，没有参考案例，不知道"好"的标准长什么样——这时候怎么办？

微软研究院给了一个很有意思的答案：**让 AI 自己来定标准。**

<!-- more -->

---

## 一个让人意外的思路

2024 年，微软研究院和滑铁卢大学联合发了一篇论文，提出了 AgentEval 框架。

核心思路说起来很简单：既然 LLM 能理解任务，那它也能理解"什么叫把这个任务做好"。

所以不需要人工预设评估标准，直接把任务描述扔给 LLM，让它自己生成一套评估维度，然后用这套维度给 Agent 的输出打分。

听起来有点"让 AI 给 AI 打分"的感觉，确实是这样。

但这个思路解决了一个真实的痛点——**评估标准的冷启动问题**。

你不需要是领域专家，不需要提前知道"好的数学辅导应该满足哪些条件"，AgentEval 会帮你想清楚。

---

## 三个智能体，各司其职

AgentEval 的架构由三个 LLM 智能体组成，分工很清晰。

### CriticAgent：负责"想清楚要评什么"

CriticAgent 是整个流程的起点。

你给它两样东西：任务描述，以及几个成功和失败的执行示例。它会输出一套评估标准，每个标准带着可接受的值域。

拿数学辅导 Agent 举例，CriticAgent 生成的标准大概长这样：

| 标准 | 可接受的值 |
|------|-----------|
| 准确性 | 正确 / 轻微错误 / 重大错误 / 不正确 |
| 简洁性 | 非常简洁 / 简洁 / 有些冗长 / 冗长 |
| 清晰度 | 非常清晰 / 清晰 / 有些不清晰 / 不清晰 |
| 效率 | 高效 / 适中 / 低效 |
| 完整性 | 完整 / 部分完整 / 不完整 |

注意这里的设计——每个标准不是简单的 0/1，而是一个有序的值域。这样打出来的分数是有梯度的，不是非黑即白。

### QuantifierAgent：负责"按标准打分"

标准有了，QuantifierAgent 接手。

它拿着 CriticAgent 生成的标准，对 Agent 的每一次执行记录逐条打分。

输出长这样：

```json
{
  "actual_success": true,
  "estimated_performance": {
    "准确性": "正确",
    "简洁性": "简洁",
    "清晰度": "非常清晰",
    "效率": "高效",
    "完整性": "完整"
  }
}
```

这里有个细节值得注意：`actual_success` 是任务有没有完成，`estimated_performance` 是完成得怎么样。

两个都重要。任务完成了，但解释得一塌糊涂，这对用户来说也是差体验。

### VerifierAgent：负责"确认标准靠不靠谱"

这是 AgentEval 里最容易被忽视、但其实最关键的一环。

CriticAgent 生成的标准不一定都好用。可能有些标准是冗余的（"准确性"和"正确性"其实说的是同一件事），可能有些标准区分度太低（所有 Agent 在这个维度上都得"高效"，没有区分意义）。

VerifierAgent 做两件事：

**检查稳定性**：同一个样本跑多次，看 QuantifierAgent 的打分结果是否一致。如果同一个输出今天打"简洁"、明天打"冗长"，这个标准就不可信。

**检查判别力**：引入对抗性样本（故意加了噪声或错误的输出），看 QuantifierAgent 能不能把它和正常输出区分开。如果区分不了，说明这个标准没有实际意义。

经过 VerifierAgent 筛选后，留下来的标准才是真正有用的评估维度。

---

## 为什么这个思路是对的

我第一次看到这个框架的时候，有点将信将疑。

让 LLM 自己生成评估标准，这靠谱吗？

后来看了他们的实验数据，改变了想法。

微软研究院在两个数据集上验证了 AgentEval：

**数学问题求解**：12,500 道高中竞赛数学题，对比了三种解法——AutoGen 多智能体、LangChain ReAct、直接用 GPT-4。

结果是：AgentEval 不仅能区分三种解法的性能差异，还能在两种解法都"成功"的情况下，发现它们在清晰度、效率等维度上的细微差别。

这是纯粹的成功/失败指标做不到的。

**ALFWorld 家务任务**：模拟家庭环境里的多轮交互决策，对比了 ReAct、AutoGen 双智能体、AutoGen 三智能体。

同样的结论：AgentEval 能给出比"完成率"更细粒度的评估。

更重要的是，这两个数据集是完全不同的领域——一个是数学，一个是家务。AgentEval 在两个领域都跑通了，说明这个框架确实有泛化能力，不是针对特定场景调出来的。

## 动手跑一遍

理论说完了，看代码。

AgentEval 已经集成进了 AutoGen 库，用起来不复杂。

### 第一步：定义任务

```python
import autogen
from autogen.agentchat.contrib.agent_eval.task import Task
from autogen.agentchat.contrib.agent_eval.agent_eval import generate_criteria, quantify_criteria

config_list = autogen.config_list_from_json("OAI_CONFIG_LIST")

# 定义要评测的任务
task = Task(
    **{
        "name": "数学问题求解",
        "description": "给定任何数学问题，系统需要尽可能简洁准确地解决问题",
        # 一个成功的执行示例
        "successful_response": """
        问题：求 x² - 5x + 6 = 0 的解
        解：使用因式分解法
        x² - 5x + 6 = (x-2)(x-3) = 0
        所以 x = 2 或 x = 3
        """,
        # 一个失败的执行示例
        "failed_response": """
        问题：求 x² - 5x + 6 = 0 的解
        解：这是一个二次方程，我需要用求根公式...
        （计算过程冗长且出现错误）
        x ≈ 2.1 或 x ≈ 2.9（错误答案）
        """,
    }
)
```

### 第二步：生成评估标准

```python
# CriticAgent 自动生成评估标准
criteria = generate_criteria(
    task=task,
    llm_config={"config_list": config_list}
)

# 打印生成的标准
for criterion in criteria:
    print(f"标准：{criterion['name']}")
    print(f"描述：{criterion['description']}")
    print(f"可接受值：{criterion['accepted_values']}")
    print("---")
```

输出大概长这样：

```
标准：准确性
描述：解决方案必须正确，并严格遵守适合该问题的数学原理
可接受值：['正确', '轻微错误', '重大错误', '不正确']
---
标准：简洁性
描述：提供的解释和方法应该直接切题，避免不必要的步骤
可接受值：['非常简洁', '简洁', '有些冗长', '冗长']
---
标准：相关性
描述：回应内容必须与所提问题相关，并应解决具体的问题要求
可接受值：['高度相关', '相关', '有些相关', '不相关']
```

### 第三步：对实际输出打分

```python
# 要评测的 Agent 输出
test_case = """
问题：求 x² - 5x + 6 = 0 的解
Agent 回答：
因式分解：(x-2)(x-3) = 0
x = 2 或 x = 3
"""

ground_truth = "x = 2 或 x = 3"

# QuantifierAgent 打分
result = quantify_criteria(
    llm_config={"config_list": config_list},
    criteria=criteria,
    task=task,
    test_case=test_case,
    ground_truth=ground_truth,
)

print(result)
# 输出：
# {
#   "actual_success": true,
#   "estimated_performance": {
#     "准确性": "正确",
#     "简洁性": "非常简洁",
#     "相关性": "高度相关"
#   }
# }
```

三步跑完，你就拿到了一个多维度的评测结果。

## 这个框架的边界在哪

用了一段时间之后，我觉得 AgentEval 有几个地方需要注意。

**它适合"成功有明确定义"的任务。**

AgentEval 的论文里说得很清楚：框架目前专注于成功可以明确判断的任务，比如数学题（答案对不对是清楚的）、家务任务（有没有完成是清楚的）。

如果你做的是"帮我写一封邮件"这种开放式任务，成功本身就是模糊的，AgentEval 生成的标准可信度会下降。

**CriticAgent 生成的标准需要人工审核。**

微软研究院在文章里特别强调了这一点：**强烈建议应用开发者利用其领域专业知识对建议的标准进行验证。**

这不是客套话。我自己跑过几次，CriticAgent 有时候会生成一些听起来合理但实际上没有区分度的标准。比如"相关性"——几乎所有 Agent 的输出都会被打"高度相关"，这个标准就没什么用。

VerifierAgent 能帮你过滤掉一部分，但不是全部。最终还是需要人来判断哪些标准真正有价值。

**打分结果是定性的，不是定量的。**

"准确性：正确"、"简洁性：简洁"——这些是文字标签，不是数字。

如果你想做横向比较（比如 Agent A 的平均分 vs Agent B 的平均分），需要自己把这些标签转换成数值。这一步 AgentEval 没有帮你做。

## 和 Anthropic 方法论的对比

读到这里，你可能会想：AgentEval 和上一篇讲的 Anthropic 方法论，到底有什么区别？

说白了，两者解决的是不同阶段的问题。

**Anthropic 的方法论**解决的是"已经知道要评什么，怎么评得更严格"——评分器怎么设计、非确定性怎么处理、评测套件怎么维护。

**AgentEval** 解决的是"还不知道要评什么，怎么快速生成一套评估标准"——冷启动问题。

实际项目里，两者可以结合用：

用 AgentEval 的 CriticAgent 快速生成初始标准，人工审核筛选，然后按 Anthropic 的方法论把这些标准落地成具体的评分器。

这样既解决了冷启动，又保证了评测的严格性。

---

## 一个容易被忽视的细节

AgentEval 论文里有一个数据，我觉得很能说明问题。

在数学问题求解的实验里，AutoGen、LangChain ReAct、Vanilla GPT-4 三种方案的"任务完成率"差距并不大。

但用 AgentEval 的多维度评估之后，差距就出来了——AutoGen 在准确性上明显优于另外两种，而在简洁性上，Vanilla GPT-4 反而更好。

这说明什么？

**单一的成功/失败指标会掩盖很多信息。** 你以为三种方案差不多，其实它们各有优劣，只是在不同维度上。

如果你只看完成率，你会选哪个都无所谓。但如果你的用户特别在意解释的简洁性，那 Vanilla GPT-4 可能才是更好的选择。

评测的价值，就在这里。

---

## 📝 小结

AgentEval 的核心思路：用三个 LLM 智能体完成评测的全流程。

**CriticAgent**：给任务描述和示例，自动生成评估标准。解决冷启动问题。

**QuantifierAgent**：拿着标准，对 Agent 的每次输出逐条打分。输出多维度评测结果。

**VerifierAgent**：检查标准的稳定性和判别力，过滤掉没用的标准。保证评测质量。

用的时候注意三点：适合成功有明确定义的任务；CriticAgent 生成的标准要人工审核；打分结果是定性标签，需要自己转换成数值做比较。

和 Anthropic 方法论结合用效果最好——AgentEval 解决冷启动，Anthropic 方法论保证严格性。
