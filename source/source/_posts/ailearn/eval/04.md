## 为什么选 DeepEval

市面上 Agent 评测工具不少，我用下来觉得 DeepEval 最顺手，原因很简单：

**它和 Pytest 是同一套思路。**

你写过单元测试吗？`assert` 一下，通过就绿，失败就红。DeepEval 就是把这套逻辑搬到了 LLM 评测上——`assert_test` 一下，分数够就通过，不够就报错。

不需要学一套全新的框架，不需要搭一个评测平台，就是 Python 文件 + `deepeval test run`，10 分钟能跑起来。

另外一个原因：**它的 Agent 专用指标是真的好用。**

`ToolCorrectnessMetric`（工具调用对不对）、`PlanAdherenceMetric`（有没有按计划执行）、`AgentGoalCompletionMetric`（目标完成了吗）——这三个指标覆盖了 Agent 评测最核心的三个维度，拿来就能用，不需要自己从头设计。

每天 2000 万次评估量，这个数字说明它在生产环境里是经过验证的。

## 5 分钟跑通第一个评测

先写一个最简单的例子，感受一下整体流程。

```python
# test_basic.py
from deepeval import assert_test
from deepeval.test_case import LLMTestCase, SingleTurnParams
from deepeval.metrics import GEval

def test_answer_quality():
    # 定义评估指标：用自然语言描述"什么叫好答案"
    quality_metric = GEval(
        name="回答质量",
        criteria="判断 actual_output 是否准确、清晰地回答了用户问题。",
        evaluation_params=[
            SingleTurnParams.INPUT,
            SingleTurnParams.ACTUAL_OUTPUT
        ],
        threshold=0.7
    )

    # 创建测试用例
    test_case = LLMTestCase(
        input="Python 里怎么反转一个列表？",
        actual_output="可以用 list.reverse() 原地反转，或者用切片 list[::-1] 返回新列表。",
    )

    assert_test(test_case, [quality_metric])
```

跑起来：

```bash
deepeval test run test_basic.py
```

终端会输出每个指标的分数和判断理由，通过就绿，失败就红。

就这么简单。

## 两种评估模式，搞清楚用哪个

DeepEval 有两种评估方式，很多人一开始搞混。

**端到端评估**：把 Agent 当黑盒，只看输入和输出。

```
用户输入 → [Agent 黑盒] → 最终输出 → DeepEval 打分
```

适合什么场景？你只关心最终结果，不在乎 Agent 内部怎么跑的。比如评测一个问答机器人，只看回答质量。

**组件级评估**：追踪 Agent 内部每一步，对每个环节单独打分。

```
用户输入 → [追踪] → 检索 Span → 生成 Span → 工具调用 Span → 输出
                        ↓打分         ↓打分          ↓打分
```

适合什么场景？你想知道 Agent 哪个环节出了问题。比如 RAG Agent 回答质量差，是检索出了问题还是生成出了问题？

做 Agent 评测，**大多数时候你需要组件级评估**。因为 Agent 的问题往往不在最终输出，而在中间某个步骤。

## Agent 评测的三个核心指标

这是这篇文章最重要的部分。

DeepEval 为 Agent 专门设计了几个指标，我觉得最实用的是这三个。

### 工具调用正确性（ToolCorrectnessMetric）

Agent 调用了工具，但调对了吗？

这个指标检查两件事：调了哪些工具（工具名），以及调的顺序对不对（可选）。

```python
from deepeval import evaluate
from deepeval.test_case import LLMTestCase, ToolCall
from deepeval.metrics import ToolCorrectnessMetric

test_case = LLMTestCase(
    input="帮我查一下这个订单的退款政策",
    actual_output="根据我们的政策，您可以在 30 天内申请全额退款。",
    # Agent 实际调用的工具
    tools_called=[
        ToolCall(name="WebSearch"),
        ToolCall(name="PolicyQuery")
    ],
    # 预期应该调用的工具
    expected_tools=[
        ToolCall(name="PolicyQuery")
    ],
)

metric = ToolCorrectnessMetric(threshold=0.8)
evaluate(test_cases=[test_case], metrics=[metric])
```

分数怎么算？

```
工具正确性 = 正确使用的工具数 / 总调用工具数
```

上面这个例子，Agent 调了 `WebSearch` 和 `PolicyQuery` 两个工具，但预期只需要 `PolicyQuery`。多调了一个，分数就会打折。

如果你还想验证工具的入参和输出，可以加参数：

```python
from deepeval.test_case import ToolCallParams

metric = ToolCorrectnessMetric(
    threshold=0.8,
    evaluation_params=[
        ToolCallParams.INPUT_PARAMETERS,  # 验证入参
        ToolCallParams.OUTPUT             # 验证输出
    ],
    should_consider_ordering=True  # 考虑调用顺序
)
```

### 规划遵循度（PlanAdherenceMetric）

Agent 有没有按照自己的计划执行？

这个指标需要配合追踪（Trace）使用。它会从 Agent 的推理过程里提取"计划"，然后检查实际执行步骤有没有遵循这个计划。

```python
from deepeval.tracing import observe, update_current_trace
from deepeval.dataset import Golden, EvaluationDataset
from deepeval.metrics import PlanAdherenceMetric
from deepeval.test_case import ToolCall

@observe
def search_weather(city):
    # 模拟天气查询工具
    return f"{city}今天晴，25°C"

@observe
def weather_agent(user_input):
    # Agent 内部：先规划，再执行
    tools = [ToolCall(name="SearchWeather")]
    result = search_weather("旧金山")
    output = f"根据查询结果：{result}"

    update_current_trace(
        input=user_input,
        output=output,
        tools_called=tools
    )
    return output

# 运行评估
dataset = EvaluationDataset(goldens=[
    Golden(input="旧金山今天天气怎么样？")
])
metric = PlanAdherenceMetric(threshold=0.7, model="gpt-4o")

for golden in dataset.evals_iterator(metrics=[metric]):
    weather_agent(golden.input)
```

有一个细节：**如果 Agent 的推理过程里没有明确的规划步骤，VerifierAgent 默认给满分**。所以这个指标对有 Chain-of-Thought 或 ReAct 推理的 Agent 更有意义。

### 目标完成度（AgentGoalCompletionMetric）

Agent 最终有没有完成用户的目标？

这是最直接的指标，也是最难评的指标。

```python
from deepeval.metrics import AgentGoalCompletionMetric
from deepeval.test_case import LLMTestCase

test_case = LLMTestCase(
    input="帮我预订明天下午 3 点从北京到上海的机票，靠窗座位",
    actual_output="已为您预订明天下午 3:00 CA1234 航班，北京首都机场 → 上海虹桥，靠窗座位 12A，票价 ¥680。",
    # 可以提供额外的上下文，帮助评判
    context=["用户账户余额充足", "12A 座位可用"]
)

metric = AgentGoalCompletionMetric(threshold=0.8)
metric.measure(test_case)
print(f"分数：{metric.score}")
print(f"理由：{metric.reason}")
```

这个指标用 LLM 来判断，所以它能理解语义——即使 Agent 的输出格式和预期不完全一样，只要实质上完成了目标，也能得高分。

## 一个完整的 Agent 评测示例

把三个指标组合起来，评测一个客服 Agent：

```python
# test_customer_service_agent.py
import pytest
from deepeval import assert_test
from deepeval.test_case import LLMTestCase, ToolCall, SingleTurnParams
from deepeval.metrics import (
    ToolCorrectnessMetric,
    AgentGoalCompletionMetric,
    GEval
)

# 模拟客服 Agent 的输出（实际使用时替换为真实调用）
def run_customer_service_agent(user_input):
    return {
        "output": "您好！根据我们的退款政策，30天内可申请全额退款。我已为您提交退款申请，预计3-5个工作日到账。",
        "tools_called": [
            ToolCall(name="QueryOrderInfo"),
            ToolCall(name="SubmitRefundRequest")
        ]
    }

@pytest.mark.parametrize("input_text,expected_tools,expected_goal", [
    (
        "我买的商品质量有问题，想退款",
        [ToolCall(name="QueryOrderInfo"), ToolCall(name="SubmitRefundRequest")],
        "帮助用户完成退款申请"
    ),
])
def test_customer_service(input_text, expected_tools, expected_goal):
    result = run_customer_service_agent(input_text)

    test_case = LLMTestCase(
        input=input_text,
        actual_output=result["output"],
        tools_called=result["tools_called"],
        expected_tools=expected_tools,
    )

    # 指标1：工具调用对不对
    tool_metric = ToolCorrectnessMetric(
        threshold=0.8,
        should_consider_ordering=True
    )

    # 指标2：目标完成了吗
    goal_metric = AgentGoalCompletionMetric(threshold=0.7)

    # 指标3：回答质量（自定义）
    quality_metric = GEval(
        name="客服回答质量",
        criteria="回答是否礼貌、准确、包含具体的处理结果和时间预期",
        evaluation_params=[
            SingleTurnParams.INPUT,
            SingleTurnParams.ACTUAL_OUTPUT
        ],
        threshold=0.7
    )

    assert_test(test_case, [tool_metric, goal_metric, quality_metric])
```

跑起来：

```bash
deepeval test run test_customer_service_agent.py
```

三个指标，覆盖了工具使用、目标达成、回答质量三个维度。这才是一个 Agent 评测应该有的样子。

## 指标选多少合适

这里有个坑，很多人踩过。

指标选太多，评测跑得慢，而且结果难以解读——10 个指标，有 3 个没过，你不知道该优先修哪个。

DeepEval 官方的建议是：**不超过 5 个指标**。

我自己的经验是按场景分类：

**RAG Agent**：`ContextualPrecision`（检索精准度）+ `Faithfulness`（有没有幻觉）+ 1 个自定义质量指标。

**工具调用 Agent**：`ToolCorrectnessMetric` + `AgentGoalCompletionMetric` + 1 个自定义指标。

**对话 Agent**：`ConversationCompleteness`（对话完整性）+ `AgentGoalCompletionMetric` + 1 个自定义指标。

自定义指标用 `GEval`，用自然语言描述你的业务标准，比如"回答是否包含具体的处理时间"、"有没有主动询问用户的订单号"。

## 塞进 CI/CD

评测写好了，下一步是让它自动跑。

DeepEval 和 Pytest 原生集成，直接加进 GitHub Actions 就行：

```yaml
# .github/workflows/agent-eval.yml
name: Agent Evaluation

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  evaluate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - name: 安装依赖
        run: |
          pip install deepeval
          pip install -r requirements.txt

      - name: 运行 Agent 评测
        env:
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
        run: |
          deepeval test run tests/test_agent.py --n-workers 4
```

`--n-workers 4` 是并行跑，4 个 worker 同时跑，速度快很多。

加了这个之后，每次 PR 都会自动跑评测。如果有指标没过，PR 就会标红，提醒你在合并前修复。

## 一个容易忽视的细节：评判模型的选择

DeepEval 的大多数指标用的是 LLM-as-Judge——用一个 LLM 来判断另一个 LLM 的输出。

这里有个原则：**评判模型要比被评测的 Agent 更强，或者至少同级。**

用 GPT-3.5 评 GPT-4 的输出，结果不可信。GPT-3.5 可能根本看不出 GPT-4 输出里的细微问题。

默认情况下，DeepEval 用 GPT-4o 作为评判模型。如果你的 Agent 用的是 GPT-4o，可以换成 o1：

```python
metric = ToolCorrectnessMetric(
    threshold=0.8,
    model="o1"  # 用更强的模型来评判
)
```

如果你不想用 OpenAI，也可以换成其他模型：

```python
# 用 Anthropic Claude
import os
os.environ["ANTHROPIC_API_KEY"] = "your-key"
metric = GEval(..., model="claude-opus-4-5")

# 用本地 Ollama
from deepeval.models import OllamaModel
metric = GEval(..., model=OllamaModel(model="llama3"))
```

本地模型的好处是不花钱，坏处是评判质量可能不如 GPT-4o。

## 从端到端到组件级：一个进阶示例

如果你想追踪 Agent 内部每个步骤，用 `@observe` 装饰器：

```python
import asyncio
from deepeval.tracing import observe, update_current_span, update_current_trace
from deepeval.test_case import LLMTestCase
from deepeval.metrics import AnswerRelevancyMetric, FaithfulnessMetric
from deepeval.dataset import EvaluationDataset, Golden

@observe()
async def rag_agent(query: str) -> str:
    chunks = await retrieve(query)
    answer = await generate(query, chunks)
    # 更新整个 trace 的输入输出
    update_current_trace(input=query, output=answer)
    return answer

@observe()
async def retrieve(query: str) -> list[str]:
    # 模拟检索
    return ["相关文档片段 1", "相关文档片段 2"]

@observe(metrics=[AnswerRelevancyMetric(), FaithfulnessMetric()])
async def generate(query: str, chunks: list[str]) -> str:
    response = "基于检索结果生成的回答..."
    # 对这个 span 单独打分
    update_current_span(
        test_case=LLMTestCase(
            input=query,
            actual_output=response,
            retrieval_context=chunks
        ),
    )
    return response

# 运行评估
dataset = EvaluationDataset(goldens=[
    Golden(input="DeepEval 是什么？"),
    Golden(input="怎么评测 RAG 系统？"),
])

for golden in dataset.evals_iterator():
    task = asyncio.create_task(rag_agent(golden.input))
    dataset.evaluate(task)
```

这样跑完，你能看到每个 `generate` span 的 `AnswerRelevancyMetric` 和 `FaithfulnessMetric` 分数，而不只是整体的输出质量。

哪个查询的检索质量差，哪个生成步骤出现了幻觉——一目了然。

## 📝 小结

DeepEval 上手的核心就三步：

**装好，写测试用例，跑起来。**

Agent 评测最重要的三个指标：

- `ToolCorrectnessMetric`：工具调用对不对，支持验证工具名、入参、输出、顺序
- `PlanAdherenceMetric`：有没有按计划执行，需要配合追踪使用
- `AgentGoalCompletionMetric`：目标完成了吗，用 LLM 语义判断

两个注意点：指标别选太多，不超过 5 个；评判模型要比被评测 Agent 更强或同级。

加进 CI/CD 之后，每次提交都自动跑评测，有问题在合并前就能发现。
