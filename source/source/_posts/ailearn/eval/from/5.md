# 使用 Agent-EvalKit 系统化评估 AI 智能体

## 背景

构建 AI 智能体的团队通常像评估其他软件一样评估它们：检查输出是否符合预期。但自主选择工具并跨多个来源顺序执行操作的智能体，会产生仅靠输出级别测试无法完全表征的行为。

一个智能体可能在工具返回空结果时产生幻觉、捏造事实，却仍然提供结构良好、可操作的响应。它也可能在跳过可靠流程所需的验证步骤的情况下得出正确结论。由于这些失败隐藏在最终响应的表面之下，捕获它们需要追踪智能体完整执行路径的评估：智能体调用了哪些工具、这些工具返回了什么数据，以及响应是否忠实地反映了这些数据。

弥合这一差距需要大多数智能体团队没有人力从头构建的基础设施：带有基准结果的测试用例、用于捕获工具调用和中间状态的可观测性工具，以及在表面准确性之外评估忠实度和工具使用情况的指标。

---

## Agent-EvalKit 简介

**Agent-EvalKit** 是一个开源工具包（Apache 2.0 许可），通过与 AI 编码助手（包括 Claude Code、Kiro CLI 和 Kilo Code）集成，使这种评估基础设施变得可用。它将整个工作流程引入您的开发环境，而不是将评估视为独立的部署后工作。

您用自然语言描述评估目标，工具包处理每个阶段——从读取智能体的源代码和生成有针对性的测试用例，到运行评估并生成包含改进建议的报告，这些建议引用了代码库中的具体位置。

## 智能体评估的要求

除了基础设施本身，选择测量什么同样具有挑战性。智能体质量跨越没有单一指标能够捕获的多个维度：

- **忠实度（Faithfulness）**：响应是否基于工具实际返回的内容
- **工具参数准确性（Tool Parameter Accuracy）**：智能体是否以正确的输入调用了正确的工具
- **响应质量（Response Quality）**：最终输出是否连贯且对提问者有用

响应可能读起来很好，却悄悄地在空工具结果上产生幻觉；智能体可能通过一系列错误的工具调用得出合理的答案。因此每个维度都必须单独检查，而不是从相邻维度推断。

没有单一的评估器风格能很好地处理所有三个维度：
- **基于代码的评估器**：提供快速、可复现的结果，但会惩罚有效的方法变体
- **LLM 作为评判者的评估器**：以额外推理和精心提示设计为代价提供细致评估

最有效的评估策略结合了两种方法。将评估分数转化为具体代码变更是许多工作最终停滞的地方，这就是为什么评估工作流程需要以具体的代码级建议而非数字仪表板结束。

## Agent-EvalKit 的工作原理

Agent-EvalKit 通过您现有的 AI 编码助手工作，而不是作为独立的评估平台运行。您的助手（无论是 Claude Code、Kiro CLI 还是 Kilo Code）通过在评估过程的每个阶段应用其读取代码和推理智能体行为的能力，成为评估引擎。

您通过斜杠命令（如 `/evalkit.plan` 和 `/evalkit.data`）驱动此工作流程，附加自然语言指导，告诉助手哪些质量维度对您的智能体最重要。

### 六个评估阶段

工具包将工作组织为六个阶段，每个阶段在 `eval/` 目录中生成供下一阶段使用的产物：

| 阶段 | 命令 | 说明 |
|------|------|------|
| **计划** | `/evalkit.plan` | 读取智能体代码，了解其工具和框架，生成评估计划，将每个指标与具体评估方法配对 |
| **数据** | `/evalkit.data` | 生成基于评估计划的测试用例，每个用例都有针对特定行为和失败模式的输入和预期结果 |
| **追踪** | `/evalkit.trace` | 通过添加 OpenTelemetry 兼容的追踪使完整执行路径可见。支持 Strands、LangGraph 和 CrewAI 等框架 |
| **运行智能体** | `/evalkit.run_agent` | 针对每个测试用例执行智能体，为每次运行生成结构化追踪文件，捕获工具调用、模型响应和中间状态的完整历史 |
| **评估** | `/evalkit.eval` | 将计划中的指标实现为可执行评估代码，针对收集的追踪运行，并保存结构化结果 |
| **报告** | `/evalkit.report` | 分析测试用例的模式，生成引用智能体代码中具体位置的优先建议，每个建议包含预期影响 |

## 演示研究：评估旅行研究智能体

### 背景

在开发使用 Strands Agents SDK 和 Amazon Bedrock 构建的旅行研究智能体期间，我们注意到智能体有时在响应中提供可疑的精确数字。该智能体使用网络搜索、航班信息、气候数据、货币转换和预算计算工具帮助用户规划旅行，但我们无法确定精确度问题有多普遍或哪些查询会触发它。

### 评估过程

Agent-EvalKit 分析了智能体的代码，并在计划阶段围绕三个指标设计了重点评估：

1. **忠实度（Faithfulness）**：响应是否基于工具实际返回的数据
2. **工具参数准确性（Tool Parameter Accuracy）**：智能体是否以正确的输入调用工具
3. **响应质量（Response Quality）**：输出是否连贯且有用

数据阶段生成了 100 个多轮测试会话，涵盖目的地研究、季节时机、行程构建、比较问题和预算计算，后续阶段在捕获详细执行追踪的同时运行每个会话。

### 评估结果

结果揭示了质量和可靠性之间的明显分歧：

| 指标 | 得分 | 说明 |
|------|------|------|
| **响应质量** | 83.9% | 智能体提供了清晰、可操作的旅行建议 |
| **工具参数准确性** | 64.5% | 智能体通常选择了正确的工具，但有时传递了不精确的参数 |
| **忠实度** | **32.3%** | ⚠️ 严重问题：智能体在工具返回空或不完整结果时捏造汇率、温度和景点详情 |

### 根因分析

报告将幻觉防护措施确定为最高优先级修复，建议：
- 在系统提示中添加指令，当工具返回空结果时进行披露
- 改进所有代码路径中的工具错误处理

**在运行 Agent-EvalKit 之前**，我们知道智能体有时看起来不可靠。**之后**，我们知道根本原因是空工具输出触发了幻觉，并有具体的代码变更来解决它。

## 快速开始

### 前提条件

- 启用了基础模型的活跃 AWS 账户（在 Amazon Bedrock 控制台中确认）
- Python 3.11 或更高版本和 Git
- `uv` 包管理器（macOS/Linux 安装：`curl -LsSf https://astral.sh/uv/install.sh | sh`）
- 已安装并配置的支持 AI 编码助手（Claude Code、Kiro CLI 或 Kilo Code）

### 安装

```bash
# 使用 uv 安装工具包
uv tool install evalkit --from git+https://github.com/awslabs/Agent-EvalKit.git

# 初始化评估项目
evalkit init my-agent-evaluation
cd my-agent-evaluation
cp -r /path/to/your/agent .

# 启动 AI 助手
claude
```

### 运行评估

**快速引导模式**（推荐新手）：
```bash
/evalkit.quick 评估 ./my_agent 的响应质量和工具准确性
```

**分阶段精细控制**：
```bash
/evalkit.plan 评估 ./my_agent 的响应质量和工具准确性
/evalkit.data
/evalkit.trace
/evalkit.run_agent
/evalkit.eval
/evalkit.report
```

## 最佳实践

1. **从窄范围开始**：聚焦于 2-3 个针对智能体最关键质量维度的指标，在后续评估中扩大范围

2. **用领域知识引导**：在每个阶段描述您观察到的具体输入、边缘情况和失败模式。指令越有针对性，生成的测试用例、指标和建议就越相关

3. **执行前审查测试用例**：数据阶段从评估计划中综合用例，但您对真实用户行为的理解是不可替代的

4. **每次重大变更后评估**：尽早发现回归并衡量每次改进的影响

5. **逐步处理建议**：从报告中影响最大的项目开始，实施修复，重新评估以确认改进，然后继续下一个发现

6. **在生产中持续监控**：使用 Amazon Bedrock AgentCore Observability 从真实流量中捕获追踪，并使用 AgentCore Evaluation 对这些追踪运行质量指标

7. **保持评估者与人类专家一致**：定期将 LLM 作为评判者的分数与领域专家或人工注释者的判断进行比较

## CI/CD 集成

对于准备自动化的团队，Agent-EvalKit 可以集成到 CI/CD 流水线中：

```
代码变更 → 触发评估 → 质量门控（检查指标阈值和回归）→ 失败路由回评估报告中的标记项目
```

一旦流水线就位，每轮测试都会重用上一轮的测试用例和工具，因此随着项目成熟，运行新评估的成本会下降。

---

## 结论

Agent-EvalKit 通过将每个步骤（从评估设计到指标计算和报告）委托给您已经使用的同一 AI 助手，为 AI 智能体评估提供了系统化的形式。

模糊的质量担忧变成了结构化的证据体：测试用例、执行追踪、指标分数和优先建议，所有这些都与代码中的具体位置相关联。
