然后 Agent 上线了。

> "我问了一个很简单的问题，Agent 给了一个完全不相关的答案。"

你去翻评测记录，所有指标都是绿的。

这就是离线评测的边界。

## 离线评测覆盖不了的那 20%

离线评测有一个根本性的局限：**你只能测试你想到的场景。**

你写了 200 个测试用例，覆盖了你认为用户会问的问题。但真实用户的输入千变万化——他们会用你没想到的表达方式，会问你没预料到的问题，会在对话中途突然转换话题。

Anthropic 在他们的评测方法论里用了一个比喻：**瑞士奶酪模型（Swiss Cheese Model）**。

每一层防护都有漏洞，就像奶酪上的孔。单独一层不够，但多层叠加，从一层漏过去的问题会被下一层捕获。

离线评测是一层，生产监控是另一层。

两层叠加，才能覆盖大多数问题。

Anthropic 给出了各种方法的对比：

| 方法 | 优势 | 局限 |
|------|------|------|
| **离线评测** | 快速迭代、完全可复现、不影响用户 | 只测试你想到的场景 |
| **生产监控** | 揭示真实用户行为、捕获合成评测遗漏的问题 | 被动，问题到达用户后才知道 |
| **A/B 测试** | 衡量实际用户结果 | 慢，只测试已部署的变更 |
| **用户反馈** | 发现未预料到的问题 | 稀疏，偏向严重问题 |

没有哪一种方法能单独解决所有问题。

## 生产监控的核心：追踪

要监控生产环境，需要先能"看见"Agent 在做什么。

这就是追踪（Tracing）的作用。

追踪记录 Agent 的每一步：收到了什么输入、调用了哪些工具、工具返回了什么、最终输出了什么。有了这些记录，才能在事后分析哪里出了问题。

目前最通用的追踪标准是 **OpenTelemetry（OTel）**。它是一个开放标准，主流的 Agent 框架都支持——LangGraph、Strands、CrewAI，以及 AWS 的 Agent-EvalKit。

用 OTel 追踪一个 Agent 很简单：

```python
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter

# 初始化追踪器
provider = TracerProvider()
exporter = OTLPSpanExporter(endpoint="http://localhost:4317")
provider.add_span_processor(BatchSpanProcessor(exporter))
trace.set_tracer_provider(provider)

tracer = trace.get_tracer("my-agent")

def run_agent(user_input: str) -> str:
    with tracer.start_as_current_span("agent-run") as span:
        # 记录输入
        span.set_attribute("agent.input", user_input)

        # 调用工具
        with tracer.start_as_current_span("tool-call") as tool_span:
            tool_span.set_attribute("tool.name", "QueryDatabase")
            result = query_database(user_input)
            tool_span.set_attribute("tool.output", str(result))

        # 生成输出
        output = generate_response(user_input, result)

        # 记录输出
        span.set_attribute("agent.output", output)
        return output
```

每次 Agent 运行，都会生成一条追踪记录，包含完整的执行路径。

## DeepEval 的在线评估

追踪记录有了，下一步是对这些记录自动打分。

DeepEval 提供了一个叫"在线评估"的功能，配合 Confident AI 平台，可以对生产流量实时打分。

原理很简单：在 Agent 的每次调用里，加一行代码，把这次调用关联到一个指标集合。Confident AI 会在后台异步运行评估，不影响 Agent 的响应速度。

```python
from deepeval.tracing import observe, update_current_trace

@observe()
def customer_service_agent(user_input: str) -> str:
    # 正常的 Agent 逻辑
    result = process_request(user_input)
    output = generate_response(result)

    # 关键：关联到在线评估指标集合
    update_current_trace(
        input=user_input,
        output=output,
        metric_collection="客服 Agent 生产监控"  # 在 Confident AI 上配置的指标集合
    )

    return output
```

在 Confident AI 平台上，你可以配置这个指标集合包含哪些指标，以及每个指标的阈值。

每次 Agent 被调用，Confident AI 就会在后台跑一次评估，把分数记录下来。

你可以在平台上看到：
- 每天的平均分数趋势
- 哪些用户输入触发了低分
- 哪个指标最近在下降

## 不用云平台的方案

如果你不想用 Confident AI，也可以自己搭一套简单的生产监控。

思路是：把每次 Agent 调用的输入、输出、工具调用记录下来，然后定期批量跑评估。

```python
import json
import asyncio
from datetime import datetime
from deepeval.test_case import LLMTestCase, ToolCall
from deepeval.metrics import AgentGoalCompletionMetric, FaithfulnessMetric
from deepeval import evaluate

# 第一步：记录生产流量
class ProductionLogger:
    def __init__(self, log_file: str):
        self.log_file = log_file

    def log(self, user_input: str, output: str, tools_called: list, tool_outputs: list):
        record = {
            "timestamp": datetime.now().isoformat(),
            "input": user_input,
            "output": output,
            "tools_called": [t.name for t in tools_called],
            "tool_outputs": tool_outputs,
        }
        with open(self.log_file, "a") as f:
            f.write(json.dumps(record, ensure_ascii=False) + "\n")

logger = ProductionLogger("production_logs.jsonl")

def run_agent_with_logging(user_input: str) -> str:
    tools_called = []
    tool_outputs = []

    # 正常的 Agent 逻辑（追踪工具调用）
    output = run_agent(user_input, tools_called, tool_outputs)

    # 记录到日志
    logger.log(user_input, output, tools_called, tool_outputs)

    return output

# 第二步：定期批量评估（比如每天凌晨跑一次）
def run_daily_evaluation():
    # 读取最近 24 小时的日志
    records = []
    with open("production_logs.jsonl") as f:
        for line in f:
            records.append(json.loads(line))

    # 随机抽样 50 条（全量太贵）
    import random
    sample = random.sample(records, min(50, len(records)))

    # 构建测试用例
    test_cases = []
    for record in sample:
        test_cases.append(LLMTestCase(
            input=record["input"],
            actual_output=record["output"],
            tools_called=[ToolCall(name=t) for t in record["tools_called"]],
            retrieval_context=record["tool_outputs"],
        ))

    # 跑评估
    metrics = [
        AgentGoalCompletionMetric(threshold=0.7),
        FaithfulnessMetric(threshold=0.7),
    ]

    results = evaluate(test_cases=test_cases, metrics=metrics)

    # 记录每天的分数
    daily_score = {
        "date": datetime.now().strftime("%Y-%m-%d"),
        "goal_completion": results.metrics_data["AgentGoalCompletionMetric"].avg_score,
        "faithfulness": results.metrics_data["FaithfulnessMetric"].avg_score,
        "sample_size": len(sample),
    }

    with open("daily_scores.jsonl", "a") as f:
        f.write(json.dumps(daily_score, ensure_ascii=False) + "\n")

    print(f"今日评估完成：目标完成度 {daily_score['goal_completion']:.2%}，忠实度 {daily_score['faithfulness']:.2%}")
```

这套方案不需要任何云平台，本地就能跑。

## 最有价值的事：从生产日志里挖测试用例

生产监控最大的价值，不只是发现问题，而是**把发现的问题变成测试用例**。

这是真正的闭环。

每次生产环境里出现低分用例，就把它加入测试集。下次离线评测就会覆盖这个场景，防止同样的问题再次出现。

```python
def extract_failure_cases(
    log_file: str,
    output_file: str,
    score_threshold: float = 0.6
):
    """从生产日志里提取低分用例，加入测试集"""

    failure_cases = []

    with open(log_file) as f:
        for line in f:
            record = json.loads(line)

            # 只处理有评估分数的记录
            if "eval_score" not in record:
                continue

            # 低于阈值的用例
            if record["eval_score"] < score_threshold:
                failure_cases.append({
                    "input": record["input"],
                    "actual_output": record["output"],
                    "tools_called": record["tools_called"],
                    "eval_score": record["eval_score"],
                    "failure_reason": record.get("failure_reason", ""),
                    "source": "production",
                    "added_at": datetime.now().isoformat(),
                })

    # 追加到测试集
    with open(output_file, "a") as f:
        for case in failure_cases:
            f.write(json.dumps(case, ensure_ascii=False) + "\n")

    print(f"从生产日志提取了 {len(failure_cases)} 个失败用例，已加入测试集")
    return failure_cases
```

这个函数每周跑一次，把上周生产环境里的低分用例自动加入测试集。

时间长了，你的测试集会越来越贴近真实用户的使用场景，离线评测的覆盖率也会越来越高。

## AWS Agent-EvalKit 的生产监控思路

AWS 的 Agent-EvalKit 在这方面做得很系统。

他们的核心思路是：**用 OTel 追踪捕获完整的执行路径，然后对追踪记录运行质量指标。**

不只是看最终输出，而是看整个执行过程——工具调用了什么、返回了什么、Agent 的推理过程是什么。

他们在旅行 Agent 的案例里发现了一个典型问题：

```
响应质量：83.9%  ✓
工具参数准确性：64.5%  ✗
忠实度：32.3%  ✗（严重问题）
```

响应质量看起来不错，但忠实度只有 32.3%。

原因是：当工具返回空结果时，Agent 没有处理，直接"编"了一个答案——汇率、温度、景点详情，全是捏造的。

如果只看最终输出，这个问题很难发现。用户看到的是一个格式完整、语气自信的回答，根本不知道里面的数据是假的。

只有追踪到工具调用层面，才能发现"工具返回空，但 Agent 输出了具体数字"这个矛盾。

这就是为什么生产监控要追踪到工具调用层面，而不只是看最终输出。

## 设置告警：什么时候该主动通知你

生产监控不能只是被动查看，还需要主动告警。

什么情况下应该触发告警？

**分数骤降**：某个指标的 7 日均值突然下降超过 10%，说明可能有回归问题。

**高频失败**：某类用户输入的失败率超过 30%，说明这个场景有系统性问题。

**新型失败模式**：出现了之前没见过的失败原因，说明用户开始用新的方式使用 Agent。

用 Python 实现一个简单的告警：

```python
import json
from collections import defaultdict
from datetime import datetime, timedelta

def check_alerts(log_file: str, alert_threshold: float = 0.1):
    """检查是否需要触发告警"""

    # 读取最近 7 天的评分记录
    seven_days_ago = datetime.now() - timedelta(days=7)
    recent_scores = []
    older_scores = []

    with open("daily_scores.jsonl") as f:
        for line in f:
            record = json.loads(line)
            record_date = datetime.strptime(record["date"], "%Y-%m-%d")

            if record_date >= seven_days_ago:
                recent_scores.append(record)
            elif record_date >= seven_days_ago - timedelta(days=7):
                older_scores.append(record)

    if not recent_scores or not older_scores:
        return

    # 计算均值
    recent_avg = sum(r["goal_completion"] for r in recent_scores) / len(recent_scores)
    older_avg = sum(r["goal_completion"] for r in older_scores) / len(older_scores)

    # 检查是否骤降
    drop = older_avg - recent_avg
    if drop > alert_threshold:
        send_alert(
            f"⚠️ 目标完成度下降告警\n"
            f"上周均值：{older_avg:.2%}\n"
            f"本周均值：{recent_avg:.2%}\n"
            f"下降幅度：{drop:.2%}\n"
            f"请检查最近的代码变更"
        )

def send_alert(message: str):
    """发送告警（可以接入钉钉、企业微信、Slack 等）"""
    print(f"[ALERT] {message}")
    # 实际使用时替换为真实的通知渠道
    # requests.post(webhook_url, json={"text": message})
```

## 一个完整的生产监控方案

把上面的内容串起来，一个完整的生产监控方案长这样：

```
Agent 上线
    ↓
每次调用 → OTel 追踪 → 记录到日志
    ↓
每天凌晨 → 批量评估 → 记录日分数
    ↓
每天检查 → 分数告警 → 主动通知
    ↓
每周 → 提取失败用例 → 加入测试集
    ↓
下次 PR → 离线评测覆盖新场景 → 防止回归
```

这个闭环跑起来之后，你的评测体系会随着时间越来越完善：

- 测试集越来越贴近真实用户
- 离线评测的覆盖率越来越高
- 生产环境的问题越来越少

## 一个容易踩的坑：评估成本

生产监控有一个实际问题：**评估很贵。**

每次调用 LLM-as-Judge 来评估，都要花钱。如果你的 Agent 每天有 10 万次调用，全量评估根本不现实。

几个控制成本的策略：

**抽样评估**：不是每次调用都评估，而是随机抽取 1-5% 的流量。对于大多数场景，这个样本量已经足够发现系统性问题。

**分层抽样**：不是完全随机，而是按用户输入的类型分层。确保每类场景都有足够的样本。

**触发式评估**：只对"可疑"的调用评估——比如 Agent 的响应时间异常长、工具调用次数异常多、或者用户在对话后立即退出。

```python
def should_evaluate(record: dict) -> bool:
    """决定这条记录是否需要评估"""

    # 随机抽样 3%
    import random
    if random.random() < 0.03:
        return True

    # 工具调用次数异常多（可能有问题）
    if len(record.get("tools_called", [])) > 10:
        return True

    # 响应时间异常长（可能有问题）
    if record.get("response_time_ms", 0) > 30000:
        return True

    return False
```

## 📝 小结

生产监控和离线评测不是替代关系，是互补关系。

离线评测快速、可复现，但只能覆盖你想到的场景。生产监控慢、被动，但能发现你没想到的问题。

两层叠加，才是 Anthropic 说的"瑞士奶酪模型"——每层都有漏洞，但多层叠加，大多数问题都能被捕获。

生产监控的核心是三件事：

**追踪到工具调用层面。** 只看最终输出不够，要追踪完整的执行路径。忠实度问题、工具滥用问题，只有在工具调用层面才能发现。

**把失败用例加入测试集。** 这是生产监控最大的价值——把真实用户的失败场景变成测试用例，让离线评测越来越贴近真实。

**控制评估成本。** 全量评估不现实，用抽样 + 触发式评估，把成本控制在合理范围内。
