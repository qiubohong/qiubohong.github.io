前五篇把评测的基础设施搭起来了。

工具选好了（DeepEval），指标定好了（工具正确性、忠实度、目标完成度），数据集也建起来了。

然后你跑了一次评测，终端输出了一堆分数：

```
ToolCorrectnessMetric:     0.72  ✗ FAILED
FaithfulnessMetric:        0.85  ✓ PASSED
AgentGoalCompletionMetric: 0.61  ✗ FAILED
```

然后呢？

这是很多团队卡住的地方。分数有了，但不知道该怎么用。

## 分数只是起点，不是终点

很多人拿到评测分数之后，第一反应是：哪个分数低，就去改哪个。

这个直觉没错，但不够。

分数告诉你"哪里有问题"，但不告诉你"问题是什么"。

`ToolCorrectnessMetric` 0.72，这说明 Agent 有 28% 的工具调用是错的。但错在哪？是调了不该调的工具？还是工具调对了但参数传错了？还是调用顺序乱了？

不看具体的失败用例，你根本不知道。

Anthropic 的工程师在他们的评测方法论里反复强调一件事：

**阅读记录（Read the transcripts）。**

不是看分数，是看记录——每一次失败的完整过程，Agent 说了什么、调了什么工具、工具返回了什么、最后输出了什么。

这听起来很费时间。但他们的经验是：**不阅读记录，就无法知道评分器是否运行良好，也无法知道失败是否公平。**

## 怎么读记录

DeepEval 的每次评测都会保存详细的失败原因。

```python
from deepeval.test_case import LLMTestCase, ToolCall
from deepeval.metrics import ToolCorrectnessMetric
from deepeval import evaluate

test_case = LLMTestCase(
    input="帮我查一下北京到上海的高铁票",
    actual_output="北京到上海的高铁最快约 4.5 小时，G1 次列车，票价二等座 ¥553。",
    tools_called=[
        ToolCall(name="WebSearch"),
        ToolCall(name="TrainQuery"),
        ToolCall(name="WeatherQuery"),  # 多调了一个天气查询
    ],
    expected_tools=[
        ToolCall(name="TrainQuery")
    ],
)

metric = ToolCorrectnessMetric(threshold=0.8)
metric.measure(test_case)

# 关键：看失败原因
print(f"分数：{metric.score}")
print(f"原因：{metric.reason}")
```

输出大概是这样：

```
分数：0.67
原因：Agent 调用了 3 个工具，但预期只需要 TrainQuery。
      WebSearch 是冗余调用，WeatherQuery 与任务无关。
      正确工具 TrainQuery 被调用，但额外调用降低了精确度。
```

这个原因比分数有用得多。

你现在知道了：Agent 有"工具滥用"的倾向——任务明确的时候，它还是会多调几个工具"以防万用"。

这是一个可以针对性修复的问题：在系统提示里加一条"只调用完成任务必要的工具，不要调用额外工具"。

## pass@k 和 pass^k：选哪个

读完记录，你会发现另一个问题：同一个测试用例，有时候过，有时候不过。

Agent 的输出是非确定性的。同样的输入，跑 5 次可能有 3 次通过、2 次失败。

这时候分数到底是多少？

Anthropic 给出了两个指标：

**pass@k**：k 次尝试里，至少有 1 次通过的概率。

**pass^k**：k 次尝试里，全部通过的概率。

举个例子，跑 5 次，3 次通过：
- `pass@5` = 3/5 = 60%（至少一次通过）
- `pass^5` = 0%（没有全部通过）

两个指标都有用，但适用场景不同。

**用 pass@k 的场景**：你的 Agent 是一个辅助工具，用户可以多试几次，一次成功就够了。比如代码生成工具——用户可以重新生成，只要最终能生成正确的代码就行。

**用 pass^k 的场景**：你的 Agent 直接面向用户，每次都要稳定输出。比如客服 Agent——用户不会接受"你再问一遍"，每次回答都必须靠谱。

大多数面向用户的 Agent，应该用 `pass^k`，要求更严格。

用 DeepEval 跑多次评测很简单：

```python
from deepeval import evaluate
from deepeval.test_case import LLMTestCase
from deepeval.metrics import AgentGoalCompletionMetric

# 同一个测试用例跑 5 次
results = []
for i in range(5):
    test_case = LLMTestCase(
        input="帮我预订明天的机票",
        actual_output=run_agent("帮我预订明天的机票"),  # 每次重新调用 Agent
    )
    metric = AgentGoalCompletionMetric(threshold=0.7)
    metric.measure(test_case)
    results.append(metric.score >= 0.7)

pass_at_5 = sum(results) / 5
pass_hat_5 = all(results)

print(f"pass@5: {pass_at_5:.0%}")
print(f"pass^5: {'通过' if pass_hat_5 else '未通过'}")
```

## 质量门控：让评测真正卡住问题

评测跑起来了，但如果只是本地跑、看看分数、然后继续开发，评测的价值就打了折扣。

**评测真正的价值，是在代码合并之前卡住问题。**

这就是质量门控（Quality Gate）的作用。

设计质量门控，需要回答三个问题：

**哪些指标必须通过？** 不是所有指标都同等重要。对客服 Agent 来说，`AgentGoalCompletionMetric` 是核心指标，必须通过；`ToolCorrectnessMetric` 是辅助指标，可以有一定容忍度。

**阈值设多少？** 太高了，每次 PR 都会失败，开发效率崩溃；太低了，质量门控形同虚设。一个实用的起点：把当前版本的分数作为基线，设置"不能低于基线 5%"的规则。

**失败了怎么处理？** 是直接阻断合并，还是只发警告？建议核心指标阻断合并，辅助指标只发警告。

用 DeepEval + GitHub Actions 实现质量门控：

```python
# tests/test_agent_quality_gate.py
import pytest
from deepeval import assert_test
from deepeval.test_case import LLMTestCase, ToolCall
from deepeval.metrics import (
    ToolCorrectnessMetric,
    AgentGoalCompletionMetric,
    FaithfulnessMetric,
)
from deepeval.dataset import EvaluationDataset

# 加载评测数据集
dataset = EvaluationDataset()
dataset.pull(alias="客服 Agent 测试集 v2")

@pytest.mark.parametrize("golden", dataset.goldens)
def test_quality_gate(golden):
    # 调用真实 Agent
    result = run_agent(golden.input)

    test_case = LLMTestCase(
        input=golden.input,
        actual_output=result["output"],
        tools_called=result["tools_called"],
        expected_tools=golden.expected_tools,
        retrieval_context=result["tool_outputs"],
    )

    # 核心指标：必须通过（阻断合并）
    goal_metric = AgentGoalCompletionMetric(threshold=0.75)
    faithfulness_metric = FaithfulnessMetric(threshold=0.70)

    # 辅助指标：警告但不阻断
    tool_metric = ToolCorrectnessMetric(threshold=0.65)

    assert_test(test_case, [goal_metric, faithfulness_metric, tool_metric])
```

```yaml
# .github/workflows/quality-gate.yml
name: Agent Quality Gate

on:
  pull_request:
    branches: [main]

jobs:
  quality-gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - name: 安装依赖
        run: pip install deepeval -r requirements.txt

      - name: 运行质量门控评测
        env:
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
          CONFIDENT_API_KEY: ${{ secrets.CONFIDENT_API_KEY }}
        run: |
          deepeval test run tests/test_agent_quality_gate.py \
            --n-workers 4 \
            --exit-on-first-failure  # 有指标失败立即停止
```

加了这个之后，每次 PR 都会自动跑评测。核心指标没过，PR 就会标红，合并按钮变灰。

## 从分数到代码改进：一个完整的例子

光有分数还不够，还需要知道怎么改。

Agent-EvalKit 的报告功能做了一件很有价值的事：**它把评测结果和代码位置关联起来。**

不是说"忠实度 32.3%，需要改进"，而是说"第 47 行的 `get_exchange_rate` 函数在 API 返回空结果时没有处理，建议在系统提示里加入空结果处理指令"。

这个思路值得借鉴。

我自己的做法是建立一个"失败模式 → 改进方向"的映射：

**工具调用冗余（多调了不该调的工具）**

根因：系统提示里没有明确限制工具使用范围。

改进：在系统提示里加"只调用完成当前任务必要的工具"，并列出每类任务应该使用的工具清单。

**忠实度低（回答和工具返回数据对不上）**

根因：工具返回空结果或异常时，Agent 没有处理，直接"编"了一个答案。

改进：在系统提示里加"如果工具返回空结果，必须明确告知用户无法获取该信息，不要猜测或编造"。

**目标完成度低（没有完成用户的核心需求）**

根因：通常是 Agent 在多步骤任务中途"迷路"了，或者误解了用户意图。

改进：增加任务分解步骤，让 Agent 在执行前先复述理解的任务，确认无误后再执行。

## 一个容易忽视的信号：评测饱和

随着你不断优化 Agent，评测分数会越来越高。

这听起来是好事，但有一个陷阱：**当所有测试用例都通过了，评测就失去了改进信号。**

100% 通过率的评测，只能追踪回归，不能告诉你 Agent 还有哪些能力可以提升。

Anthropic 把这个叫做"评测饱和"。他们的建议是：**当评测接近饱和时，需要开发更难的评测。**

怎么判断评测是否饱和？

看通过率的趋势。如果连续几个版本通过率都在 95% 以上，说明这批测试用例对当前 Agent 来说太简单了。

这时候需要做两件事：

**加入更难的测试用例。** 多步骤任务、需要跨工具协作的任务、边缘情况更极端的任务。

**把能力评测和回归评测分开。** 回归评测保持高通过率（确保不退步），能力评测保持低通过率（持续挑战 Agent 的上限）。

```python
# 两套数据集，分开跑
# 回归评测：通过率应该接近 100%
regression_dataset = EvaluationDataset()
regression_dataset.pull(alias="回归测试集")

# 能力评测：通过率 50-70% 是正常的
capability_dataset = EvaluationDataset()
capability_dataset.pull(alias="能力挑战集")
```

## 评测结果的可视化

分数看多了，需要一个更直观的方式来追踪趋势。

DeepEval 配合 Confident AI 平台，可以自动生成评测报告，追踪每个版本的指标变化。

但如果你不想用云平台，也可以自己简单记录：

```python
import json
from datetime import datetime
from deepeval import evaluate
from deepeval.dataset import EvaluationDataset

def run_and_record(version_tag: str):
    dataset = EvaluationDataset()
    dataset.pull(alias="客服 Agent 测试集 v2")

    metrics = [
        AgentGoalCompletionMetric(threshold=0.7),
        FaithfulnessMetric(threshold=0.7),
        ToolCorrectnessMetric(threshold=0.7),
    ]

    results = evaluate(
        test_cases=dataset.test_cases,
        metrics=metrics,
    )

    # 记录每个版本的分数
    record = {
        "version": version_tag,
        "timestamp": datetime.now().isoformat(),
        "scores": {
            "goal_completion": results.metrics_data["AgentGoalCompletionMetric"].avg_score,
            "faithfulness": results.metrics_data["FaithfulnessMetric"].avg_score,
            "tool_correctness": results.metrics_data["ToolCorrectnessMetric"].avg_score,
        }
    }

    # 追加到历史记录
    with open("eval_history.jsonl", "a") as f:
        f.write(json.dumps(record, ensure_ascii=False) + "\n")

    return record

# 每次发版前跑一次
run_and_record("v1.2.3")
```

这样你就有了一个简单的评测历史，可以看到每个版本的分数变化趋势。

## 一个真实的迭代案例

把上面的方法串起来，看一个完整的迭代过程。

**初始状态**：客服 Agent 上线，跑第一次评测。

```
AgentGoalCompletionMetric: 0.61  ✗
FaithfulnessMetric:        0.72  ✓
ToolCorrectnessMetric:     0.68  ✗
```

**阅读失败记录**：

- 目标完成度低的用例：大多数是多步骤任务，Agent 在第二步就"忘了"第一步的结果。
- 工具调用错误的用例：Agent 在查询订单状态时，同时调用了"查询物流"和"查询退款状态"，但用户只问了订单状态。

**定位根因**：

- 多步骤任务失忆：上下文窗口管理问题，或者系统提示里没有要求 Agent 保持任务连贯性。
- 工具滥用：系统提示里没有明确的工具使用约束。

**针对性修改**：

```python
# 修改系统提示
SYSTEM_PROMPT = """
你是一个客服助手。

工具使用规则：
- 只调用完成当前用户请求所必需的工具
- 查询订单状态只需调用 QueryOrderStatus，不需要同时查询物流和退款
- 如果工具返回空结果，告知用户无法获取该信息，不要猜测

多步骤任务规则：
- 在开始执行前，先复述你理解的任务目标
- 每完成一步，确认结果后再进行下一步
- 保持对整个任务目标的追踪
"""
```

**重新评测**：

```
AgentGoalCompletionMetric: 0.78  ✓  (+0.17)
FaithfulnessMetric:        0.81  ✓  (+0.09)
ToolCorrectnessMetric:     0.83  ✓  (+0.15)
```

三个指标全部通过，而且提升幅度很明显。

这就是评测驱动开发的完整闭环：**跑评测 → 读记录 → 找根因 → 改代码 → 再评测。**

## 📝 小结

评测结果的使用，核心是三件事：

**读记录，不只看分数。** 分数告诉你哪里有问题，记录告诉你问题是什么。Anthropic 的工程师说"阅读记录"是评测里最重要的事，这不是客套话。

**设质量门控，让评测卡住问题。** 核心指标阻断合并，辅助指标只发警告。阈值从当前基线出发，设"不能低于基线 5%"的规则。

**区分 pass@k 和 pass^k。** 面向用户的 Agent 用 pass^k，要求每次都稳定；辅助工具用 pass@k，一次成功就够。

别忘了评测饱和的问题——通过率接近 100% 的时候，需要加入更难的测试用例，把能力评测和回归评测分开。
