> Ontology 是可选的——直到你的 AI 需要规模化。单个 Agent、单个数据源、单个业务场景，一个好的 Prompt 加上精心设计的 RAG 就够了。但一旦你的 Agent 需要跨多个系统工作，语义歧义就会成为最大的隐形障碍。

教育硬件企业的数据现实是这样的：需求在禅道，代码在 GitLab，Bug 在 TAPD，设备信息在内部 Wiki，机型参数在 Excel，OTA 发版记录在另一个系统。

这还不是最麻烦的。最麻烦的是，AI 要在这些系统里工作，首先要搞清楚一件事：这些系统里的"版本"、"机型"、"Bug"，说的是同一个东西吗？

答案往往是：不是。

这就是语义歧义问题，也是 AI 规模化最大的隐形障碍。Ontology 要解决的，就是这个。

## 1. 数据歧义：AI 规模化最大的隐形障碍

先说一个真实的场景。

你让 AI 帮你分析"最近三个版本的 Bug 趋势"。AI 去查了数据，给你一份报告。但你发现报告里的数字和你印象里的不一样——原来，禅道里的"版本"是需求版本，TAPD 里的"版本"是 Bug 修复版本，GitLab 里的"版本"是代码 Tag，三个系统的"版本"根本不是同一个东西。

AI 不知道这三个是不同的概念，于是它把三份数据混在一起，给出了一个看起来有模有样、但实际上毫无意义的报告。

这不是 AI 笨，是**语义的问题**。

Ontology 就是解决这个问题的。它的核心思想是：**把你业务里的概念、属性、关系，用机器能懂的方式写清楚**，让 AI 在跨系统工作时有一个统一的语义参照。

## 2. 教育硬件产研的语义歧义地图

在动手建 Ontology 之前，先把歧义找出来。这是教育硬件产研最常见的语义歧义：

| 概念 | 禅道叫法 | TAPD 叫法 | GitLab 叫法 | 实际含义 |
|------|---------|---------|------------|---------|
| 软件版本 | 迭代版本 | 修复版本 | Tag / Release | 不同！需要映射 |
| 需求 | 需求 | Story | Issue | 基本一致，但字段不同 |
| Bug | 缺陷 | Bug | Issue（type=bug） | 基本一致 |
| 机型 | 产品型号 | 设备型号 | - | 可能有命名差异 |
| 测试环境 | 测试版本 | 测试环境 | Branch | 不同！ |

这张表就是你的"语义歧义地图"。每一行歧义，都是 AI 可能出错的地方。

## 3. 三个层次理解 Ontology 在产研中的价值

### 🟢 小白层次：Ontology 是 AI 的"公司术语词典"

你雇了一个新员工，他很聪明，但不了解公司的术语体系。你给他一本详细的术语词典——里面写了"版本"在不同系统里的含义、"机型"的标准命名规则、"Bug 严重程度"的分级标准。

这本词典就是 Ontology。有了它，AI 才能真正理解你的业务，而不是靠猜。

### 🔵 开发者层次：Ontology 是 Agent 的类型系统

写代码时，你知道类型系统的价值——它让编译器帮你发现错误，让 IDE 给你自动补全，让代码更可维护。

Ontology 对 Agent 的作用类似。它定义了业务领域的"类型"：什么是需求、什么是 Bug、它们之间有什么关系、哪些操作是合法的。

有了这个类型系统，Agent 的行为就从"随机的"变成了"可预测的"。

### 🔴 专家层次：Ontology 是神经符号 AI 的接口层

LLM 的推理是统计性的，不是符号性的。它能"感觉"到答案，但无法保证推理链的正确性。

Ontology 提供了符号主义的那一半——显式的概念定义、确定性的关系约束、可验证的推理规则。把 LLM 的语言理解能力和 Ontology 的结构化推理能力结合，就是当前最前沿的**神经符号 AI** 方向。

Palantir、Microsoft Fabric、OpenAI 都在往这个方向走。

## 4. 教育硬件产研 Ontology 的四个核心要素

参照 Palantir 的"数据/逻辑/行动/安全"四要素架构，结合教育硬件产研的特点：

### 4.1 数据层：统一概念定义

把产研流程中的核心概念定义清楚，消除歧义：

```yaml
# 产研核心概念定义（Ontology 数据层）

概念:
  软件版本:
    定义: "一次完整的软件发布，包含需求、代码、测试三个维度"
    属性:
      - 版本号: "格式 X.Y.Z，X=大版本，Y=功能版本，Z=修复版本"
      - 发布日期: "OTA 全量推送的日期"
      - 目标机型: "此版本覆盖的机型列表"
    映射:
      禅道: "迭代版本"
      TAPD: "修复版本"
      GitLab: "Tag（格式 v{版本号}）"

  机型:
    定义: "一款具体的教育硬件产品型号"
    属性:
      - 型号编码: "内部唯一标识，如 BBK-X10"
      - Android版本: "出厂预装的 Android 版本"
      - 屏幕尺寸: "英寸，如 10.1"
      - 内存规格: "RAM/ROM，如 4GB/64GB"
    映射:
      禅道: "产品型号"
      TAPD: "设备型号"
      Wiki: "机型参数表中的型号列"

  Bug:
    定义: "软件中已确认的缺陷，影响用户正常使用"
    属性:
      - 严重程度: "P0/P1/P2/P3（P0=崩溃，P1=功能不可用，P2=功能异常，P3=体验问题）"
      - 影响机型: "此 Bug 在哪些机型上出现"
      - 影响版本: "此 Bug 在哪些版本上存在"
    映射:
      禅道: "缺陷"
      TAPD: "Bug"
      GitLab: "Issue（type=bug）"
```

### 4.2 逻辑层：定义业务规则

把隐性的业务规则显式化，让 AI 能做确定性推理：

```yaml
# 业务规则（Ontology 逻辑层）

规则:
  OTA发布规则:
    - "P0 Bug 未修复，禁止 OTA 全量发布"
    - "崩溃率 > 基线 120%，禁止 OTA 全量发布"
    - "新版本必须覆盖出货量前 5 的机型"

  Bug优先级规则:
    - "崩溃类 Bug 自动升级为 P0"
    - "影响机型数 > 3 的 Bug 自动升级为 P1"
    - "P0 Bug 必须在 24 小时内响应"

  版本兼容性规则:
    - "新功能必须在 Android 8.0+ 上可用"
    - "UI 变更必须在所有目标机型上通过视觉测试"
```

有了这些规则，AI 就能做确定性推理：当它发现某个 Bug 影响了 4 个机型，它会自动知道这是 P1 级别，不需要你告诉它。

### 4.3 行动层：定义 AI 能做什么

明确 AI 在不同场景下能执行哪些操作：

| 场景 | AI 可以做 | AI 不能做 | 需要人工确认 |
|------|---------|---------|------------|
| Bug 分析 | 查询 Bug 数据、生成分析报告 | 修改 Bug 状态 | 提出修复方案 |
| 代码生成 | 生成代码、运行测试 | 直接合并到主干 | 提交 PR |
| OTA 发布 | 检查发布条件、生成发布报告 | 触发 OTA 推送 | 发布决策 |
| 需求分析 | 拆解需求、估算工时 | 修改需求状态 | 优先级排序 |

### 4.4 安全层：权限绑定在 Ontology 上

这是 Palantir 最核心的设计思想：**把权限绑定在 Ontology 上，而不是绑定在 API Key 上**。

传统做法是给 AI 一个 API Key，它能访问什么取决于这个 Key 的权限范围。问题是这个范围很难精细控制。

Ontology 的做法是：AI 只能访问本体中明确授权的对象和关系。越界了，直接拦截。

**教育硬件产研的权限设计**：

```yaml
# AI 访问权限（Ontology 安全层）

角色: 开发者AI
  可读:
    - 需求文档（本人负责的需求）
    - 代码仓库（本人有权限的仓库）
    - Bug 记录（全部）
    - 机型参数表（全部）
  可写:
    - 代码（通过 PR，不能直接合并）
    - 测试用例（全部）
  禁止:
    - 用户数据（任何情况下）
    - 财务数据（任何情况下）
    - 其他团队的代码仓库

角色: 测试AI
  可读:
    - 需求文档（全部）
    - 测试用例（全部）
    - Bug 记录（全部）
  可写:
    - 测试用例（全部）
    - Bug 记录（创建、更新状态）
  禁止:
    - 代码仓库（任何情况下）
    - 用户数据（任何情况下）
```

## 5. 时间感知：别让 AI 拿着过期数据说话

这是 Ontology 工程里最容易被忽视的一个维度，但在教育硬件产研里特别重要。

一款机型今年出货的版本和去年出货的版本，硬件参数可能完全不同。AI 如果拿着旧数据做分析，结论就是错的——而且它还特别自信。

OpenAI 在知识图谱实战里提出了"时间感知三元组"的概念：每条事实都带两个时间戳——`t_created`（从哪天开始真）和 `t_expired`（哪天开始不真了）。

**教育硬件产研的时间感知设计**：

| 数据类型 | 时间敏感性 | 处理方式 |
|---------|---------|---------|
| 机型参数 | 高（每批次可能不同） | 带批次号和生效日期 |
| 系统版本兼容性 | 高（随 Android 版本更新） | 带版本范围 |
| Bug 状态 | 高（随修复进展变化） | 带状态变更时间戳 |
| 业务规则 | 中（随产品策略调整） | 带生效日期 |
| 代码架构 | 低（相对稳定） | 定期更新即可 |

**实践建议**：

1. 在 AGENTS.md 里标注数据的"有效期"：`机型参数表（最后更新：2026-08-01，每季度更新）`
2. 对于高时间敏感性的数据，在 Prompt 里明确告诉 AI："请确认你使用的数据是最新版本"
3. 建立数据更新提醒机制：当关键数据超过有效期时，自动提醒相关人员更新

## 6. 从零开始的 Ontology 建设路径

别想着一次性把所有概念都定义完，那样只会把自己搞死。按影响范围来，先解决最痛的问题。

**第一步（第1-2周）：消除最高频的歧义**

找出 AI 最常出错的 3-5 个概念，先把这些定义清楚。通常是：
- 版本（需求版本 vs 代码版本 vs 发布版本）
- 机型（不同系统的命名差异）
- Bug 严重程度（统一分级标准）

**第二步（第3-4周）：建立核心业务规则**

把隐性的业务规则显式化。这些规则往往存在老员工脑子里，新人不知道，AI 更不知道：
- OTA 发布的质量门禁条件
- Bug 优先级的判断规则
- 版本兼容性的约束条件

**第三步（第5-8周）：权限绑定**

把 AI 的访问权限绑定在 Ontology 上：
- 定义不同角色的 AI 能访问什么
- 在 CI/CD 中加入权限检查

**第四步（持续）：时间感知**

- 为关键数据添加有效期标注
- 建立数据更新提醒机制，过期了自动提醒

## 7. Ontology 和 Harness 的关系

这两个概念不是竞争关系，而是互补的：

| 维度 | Harness | Ontology |
|------|---------|---------|
| 解决的问题 | AI 怎么工作（工作框架） | AI 理解什么（语义基础） |
| 作用层次 | 执行层 | 语义层 |
| 优先级 | 先做 | 规模化后做 |
| 类比 | 工作流程和规范 | 公司术语词典和业务规则 |

**实践建议**：先做 Harness（工作框架），再做 Ontology（语义基础）。

- 单个项目、单个数据源：只需要 Harness
- 跨项目、跨系统、多 Agent 协作：Harness + Ontology 都需要

教育硬件产研的规模化路径：
1. **阶段0-1（筑基+试点）**：重点做 Harness，建立工作框架
2. **阶段2（规模化）**：开始建 Ontology，消除跨系统语义歧义
3. **阶段3（持续优化）**：Harness + Ontology 协同演进

## 8. 度量 Ontology 效果

Ontology 的效果比 Harness 更难量化，但有几个可观测的指标：

| 指标 | 含义 | 目标 |
|------|------|------|
| **跨系统查询准确率** | AI 跨系统查询的结果准确率 | > 90% |
| **语义歧义导致的错误数** | 因概念混淆导致的 AI 错误数量 | 持续下降 |
| **AI 需要人工澄清的频率** | AI 因不理解概念而需要人工解释的次数 | 持续下降 |
| **权限越界拦截次数** | AI 尝试访问未授权数据被拦截的次数 | 趋近于 0 |

## 9. 📝 小结

Ontology 不是哲学课，是工程问题。说白了就是：把你业务里大家都知道但没写下来的东西，用机器能懂的方式写清楚。

教育硬件产研的数据分散在多个系统里，同一个概念在不同系统里叫法不同、口径不同。AI 没有统一的语义层，就像一个新员工没有公司术语词典——只能靠猜，猜错了还特别自信。这种错误很隐蔽，因为 AI 给出的报告看起来有模有样，你不仔细核对根本发现不了。

四个核心要素按顺序来：数据层（统一概念定义）→ 逻辑层（显式化业务规则）→ 行动层（明确 AI 能做什么）→ 安全层（权限绑定在 Ontology 上）。不要跳步，每一步都有它的价值。

时间感知这个维度容易被忽视，但在教育硬件里特别重要。机型参数、系统兼容性、Bug 状态都会随时间变化，AI 拿着过期数据说话，结论就是错的。在 AGENTS.md 里标注数据有效期，是最低成本的解法。

最后记住那个判断标准：**Ontology 是可选的——直到你的 AI 需要规模化**。单个项目先做好 Harness，跨系统规模化时再建 Ontology。别提前过度设计。
