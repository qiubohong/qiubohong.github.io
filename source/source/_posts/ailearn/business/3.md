> 教育硬件的软件研发，和纯互联网公司有本质不同——**设备碎片化**（多机型、多系统版本）、**长周期OTA迭代**、**教育内容与软件深度耦合**。这三个特点决定了一件事：你不能照搬互联网公司的AI落地方案，得走自己的路。

我见过不少团队引入AI工具的方式：老板拍板买了CodeBuddy，全员安装，然后等着效率提升。三个月后，没人说好也没人说不好，就这么不了了之了。

问题不在工具，在于没有基线、没有实验、没有度量——根本不知道有没有效果，自然也不知道哪里出了问题。

筑基阶段要解决的，就是这个问题。核心逻辑只有一句话：**先工具化，再流程化，后智能化**。

## 2. 第1周：工具选型——教育硬件企业的特殊考量

教育硬件企业的软件研发涉及**安卓应用、系统固件、后端服务、算法模型**等多类代码，工具选型需兼顾多语言、多平台。

### 2.1 推荐工具组合

| 场景 | 推荐工具 | 理由 |
|------|---------|------|
| 安卓应用开发 | **Android Studio + 通义灵码** | 通义灵码原生集成 Android Studio，中文支持好，已有多家硬件企业验证 |
| 多端代码生成 | **腾讯云CodeBuddy** | 覆盖腾讯内部超95%工程师，编码时间缩短40%，中文支持好 |
| 后端/全栈 | **Cursor / 通义灵码** | 国内外主流，支持Java/Go/Python等多语言 |
| 教育内容代码 | **AI Coding生成小程序模块** | 已有教育App实践：AI写70%代码、工程师精调30% |

### 2.2 选型注意事项

> ⚠️ **遗留代码库的坑**：教育硬件企业普遍有多年迭代的历史代码库（学习机系统、点读机固件等），AI在遗留代码上的效率增益通常**低于10%**，远低于全新项目的35-40%。
>
> **建议**：新功能/新模块优先使用AI，遗留代码改造放在后期。

### 2.3 工具选型评估表（模板）

| 评估维度 | 权重 | 工具A得分 | 工具B得分 | 备注 |
|---------|------|---------|---------|------|
| 安卓/Java支持质量 | 30% | | | 核心场景 |
| 中文代码注释支持 | 15% | | | 团队习惯 |
| 数据安全/私有化部署 | 20% | | | 教育内容合规 |
| 团队学习成本 | 15% | | | 上手难度 |
| 价格/ROI | 20% | | | 成本控制 |

**第1周交付物**：工具选型评估报告（含推荐方案、成本估算、风险说明）

## 3. 第1-2周：立治理章程——把责任写清楚

AI生成的代码出了问题，谁负责？这个问题不提前说清楚，后面一定会扯皮。

### 3.1 章程核心条款

| 条款 | 具体内容 | 教育硬件特有考虑 |
|------|---------|----------------|
| **责任归属** | AI生成代码的作者 = 最终责任人，AI只是辅助工具 | 固件代码出问题影响面大，责任必须明确到人 |
| **权限控制** | 谁能用AI、能访问哪些代码库、能调哪些模型 | 核心固件库、教育内容库需严格控制AI访问权限 |
| **透明追溯** | 所有AI辅助行为通过日志可追踪 | 便于回溯问题根因，OTA事故尤其需要 |
| **人类审查** | 关键代码必须经人工评审才能合并 | 固件/系统级代码评审标准需高于普通应用代码 |
| **内容合规** | 教育内容相关代码需额外人工审核 | 涉及未成年人保护、版权等合规要求 |

### 3.2 AI使用分级管理

不同类型的代码，AI使用权限不同：

| 代码类型 | AI使用级别 | 说明 |
|---------|-----------|------|
| 普通业务逻辑 | ✅ 完全开放 | 可用AI生成、补全、重构 |
| 教育内容相关 | ⚠️ 辅助+人工审核 | AI辅助，但内容必须人工核查 |
| 系统应用层 | ⚠️ 辅助+严格评审 | AI辅助，代码评审标准提高 |
| 核心固件/驱动 | ❌ 仅辅助，禁止全量生成 | AI只做建议，不做主力输出 |

### 3.3 章程签署流程

1. 技术负责人起草初稿（第1周）
2. 全员评审讨论（第2周初）
3. 管理层确认签署（第2周末）
4. 全员宣贯培训（第3周）

**第1-2周交付物**：AI治理章程（正式版，含签署记录）

## 4. 第2-3周：采基线数据——没有before就没有after

引入AI之前，先把"现在是什么状态"记下来。没有基线，后面什么都说不清楚。

### 4.1 基线采集清单

| 维度 | 指标 | 采集方式 | 采集周期 |
|------|------|---------|---------|
| **速度** | 需求→提测周期 | 项目管理工具（TAPD/禅道） | 4周滚动 |
| **速度** | 版本发布周期（OTA） | 发版记录 | 4周滚动 |
| **速度** | 代码评审平均时长 | Git平台统计 | 4周滚动 |
| **质量** | 线上Bug率（按机型/系统版本拆分） | Bug管理平台 | 4周滚动 |
| **质量** | 崩溃率（按Android版本） | 监控平台（腾讯腾讯火蜘蛛/自研） | 4周滚动 |
| **质量** | 测试用例通过率 | 测试管理平台 | 4周滚动 |
| **人力** | 人均月交付需求数 | 项目管理工具 | 4周滚动 |
| **人力** | 编码时间占比（vs 联调/测试/修Bug） | 工时统计 | 4周滚动 |
| **教育硬件特有** | 多机型适配工时占比 | 工时统计 | 4周滚动 |
| **教育硬件特有** | OTA回滚率 | 发版记录 | 4周滚动 |
| **教育硬件特有** | 机型兼容性问题数量 | Bug管理平台 | 4周滚动 |
| **体验** | 开发者满意度（NPS） | 匿名问卷 | 一次性 |

> ⚠️ **重要**：基线采集必须覆盖**至少4周**的数据，排除季节性波动。少于4周的数据，说服力不够，后续对比也站不住脚。

### 4.2 开发者满意度问卷（基线版）

以下问题在引入AI前做一次，引入后每月做一次，对比变化：

1. 你对当前开发工具链的满意度如何？（1-10分）
2. 你每天花在"重复性编码"上的时间大概是多少？（<1h / 1-2h / 2-4h / >4h）
3. 你觉得当前最耗时的工作环节是什么？（多选）
4. 你对引入AI编程工具的期待程度？（1-10分）
5. 你最担心AI工具带来的问题是什么？（开放题）

**第2-3周交付物**：基线数据报告（含各项指标的当前值、趋势图、问卷结果）

## 5. 第3-4周：选试点范围——从哪里开始最稳

### 5.1 试点场景优先级

| 优先级 | 试点场景 | 理由 | 预期增益 |
|--------|---------|------|---------|
| 🥇 **首选** | **单元测试/UI测试自动化生成** | 测试是公认AI提效最明显的环节，不涉及核心业务风险，失败成本低 | 测试编写效率提升50-70% |
| 🥈 **次选** | **新功能模块的CRUD代码生成** | 新功能AI增益高（35-40%），不涉及遗留代码 | 编码效率提升30-40% |
| 🥉 **备选** | **教育内容页面/H5批量生成** | 已有教育行业成功案例，页面类代码重复度高 | 页面开发效率提升40-60% |

### 5.2 试点团队选择原则

1. **自愿参与**：强制推行效果往往很差，找愿意尝试的团队
2. **规模适中**：3-8人的小团队，便于管理和数据采集
3. **有对照组**：同类型工作的另一个团队作为对照，确保数据可比
4. **技术负责人支持**：团队TL要认可这件事，否则推不动

### 5.3 试点实验方案模板

```
【实验名称】AI辅助开发对[试点场景]效能影响实验
【实验周期】YYYY-MM-DD ~ YYYY-MM-DD（共X周）
【参与团队】
  - AI组：[团队名]，[X]人
  - 对照组：[团队名]，[X]人
【控制变量】
  - 需求类型：同为[XX类型，如"学习机新功能模块"]
  - 复杂度分级：同为[P1/P2级]
  - Android版本：同为[Android X]
  - 时间周期：同期对比，排除季节性因素
【观测指标】
  - 核心指标：编码交付周期、缺陷密度
  - 质量护栏：崩溃率（不得高于基线）、OTA回滚率（不得高于基线）
  - 特有指标：多机型适配工时（AI组 vs 对照组）
  - 体验指标：开发者满意度（每周问卷）
【停机条件】
  - 崩溃率较基线上升超过20%
  - 出现P0级生产事故
  - 开发者满意度持续下降（连续2周低于基线）
【预期产出】
  - 实验报告（含数据、结论、建议）
  - Prompt模板库（至少3个可复用模板）
  - AI使用最佳实践文档
```

**第3-4周交付物**：试点实验方案（含团队确认、时间表、评审通过记录）

## 6. 筑基阶段完整检查清单

在进入试点阶段之前，确认以下所有项都已完成：

- [ ] 工具选型评估报告已完成，工具已采购/申请
- [ ] AI治理章程已定稿，全员签署
- [ ] 基线数据已采集（至少4周），报告已输出
- [ ] 开发者满意度基线问卷已完成
- [ ] 试点团队已确定（含AI组和对照组）
- [ ] 试点实验方案已定稿，评审通过
- [ ] 试点启动会已安排

**有一条没做到，就先别进入试点阶段。**

## 7. 常见问题

**Q：工具选型怎么选？通义灵码、CodeBuddy、Cursor怎么区分？**

三个都是国内可用的主流选择，关键看团队主力语言和使用场景。安卓/Java为主的团队，CodeBuddy的中文支持和Java理解更好，而且国内服务器延迟低；通义灵码在阿里云体系内集成更深，适合已在用阿里云效的团队；全栈/后端为主的团队，Cursor的多语言能力和上下文理解更强。别在这里纠结太久——先各申请1-2个试用账号，让团队实际用一周，用脚投票比任何评测都准。
**Q：基线数据采集，现有工具不支持怎么办？**

先用能采集到的，不要因为"数据不完整"就不采集。哪怕只有需求周期和Bug数量，也比没有强。后续可以逐步完善数据采集能力。

**Q：找不到愿意做对照组的团队怎么办？**

可以用同一个团队的历史数据作为对照（时间序列对比），但要注意控制其他变量（需求复杂度、人员变化等）。这种方式说服力弱一些，但总比没有对照好。

## 8. 📝 小结

筑基阶段说白了就是"磨刀不误砍柴工"。很多团队急着上工具、急着看效果，结果三个月后一地鸡毛——不知道有没有效果，也不知道哪里出了问题。

工具选型这件事，教育硬件有自己的坑：遗留代码多（AI在上面效果差）、固件安全要求高（不能乱用AI生成）、内容合规要求严（教育内容不能完全交给AI）。这三点决定了你不能照搬互联网公司的方案。

治理章程不是走形式。我见过不少团队把章程当PPT做，做完就放在那里没人看。真正有用的章程，是每个人都知道"AI生成的代码出了问题我来负责"——这句话要落到纸上，要签字，要有人追。

基线数据是这个阶段最重要的产出，没有之一。没有before，就没有after。哪怕数据不完整，也要先采起来。

最后，试点从测试自动化开始。这不是随便说的——测试是公认AI提效最明显的环节，失败成本最低，而且不涉及核心业务风险。先在这里跑通，再往其他环节扩展。
