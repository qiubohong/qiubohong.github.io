> 试点阶段最重要的一句话：**用数据说话，而不是用感觉说话**。没有对照组、没有控制变量、没有统计显著性，任何"AI让我们效率提升了X%"的说法都站不住脚。这个阶段的目标，是用6-8周的严格实验，给规模化推广提供可信的决策依据。

试点阶段有个常见的坑：AI组的人都是主动报名的，对照组的人是被安排的。这样的实验结果，有多少是AI的功劳，有多少是"主动参与者本来就更积极"的功劳？说不清楚。

所以实验设计比实验执行更重要。

## 1. 阶段概览

| 项目 | 内容 |
|------|------|
| **时长** | 6-8周 |
| **核心目标** | 通过对照实验验证AI工具的实际效果，用数据支撑规模化决策 |
| **关键产出** | 实验报告、ROI初算、Prompt模板库（≥3个）、最佳实践文档 |
| **负责人** | PMO + 技术负责人 |
| **前提条件** | 筑基阶段全部完成（工具选型、治理章程、基线数据、试点方案） |

## 2. 实验设计：先把框架搭对

### 2.1 完整实验设计模板

```
【实验名称】AI辅助开发对[试点场景]效能影响实验
【实验周期】YYYY-MM-DD ~ YYYY-MM-DD（共X周）

【参与团队】
  - AI组：[团队名]，[X]人，负责人：[姓名]
  - 对照组：[团队名]，[X]人，负责人：[姓名]

【控制变量】（以下变量两组必须保持一致）
  - 需求类型：同为[XX类型，如"学习机新功能模块"]
  - 需求复杂度：同为[P1/P2级，按故事点估算]
  - 团队规模：同为[X]人
  - Android目标版本：同为[Android X]
  - 时间周期：同期对比，排除节假日、发版冲刺等干扰

【观测指标】
  核心指标（决定实验成败）：
  - 编码交付周期（从任务开始到提测的时间）
  - 缺陷密度（每千行代码的Bug数量）

  质量护栏（触发则停止实验）：
  - 崩溃率：不得高于基线值的120%
  - OTA回滚率：不得高于基线值的120%
  - 代码评审通过率：不得低于基线值的80%

  教育硬件特有指标：
  - 多机型适配工时（AI组 vs 对照组）
  - 机型兼容性Bug数量

  体验指标：
  - 开发者满意度（每周问卷，1-10分）
  - AI工具使用频率（日均活跃使用时长）

【停机条件】（满足任一条件立即停止实验）
  - 崩溃率较基线上升超过20%
  - 出现P0/P1级生产事故
  - 开发者满意度连续2周低于基线值
  - AI组核心指标连续3周无改善

【预期产出】
  - 实验报告（含原始数据、统计分析、结论、建议）
  - Prompt模板库（至少3个可复用模板）
  - AI使用最佳实践文档
  - ROI初步测算报告
```

### 2.2 实验设计的常见错误

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| AI组全是主动报名者 | 结果混入"积极性偏差" | 两组都要有主动和被动参与者 |
| 两组需求复杂度不同 | 无法归因 | 严格控制需求类型和复杂度 |
| 实验期间有大版本发布 | 干扰数据 | 避开发版冲刺期，或单独记录 |
| 只看速度不看质量 | 速度提升但Bug激增 | 质量护栏必须同步监控 |
| 实验周期太短（<4周） | 数据不稳定，J-Curve效应未消退 | 至少6周，前2周是适应期 |

## 3. 三层度量体系：DORA × SPACE × AI专属

光看一个维度容易被误导。三层叠加，才能看清楚发生了什么。

### 3.1 第一层：DORA——看"交付结果"

这四个指标是行业公认的研发效能基准，教育硬件企业需要结合OTA发版特点做适配：

| DORA指标 | 通用定义 | 教育硬件适配 | 采集方式 |
|---------|---------|------------|---------|
| **部署频率** | 代码部署到生产的频率 | OTA推送频率（全量/灰度） | 发版记录 |
| **变更前置时间** | 代码提交到生产部署的时间 | 需求提测→OTA推送的时间 | CI/CD流水线 |
| **变更失败率** | 导致服务降级的部署比例 | OTA回滚率 + 热修复率 | 发版记录 |
| **故障恢复时间** | 生产故障的平均恢复时间 | 崩溃/ANR问题的平均修复时间 | 监控平台 |

> 💡 教育硬件企业的OTA发版周期通常是**2-4周**，远长于互联网公司的每日发布。因此"部署频率"这个指标的绝对值会偏低，重点看**相对变化趋势**，而不是和互联网公司比较。

### 3.2 第二层：SPACE——解释"为什么结果变成这样"

DORA告诉你结果，SPACE告诉你原因：

| SPACE维度 | 具体指标 | 采集方式 |
|---------|---------|---------|
| **满意度（Satisfaction）** | 开发者NPS、工具满意度评分 | 每周匿名问卷 |
| **绩效（Performance）** | 人均需求交付数、任务完成率 | 项目管理工具 |
| **活动（Activity）** | 编码时间占比、PR数量、代码提交频率 | Git统计 |
| **沟通协作（Communication）** | 代码评审效率、评审轮次 | Git平台 |
| **效率（Efficiency）** | 上下文切换次数、专注编码时长 | 工时统计/IDE插件 |

### 3.3 第三层：AI专属指标——看"AI用得怎么样"

| 指标 | 计算方式 | 参考值 |
|------|---------|--------|
| **工具活跃率** | 日均活跃使用AI工具的开发者数 / 团队总开发者数 | 目标>70% |
| **AI代码占比** | AI生成代码行数 / 总新增代码行数 | 行业参考：腾讯50% |
| **AI代码接受率** | 开发者接受AI建议的比例 | 目标>40% |
| **Token消耗** | 人均Token使用量（成本侧） | 用于ROI测算 |
| **AI辅助编码时间占比** | AI辅助的编码时间 / 总编码时间 | 目标>30% |

### 3.4 教育硬件特有指标

这是和纯互联网公司最大的差异，必须单独追踪：

| 指标 | 定义 | 为什么重要 |
|------|------|---------|
| **多机型适配工时** | 为适配不同机型/屏幕尺寸花费的工时 | 教育硬件碎片化严重，这是主要痛点之一 |
| **OTA发版周期** | 从代码冻结到全量推送的时间 | 反映整体交付效率 |
| **OTA回滚率** | 发布后需要回滚的OTA比例 | 质量底线，AI不能让这个指标变差 |
| **机型兼容性Bug率** | 因机型差异导致的Bug数量 / 总Bug数量 | AI生成代码是否加剧了兼容性问题 |

## 6. J-Curve效应：头2周效率下降是正常的

这个现象值得单独说一下，因为很多团队在这里放弃了。

J-Curve效应是指：引入新工具的头几周，效率往往会**先下降**，因为大家在学习和适应。表现为：
- 编码时间变长（在想怎么写Prompt）
- 代码评审时间变长（在学习如何审查AI生成代码）
- 开发者满意度可能下降（工具还不熟练，感觉在添麻烦）

**这是正常现象，不是AI没用的证据。**

| 阶段 | 时间 | 典型表现 |
|------|------|---------|
| 适应期 | 第1-2周 | 效率可能下降10-20%，满意度波动 |
| 平台期 | 第3-4周 | 效率回到基线水平，开始找到节奏 |
| 收益期 | 第5周+ | 效率开始超越基线，满意度上升 |

> ⚠️ **给管理层的提醒**：如果在第1-2周看到效率下降就叫停实验，那永远看不到真正的效果。建议提前和管理层说清楚J-Curve效应，设定"至少跑满6周"的底线。

## 7. Prompt模板库：试点阶段必须沉淀的资产

试点阶段最重要的"软资产"，是一套可复用的Prompt模板。这些模板是后续规模化推广的核心工具。

### 7.1 教育硬件场景Prompt模板示例

**模板1：安卓单元测试生成**
```
你是一个安卓开发专家，熟悉JUnit4、Mockito和Espresso测试框架。
请为以下[类名/方法名]生成完整的单元测试：

[粘贴代码]

要求：
1. 覆盖正常流程、边界条件、异常情况
2. 使用Mockito模拟外部依赖
3. 测试方法命名遵循：should_[期望结果]_when_[条件]
4. 添加中文注释说明每个测试的目的
5. 目标覆盖率：行覆盖率>80%
```

**模板2：多机型适配代码生成**
```
你是一个安卓适配专家，熟悉不同屏幕尺寸和Android版本的兼容性处理。
以下代码需要适配[机型列表/屏幕尺寸范围/Android版本范围]：

[粘贴代码]

请：
1. 识别可能存在的兼容性问题
2. 提供适配方案（优先使用官方API，避免硬编码）
3. 对每个适配点添加注释，说明为什么需要这样处理
4. 如果需要版本判断，使用Build.VERSION.SDK_INT
```

**模板3：教育功能模块代码生成**
```
你是一个教育App开发专家，了解学习机/点读机的产品形态。
请根据以下需求描述，生成[功能模块名]的实现代码：

需求描述：[粘贴需求文档或描述]
技术约束：
- 目标Android版本：[X]
- 目标机型：[机型列表]
- 现有代码架构：[MVP/MVVM/MVI]
- 依赖库：[列举主要依赖]

要求：
1. 代码结构清晰，遵循现有架构模式
2. 关键逻辑添加中文注释
3. 考虑内存和性能优化（学习机硬件配置较低）
4. 提供单元测试骨架
```

### 7.2 Prompt模板沉淀规范

每个Prompt模板需要记录：
- **模板名称**：简洁描述用途
- **适用场景**：什么情况下用这个模板
- **模板内容**：完整的Prompt文本
- **使用说明**：需要替换哪些占位符
- **效果评估**：使用后的实际效果（好用/一般/需改进）
- **贡献者**：谁提交的，方便后续追问

## 9. 📝 小结

试点阶段做完，你应该能回答三个问题：AI到底有没有效果？效果有多大？哪些场景最有效？如果这三个问题还是模糊的，说明实验设计或数据采集有问题，不要急着进入规模化。

三层度量体系（DORA × SPACE × AI专属）不是为了好看，是因为单看任何一层都会被误导。DORA告诉你结果，SPACE告诉你原因，AI专属指标告诉你工具用得怎么样。教育硬件还要额外盯着多机型适配工时和OTA回滚率——这两个是行业特有的质量底线。

J-Curve效应这件事，建议在实验启动前就和管理层说清楚。头两周效率下降是正常的，不是AI没用，是大家在适应。如果管理层不理解这个，很可能在最关键的时候叫停实验。

Prompt模板库是这个阶段最容易被忽视的产出。好用的Prompt不记下来，下次还得重新摸索。建议每周固定时间让AI组成员更新一次，哪怕只有一条，也比没有强。

行业参考：腾讯2025年数据，超90%工程师在用AI编程助手，50%新增代码由AI辅助生成，整体效能提升超20%。这条路是走得通的，但前提是实验做扎实。
