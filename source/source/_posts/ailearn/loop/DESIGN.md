### 第 04 篇：你的 Agent 为什么跑着跑着就"失忆"了？

**发布日期建议**：第 03 篇后 3-4 天
**字数目标**：3000-3500 字
**阅读时长**：7 分钟
**难度**：⭐⭐⭐ 进阶

#### 写作目标
讲清楚 Agent 的上下文管理问题和解决方案，这是生产环境中最常遇到的痛点。

#### 大纲

```
【开头 - 痛点共鸣】
- 场景：让 Agent 帮你重构一个大项目，做到第 10 步它突然忘了前面做过什么，开始重复操作。
- 根本原因：Token 窗口有限，塞不下所有历史。
- 这就像人的短期记忆 —— 你在超市记住 7 件商品已经很不容易了，Agent 也一样。

【第一节：Token 窗口的本质】
- 什么是上下文窗口，为什么它有上限
- 一个直观计算：一次完整的 Agent 交互大概消耗多少 Token
- 为什么"窗口越大越好"不是正确答案（成本、延迟、注意力稀释）

【第二节：三种上下文管理策略】
- 策略一：压缩（Summarization）
  - 把长对话压缩成摘要
  - 什么时候触发压缩
  - 压缩会丢信息怎么办
- 策略二：截断（Truncation）
  - 保留最近 N 轮，丢弃更早的
  - 用系统提示词记住关键上下文
- 策略三：外部存储（Checkpoint/RAG）
  - 把对话历史存到外部，需要时检索
  - Claude 的 checkpoint 机制
  - 什么时候做 checkpoint

【第三节：会话连续性设计】
- 问题：用户关掉浏览器，回来后 Agent 还能接着做吗？
- 会话恢复的实现思路
- 持久化什么：消息历史、工具状态、任务进度
- 实际案例：Claude 的 session resumption 机制

【第四节：实战建议 — 上下文管理的决策指南】
- 小任务（< 10 轮）：不需要管理，直接塞满
- 中任务（10-50 轮）：触发压缩 + 保留关键节点
- 大任务（50+ 轮）：checkpoint + 外部存储 + 子任务拆分
- 一张决策表

【结尾】
- 总结：Agent 不"失忆"的三板斧
- 新问题：当一个 Agent 搞不定怎么办？
- 下一篇预告：多 Agent 协作的编排之道
```

### 第 05 篇：当一个 Agent 不够用：多 Agent 协作的编排之道

**发布日期建议**：第 04 篇后 3-4 天
**字数目标**：3200-3500 字
**阅读时长**：8 分钟
**难度**：⭐⭐⭐⭐ 高级

#### 写作目标
讲清楚何时需要多 Agent、如何设计 Agent 间的协作机制。

#### 大纲

```
【开头 - 场景引入】
- 一个真实需求："帮我把这个项目从 JavaScript 迁移到 TypeScript"
- 拆一下：需要读代码的 Agent、改代码的 Agent、跑测试的 Agent、检查类型的 Agent
- 一个 Agent 能搞定吗？能，但效率很低。就像一个人同时当建筑师、泥瓦匠、水电工。

【第一节：什么时候该从单 Agent 升级到多 Agent】
- 四个信号：
  - 工具集太大，Agent 选错工具的概率增加
  - 任务需要不同的"专业知识"（不同 system prompt）
  - 步骤之间有明确的分工界限
  - 需要互相校验（一个干活一个检查）
- 不要过早多 Agent：增加复杂度，调试难度翻倍

【第二节：Orchestrator + Expert 模式】
- 核心架构图：一个编排者 + 若干专家
- Orchestrator 的职责：
  - 理解用户意图
  - 把任务拆分给合适的专家
  - 汇总结果
  - 决定是否需要追加轮次
- Expert Agent 的特点：
  - 独立的 system prompt（专业能力）
  - 独立的工具集（权限隔离）
  - 独立的对话历史（互不干扰）
- 实际案例：Saik0s/agent-loop 的实现解读

【第三节：Agent 间的信息传递】
- 问题：专家 A 的结果，专家 B 怎么知道？
- 三种传递方式：
  - 共享文件系统（简单粗暴）
  - Orchestrator 转发摘要（可控）
  - 共享记忆存储（复杂但强大）
- 各自的适用场景和权衡

【第四节：配置驱动的 Agent 定义】
- 用 Markdown/YAML 定义一个 Expert Agent
- 优势：非工程师也能配置新专家
- Saik0s/agent-loop 的 Markdown 配置示例
- 什么时候适合配置驱动 vs 代码驱动

【第五节：踩坑指南】
- 坑一：Agent 之间互相推诿（"这不是我的职责"）
- 坑二：Orchestrator 自己干活，不分发给专家
- 坑三：信息丢失 —— 专家做了重要决策但没传回来
- 对应的解决方案

【结尾】
- 总结：多 Agent 不是"越多越好"，是"分得好"
- 下一篇预告：三种 Loop 方案怎么选？给你一张决策地图
```

### 第 06 篇：Agent Loop 选型指南：三种方案怎么选？

**发布日期建议**：第 05 篇后 3-4 天
**字数目标**：2800-3200 字
**阅读时长**：6 分钟
**难度**：⭐⭐ 总结决策

#### 写作目标

#### 大纲

```
【开头 - 实用主义】
- "学了这么多方案，回到你自己的项目上 —— 到底该用哪种？"
- 这篇不讲新概念，只帮你做决策

【第一节：三种方案横向对比】
- 一张大表：
  | 维度 | 确定性循环 | SDK Agent Loop | 多 Agent 编排 |
  | 复杂度 | 低 | 中 | 高 |
  | 灵活性 | 低 | 高 | 高 |
  | 可预测性 | 高 | 中 | 低 |
  | 调试难度 | 简单 | 中等 | 困难 |
  | 适用场景 | 固定流程 | 通用任务 | 复杂协作 |
  | 代表实现 | Google ADK | Claude/OpenAI | Saik0s/agent-loop |

【第二节：场景选型决策树】
- 你的任务是否步骤固定？→ 确定性循环
- 需要多种专业能力？→ 多 Agent
- 其他情况 → SDK Agent Loop
- 配一张决策树流程图

【第三节：混合使用的实战建议】
- 其实不用"只选一种"
- 常见组合：
  - Orchestrator 用 Agent Loop + 子任务用确定性循环
  - 主 Loop 用 SDK 风格 + 特定步骤用固定流程

【第四节：你自己的 Agent Loop 设计清单】
- 10 个问题帮你检查你的 Loop 设计：
  1. 终止条件明确吗？
  2. 有兜底的最大迭代限制吗？
  3. 上下文管理策略选好了吗？

  5. 有可观测性（日志、trace）吗？
  6. 需要 Hooks 做安全检查吗？
  7. 会话断开后能恢复吗？
  8. 单 Agent 够用还是需要多 Agent？
  9. Agent 间信息传递机制确定了吗？
  10. 有没有过度设计？
```

### 4.3 去 AI 味写作指南（chinese-writer-de-ai 应用）

**全系列需要遵守的写作原则**：

| 规则 | 示例 |
|------|------|
| ❌ 不用"首先、其次、再者、综上" | ✅ 用自然过渡："第一个问题是…" "还有就是…" "说到底…" |
| ❌ 不用"值得注意的是" | ✅ "其实有个容易忽略的点" |
| ❌ 不用"本文将探讨" | ✅ "这篇聊聊" / "我们来看看" |
| ❌ 不用"随着XX的发展" | ✅ 用具体事件/数据开头 |
| ❌ 句子超 40 字 | ✅ 一句话一个意思，短句为主 |
| ❌ 所有段落等长 | ✅ 长短交替，有节奏感 |
| ✅ 多用"你"、"我" | 拉近距离 |
| ✅ 多用问句 | 引发思考 |
| ✅ 加入个人观察 | "我在做 XX 项目时发现…" |
| ✅ 适当用类比 | 复杂概念 → 生活常识 |

**公众号特别优化**：
- 小标题要吸引眼球，用问句或反直觉表述

- 每篇至少 2-3 张配图（流程图、对比图、代码截图）
