## 一、逐页讲稿

### P1 封面

- **本页是什么**：本讲封面，抛出核心命题「模型聪明 ≠ 干活靠谱」。
- **开场/衔接话术**：「上一讲我们让 Agent 跑起来了，还知道怎么让它不『失忆』、怎么看见它在干嘛。但会跑，不等于能上线。今天要解决一个更现实的问题：怎么让 Agent 跑得稳、敢上线。先抛一句话，这句话是整节课的地基——**模型聪明，不等于干活靠谱**。」
- **核心讲解**：开场先破一个迷思：很多人以为 Agent 不好用是模型不够强，于是不停换更强的模型。但大厂的实践告诉我们，同样的模型，效果能差 20 个百分点以上，差别不在模型，在「模型外面那套东西」。今天讲工程化三件套：**约束（Harness）、评测、安全**。学完你手里会多一张「上线前检查清单」，任何 Agent 上线前照着打勾，就能避开大部分坑。这 50 分钟信息量大，节奏是「先讲怎么驯服模型，再讲怎么证明有效，最后讲怎么守住底线」。
- **页面关键元素指引**：强调副标题「模型聪明≠干活靠谱，能力要靠框架驯服」这个对立关系。
- **现场动作/Demo**：无
- **可能的学员提问 & 回答**：
  - Q：「工程化和上一讲的机制有什么区别？」A：「上一讲是『懂它怎么跑』，这一讲是『让它跑得稳、能验收、敢上线』——机制解决能不能跑，工程化解决可不可信。」
- **时长**：约 2 分钟

### P2 Harness：智能体马具

- **本页是什么**：本讲第一个重点页，用「马具」隐喻引入 Harness，并用 Terminal Bench 52.8%→66.5% 的巨型数字证明「能力不只靠模型，更靠框架」。
- **开场/衔接话术**：「先认识今天的主角——Harness。Harness 这个词原意是『马具』：马鞍、缰绳、马镫这些。马本身很强，但没有马具，马的力量是随机的、难控制的；有了马具，骑手才能把马的力量引到正确的方向。」
- **核心讲解**：AI 模型就像那匹马——能力是「尖刺型」的，某些地方极强，某些地方又莫名其妙失误。Harness 就是围绕模型搭的一套系统，把它的能力引导到你需要的方向，同时在它容易出错的地方设保护。证据来了，看这个巨型数字：LangChain 团队在 Terminal Bench 2.0 上做实验，**同样的模型（GPT-5.2-Codex），只改 Harness 设计，得分从 52.8% 提到 66.5%，整整 +13.7 个百分点**。没换模型、没加算力，只是把「模型外面的那套东西」重新设计了一遍。LangChain 的原话很精辟：「Harness 的目标，是把模型天生不稳定的智能，塑造成我们需要的形态。」记住这个数字，它证明了一件反直觉的事：**当模型能力拉不开差距时，拼的就是 Harness 的质量**。
- **页面关键元素指引**：巨型数字 52.8%→66.5% 是视觉锚点，激光笔在数字上停 3 秒；右侧卡片点「尖刺型智能」和「+13.7」。
- **现场动作/Demo**：无
- **可能的学员提问 & 回答**：
  - Q：「改『外壳』具体改了啥？」A：「主要是让 AI 从『写完就交』变成『写完自测』——加了验证循环、死循环检测、上下文地图这些，接下来三页逐个拆。」
- **时长**：约 4 分钟

### P3 Harness 六大组件

- **本页是什么**：拆解 Harness 的六个核心组件，并给出 P0-P2 优先级矩阵。
- **开场/衔接话术**：「那这套『马具』具体由什么组成？一个完整的 Harness 有六个维度的设计，但注意——**不是所有组件都同等重要**，我们按投入产出比排个优先级。」
- **核心讲解**：六大组件分别是：系统提示词（定义工作框架和行为规范）、工具集（给 AI 提供执行能力）、中间件（在关键节点拦截纠偏）、上下文管理（控制 AI 的信息视野）、执行流程（设计任务节奏）、验证层（确保结果真正符合要求）。但千万别想着当「六边形战士」，优先级矩阵才是重点：**P0 必做的是「系统提示词 + 验证层」**——系统提示词投入低、效果高，是第一件要做的事；验证层投入中等、效果极高，是第二件。P1 重要的是「工具集 + 执行流程」。P2 进阶才是「中间件 + 上下文管理」，找到失败模式再加。给新手的策略一句话：**先把 P0 做好，效果就能提升 50% 以上**，别一上来就六个全上。
- **页面关键元素指引**：左列表右矩阵，先左后右；在 P0 那两行「系统提示词 / 验证层」重点停一下。
- **现场动作/Demo**：无
- **可能的学员提问 & 回答**：
  - Q：「为什么中间件和上下文管理是 P2 不是 P0？」A：「因为它们是针对『已知失败模式』的定向修复——你得先跑起来、发现 Agent 到底在哪里翻车，再针对性地加。没找到失败模式就加中间件，是过度设计。」
- **时长**：约 4 分钟

### P4 关键机制：强制验证

- **本页是什么**：讲 Harness 里最有价值、最容易落地的实践——Build & Verify 四阶段工作流 + 防死循环中间件。
- **开场/衔接话术**：「六个组件里，验证层为什么排在 P0？因为 AI 有一个天然的毛病：写完代码，自己看一眼觉得没问题，就停了。它不测试、不验证、不查边界，直接交差。LangChain 分析了大量 Trace 后发现，最常见的失败不是『不会写』，而是『写完不验证』。」
- **核心讲解**：解决之道叫 Build & Verify，核心思路是**把「验证」从可选项变成必选项**。四个阶段：**规划与发现**（读懂任务、扫代码库、想好怎么验证）→ **构建**（实现功能，同时写测试，覆盖正常路径 + 边界 + 异常）→ **验证**（跑测试，读完整输出，对照任务要求检查——注意是对照任务要求，不是对照自己写的代码）→ **修复**（回到原始需求，改完重新验证）。这里有个细节特别重要：AI 验证时有个天然偏差，它倾向于「用自己写的代码验证自己写的代码」，等于自己给自己打分，所以要特别强调「对照任务要求」。光靠提示词还不够，还要加两个中间件兜底：**PreCompletionChecklistMiddleware**（AI 想退出时拦截它，强制做完验证清单才放行）和 **LoopDetectionMiddleware**（追踪同一文件的编辑次数，超过阈值就注入「重新审视你的方案」的警告，打破死循环）。
- **页面关键元素指引**：指右侧四阶段流程闭环，在「验证」到「修复」的回环上强调「不通过不许交」。
- **现场动作/Demo**：可选演示。若有时间，展示 PreCompletionChecklistMiddleware 的拦截日志（见代码示例 2.1），让学员看到「AI 想交差 → 被拦 → 补验证」的过程。
- **可能的学员提问 & 回答**：
  - Q：「这个和 TDD 有什么区别？」A：「理念像，但这是**给 AI 设计的工作流程，不是给人的**。人写 TDD 会自觉，AI 不会，所以必须靠提示词 + 中间件『强制执行』，否则它写完就交。」
- **时长**：约 5 分钟

### P5 上下文工程

- **本页是什么**：讲如何管理 AI 的「视野」，核心原则「可见即存在」和「地图优于百科全书」。
- **开场/衔接话术**：「验证解决了『写完不测』的问题。但还有个更隐蔽的坑——AI 看到的和你以为它看到的不一样。OpenAI 工程师有句话特别扎心：从 AI 的角度看，它在运行时访问不到的任何内容，都是不存在的。」
- **核心讲解**：你存在 Google Docs 里的设计文档、存在 Slack 里的架构决策、存在你脑子里的隐性知识——对 AI 来说统统不存在。所以上下文工程要解决两个相反的问题：**信息不足**（AI 需要的信息没放进上下文，它就不知道）和**信息过载**（塞太多，AI 找不到重点，甚至出现「上下文焦虑」，窗口快满时草草收尾）。两个解法：第一，「可见即存在」——把 AI 需要的信息放进它能访问的地方（代码仓库、文档、工具）。第二，「地图优于百科全书」——别把所有信息都塞进上下文，给 AI 一份 100 行的 AGENTS.md 导航地图，告诉它「去哪里找」，而不是「把一切都给它」。OpenAI 试过把信息全塞进一个大文档，结果失败：上下文是稀缺资源，当一切都「重要」时，一切都不重要。
- **页面关键元素指引**：指向 AGENTS.md 深卡，强调「100 行、是目录不是百科全书」；对比图「塞一本书」vs「给一张地图」。
- **现场动作/Demo**：无
- **可能的学员提问 & 回答**：
  - Q：「AGENTS.md 和上一讲的 CLAUDE.md 什么关系？」A：「同一类东西，不同叫法，都是『持久导航/规则文件』。区别在于定位——CLAUDE.md 偏『规则约束』，AGENTS.md 偏『项目地图』，实践中经常合在一起用。」
- **时长**：约 4 分钟

### P6 多智能体协作

- **本页是什么**：讲规划者 + 生成者 + 评估者三角架构，解决「AI 自己评估自己不可靠」的问题。
- **开场/衔接话术**：「前面都在说单个 Agent 怎么驯服。但有个根本问题单 Agent 解决不了：让同一个 AI 既做事又评价自己做的事，效果极差。Anthropic 工程师的原话是——当被要求评估自己产出的工作时，AI 倾向于自信地称赞这些工作，即使质量明显平庸。」
- **核心讲解**：原因是 AI 生成内容时形成「内部一致性」，评估时用同一套预期，很容易得出「没问题」。解法是**三角架构**：规划者（把模糊需求扩展成完整规格，只管「做什么」）→ 生成者（按规格实现，只管「怎么做」）→ 评估者（独立评估，只管「好不好」）。三者制衡，效果远超单打独斗。Anthropic 用这套架构 4 小时花了 124 美元做出了一个能用的数字音频工作站（DAW）。两个关键设计：一是 **Sprint 合约**——每个 Sprint 开始前，生成者和评估者先对「什么叫完成」达成共识，评估才有明确标准；二是**要明确告诉评估者「要挑剔」**，否则开箱即用的 AI 是很差的 QA，会说服自己「问题不大」然后放行。给评估者配上 Playwright 让它真去点 UI，而不是只看代码。但要提醒：多智能体成本是单 Agent 的 4~10 倍，简单任务别上，**任务价值 > 10 倍额外成本时才值得**。
- **页面关键元素指引**：左三角架构图，从规划者 → 生成者 → 评估者走一遍，再点「反馈」回环；右侧卡讲 Sprint 合约和成本判断。
- **现场动作/Demo**：无
- **可能的学员提问 & 回答**：
  - Q：「这和上一讲的多 Agent 编排是一回事吗？」A：「上一讲讲的是编排 Loop（Orchestrator 带专家），这里讲的是把『评估』这个角色独立出来的质量设计。两者可以叠加：Orchestrator-Workers 负责分工，规划/生成/评估负责质量。」
- **时长**：约 4 分钟

### P7 评测：没有评测就没有改进

- **本页是什么**：讲 Agent 评测为什么难（四大难点）和评测的四层结构。
- **开场/衔接话术**：「约束讲完了。现在进入第二件套——评测。先说一个让很多人沮丧的事实：给 Agent 写评测，比给普通代码写单测难得多。Anthropic 有句话我反复读了好几遍：没有评估的团队会陷入被动循环——修复一个失败，又制造另一个，无法区分真正的回归与噪声。」
- **核心讲解**：为什么难？四个难点：**输出非确定**（同一问题问两次，两个不同但都对的答案，没法 `assertEqual`）；**过程比结果更重要**（答案对了但中间调错工具、走过弯路、甚至产生幻觉，算过吗？）；**错误会传播叠加**（第一步小错到第三步变成大错）；**没有通用基准**（客服 Agent 和代码 Agent 的「好」标准完全不同）。那评什么？四个层次：**结果层**（任务完成了吗）、**过程层**（怎么完成的、调了哪些工具）、**质量层**（完成得好不好、有没有幻觉）、**稳定性层**（跑 10 次通过几次）。大多数团队只评结果层，忽略了过程层，而这往往才是问题的根源。数据对比很触目：有评测的团队几天内能完成模型升级，没评测的要几周——不是几小时的差距，是几天 vs 几周。
- **页面关键元素指引**：指「四大难点」和「评测四层」，在「过程比结果更重要」上重点停顿。
- **现场动作/Demo**：无
- **可能的学员提问 & 回答**：
  - Q：「我只想快速上手，四个层次都要做吗？」A：「先做结果层（最好评），再补过程层（最有价值）。稳定性层是上线前必须补的。别想着一步到位。」
- **时长**：约 4 分钟

### P8 评测方法论

- **本页是什么**：讲业界主流评测方法论——Anthropic 三类评分器、pass@k vs pass^k、微软 AgentEval、以及「忠实度仅 32%」的反直觉案例。
- **开场/衔接话术**：「难归难，业界已经摸出了一套方法。这一页信息密度高，大家抓三个关键词：三类评分器、pass@k vs pass^k、忠实度 32%。」
- **核心讲解**：第一，Anthropic 把评分器分三类：**代码评分器**（字符串匹配、测试通过率，快准便宜）、**模型评分器**（LLM-as-Judge，灵活能处理主观判断，但评判模型要比被评的强）、**人工评分器**（黄金标准）。口诀：「能用代码的用代码，必须主观的用 LLM，需要黄金标准的用人工」。第二，非确定性怎么处理，两个指标：**pass@k** = 跑 k 次至少成功一次的概率（适合「一次成功就够」的工具场景）；**pass^k** = 跑 k 次全部成功的概率（适合需要稳定性的用户场景）。开发阶段看 pass@k（能不能做到），上线前看 pass^k（稳不稳定）。第三，微软 AgentEval 用三个智能体解决「评估标准从哪来」的冷启动问题：CriticAgent 生成标准、QuantifierAgent 打分、VerifierAgent 验证标准靠不靠谱。最后这个反直觉案例务必记住：AWS 评测一个旅行规划 Agent，**响应质量高达 83.9%，但忠实度只有 32.3%**——工具返回空结果时，它有近七成概率在编造数据。过程流畅 ≠ 结果正确，这就是为什么要分开测「过程」和「结果」。
- **页面关键元素指引**：右侧反直觉案例卡「忠实度 32%」是记忆点，强调「83.9% vs 32.3%」的反差。
- **现场动作/Demo**：无
- **可能的学员提问 & 回答**：
  - Q：「pass@k 和 pass^k 怎么记不混？」A：「@ 是『至少一次』，像邮件 at 一个人就够；^ 是『次次都要』，像幂次要求全部通过。开发看 @，上线看 ^。」
- **时长**：约 5 分钟

### P9 DeepEval 实战

- **本页是什么**：本讲第二个动手页，演示用 DeepEval 跑起第一个 Agent 评测，掌握三大 Agent 指标。
- **开场/衔接话术**：「方法论讲完了，该动手了。道理都懂但不知道从哪写代码？今天就给你一个 10 分钟能跑起来的工具——DeepEval。它和 Pytest 是同一套思路：你写过单测吧？`assert` 一下，绿了过、红了挂。DeepEval 就是把这套搬到 LLM 评测上。」
- **核心讲解**：三个专门为 Agent 设计的指标，拿来就能用：**ToolCorrectnessMetric**（工具调用对不对，能验证工具名、入参、输出、顺序）、**PlanAdherenceMetric**（有没有按计划执行，需配合追踪）、**AgentGoalCompletionMetric**（目标完成了吗，用 LLM 语义判断）。安装就一句 `pip install -U deepeval`，写个 `test_basic.py`，`deepeval test run` 一跑就出分。两个注意点一定要记住：**指标别选太多，不超过 5 个**——多了跑得慢、结果难解读；**评判模型要比被评测的 Agent 更强或同级**——用 GPT-3.5 评 GPT-4 的结果不可信。最后它和 Pytest 原生集成，加进 GitHub Actions，每次 PR 自动跑评测，指标没过就标红，在合并前拦下回归。
- **页面关键元素指引**：代码块是本页视觉锚点，指向 `ToolCorrectnessMetric` / `AgentGoalCompletionMetric` / `GEval` 三个关键类。
- **现场动作/Demo**：**要演示**。现场 `pip install deepeval` → 跑 `test_basic.py` → 展示终端分数和理由。若网络不稳放录屏。
- **可能的学员提问 & 回答**：
  - Q：「我不做客服 Agent，指标怎么选？」A：「按场景分类：RAG Agent 用 ContextualPrecision + Faithfulness + 一个自定义；工具调用 Agent 用 ToolCorrectness + AgentGoalCompletion + 一个自定义；自定义用 GEval，用自然语言描述你的业务标准。」
- **时长**：约 6 分钟

### P10 生产监控

- **本页是什么**：讲 Agent 上线后的持续评测——OTel 追踪、失败用例回流、告警机制（瑞士奶酪模型）。
- **开场/衔接话术**：「离线评测跑通了，Agent 上线了。上线第三天你收到一条用户反馈：『我问了个简单问题，它给了个完全不相关的答案。』你去翻评测记录，所有指标都是绿的。这就是离线评测的边界——你只能测到你想到的场景。」
- **核心讲解**：Anthropic 用「瑞士奶酪模型」打比方：每一层防护都有漏洞，单独一层不够，多层叠加才能兜住。离线评测是一层，生产监控是另一层。生产监控的核心是**追踪**：用 OpenTelemetry（OTel）记录 Agent 每一步——收到什么、调了什么工具、返回了什么、输出了什么。光看最终输出不够，要追踪到**工具调用层面**，因为忠实度问题（工具返回空、Agent 编造数据）只有在这个层面才能发现。最有价值的一步是**把失败用例回流测试集**：生产环境出现低分用例，就把它加入测试集，下次离线评测就覆盖这个场景，形成闭环。最后是告警：分数骤降（7 日均值跌 10%）、某类输入失败率超 30%、出现新型失败模式，都要主动通知。一个坑：全量评估太贵，用**抽样 + 触发式评估**（只评可疑调用）控制成本。
- **页面关键元素指引**：瑞士奶酪模型图讲「多层叠加」；右侧强调「追踪到工具层」和「失败回流」。
- **现场动作/Demo**：无
- **可能的学员提问 & 回答**：
  - Q：「离线评测和生产监控是二选一吗？」A：「不是，是互补叠加。离线评测快、可复现但覆盖有限；生产监控慢、被动但能发现你没想到的问题。两层叠加才是完整体系。」
- **时长**：约 4 分钟

### P11 安全防线

- **本页是什么**：讲 Agent 安全的三道防线——事前（红黄线黑名单 + 审计）、事中（权限收窄 + Pre-flight）、事后（夜间巡检 + 灾备）。
- **开场/衔接话术**：「最后一个话题，也是底线话题——安全。前面讲了怎么驯服、怎么评测，但如果一个高权限 Agent 被注入攻击带偏了，前面全白搭。OpenClaw 的安全实践总结成一句话：**日常零摩擦，高危必确认，每晚有巡检**。」
- **核心讲解**：三道防线，按时机分。**事前**：行为层黑名单——红线命令（`rm -rf /`、改认证、外发敏感数据、代码注入、供应链投毒）遇到必须暂停向人类确认；黄线命令（sudo、装包、改网络规则）可以执行但必须当日留痕。再加一道「极简代码审计」：装任何 Skill/MCP/第三方脚本前，先看代码再敲回车，警惕「二次下载」（`npm install`、`curl | sh`、`base64 -d | bash` 这些能绕过安检带进新代码的指令）。**事中**：权限收窄（核心配置文件 `chmod 600`）+ 哈希基线（`sha256sum` 生成指纹，巡检时对比防篡改）+ Pre-flight 高危业务风控（不可逆操作前强制风控，命中高危硬中断）。**事后**：每晚自动巡检（13 项指标显性化汇报，绝不「一切正常」一笔带过）+ Git 灾备。核心心法：**高危操作永远要有人（Human-in-the-loop）确认，这是抵御高阶攻击的最后防线**。
- **页面关键元素指引**：三层防线图按「事前 → 事中 → 事后」顺序讲，红线/黄线清单用颜色强调。
- **现场动作/Demo**：无
- **可能的学员提问 & 回答**：
  - Q：「我就做个内部小工具，也要搞三道防线吗？」A：「按风险等比缩放。内部只读小工具，把『红线命令确认 + 操作留痕』做起来就够；一旦 Agent 有写权限、碰生产、碰资金，三道防线就都得有。」
- **时长**：约 4 分钟

### P12 工程化检查清单（交付）

- **本页是什么**：收尾页，交付「上线前 10 问」检查清单，布置练习和自测。
- **开场/衔接话术**：「三件套讲完了。现在把 50 分钟的内容，压成一张你可以带走的清单——任何 Agent 上线前，问自己这 10 个问题，答不上来就别上线。」
- **核心讲解**：上线前 10 问：验证层有吗（写完自测了吗）？死循环防了吗（有 max 迭代/编辑阈值吗）？评测过了吗（结果/过程/稳定性至少跑过）？上下文工程做了吗（有导航地图吗）？多智能体的评估独立了吗？生产监控上了吗（有追踪吗）？失败用例回流了吗？权限收窄了吗（红线命令会确认吗）？高危操作有人工确认吗？灾备做了吗？这 10 问覆盖了约束、评测、安全三件套，答不出就回去补。最后收个尾：工程师的价值没有消失，只是从「写代码」变成了「设计让 AI 能写好代码的环境」——这个环境就是 Harness。会设计 Harness 的工程师，在 AI 时代反而更值钱。
- **页面关键元素指引**：居中检查清单逐条念，强调「答不上来就别上线」的硬约束；练习与自测题布置。
- **现场动作/Demo**：无
- **可能的学员提问 & 回答**：
  - Q：「这套清单会不会太重了？」A：「按项目风险缩放。毕业项目至少把前 5 问做扎实，后面几问随规模补。清单的意义不是全做，是让你知道哪里有洞。」
- **时长**：约 4 分钟

### 2.1 Build & Verify 验证拦截中间件（P4 参考）

来自 `harness/02.md`，核心逻辑摘录（完整版见素材原文）：

```python
class PreCompletionChecklistMiddleware:
    """在 AI 准备结束任务前拦截，强制执行验证清单"""
    MAX_INTERCEPTIONS = 5          # 最大拦截次数，防止无限循环

    def __init__(self):
        self.interception_count = 0

    def should_intercept(self, agent_state):
        # 拦截条件：AI 发出完成信号 + 未超拦截上限
        return (agent_state.get("status") == "completing"
                and self.interception_count < self.MAX_INTERCEPTIONS)

    def inject_verification_prompt(self, agent_state):
        """注入验证提示，强制 AI 逐项自检"""
        self.interception_count += 1
        return f"""
## 任务完成前的强制验证（第 {self.interception_count} 次检查）
1. 运行所有测试，确认 0 failures
2. 逐条对照【任务要求】（不是对照你的代码）
3. 检查边界：空输入 / 极值 / 异常格式
4. 确认没有硬编码密钥、没有未处理的 TODO
输出 JSON：verification_passed / issues_found / next_action
"""
```

### 2.2 DeepEval 三指标完整示例（P9 核心）

来自 `eval/04.md`，可直接运行：

```python
# test_customer_service_agent.py
import pytest
from deepeval import assert_test
from deepeval.test_case import LLMTestCase, ToolCall, SingleTurnParams
from deepeval.metrics import (
    ToolCorrectnessMetric,
    AgentGoalCompletionMetric,
    GEval
)

# 模拟客服 Agent 的输出（实际使用时替换为真实 Agent 调用）
def run_customer_service_agent(user_input):
    return {
        "output": "您好！根据我们的退款政策，30天内可申请全额退款。已为您提交退款申请，预计3-5个工作日到账。",
        "tools_called": [
            ToolCall(name="QueryOrderInfo"),
            ToolCall(name="SubmitRefundRequest")
        ]
    }

def test_customer_service():
    result = run_customer_service_agent("我买的商品质量有问题，想退款")

    test_case = LLMTestCase(
        input="我买的商品质量有问题，想退款",
        actual_output=result["output"],
        tools_called=result["tools_called"],
        expected_tools=[ToolCall(name="QueryOrderInfo"), ToolCall(name="SubmitRefundRequest")],
    )

    # 指标1：工具调用对不对（含顺序）
    tool_metric = ToolCorrectnessMetric(threshold=0.8, should_consider_ordering=True)
    # 指标2：目标完成了吗（LLM 语义判断）
    goal_metric = AgentGoalCompletionMetric(threshold=0.7)
    # 指标3：回答质量（自定义，用自然语言描述业务标准）
    quality_metric = GEval(
        name="客服回答质量",
        criteria="回答是否礼貌、准确、包含具体的处理结果和时间预期",
        evaluation_params=[SingleTurnParams.INPUT, SingleTurnParams.ACTUAL_OUTPUT],
        threshold=0.7
    )

    assert_test(test_case, [tool_metric, goal_metric, quality_metric])
```


## 三、动手练习与参考答案

**练习**：用第 6 讲的 Agent（龙虎榜 Agent 或自己的工具 Agent）跑一遍「上线前 10 问检查清单」，找出至少 1 个可改进点并修复。

**参考答案**（以龙虎榜 Agent 为例的典型发现与修复）：

1. **验证层缺失**：原 Agent 只调一次工具就返回结果，没有「写完自测」。修复：在系统提示词里加 Build & Verify 四阶段要求——拿到 API 返回后，先检查返回字段是否完整（日期、上榜原因是否为空），再输出总结，不允许直接照抄。
2. **死循环无防护**：如果 API 返回异常，Agent 可能反复重试同一个工具。修复：加 `max_iterations` 硬限制 + 对同一工具的重复调用计数，超过 3 次注入「换个思路」提示。
3. **没有评测**：修复：用 DeepEval 的 `ToolCorrectnessMetric`（预期工具=查询龙虎榜）+ `AgentGoalCompletionMetric`（目标=给出当日榜单总结），写一个 `test_lhb_agent.py`，跑通并记录分数作为基线。
4. **高危操作无确认**：若 Agent 被赋予了写文件/跑命令的工具，需补红线拦截——危险命令（删除、覆盖生产配置）前暂停询问用户。

## 四、自测题答案

1. **Harness 六大组件按优先级排前三？**
   P0 必做：系统提示词、验证层（前两名，投入产出比最高）；P1 重要：工具集、执行流程；P2 进阶：中间件、上下文管理。前三（按优先级）即：系统提示词 → 验证层 → 工具集/执行流程。

2. **评测为什么「忠实度」最易被忽视？**
   因为忠实度问题藏在「过程」里而非「结果」里。只看最终输出，Agent 的回答格式完整、语气自信，分数很高（案例里响应质量 83.9%）；但追踪到工具调用层面才发现：工具返回空时 Agent 在编造数据，忠实度只有 32.3%。所以要追踪到工具层、分开测「过程」与「结果」。

3. **安全三道防线分别在哪三个时机？**
   事前（执行前）：红黄线黑名单 + 代码审计；事中（执行中）：权限收窄 + 哈希基线 + Pre-flight 风控；事后（执行后）：夜间巡检 + Git 灾备。

## 五、常见坑位提醒

1. **一上来追求「六边形战士」**：六个组件全上，代码复杂度爆炸。先做 P0（系统提示词 + 验证层），效果提升 50% 以上，再针对性加组件。

2. **AI 验证「对照自己的代码」而非「对照任务要求」**：等于自己给自己打分。系统提示词里必须写死「对照任务要求，不得仅凭代码自我判断」。

3. **没加死循环防护**：AI 在同一个错误方案上反复改同一个文件。用 LoopDetectionMiddleware 追踪编辑次数，超阈值注入警告。

4. **评判模型比被评模型弱**：用 GPT-3.5 评 GPT-4 的输出，结果不可信。评判模型要更强或同级。

5. **指标选太多**：超过 5 个，跑得慢、结果难解读，10 个指标 3 个没过就不知道先修哪个。

6. **只看最终输出做监控**：忠实度问题（编造数据）只在工具调用层面能发现。OTel 必须追踪到工具层。

7. **失败用例不回流**：生产环境发现的问题不沉淀成测试用例，同样的问题反复出现。低分用例要自动加入测试集。

8. **红线命令字面匹配、遗漏变形**：匹配 `rm -rf /` 却放过 `find / -delete`。安全审计要警惕「二次下载」和「代码注入」这类绕过手段，且最终要有 Human-in-the-loop 兜底。

9. **巡检「一切正常」一笔带过**：夜间巡检必须 13 项指标逐一显性化汇报，否则会造成「脚本没跑」或「漏检」的错觉。
