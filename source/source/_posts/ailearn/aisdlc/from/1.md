## 从一个问题开始

你有没有想过，为什么很多 ML/AI 项目在"模型跑通了 Demo"之后，一到生产环境就出各种问题，而且常常是**莫名其妙、静默地**出问题？

这篇 arXiv 论文给出的答案是：因为传统软件开发生命周期（SDLC）的一个根本前提——**"系统行为完全由源代码决定"**——在数据密集型和 AI 系统上彻底失效了。

对推荐系统、风控平台、对话机器人、以及如今快速增长的 LLM 和 Agent 应用来说，系统行为是由**代码、数据、模型三者共同决定**的。即使一行代码、一个模型参数都没变，只要世界发生了变化、数据分布漂移了，系统的表现就会悄悄变差。

这篇文章系统梳理了数据工程（DE）与软件工程（SE）的融合——通过 DataOps、MLOps、LLMOps——如何一步步重塑 SDLC，并提出一个自适应的生命周期框架。

## 传统 SDLC 的确定性前提

传统 SDLC（从瀑布到迭代、螺旋、敏捷）半个世纪以来都建立在**一个核心假设**上：软件系统的行为完全由源代码决定。需求描述功能、设计分解模块、开发实现模块、测试验证代码、部署发布代码、维护演进代码——**每一个阶段、每一件工件、每一道质量关卡，最终都回溯到"代码"这个唯一真相之源**。CI/CD 压缩了提交到发布的间隔，但没有改变这个工件模型：流经流水线的仍然是代码及其编译产物。

数据密集型和 AI 系统打破了这个假设，进而打破了传统 SDLC 的三个前提：

1. **确定性（determinism）被打破**：AI 系统是概率性的，输入到输出的映射依赖学习到的参数（生成模型还依赖随机解码），所以"正确性"必须表达为容差范围内的**统计可接受性**，而非逻辑后置条件。
2. **代码优先（code primacy）被打破**：行为依赖数据集、特征定义、模型权重——这些**生活在代码仓库之外**，真相之源变成多模态的。
3. **阶段门控验证（phase-gated verification）被打破**：因为模型编码的是世界数据分布的"快照"，概念漂移和数据漂移会在**没有任何工件变化的情况下**静默地让已部署系统的行为退化。

> **核心结论：面向这类系统的生命周期，必须"连续"是由其构造决定的，而不只是"快一点"而已。**

这背后是著名的技术债问题：Sculley 等人早就指出，ML 系统背着传统代码的所有维护问题，外加一套 ML 特有的债务（纠缠、纠错级联、未声明的消费者、不稳定的数据依赖、胶水代码、管道丛林）；而且一个生产 ML 系统里，模型代码只占很小一部分。

## 三种 Ops 范式：从 DevOps 到 DataOps、MLOps、LLMOps

数据工程与软件工程的融合，通过一系列"Ops"范式落地，它们把 DevOps 的原则（自动化、协作、度量、流动）扩展到数据和模型工件上：

- **DataOps**：把敏捷和精益思想应用到分析型数据管道。
- **MLOps**：把范围扩展到模型训练、评估、部署、监控。其原则包括 CI/CD 自动化、工作流编排、可复现性、**三元组版本化（代码+数据+模型）**、持续训练、元数据追踪、反馈回路。
- **LLMOps**：专门针对构建在 LLM 之上的系统。这里的迭代单位常常是一条 prompt、一个检索语料库、或一个 Agent 编排图。RAG 让精心管理的语料库和嵌入管道成为行为面的一部分；评估转向基准套件、LLM-as-a-judge 协议、幻觉检测；多智能体编排则引入了全新的生命周期工件。

**融合的经济动机**在技术债文献里最尖锐：不融合的代价就是无限、复利式的维护成本。ML Test Score 用 28 项测试（涵盖数据、模型、基础设施、监控）把"ML 生产就绪度"变成了可度量的量。

## 一个形式化的视角：重塑后的生命周期

论文用一组轻量的形式化定义，把上述概念转变讲得精确。

**定义 1（三元组配置）**：系统配置是一个元组 `c = (k, d, f, θ, p, e)`，其中 `k` 是代码提交、`d` 是数据快照、`f` 是版本化的特征定义集合、`θ` 是模型工件（权重/参数）、`p` 是 prompt/编排工件（非 LLM 系统可为空）、`e` 是执行环境。系统可观测行为是**整个配置**的函数 `B(c)`，而不仅仅是 `k` 的函数。

> 这抓住了前两个核心转变：系统状态与逻辑由代码、数据、模型共同决定；真相之源变成多模态的。要复现任何历史行为，必须**钉住整个元组**——这正是数据版本控制、实验追踪、模型注册表、血缘系统存在的理由。

**定义 2（评估引导的规格）**：评估引导的规格是一个元组 `S = (D_eval, {m_j}, {τ_j})`，其中 `D_eval` 是精心管理的评估数据集（"黄金集"），每个 `m_j` 是可度量的质量函数（准确率、校准度、延迟、成本、公平性差距、真实性、毒性……），每个 `τ_j` 是阈值或容差带。规格的**接受区域**为：

```
A(S) = { c : m_j(B(c), D_eval) ⊴ τ_j  对所有 j }
```

> 这形式化了从"功能正确性"到"有界概率行为"的转变：需求不再是逻辑后置条件，而是在数据之上表达的、接受区域的**成员资格条件**。规格本身是一个可执行、版本化的工件——这是验收测试驱动开发（ATDD）的 AI 时代类比。

**定义 3（生成算子）**：生成算子 `G : (d, f, h) → θ` 把经过验证的数据快照 `d`、特征定义 `f` 和训练配置 `h` 映射为模型工件 `θ`。在 LLM 中心系统中，`G` 可能（额外）产出 prompt/检索配置 `p`。

**定义 4（验证门）**：验证门是决策过程 `V_S : c → {accept, reject}`，从有限样本估计 `c` 是否属于接受区域 `A(S)`。一个门在显著性水平 `δ` 上"统计可靠"，若 `Pr[V_S(c)=accept | c ∉ A(S)] ≤ δ`。

> 因为门从样本做决策，"通过"是一个**置信有界的判断**——这是"绿色构建"的概率类比。

**漂移进入模型的方式是时间依赖**：环境定义了一个随时间演化的数据生成分布 `P_t`，所以在 `t0` 时刻对 `S` 通过的配置，可能在 `t1 > t0` 时刻就退出了有效接受区域，**尽管没有任何工件变化**。

因此，生命周期的目标是一个需要维持的**不变量**，而非一个需要达到的里程碑：

```
∀t : c_t ∈ A(S_t)
```

其中已部署配置 `c_t` 和规格 `S_t`（其评估数据和阈值必须跟踪环境和监管要求）都在演化。**这个式子就是"自适应 SDLC"的形式化核心。**

### 双轨与三轨迭代

操作上，融合后的生命周期运行至少两个、AI 系统里三个**半独立**的回路：

- **代码回路（Code Loop）**：由传统敏捷实践管理——冲刺、特性开关、语义化版本、评审、CI。
- **数据回路（Data Loop）**：遵循异步的摄取、转换、验证、特征工程、治理节奏，由工作流引擎编排、数据质量框架验证。它的节奏由上游可用性和新鲜度需求决定，而非冲刺边界。
- **模型回路（Model Loop）**：在实验、训练（G）、评估（V）、注册之间迭代，节奏由漂移信号、评估回归和业务事件决定。

**整合不是靠合并这些回路**（它们的节奏不可约地不同），而是通过显式接口耦合它们：数据契约和特征存储连接数据回路与模型回路，注册表和 Serving API 连接模型回路与代码回路，共享的元数据、血缘和可观测性基础设施横跨三者。

## 各阶段的转变（逐阶段拆解）

论文用一张表总结了贯穿所有阶段变化的五个概念性转变：

| 维度 | 传统 SDLC | 数据/AI 中心 SDLC | 运营转变 |
|------|-----------|-------------------|----------|
| 系统状态与逻辑 | 确定性；代码决定状态 | 概率性；B(c) 由代码、数据、模型共同决定 | 从功能正确到有界概率行为 |
| 真相之源 | Git 仓库（代码版本化） | 代码 + 数据快照 + 特征 + 权重 + prompt，血缘关联 | 多模态、耦合版本化 |
| 测试范式 | 单元、集成、端到端测试 | schema 验证、漂移检测、统计评估、行为测试、evals | 数据与模型质量随代码一起持续验证 |
| CI/CD 流水线 | 构建 → 测试 → 部署 | CI + 持续训练 + 持续评估 + 渐进交付 | 自动重训练回路、评估门控晋升 |
| 监控与反馈 | 系统健康（CPU、延迟、错误） | + 数据漂移、概念漂移、预测质量、公平性、幻觉、成本 | 数据衰减与输出分布的实时可观测 |

### 需求工程与规划

这是**研究最少、却受冲击最大**的阶段。ML 系统的需求必须覆盖新的对象类型——训练数据、运行时数据、模型行为——并要求新的分析师能力（在承诺之前就思考数据可得性、标签质量、可达成的性能）。

需求基线沿四个轴扩展：

1. **数据需求**：来源、访问权限、体量、速度、schema、语义、新鲜度、保留期、质量阈值——每一条都是对管道的可测试义务。
2. **模型成功标准**：准确率、校准度、延迟、成本、鲁棒性、公平性、可解释性的可度量目标，表达为阈值 `τ_j` 而非二值条件。
3. **数据契约**：在写管道代码之前，就形式化生产者—消费者之间关于 schema、语义、服务级别、质量的约定。
4. **合规需求**：把隐私、溯源、监管约束编码到数据处理和模型输出上。

对 LLM 系统，这个阶段越来越采取**评估引导开发**的形式：需求直接编码为可执行规格 `S`（黄金数据集、评分规则、阈值策略），版本化并在系统整个生命周期中执行。

### 架构与系统设计

主导设计姿态从 **schema-first（模式优先）** 转向 **contract-first（契约优先）**。Data Mesh 把这种姿态泛化为架构范式——领域导向的所有权、把数据当作带 SLA 和质量保证的产品、自助式基础设施、联邦式计算治理——架构单元变成了版本化、文档化、可发现、接口严谨如软件 API 的**数据产品**。

融合后的生命周期产生了一套传统系统里没有的规范组件：

- **特征存储（Feature Store）**：版本化的特征定义，带双 Serving 路径（批量用于训练、低延迟用于推理），从构造上消除训练-服务偏斜（training–serving skew）。
- **模型注册表（Model Registry）**：记录版本、血缘、评估结果、部署阶段。
- **管道编排器（Pipeline Orchestrator）**：把数据和训练工作流表达为版本化、可测试的 DAG 代码，取代"管道丛林"这一主要债务源。
- **元数据、目录与血缘系统**：记录连接数据集、转换、特征、运行、模型的溯源图，让任何预测都能审计回溯到产生它的确切提交、管道运行和数据快照。

两个设计原则反复出现：**训练与推理层解耦**（实时推理与异步批计算隔离，模型可无感替换）；**确定性降级机制**（规则启发式、缓存响应或基线模型作为受治理的降级路径）。LLM 系统则新增 RAG（把模型耦合到向量存储和嵌入管道）、Agent 编排图与工具契约、prompt 管理层等 AI 原生元素。

### 开发与实现

融合最显眼的标志是**把"as code"纪律扩展到每一个工件**：管道、转换、特征定义、基础设施、训练工作流、评估套件、prompt、编排图都版本化、可评审、可测试，基础设施即代码（IaC）是底座。**Pull Request 成为三元组生命周期的通用变更单位。**

- **可复现开发**要求代码、数据、模型的耦合版本化。数据版本控制（如 DVC）给数据集和模型文件带来类 Git 语义。
- **实验追踪**记录每次运行的代码版本、数据版本、超参数、环境、指标；注册表把被接受的实验链接到可部署工件。
- **Notebook 到生产的鸿沟**是持续的痛点：对 100 多万个 Jupyter Notebook 的分析显示，大多数不可复现。融合后的生命周期用一条显式的晋升路径回应——从探索性 Notebook 到模块化、可测试的管道代码。

数据工程贡献了它最独特的开发实践：**左移数据质量（shift-left data quality）**。声明式期望（schema 一致性、空值、范围、唯一性、引用完整性、分布稳定性）与管道代码一起编写、在摄取时执行，在特征计算、训练或推理之前拦截畸形数据。它针对的失败模式是**静默数据损坏**——上游变更在不出执行错误的情况下破坏下游推理，这是最常被报告的生产事故之一。

### 测试与质量保证

传统测试是"代码对照规格验证"；但对学习组件来说，**没有完整规格**、大多数输入的期望输出未知（oracle 问题）、且行为依赖测试从不触碰的训练数据。融合后的生命周期把测试制度化为一套多层栈：

1. **数据测试**（schema、完整性、分布）
2. **管道测试**（转换逻辑、幂等性、失败恢复）
3. **模型评估**（留存集性能、校准度、鲁棒性、切片级行为、公平性）
4. **行为测试**（CheckList 式的最小功能、不变性、方向性测试，暴露聚合指标看不见的系统性失败）
5. **蜕变测试（metamorphic testing）**（断言输入变换下输出之间的关系，绕开 oracle 问题）
6. **LLM 评估套件**（黄金数据集、评分规则、幻觉检测、LLM-as-a-judge 协议——后者自身的偏差也需要被验证）

决定性的结构变化是：**这些层被接入 CI 作为自动化门（定义 4）**——当 schema 契约被违反、训练数据检测到漂移、留存评估跌破阈值、或公平性与鲁棒性约束回退时，晋升被阻断。

> 质量保证由此被重新定义：一个系统可以"代码正确"却 QA 失败，因为它的数据违反期望、或模型已经退化——而管道能**连续地**检测出这三类情况。

### 部署与发布工程

部署发布的是三个耦合的工件类——应用代码、数据管道、模型——它们的版本必须互相一致。流水线在经典 CI/CD 之上扩展出**持续训练（CT）**：当监控检测到漂移或计划触发器启动时，编排管道拉取新数据、验证、用 `G` 重训练候选、用 `V` 评估、注册或部署，**人工审批只保留给后果重大的情况**。

因为离线评估无法完全预测在线行为，模型和 prompt 通过**渐进交付**发布：

- **影子部署（shadow deployment）**：候选模型在线上流量上记录输出，但不实际服务；
- **金丝雀发布（canary）**：切换一小部分流量，对比质量、延迟、成本；
- **A/B 测试**：度量业务层面的效果。

两个机制尤其独特：**训练-服务偏斜消除**（特征存储和共享转换代码保证训练时的转换与推理时完全一致，从架构上而非靠测试消除经典的静默发散）；**管道感知的回滚**（回滚一个模型可能需要回滚它依赖的特征定义、嵌入索引或转换，所以注册表和血缘系统必须记录每个部署配置的完整依赖闭包，把元组 `c`——而非模型本身——作为回滚单位）。

### 监控、运维与维护

运维从应用性能监控扩展到全面的数据与 AI 可观测性：每条喂入管道的新鲜度、体量、schema、分布属性；每个模型的预测分布、置信度、切片级质量、公平性；对 LLM 和 Agent 系统，还有 token 用量、成本、延迟百分位、轨迹历史、护栏触发、用户反馈。

维护的**科学核心是漂移**。值得注意的是，Rabanser 等人的实证研究表明许多实用的分布漂移检测方法会**静默失败**——这意味着漂移检测本身是一个需要工程化、需要测试的组件。

在生命周期层面，漂移把维护从"被动的、工单驱动的活动"变成了等式 (1) 的**闭环控制问题**：监控器估计部署配置与其验证过的运行包络的距离；控制器在"继续 / 重训练 / 回滚 / 降级 / 升级"之间决策；第 4.5 节的持续训练管道充当执行器。

> 另一个警告来自反馈回路：影响其后续训练数据的系统会放大自身的偏差，所以让系统自我改进的反馈管道，本身必须被治理、采样、审计。

### 治理、安全与负责任 AI

治理被**重新实现为工程**：政策变成可执行检查，文档变成生成的工件，可审计性变成由血缘基础设施保证的属性。

- **Datasheets for Datasets**：标准化数据集的动机、组成、收集、预处理、用途、局限的文档。
- **Model Cards**：记录预期用途、评估条件、切片级性能、伦理考量。
- **溯源（provenance）** 提供执行底座；公平性监控在生产中持续运行，而非只在发布时跑一次。
- 扩大的攻击面（训练数据投毒、模型窃取与规避、prompt 注入、检索投毒）把安全工程带进了管道内部。

外部法规越来越多地强制要求"融合生命周期本就具备"的东西：欧盟 AI 法案对数据治理、文档、日志、人工监督、鲁棒性、上市后监控的义务，直接映射到 4.1–4.6 节的机制；NIST AI 风险管理框架预设持续度量与反馈；ISO/IEC 5338 形式化了 AI 特定的生命周期流程。**监管合规与工程卓越由此收敛到了同一套基础设施上。**

### 组织结构、角色与文化

这场转变既是技术的，也是组织的。数据科学家、数据工程师、软件工程师之间的孤岛溶解为跨职能产品团队（由平台团队支撑），混合角色（ML 工程师、AI 工程师、全栈数据工程师）制度化这种融合。团队从"项目交付"转向"学习系统的产品管家"。

两个文化警告值得注意：只要数据工作仍被当作低地位劳动而非工程，"数据级联（data cascades）"的问题就会让融合后的生命周期缺乏下游一切所依赖的实践；而这场转型必须保持**以人为中心**，围绕人类判断、伦理和人机协作重新设计，而非为自动化而自动化。

## 自适应、融合的生命周期框架

### 维护作为闭环控制

逐阶段分析汇聚到一个比"SDLC 多了几步"更强的论断：AI 系统需要一个**其结构能响应变化、而无需人类重新规划流程本身**的生命周期。合适的框架是控制论的：

- **被控对象（plant）**：已部署系统 + 管道 + 模型；
- **传感器层**：可观测性；
- **比较器**：评估门 + 漂移检测器（对照当前规格 `S_t`）；
- **执行器**：持续训练、渐进交付、降级、回滚、人工升级。

一个自适应 SDLC，就是让这个回路**显式、工程化、被测试、被治理**，而非自发、临时凑合。

### 五层参考结构

综合第 3、4 节，自适应融合生命周期由五层构成，论文将之表达为可测试的设计命题：

| 层 | 内容 |
|----|------|
| **L5 治理层** | 生成的文档、审计、访问控制、合规即代码 |
| **L4 控制层** | 持续训练、渐进交付、降级、回滚、人在环升级 |
| **L3 门层** | schema、质量、漂移、评估、公平性、鲁棒性、成本门 `V_S` |
| **L2 契约层** | 数据契约、特征定义、模型/Serving API、评估规格 `S` |
| **L1 工件平面** | `c = (k,d,f,θ,p,e)` 的耦合版本化与完整血缘 |

**五条设计命题：**

1. **三元组工件平面**：每个可部署行为都应能从完全版本化的配置 `c` 复现；任何不在耦合版本控制之下的工件，都在工程过程之外，构成潜在债务。
2. **契约中介的解耦**：数据、模型、代码三个回路只能通过显式、版本化的契约耦合，让每个回路以自己节奏迭代而不引发级联破坏。
3. **统一统计门控**：任何配置变更（代码、数据、特征、模型、prompt）的晋升，都必须通过在声明显著性水平 `δ` 上统计可靠、且在集成、晋升、运行时统一应用的门 `V_S`。
4. **工程化适应**：对监控信号的响应（重训练、回滚、降级、升级）应实现为受治理、被测试的控制动作，维持 `c_t ∈ A(S_t)`，人工批准与"后果"而非"惯例"绑定。
5. **构造式治理**：文档、审计轨迹、访问控制、合规证据应由交付系统的同一套基础设施生成和强制，使监管义务成为工程实践的副产物。

## 一个概念性研究模型

论文把这场转变概念化为一条因果链：

> DE 实践集成 → 集成工程实践（数据 + 代码 + ML + DevOps + 治理）→ 重塑的 SDLC（自适应、多回路、评估门控）→ 软件与系统结果

- **自变量**（DE 实践集成程度）：可通过实践采纳工具、ML Test Score、MLOps 成熟度阶段来操作化，覆盖数据版本化与血缘、数据质量工程、自动化管道、数据/ML 测试、数据/ML CI/CD、基础设施即代码、持续监控、漂移管理、可复现性、数据/AI 治理。
- **因变量**（效率、质量、可靠性、可维护性等）：可借鉴成熟的软件交付性能指标（部署频率、交付周期、变更失败率、恢复时间），并扩展出数据平面的类比指标（管道 SLA 达成率、数据事故率、漂移检测时间、重训练前置时间）。

这个模型同时支持"方差研究"（更多集成是否预测更好结果）和"过程研究"（通过哪些机制），给研究问题 RQ2 提供了可度量的形式。

## 证据基础、局限与研究议程

**证据确立了什么**：SDLC 已被重塑这一点，得到了广泛且一致的文献支持（映射研究、综述、工业案例研究都汇聚到相同的阶段级转变）。

**证据没确立什么**：证据基础以文献综述、分类法、访谈与调查研究、单组织经验报告为主；可比的实验、参与者级统计、汇总效应量基本缺失。**转变的方向已充分确立，但转变的幅度——DE–SE 集成对效率、质量、可靠性、可维护性的因果效应——仍未充分量化。** 以人为中心的约束（协作、可解释性、技能、伦理、遗留系统集成、安全）被反复识别为核心且未解决的问题。

**五条研究议程：**
1. **度量**：开发并验证融合生命周期成熟度、数据平面交付性能的测量工具。
2. **受控与纵向证据**：超越经验报告，走向纵向案例研究、准实验（采用前后对比 + 匹配对照）、代码-数据-模型工件协同演化的仓库挖掘研究。
3. **LLM 与 Agent 特定的生命周期科学**：为 eval 设计与效度、judge 可靠性、prompt 版本化语义、多 Agent 工件工程建立严谨基础（实践远超理论）。
4. **自适应流程设计**：用设计科学研究来构建和评估第 5 节的框架。
5. **可持续性与人的因素**：量化持续训练与评估的经济、环境、人力成本，并设计同时优化质量的生命周期；以及教育研究。

## 📝 小结

- 传统 SDLC 建立在"代码决定一切"的确定性前提上，数据密集型和 AI 系统打破了确定性、代码优先、阶段门控验证这三大前提
- 系统行为由代码、数据、模型三者共同决定（三元组配置 `c = (k,d,f,θ,p,e)`），且会随世界漂移而**静默退化**——即使没有任何工件变化
- 需求从"逻辑后置条件"变成"评估引导的规格"（黄金数据集 + 阈值 + 接受区域），是 ATDD 的 AI 时代类比
- 生命周期目标从"达到里程碑"变成"维持不变量"：`∀t : c_t ∈ A(S_t)`，这是自适应 SDLC 的形式化核心
- 融合通过 DataOps、MLOps、LLMOps 落地，把"as code"纪律扩展到数据、模型、prompt 等每一个工件，PR 成为三元组生命周期的通用变更单位
- 运维的核心是漂移控制：维护从被动工单变成闭环控制问题，漂移检测本身是需要工程化、测试的组件
- 治理被重新实现为工程：政策变可执行检查、文档变生成工件、可审计性由血缘基础设施保证，监管合规与工程卓越收敛到同一套基础设施
- 论文的局限：转变的**方向**已充分确立，但转变的**幅度**（因果效应大小）仍未充分量化，这是未来研究的方向
