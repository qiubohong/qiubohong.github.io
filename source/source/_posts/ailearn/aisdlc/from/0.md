## 从一个问题开始

你有没有想过，为什么很多团队明明已经用 AI 把写代码的速度提上来了，整体的交付却并没有快多少？

Anthropic 这篇博客给出的答案很直接：**代码已经不再是瓶颈，围绕代码的那些流程才是**。

组织已经开始用 AI 以一年前难以想象的速度编写代码，但审批关卡、评审、交接、政策这些"流程"却没有同步进化。很多工程团队仍然沿用同一套为"人工写代码"时代设计的管理方式，结果把智能体编程（如 Claude Code）带来的效率提升又拖了回去。

这篇文章是 Anthropic Applied AI 团队在服务客户过程中总结出的一套实战手册——**AI 原生 SDLC**（AI-Native SDLC），教你如何一个阶段一个阶段地把 AI 融入软件开发生命周期。

---

## 核心洞察：代码不再是瓶颈

软件开发生命周期（SDLC）是把软件从想法带到生产环境的完整过程。大多数组织都在运行同一套六个阶段：**规划（Plan）、设计（Design）、构建（Build）、测试（Test）、部署（Deploy）、维护（Maintain）**。

传统上，每个阶段由不同角色负责：产品经理写需求，架构师转成设计，工程师写代码，QA 验证，发布团队上线，运维监控。工作通过文档、工单、签字在各阶段流转。

这套流程是为一个时代设计的——在那个时代，**写代码是最耗时、最贵的环节**。PRD、估算仪式、安全评审，都是为了在长达数周甚至数季的开发周期里强制对齐。

但如今这个前提不成立了。当构建阶段跑得比传统 SDLC 允许的更快时，三件事会必然发生：

1. **瓶颈转移到构建阶段左右两侧**——主要是规划、评审/测试、部署，这些仍然以"人的速度"运行。
2. **控制措施与现实脱节**——逐行人工评审适合"人写的代码"，但智能体写出大部分 diff 之后，人工评审就跟不上了。
3. **治理成本上升**——例外情况仍要经过每周甚至每月才开一次的会议和委员会。

> **核心结论：构建不再是约束，围绕它的人类速度环节才是。** 人工速度的阶段时长保持不变，而构建阶段被压缩到几小时。

拿安全来举例：安全团队的规模是按"人类产出"配置的。当智能体成倍放大代码产出时，要么评审队列堆积，要么代码在评审不足的情况下上线。受监管组织两个结果都无法接受，所以安全与政策检查必须跟上智能体的节奏。

## 什么是 AI 原生 SDLC？

AI 原生 SDLC 是一个重新构想的流程，把旧的**控制目标**与新的**执行方式**结合起来。它不是线性流程，而是一个**闭环**，AI 被嵌入每一个节点。

你也会听到它被叫做"智能体 SDLC""AI SDLC"，或"智能体软件开发"——叫法不同，但指的是同一件事。

### 六个阶段的转变对比

| 阶段 | 传统 SDLC | AI 原生 SDLC |
|------|-----------|--------------|
| 规划 Plan | 需求由委员会收集，通过工作坊和签字提炼，人工撰写 | Claude 直接从源头提炼痛点，写入 `intent.md`，人类可读、机器可执行 |
| 设计 Design | 分析师写规格，设计师再解析 | 需求与设计压缩为智能体的一次工作会话，由编码为 skills 的标准引导，版本化于 git |
| 构建 Build | 测试和代码手写，文档事后才补 | 测试和代码由 AI 生成，机构知识以版本化的 `CLAUDE.md` 和 skills 维护 |
| 测试 Test | QA 在阶段边界设关卡 | 贯穿实现过程的持续 evals（评估） |
| 部署 Deploy | 人工逐行审查，治理在评审周期中不一致地进行 | 分层智能体评审，人工评审仅保留给受监管和关键代码；治理在 AI 行动时即执行，hooks 作为审批关卡 |
| 维护 Maintain | 人工盯着生产找 bug | 智能体监控线上；被突破的控制带被诊断并写回闭环作为新的 `intent.md` |

贯穿右列的主线是**"提交的工件（committed artifact）"**：每个阶段结束时向版本控制写入一个工件，下一阶段开始时读取它。早期阶段以 `.md` 文件为主——因为产品负责人和智能体都能读、都能基于同一个文件行动。从构建阶段往后，工件就是代码及其记录。

**提交链本身就是审计轨迹**：谁要求了什么、智能体生成了什么、谁批准了它。

人类仍然对每一个需要判断的决策负责，注意力随需要评审的工件而转移。

## 六个 Play 详解

Play 是这本手册的核心，分为六个非线性阶段。每个 play 都涵盖：什么变了、如何开始、具体实施步骤、治理考量、如何衡量是否有效。

一个阶段的结束以提交一个工件为标志，该提交触发下一阶段：被接受的 `intent.md` 触发需求与设计流程，被批准的 `spec.md` 触发计划模式，被合并的 PR 触发流水线，生产环境中被突破的控制带写回下一个 `intent.md`——如此循环。

---

### Play 01 —— 规划（Plan）：捕获为 intent.md

想法不再等待有人来撰写它。意图一次性、以发起者自己的话被捕获，成为一个版本化控制的、下一阶段可行动的工件。

`intent.md` 可以通过不同途径进入：某人有个想法、有人提交了工单、或一条告警暴露了一起事故（见第 6 阶段）。

**传统**：一个想法要经过待办事项、用户故事、故事点、细化会议，才有人能行动。每次交接所有权都转移，到工程团队手里的东西已经和发起者的本意差了好几层。

**AI 原生**：发起者与 Claude 头脑风暴，把结果写成 `intent.md`——一份用发起者自己语言写成的原型规格，包含想要什么、为什么、在什么约束下。

**执行步骤：**

1. 发起者用自己的话向 Claude 描述问题——今天做不到什么、谁受影响、更好是什么样、范围外是什么。无需正式语言。
2. 头脑风暴直到想法具体化。Claude 会问分析师会问的问题：范围、用户、约束、成功的样子。
3. 让 Claude 用组织模板把结果写成 `intent.md`。
4. 发起者修正 Claude 误解的任何地方。
5. 提交到共享存放处，产品负责人从那里接手。

**intent.md 示例：**

```markdown
# Intent: 理赔状态自助查询
作者：J. Ortiz（理赔运营）。状态：草稿。

## 问题
客户打电话到联络中心询问理赔进度。
客服约三分之一通话时间花在纯状态查询上。

## 提议结果
客户在门户中看到理赔状态、下一步和预计日期。

## 受影响的用户和系统
理赔客服、门户团队、理赔核心 API。

## 约束
门户会话中不新增 PII（个人身份信息）。仅使用现有认证。

## 待解决问题
第三方定损员是否也需要访问？
```

**治理考量**：证据就是已提交的 `intent.md`，列有作者、时间戳和完整修订历史。产品负责人批准，接受或拒绝的决策（送入第 2 阶段）以"合并"或"关闭评审"记录。

**如何衡量**：先行指标是从第一次对话到提交 `intent.md` 的时间（预期从数周降至数小时）；滞后指标是 `intent.md` 的"存活率"（被接受进第 2 阶段而非关闭的比例）。

---

### Play 02 —— 设计（Design）：需求与设计合二为一

需求与设计合并为一次会话。**政策在写规格时就被应用，而不是在数周后的评审里才发现。**

一旦被产品负责人批准，Claude 就取已接受的 `intent.md`，产出需求和设计规格，由组织的品牌、安全、合规、UX 相关的 skills 引导。

产品负责人**评审**该规格，但不撰写它。

**传统**：需求与设计是分开的阶段、由不同团队完成，慢且有损。

**AI 原生**：两个阶段在同一次提示会话中完成，产出受 skills 约束的规格并标记关注点。

**执行步骤：**

1. 产品负责人打开一个加载了组织 skills 的会话，附上 `intent.md`。
2. 提示词指向 `intent.md`，指明约束，要求标记关注点。先手动运行，再编码为组织级斜杠命令；最终把 `intent.md` 被接受设为触发器，自动提交 `spec.md` 作为 PR。
3. 对照想法评审规格：是否解决了问题？待解决问题是否被回答或延续？
4. 先处理标记出的关注点——这些正是分析师原本会升级的点。
5. 把 `spec.md` 与 `intent.md` 一起提交，这对文件记录"要求了什么"和"决定了什么"。
6. 产品负责人决定是否进入构建——**这一决定始终由人类做出**。

**提示词示例：**

> 阅读所附的 intent.md，产出一份将之集成进我们现有代码库的需求和设计规格。应用你可用的 skills，使计划符合我们的品牌准则、安全政策和 UX 标准。把规格完整记录为 spec.md。清晰描述任何关注点，尤其是你无法满足相互矛盾政策的地方。

**如何衡量**：先行指标是从 `intent.md` 提交到 `spec.md` 提交的耗时（两个 git 时间戳）；滞后指标是构建开始后的需求返工。

---

### Play 03 —— 构建（Build）：计划先行 + 机构知识文件化

没有已接受的计划，任何东西都不会被实现。**机构知识变成智能体读取的文件，护栏以代码而非习惯的形式运行。**

#### Claude Code 计划模式作为默认起点

工程师以计划模式启动会话，把已批准的 `spec.md` 交给 Claude，让它访谈自己、迭代计划直到满意。

**传统**：工程师读完设计直接写代码，改动方案留在脑子里，没人能评审，评审者看到的第一样东西是成品 diff，返工已经很慢。

**AI 原生**：工作从一个书面计划开始——Claude 在计划模式中只读代码库、不改任何东西。工程师在代码写出前就修正计划，批准后提交为 `plan.md`。

**执行步骤：**

1. 用计划模式启动会话。
2. 把 `intent.md` 和 `spec.md` 交给 Claude，要求产出一份实现计划：指明要改的文件、工作顺序、证明它的测试。
3. 拷问计划：可能破坏什么？哪步风险最大？放弃了哪些方案？
4. 迭代到"一个从未看过这段对话的工程师仅凭计划就能实现"。
5. 提交批准的计划为 `plan.md`，加入审计轨迹。
6. 接受计划，让 Claude 实现——有了扎实计划，实现往往一次通过。
7. 实现偏离计划时，在同一提交中更新 `plan.md`。

**plan.md 示例：**

```markdown
# 计划：理赔状态自助查询（来自 intent.md 2026-06-02）

## 变更的文件
portal/src/claims/StatusPanel.tsx（新增）、claims-api/routes/status.py、
claims-api/tests/test_status.py

## 工作顺序
1. 在现有认证后新增状态端点。
2. 面板对接该端点。
3. 接入门户导航。

## 风险
claims-core API 限流 50 rps；面板必须做缓存。

## 证明
test_status.py 覆盖四种理赔状态；截图匹配已批准的原型。
```

#### CLAUDE.md：把机构知识变成文件

`CLAUDE.md` 给 Claude 提供新入职者需要的上下文：约定、命令、架构、团队最常犯的错误。曾经存在于人脑和 wiki 里的知识，变成智能体每个会话开头读取的文件。

**执行步骤：**

1. 在仓库运行 `/init`，Claude 生成初始 `CLAUDE.md`。
2. 裁剪到"新入职者第一天需要"的程度：构建、测试、lint 命令，重要约定，Claude 反复出错的地方。
3. 提交到仓库根目录，全队共享一个版本。
4. **一条实用规则：当 Claude 犯两次同样的错误时，把纠正写进 `CLAUDE.md`**。
5. 保持在一页以内——Claude 每个会话开头会读完它，过时内容在无益地占用上下文。

**CLAUDE.md 示例：**

```markdown
# 支付服务

## 命令
- 构建：make build
- 测试：make test（单元）、make itest（集成，需要 docker）
- Lint：make lint（在 CI 中运行；push 前修复）

## 约定
- Java 21，Spring Boot 3。不再新增 Lombok。
- 金额一律用 BigDecimal，绝不用 double。
- 每个端点都需要在 src/itest 中的集成测试。

## 架构
- api/ 放 REST 控制器，core/ 放领域逻辑，adapters/ 对接外部系统。

## Claude 常犯的错
- 不要升级依赖版本；这归平台团队管。
- 遗留 v1/ 包已冻结；改动放 v2/。
```

#### Skills：把机构知识变成"可运作"的控制

Skills 是组织让机构知识可运作的方式。经验法则：**为必须一致应用的机构知识写 skill；不要把属于 `CLAUDE.md` 或提示词的内容写成 skill**。

Skill 是"建议性"控制——它让 Claude 在写代码时很可能应用政策，但没有任何东西强制会话遵守。必须始终成立的政策，需要在 skill 背后加确定性机制（hook 或评审环节）。

**skill 示例：**

```markdown
---
name: secure-api-review
description: 应用 API 安全标准。在创建或修改对外端点、评审 API 代码、
  或生成 OpenAPI 规格时使用。
---
# 安全 API 评审

当你创建或修改 API 端点时：
1. 认证：每个端点都需要网关 JWT；除 /health 外无匿名路由。
2. 输入校验：按 OpenAPI schema 校验请求体，拒绝未知字段。
3. 审计：每个改变状态的端点都发出带 actor、action、entity、timestamp 的审计事件。
4. 数据分类：schema 中标记为 pii 的字段绝不出现在日志或错误信息中。
```

> **skill 让违规变得罕见，hook 让它几乎不可能发生。**

#### Hooks 作为构建期护栏

Skill 是建议性控制，hook 是它背后的确定性层。构建期 hook 可以：阻止对受保护路径的编辑、文件编辑后运行格式化器和 linter、把凭证挡在 diff 之外。

构建期 hook 要快、且范围限定在改动的文件上；更重的检查（如完整测试套件）放在提交或 PR 处。**需要向人请求批准的 hook 属于第 5 阶段的关卡**——构建过程中的审批提示会把一个人重新放回所有并行会话的关键路径上。

#### 并行会话与子智能体

一个工程师可以同时驱动多条工作流。

- **并行会话**：另一个完整的 Claude Code 实例，在自己的 git worktree 上处理独立任务。各会话彼此一无所知，唯一共享的是驾驶它们的工程师。
- **子智能体（subagent）**：在单个会话内部运行，有自己上下文窗口和工具限制，适合反复出现的工作（如验证应用按预期运行）。

并行会话提高工程师同时在手的任务数，子智能体让每个会话专注自己的任务。工程师的职责转向编排，最终转向构建和监控闭环。

**执行步骤**：把工作按计划拆成触及不同文件的任务，共享文件的任务在单个会话里顺序执行；每个并行任务用各自 worktree（如 `claude --worktree feature-auth`）；两到三个会话是合理起点；把重复工作变成 `.claude/agents/` 下定义的子智能体。

### Play 04 —— 测试（Test）：先给 Claude 一个反馈回路

每个会话在人类看到之前先自查工作，而引导智能体的配置本身也要像它写的代码一样做回归测试。

**给 Claude 一个反馈回路**——始终给它一个验证自己工作的方式（测试、构建或截图 diff）。会话在工程师看到之前自查工作、修复自己的错误。

**传统**：代码是否有效的信号来得太晚——CI 几分钟后、测试员几天后、生产环境几周后。

**AI 原生**：会话在被人看到之前就有自查手段，迭代到检查通过，到工程师手上的已经是通过的东西。

**执行步骤：**

1. 把检查工作包成单个目标（如 `make test`），失败时非零退出。
2. 在 `CLAUDE.md` 的命令部分列出每个命令及健康输出示例。
3. 陈述可量化的目标，让 Claude 不必问你就检查。
4. 对 bug 修复，**先写失败测试**：让 Claude 把 bug 复现为测试、确认它以预期方式失败、提交该测试，然后才让它不改测试地通过。一个修复前就存在、且智能体无法改写的测试，是 bug 已消失的证明。
5. 对 UI 工作，用可视化检查闭合回路：实现、截图、对比、调整，两三轮是正常的。
6. 把验证纳入"完成"的定义，写进 `CLAUDE.md`。
7. **保护回路本身**：用 hook 阻止修复任务期间对测试文件的编辑，防止修代码的智能体削弱对代码的检查。

**CLAUDE.md 验证块示例：**

```markdown
## 验证你的工作

- 构建：make build（必须以 "Build succeeded" 结束）
- 测试：make test（全绿；绝不跳过或删除失败的测试）
- Lint：make lint（零警告）

报告任何任务完成前先跑这三个，并粘贴输出。
如果测试失败，修代码，不是修测试。
```

#### CI 中的持续 Evals

Evals 是 AI 原生世界里"阶段关卡 QA"的等价物——**每当智能体配置变化时就运行的套件**。换入新模型或改写提示词时，eval 套件说明智能体是否仍按同样标准工作。

**执行步骤：**

1. 收集 20 到 50 个真实任务及其预期/已接受结果。
2. 把每个任务写成一个 eval：提示词加上定义"可接受"的检查。
3. 套件在 CI 中按计划非交互运行，也在 `CLAUDE.md`、skills、hooks 有任何改动时运行。
4. 用结果给配置变更设关卡。
5. 每个生产事故对应一个 eval，作为回归测试留在套件里。

---

### Play 05 —— 部署（Deploy）：AI 进入评审回路 + hooks 作门禁

评审双向进行，治理在智能体行动时执行。**智能体做到生产关卡之前的一切，绝不越过它。**

#### AI 进入 PR 评审回路

Claude 既给评审也收评审：对照组织政策评审进来的 PR，也处理自己 PR 上的评审意见。这让工程师在 PR 评审中专注于判断"意图"和"风险"。

**传统**：评审容量按人类产出规划，一个 PR 等一个评审者通读，质量随负载波动。

**AI 原生**：所有 PR 获得一组相同的评审环节，发现按严重度排序。

**执行步骤：**

1. 托管版 Code Review 服务启动最快；需要控制流水线时用 `claude-code-action` 在自己 CI 里跑。
2. 技术负责人把评审政策写成仓库根目录的 `REVIEW.md`：bug 与逻辑错误、安全与漏洞、合规性（对照 `spec.md` 和 `plan.md`）。
3. 设定人工阈值：发现本身不批准也不阻止 PR，分支保护仍要求代码所有者批准。
4. 评论里 @claude，Claude 处理意见并 push 修复，PR 线程记录请求和改动。
5. 评审发现回馈到 `CLAUDE.md`——第二次标记同一错误时，纠正写进 `CLAUDE.md`。
6. 每月给发现打分调优，并在 `REVIEW.md` 里封顶 Nit 数量。

**REVIEW.md 示例：**

```markdown
# 评审指令

## 环节
- Bug：逻辑错误、损坏的边界情况、细微回归
- 安全：注入风险、认证缺口、日志中的 PII
- 合规：改动是否匹配 spec.md、plan.md 和我们的设计原则

## Important 在此的含义
Important 保留给会破坏行为、泄露数据或违反政策的发现。
风格和命名是 nit。

## 封顶 nit
每次评审最多报五个 nit；其余汇总为一个计数。

## 不报告
src/gen/ 下的生成文件，以及 CI 已强制的任何东西。
```

#### Hooks 作为审批关卡

Hook 也能**询问**——暂停动作直到特定的人批准，这正是发布门禁需要的。它放在第 5 阶段是因为发布门禁是最清晰的场景，但 hook 不限于部署：Claude 在哪里行动，hook 就在哪里运行。

**执行步骤：**

1. 工程领导层列出必须保留的人工审批关卡（变更管理签核、发布授权等）。
2. 把每道关卡表达为 hook——可 allow、ask 或 block 的脚本。
3. 团队 hook 放 `.claude/settings.json`，不可妥协的 hook 放托管设置（工程师无法关闭）。
4. block 应自解释：阻止动作时，原因和审批路径出现在 Claude 输出中。

**门禁脚本示例：**

```bash
#!/bin/bash
# 生产部署需要指定的发布授权
cmd=$(jq -r '.tool_input.command' < /dev/stdin)
if [[ "$cmd" == *"deploy"* && "$cmd" == *"production"* ]]; then
   if [ -z "$RELEASE_APPROVAL" ]; then
     echo "生产部署需要发布授权。" >&2
     exit 2 # exit 2 阻止动作；消息传给 Claude
   fi
fi
exit 0
```

#### CI/CD 集成与部署

在流水线内非交互运行 Claude Code，沙箱化执行，通过 MCP 暴露部署能力，并在需要之前就演练好回滚路径。

**执行步骤：** 从只读判断步骤开始（分诊失败构建、总结 flaky 测试）；在现有关卡后加写步骤（智能体写的任何东西都以 PR 形式经分支保护进入，**没有通往 main 的路径**）；沙箱化执行；通过 MCP 暴露 deploy/status/rollback；按环境分层自主性；回滚应是演练最多的路径。

> **治理核心原则：智能体可以做到生产关卡之前，但不能越过它。**

### Play 06 —— 维护（Maintain）：闭合闭环

闭环闭合。一个触发器在调用路径中没有任何人地调用 Claude，它所发现的东西作为 `intent.md` 重新进入流水线。

前面讨论的都是每个阶段需要人来启动。这一阶段的重心转向**自主运行 Claude 来闭合闭环**。

例如，一个持续运行的监控智能体可以基于一条 bug 工单创建 `intent.md`，然后流经需求、计划、构建、测试、评审各阶段。第 6 阶段无头运行，阶段之间有独立的置信度关卡（确定性检查或对抗性评审智能体）决定是继续还是升级给人类。

**传统**：维护是被动阶段，凌晨 3 点的告警可能被漏掉，复盘行动可能根本没进入代码库。

**AI 原生**：一个触发器（控制带被突破、工单、频道消息、计划）在路径中无人的情况下调用 Claude，它诊断、只通过门禁路由行动、把发现写成 `intent.md`。

#### 闭合闭环（Closing the Loop）

一个确定性脚本监控生产环境，控制带被突破时调用 Claude。

**执行步骤：**

1. 选一个带稳定滚动基线的指标（如 CI 测试失败率、部署后 5xx 率、PR 周期时间）。
2. 写检测脚本（滚动窗口的均值与标准差，配合 Western Electric 等规则），完全确定性、不涉及模型。
3. 响应层级定义在版本化配置里：1σ 只记录；2σ 只读诊断；3σ 可行动（但只能开 PR 进评审关卡或触发预先批准的 runbook）。
4. 触发器层可以是计划工作流、webhook 或 Cron Job。Claude 无状态、非交互运行，闭环可在无人启动的情况下开始和结束。
5. 智能体把诊断写成 `intent.md`，走流水线。
6. 服务负责人分诊队列：修复、排期或忽略（忽略会调优控制带、降噪）。
7. 修复上线时，为事故添加一个 eval。

**bands.yaml 示例：**

```yaml
metric: ci_test_failure_rate
baseline: rolling_30d
rules: western_electric
tiers:
  1sigma: { action: log }
  2sigma: { action: diagnose,
            tools: "Read,Grep,Bash(gh run view *)" }
  3sigma: { action: propose,
            routes: [pull_request, runbook:rollback-deploy] }
```

**示例场景：** CI 失败率突破 3σ → 隔离 flaky 测试或开回滚 PR；部署后 5xx 率突破 3σ → 触发现有回滚流水线；PR 周期时间触发漂移规则 → 为工程领导层写报告。

#### 定期代码库扫描（Claude Security）

安全扫描是对"特定模型下代码库"的时间点陈述，两个半边都会过时：代码每周在变，每一代模型都能发现上一代漏掉的漏洞。AI 原生的答案是**按计划运行扫描、调用路径中无人、把发现送过与其他变更相同的关卡**。

#### Claude Tag 值班

事故也可能通过 Slack 或 Teams 等渠道到来——比如事故频道里一条晚上 10 点要求紧急修复的消息。Claude Tag（公开 beta）让 Claude 以自己的身份成为这些频道的成员，每个新事故都有一个"第一响应者"，响应本身也成为闭环和未来事故记忆的一部分。

> 频道就是审计轨迹：请求、诊断、人类授权和修复都留在事故被处理的地方。

---

## 📝 小结

- 核心洞察是"代码不再是瓶颈"：围绕代码的规划、评审、部署等"人类速度"环节才是新瓶颈，构建阶段已被压缩到几小时
- AI 原生 SDLC 把线性流程变成闭环，用提交工件（`intent.md` → `spec.md` → `plan.md` → diff/PR → 事故记录）串联各阶段，提交链本身就是审计轨迹
- 六个阶段的改造各有抓手：规划写 `intent.md`、设计合并需求与设计、构建用计划模式 + `CLAUDE.md`、测试给反馈回路 + 持续 evals、部署用 AI 评审 + hooks 门禁、维护闭合闭环
- 贯穿始终的两个机制：`CLAUDE.md`（机构知识）+ skills/hooks（确定性护栏），前者是建议性控制，后者是强制层——skill 让违规罕见，hook 让它几乎不可能发生
- 人类角色始终不变：负责所有需要判断的决策，注意力集中在"关卡"上，评审智能体标记的内容而非从头开始
- 治理的核心理念是"智能体可以做到生产关卡之前，但不能越过它"，通过分支保护、hooks、沙箱、托管设置层层强制
