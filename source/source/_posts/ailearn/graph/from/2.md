你不需要一个 Python 编排框架。Anthropic 的 Claude Code 已经内置了图工程所需的基本组件：作为节点的子智能体（Subagent）、一个编排器（Orchestrator），以及共享状态。这篇文章说明了怎么用 Claude Code 现有的能力搭出一张Agent 图。

## 1. 图工程和 Claude Code 已经内置的东西

图工程（Graph Engineering）说的是把多个专门的智能体连接成一张由节点、边和共享状态组成的图。对大多数构建者来说，最意外的一点是：根本不需要一个 Python 编排框架就能做到这件事——Claude Code 本身就已经内置了这些基本组件。子智能体（Subagent）就是节点。负责调用它们的主智能体是编排器节点，它在各个子智能体之间的路由就是边。当交互式版本不够用的时候，Claude Agent SDK 就是把整套东西搬进代码里的方式。如果你一直在读关于图工程的文章，又不知道具体该用什么工具去实践，这就是最短的路径：你手上大概已经打开了这个工具。

当"图工程"这个说法在 2026 年 7 月中旬开始流行起来时，这个措辞让它听起来像是一门你必须重新去学的新学科。但 Anthropic 早就用一个更朴素的名字把这套模式发出来了。他们那篇关于构建高效 Agent 的指南，列出了五种可组合的模式——提示链（Prompt Chaining）、路由（Routing）、并行化（Parallelization）、编排器-工作者（Orchestrator-Workers）和评估器-优化器（Evaluator-Optimizer）。把这些模式当作图去读，一切就清晰了：提示链是一串排成一条线的节点，路由是一条条件边，编排器-工作者则是一个中心节点向多个工作者节点分发任务、再把结果汇聚回来。图工程是标签，这才是机制本身。

## 2. "用 Claude 做图工程"到底是什么意思

把这个术语拆开看，一张图其实就是三样东西：**节点**（完成某一项工作的智能体或步骤）、**边**（决定接下来运行哪个节点的路由，包括分支、扇出、扇入和循环回退）、**共享状态**（沿着边流动的数据）。一个单一的智能体循环，就是最小的图——一个节点，带一条指回自身的边。当一个节点已经不够用、需要把几个专门化的节点接在一起时，你做的事就是图工程。

用 Claude 来做这件事，并不意味着要先去学一套新的 API。它意味着把这三个部分映射到 Claude Code 已经暴露出来的工具上：

- **节点 → 子智能体**。每个子智能体都是一个独立的智能体实例，拥有自己的上下文窗口、自己的系统 Prompt 和受限的工具权限。这种隔离恰恰是一个好节点应该具备的：一个只负责读取和搜索的研究员子智能体，一个只负责起草的写手，一个只负责挑毛病的审阅者，彼此互不干扰对方的上下文。
- **边 → 编排器的路由**。你的主 Claude 会话本身就是一个节点，它决定何时生成哪个子智能体、给出什么样的任务简报，这些决策就是边。因为编排器是在运行时进行路由，而不是照着一张写死的流程图走，你不用手绘一张图就能获得动态的边。
- **共享状态 → 返回的结果**。子智能体的最终输出会流回编排器，编排器再把相关的部分传给下一个节点。这次交接，就是状态沿着边在流动。

## 3. Claude Code 已经给你的基本组件

在 Claude Code 里搭一张图，用得上三样东西，按你愿意投入的程度大致排序：

- **`.claude/agents/` 目录下的子智能体**。为每个节点放一个带 YAML frontmatter 的 markdown 文件——一个名字、一段描述、它可以使用的工具，以及它的系统 Prompt。主智能体会读取这些文件，并把任务委派给它们。这是搭建一张多节点图最快的方式，而且因为它就是仓库里的几个文件，天然就纳入了版本控制。
- **作为确定性边的 Hooks**。当你需要一条每次都必然触发的边，而不是模型自己选择要不要走的边时，Claude Code 的 Hooks（在诸如工具调用完成或会话结束这类事件上运行）能给你一条有保证的转换。这就是"这个 Agent 通常会跑测试"和"写手节点交接之前测试一定会跑"之间的区别。
- **Claude Agent SDK**。当这张图需要无人值守地运行、需要像代码一样被测试、需要以编程方式向子智能体扇出任务，或者需要嵌入到一个更大的系统里时，你可以通过 SDK 在 Python 或 TypeScript 里用 `agents` 参数定义同样的节点。同样的节点-边-状态结构，现在可以嵌入到更大的系统中。先在交互环境里手工搭好这张图，等结构稳定了，再把它搬进 SDK。

顺序很重要。一张你亲手搭出来、看着它跑起来的图，才是你真正理解的图。如果在你还没见过这个结构真正跑起来之前就去用 SDK，最后大概率是在调试一套你从未真正设计过的编排逻辑。

## 4. Anthropic 自己已经在用图工程了（他们叫它编排器-工作者）

最能证明这不是一个你需要苦等的"改名重炒"的证据，就是 Anthropic 自己的多智能体研究系统。这是一张编排器-工作者的图：一个主智能体（lead agent）负责规划，唤起并行运行的专门子智能体，再由一次单独的处理来添加引用来源。子智能体是节点，主智能体是编排器节点，它的任务分配构成了边，而计划本身加上每个子智能体的调研结果就是共享状态。Anthropic 报告称，在一项内部研究评测中，这套多智能体方案比单一智能体的 Claude Opus 4 基线高出 90.2%。

同一篇文章也很诚实地谈到了代价，而这恰恰是大部分图工程炒作会跳过不提的部分。这张多智能体图消耗的 token 大约是一次普通聊天轮次的 15 倍，而且早期版本的编排器还会"过度生成"——分派出去的子智能体远超一个简单问题实际所需的数量。这就是图工程真正的权衡：你是在用 token 和协调开销去换取质量和并行度。当一项工作真的存在可拆分的部分时，一张图才值回它的成本。如果不是这样，你搭出来的只是一种更贵的方式去跑一个循环。

## 5. 如何在 Claude Code 里搭出你的第一张 Agent 图

先挑一份真正可以拆分的工作。一个不错的起点是那种有"产出步骤"和"独立检查步骤"的任务——先起草再评审、先调研再写作、先构建再测试。然后：

1. **为每个节点写一个子智能体**。给每个节点一个范围狭窄的系统 Prompt，只给它需要的工具。审阅者不应该有写入权限；写手不应该去搜网页。狭窄的节点，正是图能比一个大而全的 Prompt 更好的原因。
2. **让编排器负责路由**。让主智能体先跑研究员，把研究结果交给写手，再把草稿交给审阅者，如果审阅者判定不通过就让写手循环重来。这个循环回退就是一条真正的边——一个带条件返回的节点。
3. **工作能并行时就扇出去**。如果有三份资料需要阅读，就同时生成三个研究员子智能体，让编排器合并它们的结果。这就是扇出和扇入，也是让 Anthropic 的研究系统获得速度优势的那个动作。
4. **给那些不能信任模型自己判断的边加一个 Hook**。如果测试必须在交接之前运行，就把它做成 Hook，而不是一句礼貌的指令。

把图控制在你能叫出名字、并理解每一条边的规模内。先把它跑起来看看，再决定你是不是已经超出了交互式设置的能力范围，需要上 SDK 或专门的框架。

## 6. 什么时候不该用图

图里的每一个节点，都必须是一个能独立、可靠地交付成果的循环。一堆弱节点拼成的图，只是把注水的产出并行生产出来而已。如果一个带清晰验证机制的智能体已经能完成这项工作，把三个这样的智能体接在一起只会多花 token，什么好处也换不来。诚实的检验标准就在《Agent Graph vs Loop: When to Use Which》里——在你拆分一个本不需要拆分的任务之前，先读一读那篇文章。先把单个循环做扎实。之后你接在一起的那些节点，只有在每一个都已经能独立跑通的前提下，才值得去接。

先把哪个循环做扎实是另外一个决定，这取决于你的业务，而不是你的架构。最值得优先转化的功能，是那些你可以低成本、诚实地检验输出结果的功能，这也是为什么 SEO 和客服这类工作通常会排在任何涉及营收的事情之前。这个先后顺序在《How to Become an AI-Native Company》里有讲。

## 7. 常见问题

**能用 Claude 做图工程吗？**

可以，而且你一开始并不需要另外的框架。图工程是把多个专门化的智能体连接成一张图：节点（每个都是一个智能体或一个步骤）、边（它们之间的路由，包括分支、扇出、扇入和循环）、以及沿着这些边流动的共享状态。Claude Code 已经给了你这些组件：子智能体就是节点，负责调用它们的主智能体是编排器节点，它的路由画出了边；当你的需求超出交互式设置的能力时，Claude Agent SDK 能让你用代码定义整张图。

**什么是 Claude Code 子智能体？**

子智能体是主 Claude 会话可以生成出来、用来处理某个具体子任务的独立智能体实例。每个子智能体都在自己的上下文窗口里运行，有自己的系统 Prompt 和受限的工具权限，所以一个子智能体的工作不会污染主线程的上下文。你可以在 `.claude/agents/` 目录下用带 YAML frontmatter 的 markdown 文件来定义它们，也可以通过 Claude Agent SDK 的 `agents` 参数以编程方式定义。用图的语言说，每个子智能体就是一个节点。

**Claude Code 算不算像 LangGraph 那样的图框架？**

不完全算。LangGraph 要求你显式声明状态、节点和边，并提供一个带检查点（Checkpointing）能力的运行时。Claude Code 是让编排智能体在运行时自己决定调用哪些子智能体、以什么顺序调用，这更接近 Anthropic 谱系里"Agent"那一端，而不是一张固定的工作流图。你能获得节点-边-状态的结构，却不需要手绘一张图；只有当你需要 SDK 覆盖不到的持久化检查点、可恢复性，或者跨厂商的交接能力时，才需要去找一个专门的框架。

**搭一张 Agent 图，需要 Claude Agent SDK 吗？**

不需要。对于交互式的图，在 `.claude/agents/` 里定义几个子智能体，让主智能体负责路由到它们就足够了。当你希望这张图能无人值守运行、像代码一样被版本控制和测试、以编程方式向子智能体扇出任务，或者嵌入到一个更大的应用中时，Claude Agent SDK 才真正派上用场。先在 Claude Code 里手工搭好这张图，等结构稳定了，再把它搬进 SDK。

**用 Claude 做图工程，和单纯把Prompt 写得更好，有什么区别？**

再好的单个 Prompt，也只是一个节点在同一个上下文窗口里包办所有事情。图工程把工作拆到多个专门化的节点上，让每个节点都有干净的上下文和狭窄的任务范围——一个研究员、一个写手、一个审阅者——并在它们之间传递状态。Anthropic 自己的多智能体研究系统正是靠这一个动作报告了质量上的大幅提升，代价是实实在在的 token 开销，这正是你在做取舍时要面对的权衡。

## 9. 📝 小结

- Claude Code 本身已经内置了图工程的三个基本要素：子智能体（节点）、主智能体的路由（边）、返回结果（共享状态）
- 搭图的三种手段按投入程度递增：`.claude/agents/` 目录下的子智能体、作为确定性边的 Hooks、以及用于代码化和无人值守运行的 Claude Agent SDK
- Anthropic 自己的多智能体研究系统就是一个编排器-工作者图，报告显示比单智能体基线提升 90.2%，但代价是约 15 倍的 token 消耗
- 搭第一张图的顺序：挑一个真正能拆分的任务、每个节点写一个子智能体、让编排器负责路由、并行的工作用扇出/扇入、不可信任模型判断的边用 Hook 强制
- 图不是默认选项：每个节点必须是一个已经能独立可靠交付的循环，弱节点拼图只会更贵、更慢
