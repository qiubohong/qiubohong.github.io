图工程：2026 年从单一 Agent 循环转向多节点 Agent 图的这次转变。这篇长文讲清楚了图工程到底是什么、循环与图该怎么选、背后的主流框架，以及一次不带滤镜的"炒作核查"。

## 1. 图工程是什么

图工程是把多个专门化的智能体或步骤连接成一张图的实践——节点负责干活，边负责在节点之间路由，共享状态沿着这些边流动——用在单个 Agent 跑一个循环已经不够用的时候。这个说法在 2026 年 7 月中旬点燃了 X（推特），被定位成"回路工程"之上的那一层。一份诚实的指南首先要告诉你的是：大多数任务根本不需要它，而那些把它嘲讽为"注水内容"的人，说的话里也确实有你该记在心里的道理。

很多人是在这一刻突然想通的：你有一个 Agent，正开心地跑着一个循环——发现、计划、执行、验证、重复——一切都好，直到这项工作不再是"一件事"了。现在它变成了：先研究这个，再写出来，再找个挑剔的角色把草稿撕一遍，再决定要不要发出去还是打回去。你可以把这些全塞进一个 Agent 的循环里，然后看着它失去方向。或者你可以给每一件工作分配一个自己的节点，再把它们接起来。第二种做法，就是一张图。

这篇指南是一份平实、不带炒作的解码：一张图到底是什么，它什么时候真正胜过一个循环（什么时候只是你以后会后悔的复杂度），哪些框架早在这个流行词出现前一年就已经在悄悄做这件事了，以及对时间线上那个最大声的问题——"这是不是就是注水内容？"——给出一个清醒的回答。

## 2. 图工程到底是什么

图工程是设计你的 Agent 运行所在的这张图的实践：存在哪些专门化的节点，哪些边在节点之间路由工作，以及沿着这些边流动的是什么样的共享状态。回路工程设计的是一个 Agent 反复执行的那个循环。图工程决定的是若干个这样的循环该怎么连接。一个单一的循环，就是最小的图——一个节点，带一条指回自身的边——所以这不是要取代回路工程，而是它正上方的那一层。

2026 年 7 月 20 日,X 上出现了最锋利的一句判断标准。@shannholmberg 把循环和图形容成运行 Agent 的两种方式，"区别在于谁来决定路径，是 Agent 自己还是你"。在一个循环里，你设定目标和标准，Agent 自己挑路径去达标。在一张图里，你声明有效的路径和沿路的检查点——先走这个节点，再走那个，如果评审不通过就在这里分支——同时一些边仍然在运行时被决定，所以 Agent 的自由存在于每个节点内部，而不是横跨整个任务。

这个框定也解释了这个词为什么招黑的速度和吸粉的速度一样快。LangGraph 的作者 Harrison Chase 在同一条帖子下回复："所以我其实不太清楚图工程是什么，现在还是不太清楚……但它基本上就是 LangGraph 吧？"当一个自己的框架就是这个词的参考实现的人，都不确定这个词到底指代了什么新东西时，这个信号值得被认真对待，而不是一挥手带过——我们在《Is Graph Engineering Just LangGraph?》里认真讨论了这个问题。反方向上，@daleverett 在 7 月 19 日发了一篇题为《Loops are just shitty graphs》的文章，主张图一直才是真正的结构，单一循环只是我们凑合接受的退化情形。

有三件事图工程不是，因为这三样东西都很容易被和它搞混：

- **不是知识图谱或 GraphRAG**。那些是关于把数据建模成实体和关系用于检索。图工程是关于建模执行——接下来该跑哪个 Agent，它拿到什么状态。同一个词，不相关的问题。
- **不是一种新能力**。2026 年 7 月没有任何东西是你在 2025 年做不出来的。LangGraph、微软 AutoGen和 Google ADK 早在这个词出现之前就已经在做图编排了。新的东西是词汇。
- **不是默认选项**。大多数任务是一件事配一个验证者，那就是一个循环。在工作真正逼你去用图之前就伸手去拿图，就是给自己买了一个原本不存在的分布式系统难题。

如果你想知道具体的机制——一个节点、一条边、共享状态在实践中到底是什么——看下一节。

## 3. 我们是怎么从循环走到图的

AI 工程里的杠杆点，每年都会往离模型更远的一层移动。把整条线放在一起看会更清楚：

| 年代 | 层级 | 你在工程化什么 | 你的角色 |
|---|---|---|---|
| 2023-24 | Prompt | 你发出的请求 | 操作者 |
| 2024 | Context | 模型能看到什么 | 编辑者 |
| 2025 | Harness | 围绕模型的工具、记忆和脚手架 | 工具制造者 |
| 2026 年初 | Loop | 一个 Agent 反复执行的循环 | 系统设计者 |
| 2026 年中 | Graph | 多个 Agent/步骤之间的协调 | 组织设计者 |

前四级台阶，我们在《Loop Engineering: Stop Writing Prompts, Start Writing Verifiers》里讲过，在《From Prompts to Loops: The 4 Shifts》里追溯了整条攀升路径。图是最新的一级台阶，"最新"到只差了几天。

这个词是在 2026 年 7 月 18-19 日左右在 X 上结晶出来的。种子是一个问题。OpenClaw 的创造者 Peter Steinberger 问了一句，被@sairahul1 转述："我们现在还在谈循环，还是已经转向图了？"这就是全部的起源：不是一次发布，不是一篇论文，而是一个开发者随口在想，这个框架是不是已经悄悄换了。

不到一天，时间线就给出了回答。@svpino 用一种带调侃意味的悼词式说法："回路工程死了。图工程万岁！"@rohit4verse 给出了那个最终流传开来的说法："回路工程是上一次解锁。图工程是下一次。Agent 正在从 while 循环升级成组织架构图。专门化的节点并行运行，状态在它们之间流动。"@VaibhavSisinty 则不带话题标签地描述了这个正在发生的变化："AI Agent 的构建方式正在悄悄发生转变……过去一年，AI Agent 都是在循环里工作的。你给它一个任务。它规划。它行动。它检查。它修复。"

请注意这里面没有出现的东西：一种新能力。没有人在 7 月 18 日发布了什么 7 月 17 日做不到的东西。变化的是人们给一个他们早就已经在面对的设计问题贴上的名字——那个问题就是"一个循环已经不再是这份工作的合适形状"。记住这一点。它是下面每一个诚实观点的核心。

## 4. Agent 图到底是什么

把术语剥开，一张 Agent 图正好由三个部分组成：

- **节点**——干活的单元。一个节点通常是一个专门化的 Agent（一个"研究员"、一个"写手"、一个"审阅者"），或者是一个纯粹的确定性步骤（一个函数、一次工具调用、一次数据拉取）。每个节点只干一件事。
- **边**——节点之间的路由。一条边说的是"这个节点之后，去那个节点"。边可以是直线的（A 然后 B）、条件式的（如果评审通过就发布，不通过就打回循环）、扇出式的（一个节点同时唤起三个）、扇入式的（三个结果汇聚回一个）。
- **共享状态**——沿边流动的对象。这是每个节点读取和写入的东西：任务本身、目前为止的草稿、笔记、结论。状态是把一堆 Agent 变成一个系统，而不是一个"永远记不住上文"的群聊,的关键。

在 X 上被反复引用的那个比喻，是 @rohit4verse 说的组织架构图。一家公司不会让一个人在一次不间断的工作中同时完成研究、写作和评审。它会把这些分给不同的角色，在角色之间路由工作，再让结果向上汇总。一张 Agent 图是同样的道理：专门化的角色、明确的交接、一份共享的记录。

值得诚实说明这个比喻能延伸多远：当这些角色是真正的业务职能，而不是同一个工作流里的节点时，大多数团队根本不需要边。让每一个循环都指向同一个文件夹，读取状态、干活、再把状态写回去就够了。那个版本、以及转化各项职能的顺序，写在《How to Become an AI-Native Company》里。

这是一张经典的入门图——一个研究员喂给一个写手，一个审阅者检查草稿，一条条件边决定是发布还是打回去：

三个节点，四条边——其中一条是条件边，一条是打回写手的循环边。状态随着流动而增长：研究员的笔记随着流程带给写手，草稿随着流程带给审阅者，审阅者的结论决定了接下来走哪条边。

现在说这件事里防止整个概念变成一个全新宇宙的那一点：一个循环，就是一张只有一个节点、带一条指回自身的边的图。你学过的关于设计循环的一切——发现/计划/执行/验证的循环、停止条件、验证者——都在一个节点的内部。图不是取代循环。图是当你有好几个循环需要互相交接时得到的东西。如果你想知道单个循环具体能有哪些形态，我们在《The Types of Agentic Loops》里做了分类。图工程是决定它们怎么连接的那一层。

## 5. 什么时候该用图

这是把有用的构建者和那些为了好玩往架构图上加方框的人区分开来的问题。默认答案——我们把它当作这篇指南里最重要的一条主张——是：你大概不需要。一个范围清晰、有明确验证者的单一任务就是一个循环，在那里去伸手拿图纯粹是多余的开销。

这是一张诚实的决策表：

| 工作中的信号 | 一个循环就够了 | 该伸手拿图了 |
|---|---|---|
| 任务的形状 | 一件事，有清晰的完成标准 | 拆分成会互相交接的不同专长 |
| 并行度 | 步骤是顺序的 | 需要扇出（同时做很多件）再汇合 |
| 每步的工具/模型 | 全程用同一套工具 | 每一步用不同的模型或工具集 |
| 控制流 | 一个 Agent 可以安全地自由行动 | 需要角色之间明确、可审计的路由 |
| 故障隔离 | 一个坏步骤重试一下就行 | 想让一个坏节点失败,而不拖累其他节点 |
| 谁来验证 | Agent 自己检查自己的循环输出 | 一个专门的审阅节点检查另一个节点的工作 |

把这张表当作一组触发信号,而不是必须全部满足的清单来读。你不需要六项全中。但如果多数信号的诚实答案都落在左边那一栏，搭一张图,就是把一个两小时的任务变成一个两天的框架项目。

**过度工程——一张你根本不需要的图**

"总结这份PDF。"你搭了一张五节点的图：一个抓取器、一个分块器、一个总结器、一个审阅者、一个格式化器，还带条件边和一个共享状态对象。它能跑——但它比原本应该有的样子——一个读文件、写摘要的循环里的 Agent——更慢地搭建、更难调试、跑起来更贵。你为了回一封邮件，设计了一张组织架构图。

**恰到好处——一张值回成本的图**

"每天早上产出一份经过调研、事实核查的市场简报。"一个研究员节点同时扇出到五个信息源；一个综合器把它们的发现汇合起来；一个写手起草；一个持怀疑态度的审阅节点——不同的模型、只读权限——给出评分，不通过就打回循环。每个节点都在做一件单个循环撑不住的工作，交接本身就是意义所在。

判断标准是：这张图做的事,是不是循环做不到的。如果你能把这五个节点收回成一个 Agent 的循环而什么都不丢失，那你就应该这么做。这个具体判断——边界情形、成本计算和迁移路径——我们在《Agent Graph vs Loop: When to Use Which》里讲得更深，在《Graph Engineering vs Loop Engineering》里讲了这两门学科作为学科本身的关系。一句话版本：先把循环做扎实，只有当工作真的逼你的时候，才把它拆成一张图。

## 6. 这不就是 LangGraph 吗

时间线上最锋利的回复，大概是某种版本的"恭喜，你重新发明了 LangGraph"。这个问题值得一个直接的回答，因为它基本上是对的，装作不是这样，恰恰就是那些怀疑者在批评的那种炒作。

把 Agent 系统建模成"节点和边组成的图,状态在共享空间里流动"这个想法，早在"图工程"这个词流行起来之前，就已经在真实工具里落地了。以下是诚实的"前人做过什么"，只描述到官方文档所支持的程度（截至 2026 年 7 月）：

- **LangGraph（LangChain 出品）**，按照它自己的文档说法，是"一个用于构建、管理和部署长时间运行、有状态 Agent 的低层编排框架和运行时"。实际使用中你定义一个 StateGraph，添加节点，再添加节点之间的边——正好就是上面说的那个节点/边/状态模型。如果你用过 LangGraph，你其实一直在用另一个名字做图工程。
- **微软 AutoGen —— GraphFlow** 把基于图的多智能体编排带进了 AutoGen：你描述一个 Agent 团队如何连接、如何交接，而不是让一个 Agent 孤立地跑。（这里只描述到给定的这个程度，具体 API 请查阅当前的 AutoGen 文档，它在 2026 年一直在变动。）
- **GoogleADK（Agent Development Kit）** 把图模型做成了一个主打特性。它的文档描述的是通过"结构化、基于图的架构"来编排"复杂任务"，并提供了命名的顺序、并行和循环工作流 Agent，以及 Agent 路由——把扇出/扇入和循环当作一等公民。（它的 Go SDK 在 2026 年迎来了 2.0 正式版；图模型也覆盖了 Python/TypeScript/Java/Kotlin 各个 SDK。）
- **A2A（Agent2Agent）** 是一个开放协议，让 Agent 可以跨系统互相委派任务——也就是"不同团队各自拥有的图之间的边"这一层。它值得被提到，因为它是"多 Agent 协作"这个想法在企业里早有真实历史的最明显证据（下面一位怀疑者对此说得更具体）。

所以：图工程就是 LangGraph 吗？从技术角度看，基本是的——LangGraph、GraphFlow 和 ADK 都先到了。2026 年年中真正新出现的东西,范围更窄、也更软：给一个共享的名字,来称呼那些框架一直都在要求你做的设计决策（哪些是节点，哪些是边，状态里放什么），以及一种越来越强烈的感觉——这是一门值得单独教的技能，而不只是某个框架的细节。那是一件真实的事。只是它比"一种新范式"要小得多，我们在《Is Graph Engineering Just LangGraph?》里也是这么坦白说的。

## 7. AI 工程的五个层级是什么

在不夸大图工程的前提下,给它定位最清晰的方式，来自 @sairahul1 用一句话概括的整个技术栈："Prompt、context、harness、loop 和 graph engineering，讲清楚了！最优秀的 AI 工程师不再只是写 Prompt 了。他们工程化的是模型周围的整个系统。你可以把一个 AI 应用想象成五个层级。"

每一层都在离模型更远的地方工程化系统：

| # | 层级 | 它工程化的是什么 | 核心问题 |
|---|---|---|---|
| 1 | Prompt | 单次请求 | 我问得够好吗？ |
| 2 | Context | 模型能看到什么 | 它有正确的信息吗？ |
| 3 | Harness | 工具、记忆、脚手架 | 它能对世界行动、能记住东西吗？ |
| 4 | Loop | 一个 Agent 反复执行的循环 | 它什么时候检查自己的工作、什么时候停？ |
| 5 | Graph | 多个 Agent/步骤之间的协调 | 谁做什么，按什么顺序，共享什么状态？ |

这个技术栈有用的地方在于它是累加的，不是一个你爬上去就可以离开的梯子。一张图里全是节点；一个好节点是一个精心设计的循环；一个好循环需要一个真正的 harness——那六个组件（上下文、工具、编排、状态、评估、恢复）让一个 Agent 具备行动能力。跳过底层的某一层，图在上面只会以一种更精致的方式失败。如果你的节点是弱 Agent，把它们接成一张组织架构图，得到的只是一个弱组织。我们在《The 5 Layers of AI Engineering》里逐层拆解了整个技术栈；简短的结论是，图工程是最外层，这也是为什么它应该是你最后才伸手去拿的那一层。

## 8. 图工程是不是就是"注水内容"

到了怀疑者会直接拉到这一段的地方——他们也理应如此，因为反弹几乎是在这个词出现之前就到了。这和我们在循环指南里做的动作一样：把词和背后真实的转变分开来看，承认一切公道的批评，最后落在一个真正站得住的位置上。

批评者不是随便闹事的人。他们中的一些人,恰恰是最懂这个领域的人：

- **@RhysSullivan** 在文章出现之前就预判了这一切："明天X 上肯定会有一篇一万字的图工程注水文章"，然后，等文章真的出现了，他又干巴巴地补了一句："一篇图工程文章已经登上时间线了。"这份嘲讽针对的是围绕这个词出现的内容农场式的一窝蜂——而这份嘲讽是公道的，那一周发布的很多内容确实就是这样。
- **@DavidKPiano**，XState 的创造者——一个花了好几年做状态机工具的人——警告说："在读那篇关于'Agent 图工程'的注水文章之前，先记住这一点。"当一个真正的状态机专家,对"图"被宣布成新东西这件事翻白眼时，这不是护城行为，而是有人在指出：状态和转换组成的有向图，是几十年前就有的计算机科学。
- **@PawelHuryn** 把整条脉络都批了一遍："我要说图工程就是胡说。回路工程本来就已经够让人糊涂了……"他自己的替代方案是：跳过给机制起名字这件事，直接把目标、目标为什么重要、以及成功怎么衡量,告诉 Agent 就行。他的观点是：起名字这件事,一直在把机制（循环、图）误认成实质（目标和验证）。
- **@NathanFlurry** 把"前人早就做过"这个论点说得很具体："有意思的是这些'图工程'的帖子里都没提A2A。"在一条后续回复里："领英2025 年就在讨论这个了，IBM 动作更快。"他的论点是：多 Agent 委派这个想法（A2A 及其同类协议）在企业里已经有真实历史了，所以在 2026 年 7 月给它造一个推特词,是迟了，不是早了。

把这些全部承认下来，因为它们全都是对的。机制本身不是新的：有向图、状态机、编排引擎和 Agent 间协议，都比这个流行词早了好几年。搭这个词顺风车的很多内容确实是注水。而"图工程"这个说法本身也是可选的——你完全可以按这篇指南搭出每一套系统，一次都不用这几个字。

现在把这个词和背后的转变分开来看。在这些噪音之下，一次真实的设计升级正在发生，正是 @VaibhavSisinty 和 @rohit4verse 描述的那个：那些在 2026 年初把"跑一个循环里的 Agent"这件事做熟练了的团队，正在撞上"一个循环已经是错误形状"的那道墙，并有意识地把工作拆成协调好的、专门化的节点，让状态在它们之间流动。这次升级是真实的，无论你叫不叫它"图工程"，正如回路工程也是真实的，无论你喜不喜欢这个词。怀疑者反驳的不是这次升级本身——他们反驳的是围绕一个名字的炒作，在这一点上，他们是对的。

所以，这是和回路指南同样的过滤器：

- 团队真的在从"一个循环里的一个 Agent"转向"若干个专门化 Agent 在共享状态上协调"吗，在工作需要的时候？是的。
- 那种协调是一门独立的设计技能——挑选节点、边和状态——和设计单个循环不一样？是的。
- "图工程"这个词是新的、有实质分量的、或者没有注水的吗？不是——机制是旧的，2026 年 7 月的很多内容都是噪音。

标签是可选的。从一个循环升级到一张协调好的图，这次升级是真实的。只是别在你还不需要它之前就伸手去拿它——对你这周正在做的大多数事情来说，现在还不需要。

## 9. 你的图工程起步清单

在把一个循环变成一张图之前，先过一遍这份清单：

1. **先尽量保持它是一个循环。** 一个范围清晰、带一个好验证者的单一 Agent 能不能做这件事？如果能，到这里就打住，你已经做完了。
2. **只在真的是不同专长的时候才给节点命名。** 每个节点都应该做一件单个循环真的撑不住的工作——一个不同的模型、一个不同的工具集，或者一个只读的审阅角色。"本来可以内联进去的步骤"，不算节点。
3. **在写代码之前先画出边。** 画一下路由：什么是顺序的、什么会扇出、什么会汇入、那一条条件边/循环回退边在哪里。如果你没法把它画在一张餐巾纸上，那就说明它太复杂了。
4. **明确设计共享状态对象。** 决定沿着边流动的是什么，谁有权写入它。状态漂移是图腐烂的头号原因。
5. **给审阅节点真正的权力。** 最有价值的那个节点，通常是一个独立的、只读的验证者——一个和产出这份工作的 Agent 不同的 Agent。（这就是回路指南里"别让 Agent 自我验证"，升级成了一个节点。）
6. **隔离故障。** 确保一个节点可以失败、重试，而不会污染共享状态或拖累下游节点。
7. **选一个框架，而不是从零手搓。** LangGraph、AutoGen GraphFlow 或 Google ADK 已经给了你节点、边、状态、扇出/扇入和循环。重新发明这套运行时,本身也是一种注水。
8. **设一个开销上限和一个硬性边界。** 一张图就是很多个循环；一个弱验证者现在会并行地烧 token。给它设个上限。

如果你这周搭了一张图，胜利的标准不是"节点最多"。而是"每个节点做的都是循环做不到的事，而我还能用一口气把整件事解释清楚"。

---

## 10. 从这里开始

图工程是回路工程之上的那一层，而搭出一张糟糕图最快的方式,就是跳过循环这一步。所以诚实的第一步不是"学图"。而是：先把你第一个节点要跑的那个循环做扎实——一个 Agent，一个清晰的验证者，一个明确的停止条件——只有当工作逼你出手的时候，才把它拆成一张图。

---

## 11. 常见问题

**什么是图工程？**

图工程是设计你的 Agent 运行所在的这张图的实践：存在哪些专门化的节点，哪些边在节点之间路由工作（包括分支、扇出/扇入和循环），以及沿着这些边流动的是什么样的共享状态——而不是依赖单个 Agent 跑一个循环。这个说法在 2026 年 7 月中旬出现在 X 上，被定位成回路工程之上的一层。单一循环是一种特例：一个节点，带一条指回自身的边。

**图工程只是炒作吗？**

一部分是。像 @RhysSullivan、@DavidKPiano（XState 创造者）、@PawelHuryn 和 @NathanFlurry 这样的怀疑者说得对：机制本身不新——图编排、状态机，以及像 A2A 这样的 Agent 间协议，都比这个词早了一年以上。但把词和背后的转变分开看：从一个循环升级到一组协调好的专门化节点、状态在它们之间流动，这是团队真实会走的一步设计升级。标签是可选的。这次升级是真实的——只是别在你还不需要它之前就伸手去拿它。

**什么是 Agent 组织架构图？**

这是 @rohit4verse 用来形容 Agent 图的比喻：Agent 正在"从 while 循环升级成组织架构图"，"专门化的节点并行运行，状态在它们之间流动"。就像公司的组织架构图一样，每个节点都有自己的工作，工作在角色之间路由，结果向上汇总。这是一个有用的画面，但要记住那个提醒：大多数工作依然是一个人在一个循环里完成的，不是一整个组织。

## 12. 来源与核对

这篇指南综合了 2026 年 7 月中旬在 X 上出现的图工程讨论（Peter Steinberger 的问题,经 @sairahul1 转述，加上 @svpino、@rohit4verse、@VaibhavSisinty 的补充），以及图Agent 框架（LangGraph、微软 AutoGen、Google ADK）已经文档化的能力。它解释的是一个正在兴起的词,而不是一手的基准测试——框架细节请以 2026 年 7 月为准。框架描述已对照下方链接的官方文档核实。

- **Loop Engineering: Stop Writing Prompts, Start Writing Verifiers（AI Builder Club）**：这篇内容所依托的前一层——设计一个 Agent 运行的循环，以及为什么验证者才是瓶颈
- **LangGraph overview（LangChain）**：官方定义："一个用于构建、管理和部署长时间运行、有状态 Agent 的低层编排框架和运行时"——由一个 StateGraph（节点和边加共享状态）构成
- **Agent Development Kit（Google ADK）**：Google ADK 的基于图的架构——"通过结构化、基于图的架构编排复杂任务"——加上顺序/并行/循环工作流 Agent、Agent 路由，以及一个 A2A 协议章节
- **Harrison Chase（@hwchase17）谈图工程 —— 2026 年 7 月 20 日**：LangGraph 创造者的原话——"所以我其实不太清楚图工程是什么，现在还是不太清楚……但它基本上就是 LangGraph 吧？"
- **Shann Holmberg（@shannholmberg）谈循环与图 —— 2026 年 7 月 20 日**：这篇指南采用的判别标准——两者都是运行 Agent 的方式，"区别在于谁决定路径，是 Agent 还是你"
- **Dale Everett（@daleverett）谈循环是退化的图 —— 2026 年 7 月 19 日**："循环只是很糟糕的图"，反方观点——图一直才是真正的结构，单一循环是我们凑合接受的退化情形

## 13. 📝 小结

- 图工程是回路工程之上的一层：单一循环是最小的图（一个节点，一条指回自身的边），图是当一个循环不够用时，把多个专门化节点接起来的设计实践
- 从循环到图的转变发生在 2026 年 7 月中旬的 X 上，源头是 Peter Steinberger 的一句提问，随后被 @svpino、@rohit4verse、@VaibhavSisinty 等人放大——但期间没有出现任何真正的新能力
- 一张图由节点、边（含分支/扇出/扇入/循环）、共享状态三部分组成，判断要不要用图看六个信号：任务形状、并行度、每步工具/模型、控制流、故障隔离、验证方式
- LangGraph、微软 AutoGen GraphFlow、Google ADK 早在这个词流行之前就已经实现了图编排，"图工程"更多是给一组既有设计决策起的新名字
- AI 工程的五个层级（Prompt、Context、Harness、Loop、Graph）是累加关系,而不是替代关系,图工程是最外层，也应该是最后才用的那一层
- 怀疑者的批评基本成立（机制不新、很多内容是注水），但从单循环升级到协调化多节点图的这个设计趋势是真实的——只是别在不需要的时候硬套
