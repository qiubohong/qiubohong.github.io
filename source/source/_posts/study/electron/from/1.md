## 🟢 小白入门：进程是什么，为什么要分开

### 1.1 多进程架构的由来

Electron 从 Chromium 继承了多进程架构。早期浏览器用单进程，一个标签页崩溃整个浏览器就挂了。Chrome 的解决方案是每个标签页独立进程——一个进程崩溃不影响其他进程。

Electron 应用的结构和这个一模一样：

```
你的 Electron 应用
├── 主进程（Main Process）× 1
│   ├── 管理所有窗口
│   ├── 控制应用生命周期
│   └── 访问原生 OS API
└── 渲染进程（Renderer Process）× N
    ├── 每个 BrowserWindow 一个
    └── 负责渲染 HTML/CSS/JS
```

### 1.2 主进程能做什么

主进程跑在 Node.js 环境里，可以：

- 用 `BrowserWindow` 创建和管理窗口
- 用 `app` 模块控制应用生命周期
- 访问文件系统、系统菜单、对话框、系统托盘等原生 API

```js
// main.js
const { app, BrowserWindow } = require('electron')

function createWindow() {
  const win = new BrowserWindow({
    width: 800,
    height: 600,
    webPreferences: {
      preload: path.join(__dirname, 'preload.js')
    }
  })
  win.loadFile('index.html')
}

app.whenReady().then(() => {
  createWindow()
})

// 非 macOS 平台关闭所有窗口时退出
app.on('window-all-closed', () => {
  if (process.platform !== 'darwin') app.quit()
})
```

### 1.3 渲染进程能做什么

渲染进程就是一个普通的 Chromium 网页环境：

- 可以用 HTML、CSS、JavaScript
- **默认没有 Node.js 权限**（出于安全考虑）
- 不能直接 `require('fs')` 或调用 Electron API

这就引出了一个问题：渲染进程的 UI 怎么和主进程的原生功能交互？答案是**预加载脚本（Preload Script）**。

### 1.4 预加载脚本：安全的桥梁

预加载脚本在渲染进程的网页内容加载**之前**执行，它同时拥有：
- 渲染进程的 `window` 对象访问权
- Node.js API 访问权

```js
// preload.js
const { contextBridge, ipcRenderer } = require('electron')

// 通过 contextBridge 安全地暴露 API 给渲染进程
contextBridge.exposeInMainWorld('electronAPI', {
  setTitle: (title) => ipcRenderer.send('set-title', title),
  openFile: () => ipcRenderer.invoke('dialog:openFile')
})
```

```js
// renderer.js（渲染进程）
// 可以直接使用暴露的 API
window.electronAPI.setTitle('新标题')
```

## 🟡 熟练进阶：Context Isolation 与安全边界

### 2.1 Context Isolation 是什么

Context Isolation（上下文隔离）确保预加载脚本和 Electron 内部逻辑运行在**独立的 JavaScript 上下文**里，与网页加载的内容隔离。

**Electron 12 起默认开启。**

没有 Context Isolation 时（旧方式，不安全）：

```js
// preload.js（contextIsolation: false，危险！）
window.myAPI = { doAThing: () => {} }

// renderer.js
window.myAPI.doAThing() // 可以直接访问
```

有 Context Isolation 时（正确方式）：

```js
// preload.js（contextIsolation: true，默认）
const { contextBridge } = require('electron')
contextBridge.exposeInMainWorld('myAPI', {
  doAThing: () => {}
})

// renderer.js
window.myAPI.doAThing() // 同样可以访问，但通过安全桥接
```

### 2.2 为什么需要隔离

如果没有隔离，网页里的恶意脚本可以：
- 修改 `Array.prototype.push` 等全局对象，影响预加载脚本的行为
- 直接访问 Node.js API，执行任意系统命令

Context Isolation 让预加载脚本的 `window` 对象和网页的 `window` 对象是**不同的对象**。网页无法访问预加载脚本的内部变量。

### 2.3 contextBridge 的安全注意事项

不要直接暴露整个 `ipcRenderer`：

```js
// ❌ 危险：允许网页发送任意 IPC 消息
contextBridge.exposeInMainWorld('myAPI', {
  send: ipcRenderer.send  // 直接暴露，没有过滤
})

// ✅ 安全：每个 IPC 消息对应一个具体方法
contextBridge.exposeInMainWorld('myAPI', {
  loadPreferences: () => ipcRenderer.invoke('load-prefs'),
  saveFile: (content) => ipcRenderer.invoke('save-file', content)
})
```

### 2.4 TypeScript 类型支持

如果用 TypeScript，需要声明 `window` 上的类型：

```ts
// preload.ts
contextBridge.exposeInMainWorld('electronAPI', {
  loadPreferences: () => ipcRenderer.invoke('load-prefs')
})

// interface.d.ts
export interface IElectronAPI {
  loadPreferences: () => Promise<void>
}

declare global {
  interface Window {
    electronAPI: IElectronAPI
  }
}

// renderer.ts
window.electronAPI.loadPreferences() // 有类型提示
```

## 🟠 熟练进阶：IPC 四种通信模式

IPC（进程间通信）是渲染进程和主进程交互的唯一方式。Electron 提供了四种模式。

### 3.1 模式一：渲染进程 → 主进程（单向）

用 `ipcRenderer.send` + `ipcMain.on`，适合不需要返回值的操作（如修改窗口标题）。

```js
// preload.js
contextBridge.exposeInMainWorld('electronAPI', {
  setTitle: (title) => ipcRenderer.send('set-title', title)
})

// main.js
ipcMain.on('set-title', (event, title) => {
  const win = BrowserWindow.fromWebContents(event.sender)
  win.setTitle(title)
})

// renderer.js
window.electronAPI.setTitle('Hello Electron')
```

### 3.2 模式二：渲染进程 → 主进程（双向，等待返回值）

用 `ipcRenderer.invoke` + `ipcMain.handle`，适合需要返回值的操作（如打开文件对话框）。

```js
// preload.js
contextBridge.exposeInMainWorld('electronAPI', {
  openFile: () => ipcRenderer.invoke('dialog:openFile')
})

// main.js
async function handleFileOpen() {
  const { canceled, filePaths } = await dialog.showOpenDialog()
  if (!canceled) return filePaths[0]
}

ipcMain.handle('dialog:openFile', handleFileOpen)

// renderer.js
const filePath = await window.electronAPI.openFile()
console.log('选择的文件：', filePath)
```

> ⚠️ 注意：主进程 `handle` 里抛出的错误在序列化后只保留 `message` 属性，详见 [#24427](https://github.com/electron/electron/issues/24427)。

### 3.3 模式三：主进程 → 渲染进程（单向）

用 `webContents.send` + `ipcRenderer.on`，适合主进程主动推送消息（如菜单触发更新）。

```js
// main.js
const menu = Menu.buildFromTemplate([{
  label: '文件',
  submenu: [{
    label: '打开',
    click: () => {
      // 主动向渲染进程发消息
      mainWindow.webContents.send('update-counter', 1)
    }
  }]
}])

// preload.js
contextBridge.exposeInMainWorld('electronAPI', {
  onUpdateCounter: (callback) =>
    ipcRenderer.on('update-counter', (_event, value) => callback(value))
})

// renderer.js
window.electronAPI.onUpdateCounter((value) => {
  console.log('收到更新：', value)
})
```

### 3.4 模式四：渲染进程之间（通过主进程中转）

渲染进程之间不能直接通信，需要通过主进程中转：

```js
// renderer A（发送方）
window.electronAPI.sendToB('hello from A')

// preload.js
contextBridge.exposeInMainWorld('electronAPI', {
  sendToB: (msg) => ipcRenderer.send('relay-to-b', msg)
})

// main.js（中转）
ipcMain.on('relay-to-b', (event, msg) => {
  windowB.webContents.send('from-a', msg)
})

// renderer B（接收方）
window.electronAPI.onFromA((msg) => console.log(msg))
```

## 🔴 专家深入：进程沙盒化

### 4.1 沙盒是什么

沙盒（Sandbox）是 Chromium 的安全特性，利用操作系统限制渲染进程能访问的系统资源。沙盒化的进程只能自由使用 CPU 和内存，其他操作（文件系统、网络等）必须通过 IPC 委托给主进程。

**Electron 20 起，渲染进程默认开启沙盒。**

### 4.2 沙盒对预加载脚本的影响

沙盒化的渲染进程里，预加载脚本仍然可以使用一个**受限的 Node.js 子集**：

可用模块：
- `electron`（仅渲染进程模块：`contextBridge`、`ipcRenderer`、`nativeImage` 等）
- `events`、`timers`、`url`
- `node:events`、`node:timers`、`node:url`

可用全局变量：`Buffer`、`process`、`clearImmediate`、`setImmediate`

**不能用 CommonJS 拆分预加载脚本**——`require` 是 polyfill，功能有限。如果需要拆分，用 webpack 或 Parcel 打包。

### 4.3 沙盒配置

```js
// 禁用单个进程的沙盒（有安全风险）
const win = new BrowserWindow({
  webPreferences: {
    sandbox: false
  }
})

// 全局强制开启沙盒（推荐）
app.enableSandbox()
app.whenReady().then(() => {
  const win = new BrowserWindow()  // sandbox: false 会被忽略
})

// 注意：nodeIntegration: true 会自动禁用沙盒
const win = new BrowserWindow({
  webPreferences: {
    nodeIntegration: true  // 同时禁用了沙盒！
  }
})
```

### 4.4 沙盒与 Context Isolation 的关系

这两个是独立的安全机制，但相互影响：

| 配置 | 沙盒 | Context Isolation | 安全级别 |
|------|------|-------------------|---------|
| 默认（Electron 20+） | ✅ 开启 | ✅ 开启 | 最高 |
| `nodeIntegration: true` | ❌ 关闭 | ❌ 关闭 | 最低 |
| `sandbox: false` | ❌ 关闭 | ✅ 开启 | 中等 |

## 🔴 专家深入：MessagePorts 直连通信

### 5.1 为什么需要 MessagePorts

标准 IPC 通信都要经过主进程中转。MessagePorts 允许两个渲染进程**直接通信**，绕过主进程，性能更好，适合高频消息传递。

### 5.2 基本概念

MessagePorts 是 Web 标准 API（Channel Messaging），Electron 在主进程里扩展了它：

```js
// 渲染进程（Web 标准用法）
const channel = new MessageChannel()
const port1 = channel.port1
const port2 = channel.port2

port2.postMessage({ answer: 42 })

// 把 port1 发给主进程
ipcRenderer.postMessage('port', null, [port1])
```

```js
// 主进程（Electron 扩展：MessagePortMain）
ipcMain.on('port', (event) => {
  const port = event.ports[0]  // MessagePortMain 实例
  port.on('message', (event) => {
    console.log(event.data)  // { answer: 42 }
  })
  port.start()  // 必须调用 start() 才开始接收消息
})
```

### 5.3 实战：两个渲染进程直接通信

```js
// main.js：建立通道，把两端分别发给两个窗口
const { BrowserWindow, app, MessageChannelMain } = require('electron')

app.whenReady().then(async () => {
  const mainWindow = new BrowserWindow({ /* ... */ })
  const secondaryWindow = new BrowserWindow({ /* ... */ })

  const { port1, port2 } = new MessageChannelMain()

  // 窗口就绪后发送端口
  mainWindow.once('ready-to-show', () => {
    mainWindow.webContents.postMessage('port', null, [port1])
  })
  secondaryWindow.once('ready-to-show', () => {
    secondaryWindow.webContents.postMessage('port', null, [port2])
  })
})
```

```js
// preloadMain.js 和 preloadSecondary.js
const { ipcRenderer } = require('electron')

ipcRenderer.on('port', (e) => {
  window.electronMessagePort = e.ports[0]
  window.electronMessagePort.onmessage = (messageEvent) => {
    // 处理来自另一个窗口的消息
    console.log('收到消息：', messageEvent.data)
  }
})
```

```js
// 任意一个渲染进程发消息给另一个
window.electronMessagePort.postMessage({ type: 'sync-data', payload: {...} })
```

### 5.4 MessagePorts 的 close 事件（Electron 扩展）

Electron 为 MessagePort 添加了 `close` 事件，当通道另一端关闭时触发：

```js
// 渲染进程
port.addEventListener('close', () => {
  console.log('对端已关闭')
})

// 主进程
port.on('close', () => {
  console.log('对端已关闭')
})
```

### 5.5 Worker 线程与 MessagePorts

MessagePorts 也可以用于主进程和 Worker 线程之间的通信：

```js
// main.js
const { Worker } = require('node:worker_threads')
const { MessageChannelMain } = require('electron')

const { port1, port2 } = new MessageChannelMain()
const worker = new Worker('./worker.js', {
  workerData: { port: port2 },
  transferList: [port2]
})

port1.on('message', (event) => {
  console.log('Worker 返回：', event.data)
})
port1.start()
```

## 📊 进程通信方式对比

| 方式 | 方向 | 适用场景 | 性能 |
|------|------|---------|------|
| `ipcRenderer.send` + `ipcMain.on` | 渲染→主 | 单向通知，无需返回值 | 中 |
| `ipcRenderer.invoke` + `ipcMain.handle` | 渲染→主（双向） | 需要返回值的操作 | 中 |
| `webContents.send` + `ipcRenderer.on` | 主→渲染 | 主进程主动推送 | 中 |
| `MessagePorts` | 渲染↔渲染 | 高频消息、直连通信 | 高 |

## 📝 小结

**小白要记住：**
- Electron 有主进程（Node.js）和渲染进程（Chromium）两种进程
- 渲染进程默认没有 Node.js 权限，通过预加载脚本 + `contextBridge` 安全桥接

**熟练要掌握：**
- Context Isolation 默认开启，保护预加载脚本不被网页污染
- IPC 有四种模式，根据通信方向和是否需要返回值选择
- 不要直接暴露 `ipcRenderer.send`，要封装成具体方法

**专家要理解：**
- 沙盒化（Electron 20+ 默认）限制渲染进程的系统访问，预加载脚本只有受限的 Node.js 子集
- `nodeIntegration: true` 同时禁用沙盒和 Context Isolation，生产环境绝对不要用
- MessagePorts 允许渲染进程直连通信，适合高频数据传输场景
